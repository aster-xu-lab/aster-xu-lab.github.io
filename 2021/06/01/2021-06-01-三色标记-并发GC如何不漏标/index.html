三色标记：并发GC如何做到不漏标不误回收

可达性分析，要面对一个残酷的现实

JVM 判定对象能否回收，靠可达性分析：从 GC Roots（栈帧局部变量、静态变量、常量引用、native 引用、活跃线程/锁对象等）沿着引用往下走，从根可达的存活，其余回收。

这个过程要遍历整个对象图，很慢。最早的收集器选择”全停顿”来做——STW 期间业务线程全停，图不会变，标记很安全，代价是停顿时间长。

于是有了 CMS、G1 这样的并发收集器：大部分标记阶段和业务线程并发执行，不停顿。

但并发立刻带来一个难题：你标记的同时，业务线程在改对象图——引用被删了、被加了、对象被换引用了。怎么保证”该标的不漏、该回收的不误收”？

这就是三色标记法要解决的问题。

一、三色：白、灰、黑

把标记过程中对象的状态分成三种颜色：

颜色 含义
白 还没被访问到。标记结束时仍是白 = 垃圾，回收
灰 自己已访问（存活），但孩子还没全部访问完
黑 自己和所有孩子都访问完了，确定存活

二、漏标：一个看似正确却致命的 bug

经典的漏标场景：

并发过程中发生两次修改：

结果：标记继续扫，B 标完变黑，但 B 已经不引用 D 了，所以 D 再也不会被扫到——D 保持白色。可 D 实际还被 A 引用着，是可达的存活对象。

白色 + 可达 = 被误回收。 这是最严重的 bug——存活对象被当成垃圾清掉了。

漏标必须同时满足两个条件：

  1. 已访问的黑色对象，新增了指向白色对象的引用；
  2. 这个白色对象，删掉了原本指向它的引用。

（缺任何一个都不行：只有 ① 没有 ②，D 还连着 B，B 标完孩子时还能扫到 D；只有 ② 没有 ①，D 断了 B 但也没人引它，本来就是垃圾。）

三、两个解法：增量更新与原始快照

要防漏标，打破上面任意一条即可。

解法一：增量更新（Incremental Update，CMS 用）

针对条件 ①：黑色对象新增了指向白色的引用时，把黑色对象重新标灰，丢回队列再扫一遍它的孩子。

相当于说：你”黑”了也不许新增指向白的引用，一旦新增，我就把你打回灰重新标记，保证新增引用指向的对象能被扫到。

解法二：原始快照（SATB，G1 用）

针对条件 ②：记录并发开始那一刻的对象引用快照，以当时的图为准。即使 B 删掉了指向 D 的引用，SATB 仍然把 D 当作”并发开始时就存在”的引用保留下来。

代价：可能有更多本来可回收的垃圾被保留——这些”本该回收但被快照救活”的对象叫浮动垃圾，留给下一轮 GC 处理。SATB 的哲学是”宁可多留垃圾，绝不误回收活对象”。

四、写屏障：解法的实现载体

增量更新和 SATB 都要求”对象引用被修改时”能感知到——靠的是写屏障（Write Barrier）：JIT 编译器在字段赋值处插入一段钩子逻辑，每次引用被改就执行。

这里有一个非常容易搞混的点，复习卡里我专门标过：

GC 写屏障 ≠ volatile 内存屏障。

  • volatile 的内存屏障是 CPU 指令级别的，保证可见性/有序性；
  • GC 的写屏障是 JVM 在字段赋值处插的钩子，用于维护卡表 / 标记快照，服务的是垃圾回收。

两个都叫”屏障”，一个管并发可见性，一个管 GC 标记，完全两码事。

五、和 G1 的整体关系

G1 是三色标记 + SATB 的典型落地，整套机制放在一起看：

  • 堆分成等大小 Region，回收时只挑”垃圾多的 Region”（CSet）；
  • 一个 Region 里的对象被别的 Region 引用，靠 **RSet（Remembered Set）**记录，回收某个 Region 时只扫它的 RSet，不用遍历全堆；
  • 并发标记用三色标记 + SATB，防止并发改图漏标活对象；
  • RSet 和 SATB 的维护，都靠字段赋值时的写屏障。

所以”G1 为什么停顿可预测、为什么能并发标记”这串问题，最终都会落到写屏障和三色标记上。

总结

  • 三色标记：白（未访问）→ 灰（自己存活、孩子没标完）→ 黑（全部标完），结束剩白即垃圾；
  • 并发标记的致命 bug 是漏标，两个条件：黑对象新增指向白的引用 + 白对象原引用被删；
  • 增量更新（CMS）：黑对象新增指向白的引用时打回灰重扫；
  • 原始快照 SATB（G1）：按并发开始时的图为准，宁可留浮动垃圾，不误回收活对象；
  • 实现载体是 GC 写屏障，跟 volatile 的 CPU 内存屏障不是一回事。
