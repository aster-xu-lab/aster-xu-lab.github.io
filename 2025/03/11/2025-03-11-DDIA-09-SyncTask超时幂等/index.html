DDIA-09-实战：SyncTask引擎的超时控制与幂等设计——V2版本的工程修复

开篇：一个线程池耗尽引发的血案

2023年秋天，凌晨三点，手机警报响了。

告警内容很简单：订单同步积压。看监控，任务调度一切正常，xxl-job 的调度日志显示每次触发都成功了。但任务就是卡住不动，所有新提交的 Handler 都在排队。

登录服务器一看，线程池队列已经堆满，所有工作线程都在运行状态。再看堆栈，8 个线程全部卡在同一个 Handler 上——那个负责调用第三方物流接口的 Handler，对方接口响应超时，HTTP 连接池的连接全部耗尽，但我们的代码里没有设置超时时间。

一行 RestTemplate 调用，没有 setConnectTimeout，没有 setReadTimeout，也没有任何超时后的 fallback 机制。

一个 Handler 卡住，线程池 8 个线程全部阻塞，所有 49 个 Handler 的后续任务全部排队，系统不可用。

这就是 DDIA 第九章说的那句话：“在一个由许多部件组成的系统中，某个部件出问题是常态，而不是例外。你的系统必须能容忍部分失效。” 而我们 V1 版本的 SyncTask 引擎，显然做不到。

V1 的问题全景

SyncTask 引擎寄居在 xxl-job 之上，V1 版本的设计很简单：一个固定的线程池，轮询待执行的任务，逐个调用 handler.execute()。伪代码大体是这样：

看起来很干净。但在我们的场景里，93 个 Handler 对接了 10 多个外部系统：金蝶 ERP、聚水潭 WMS、华为商品中心、企业微信通知、多个第三方物流接口……每一个外部系统都可能在某个时刻变慢、超时、或完全不可用。

V1 版本面对这些问题，毫无抵抗能力：

  1. 无超时控制：handler.execute() 是一个纯粹的同步调用，没有 timeout 保护
  2. 无故障隔离：所有 Handler 共用线程池，一个卡住，全部阻塞
  3. 无幂等保证：任务可能被 xxl-job 重复调度，DB 里有重复记录
  4. 无降级出口：没有 onTimeout/onException 的扩展点

DDIA 第九章讲的是”一致性与共识”，看起来跟我们这个任务引擎没什么关系。但 Kleppmann 用大量篇幅讨论了一个前置问题：在分布式系统中，你如何确认一个操作真的失败了？ 答案是：你不能。你只能通过超时来推测它失败了，然后决定怎么办。

这个洞察，恰好是 SyncTask V2 所有改进的起点。

修复 1：CompletableFuture.orTimeout —— 每个任务独立超时

Java 9 引入了一个简单但关键的 API：CompletableFuture.orTimeout(long timeout, TimeUnit unit)。它的语义非常精确：如果这个 Future 在指定时间内没有完成，就以 TimeoutException 异常完成它。

V2 的核心改造，就是把每个 Handler 的执行包装成一个 CompletableFuture，并给它一个独立的超时时间：

关键点在于每个 Handler 独立超时。Handler A 调用金蝶接口超时了，30 秒后它的 Future 以 TimeoutException 完成，对应的任务标记为失败，但 Handler B、Handler C 不受影响，继续执行各自的任务。

一个任务挂了，不再影响其他所有任务。这是 V2 最重要的工程改进。

有人可能会问：为什么不直接用线程池的 Future.get(timeout) ？两个原因。第一，get(timeout) 是阻塞的，你需要在某个地方等待它，这又回到线程池被占用的问题。第二，orTimeout 是异步的、非阻塞的——超时后框架自动触发 exceptionally 回调，你没占用任何额外线程来等待。

这也是 DDIA 第九章反复强调的一个主题：超时检测不能依赖同步等待，它必须是系统架构的一部分，而不是调用方的负担。

修复 2：批次聚合 + 整体超时

单个 Handler 有超时还不够。V2 引入了一个重要的执行模型：批次聚合。

业务场景是这样的：一个 xxl-job 触发周期，需要执行一批任务（比如50个）。V1 是一个一个串行执行。V2 把它们聚合成一个批次，用 CompletableFuture.allOf 并行执行：

这里有两层超时：单任务 30 秒，整批 120 秒。含义是：

  • 正常情况：所有任务在 30 秒内完成，整批结束
  • 部分任务超时：个别任务 30 秒后以 TimeoutException 完成，但不影响其他任务，整批继续等待
  • 整体超时：如果 120 秒后仍有任务没完成（比如线程池被大量慢任务拖住），整批以超时结束，未完成的任务标记为失败

这里有一个重要的架构决策：部分成功是合法的。一批 50 个任务，其中 3 个超时失败了，47 个成功——这是正常现象，不是异常。V2 的批次结果会明确区分 成功数、失败数、超时数，而不是简单地整体成功或失败。

这跟微服务里 “partial failure” 的处理思路完全一致。DDIA 第九章讲了两阶段提交（2PC）的局限——它要求所有参与者都同意，任何一个不同意就全部回滚。但现实世界的分布式系统，很多时候要接受部分失败并继续前进。SyncTask V2 的批次聚合，就是这样一种务实的折中。

修复 3：线程池隔离 —— 不同 Handler，不同待遇

一个 Handler 慢，不应该拖慢其他 Handler。这是我们用 orTimeout 解决了的问题。

但还有一种更隐蔽的问题：资源竞争。假设你有 49 个 Handler 共用 8 个线程。其中 5 个日志/通知类 Handler 占用了 5 个线程（虽然它们单个很快，但数量多），那核心的业务 Handler 只剩 3 个线程可用。

修复 4：幂等设计——预防重复执行比事后补偿更简单

任务引擎有个绕不开的问题：xxl-job 自己是至少一次（at-least-once）调度语义。调度器可能因为网络抖动重试，也可能因为前一次没来得及更新分片状态而再次触发。

如果我们的 Handler 没有幂等保护，同一个订单被同步两次，就会产生重复数据——最坏的情况，一个订单被创建两次，仓库发了两份货。

V2 的幂等设计分为两层：

第一层：任务状态机 + 乐观锁

通过一次带条件的 UPDATE 来”抢占”任务。如果 0 行被更新，说明这个任务已经被其他调度周期抢走了——直接跳过，不做任何事。这就是乐观锁抢占模式。

第二层：唯一索引兜底

即使应用层的状态机被绕过（比如直接写库），数据库层还有唯一约束兜底。INSERT ... ON DUPLICATE KEY UPDATE 保证同一天的同一笔订单、同一个 Handler 只会产生一条记录。

很多团队喜欢在幂等上做复杂的分布式锁，或者引入 Redis 做去重。我们的经验是：预防重复执行比事后补偿简单得多，而数据库的唯一约束是最可靠、最简单的预防手段。

这也呼应了 DDIA 第九章的一个观点：在分布式系统中，”恰好一次”语义并不存在——你不可能同时保证可靠性和恰好一次。但你可以通过幂等性让”至少一次”的行为表现得像”恰好一次”。Kleppmann 称之为”幂等写入”（idempotent write），这是构建可靠系统的基本技术之一。

修复 5：ThreadLocal 泄漏修复——线程池复用的隐形炸弹

这个问题发现得很晚，因为它不会直接报错，只会慢慢泄露。

我们的 Handler 在执行时会从 TaskContext 里获取当前任务的任务 ID、批次号等信息。在最开始的实现里，我们把 TaskContext 放进了 ThreadLocal，Handler 执行完成后……就忘了清理。

线程池的线程是复用的。这次任务执行完了，线程不销毁，它身上的 ThreadLocal 里的上一次任务上下文也不会自动消失。下次这个线程被分配执行另一个任务时，如果新任务忘记设置 TaskContext，它读到的是上一个任务的旧数据。

最典型的问题：告警消息里竟然出现了上一批任务的任务 ID。

说实话，如果你问我 V2 最大的遗憾是什么，我会说是监控。虽然埋点都留好了，但我们没有接 Prometheus、没有 Grafana 面板，告警还是靠 xxl-job 的邮件通知 + 人工巡检。这也是团队当时工程化水平的一个侧面反映——知道该做什么，但优先级被业务压着没能做。

不过，埋点本身已经为后续的 Metrics 升级做好了准备。后来只需要加一个 TaskLifecycleListener 的实现类，把 afterExecute、onTimeout、onException 的数据推送到 Prometheus pushgateway，就可以看到每类任务的执行耗时分布、超时率、成功率——这是 V3 的事了。

结尾：工程是迭代出来的

SyncTask V2 的这些改进，没有一个是开天眼一次做对的。

线程池隔离，是通知服务挂了三次之后才加的。orTimeout，是凌晨告警之后第二天早上改的。幂等设计，是对账发现重复数据之后补的。ThreadLocal 泄漏，是排查了一个告警乱码 bug 之后修的。

每一条改进后面，都有一个线上事故。如果你问我架构能力是怎么长的，答案就是：被事故喂出来的。

DDIA 第九章结尾有一段话，大意是：分布式系统的难点不是实现功能，而是处理各种可能的故障。你要考虑网络分区、时钟不可靠、节点重启、消息乱序……一个看似简单的操作，在分布式环境下可能以十几种方式失败。

SyncTask 引擎面对的，正是这种”部分失效”的典型场景。93 个 Handler，10 多个外部系统，任何一个都可能在任意时刻出问题。V2 用超时控制 + 故障隔离 + 幂等设计，让引擎从”一个卡住全部死”变成了”挂了几个不影响整体”。

这不是因为 V2 的架构有多超前，恰恰相反——V2 的每一项改进都是被逼出来的，是塌了一次才补上一块砖。

工程就是这样：不是设计出来的，是迭代出来的。
