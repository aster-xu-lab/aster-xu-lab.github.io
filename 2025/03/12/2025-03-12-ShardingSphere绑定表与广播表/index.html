ShardingSphere 绑定表与广播表：JOIN 与配置表的两大解法

JOIN 在分片下的尴尬

分库分表后，JOIN 是个老大难。以订单为例：or_sales_info 和 or_sales_item 都在分片，按 order_id 关联。如果两张表的分片规则相同，但 ShardingSphere 不知道它们”按同一口径分片”，就会产生笛卡尔积——4分片 × 4分片 = 16 种组合，结果大量重复且几乎必然错误。

绑定表：解决分片表 JOIN

绑定表的本质是：告诉 ShardingSphere，这两张表按相同的分片键路由，JOIN 只在各自对应的分片内进行。

效果：

实测：主表 4 条 + 明细 8 条，未绑定会 JOIN 出 32 条错数据；绑定后正确返回 8 条。

前提：两张表必须用同一个分片键、同一种分片算法，否则绑定校验会报 InvalidBindingTablesException。

踩坑：两表各配一个独立但结构相同的 INLINE 算法（表达式模式一致，仅表名不同），比”共用一个算法”更稳。

广播表：解决配置/字典表 JOIN

业务里还有一类小表：平台配置、字典、商品类目——数据量小、变动少、但经常要和分片表一起 JOIN。比如 t_platform_config。

广播表的设计：让这张表在每个分片都存一份完整副本。JOIN 时随便取哪个分片的副本都行，不产生笛卡尔积。

INSERT 会自动写进每个分片，SELECT 只查一个分片（数据都一样）。

⚠ 注：ShardingSphere 5.4 Java API 的 ShardingRuleConfiguration 里没有 broadcastTables 字段，广播表只在 YAML 配置模式支持。纯 JDBC 验证时我是”手动向每个物理表插副本”来模拟的。

两者对比

绑定表 广播表
解决什么 分片表之间 JOIN 笛卡尔积 配置表参与 JOIN
表特征 都按同一分片键分片 小表、全量复制
机制 绑定路由组 每分片存副本
JOIN 结果 分片内精确 JOIN 任取一份副本

小结

  • 业务分片表JOIN → 绑定表（前提：同分片键同算法）
  • 小配置表 → 广播表（每分片存副本）

这两招能在分片环境下安全地做 JOIN，是 or_sales_info 这类订单体系必备的配置。
