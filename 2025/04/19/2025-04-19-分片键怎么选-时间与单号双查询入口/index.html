分片键怎么选？从"时间主分片"修正为"单号主分片"的选型复盘

本文记录一个分片键选型的重要修正：一开始基于”数据按时间查询”选择了时间主分片，但业务确认所有事件都按单号处理后，修正为单号主分片。这个修正过程本身就是分片键选型的最好案例。

一、初始思考：按时间查 + 按单号查，一个分片键不够

or_sales_info 有 6000 万数据，最初看到两个查询入口：

  1. 按时间查：WHERE trade_time BETWEEN ...
  2. 按平台单号查：WHERE outer_order_no = '221001008'

一个分片键没法同时精准命中两个入口：

最初基于”90% 查询带时间”的判断，选了时间主分片 + 单号反向索引表（双表结构，用反相索引补单号查询）。

二、关键转折：业务确认”所有事件都按单号”

深入业务后确认了一个决定性事实——所有业务事件（创建/发货/取消/签收）都按单号处理：

这意味着单号是业务操作的主维度，比”按时间查报表”高频得多。而如果表按时间分片，每一次发货/取消/签收都会广播所有月表——写路径广播比读更严重（要锁、要事务）。

三、修正结论：单号主分片

既然所有事件都按单号，单号必须是主分片键：

写入/事件：全按单号精准路由

时间统计：走 Doris/ES，不裸查 MySQL 分片

四、单号怎么均匀分片

单号是字符串（平台侧生成，格式各异）。均匀分片的要点：

  1. 用字符串专用哈希：HASH_MOD（auto-tables 模式）或自定义 FNV/Murmur，别裸用 String.hashCode()
  2. 单号本身要有”熵”：若单号是自增/低位规律，哈希也难救（但平台生成受限，靠好哈希兜底）
  3. 实测分布：跑真实单号样本看桶均衡度，倾斜就换哈希

五、反向索引表的取舍：单号主分片后不需要

新的认知：单一分片键无法同时满足”按单号”和”按时间”两个入口，但”主”的选择决定要不要反向索引。

主分片键 单号查询 时间查询 是否需要反相索引
时间 广播 精准 需单号反相索引
单号 精准 广播 不需要(走 Doris)

单号主分片后，order_no 本身就是分片键，天然精准路由，不需要 order_no 反向索引表（它只存在于”非单号分片”方案里补单号查询）。时间统计交给 Doris，也不需要在 MySQL 建时间索引。

六、扩容：单号 hash 分片的代价

时间分片”加月表天然扩容”的优势在单号 hash 分片下没有了——扩展分片基数（8→16片）需 rehash：

但这是交易系统按单号分片的必要代价，换来的是所有业务事件零广播精准路由。

七、小结：分片键选型的第一原则

分片键对准”最高频、最核心的操作维度”，而不是”查询最多的维度”。

  • 这里”查询最多”是时间，但”操作最高频“是单号（所有事件按单号）
  • 交易系统写入/状态流转都带单号 → 单号主分片（业界主流）
  • 时间统计交给 Doris/ES 宽表（Canal 同步），不纠结 MySQL 分片能否扛时间查询

这次修正的核心教训：选分片键前，先搞清楚业务的操作主维度（订单就是单号），而不是只看查询形态。写路径的广播（事件 update）比读路径广播严重得多，交易系统必须让主维度精准路由。
