DDIA-08-隔离级别的事务世界：从读未提交到可序列化

引言

当两个用户同时抢最后一瓶茅台，你的数据库在做减法的时候，看到的到底是哪个数字？这是一个看似简单，实则暗藏杀机的问题。

DDIA第8章用了整整一章讨论一致性和共识，而事务隔离级别正是”单机一致性”的基石。理解它，是你理解分布式一致性的必要前提。

一、四种隔离级别全景

Read Uncommitted（读未提交）

可以读到其他事务尚未提交的修改。

并发问题：脏读——T2读到了T1还没提交的数据，T1后来回滚了，T2基于”脏数据”做出了错误决策。生产环境几乎没人用。

Read Committed（读已提交）

PostgreSQL的默认级别。只能读到其他事务已经提交的修改。脏读被消除了。但不可重复读仍存在——同一事务内两次SELECT可能读到不同值。

实现机制：MVCC每次SELECT创建新Read View，看到最新已提交版本。

Repeatable Read（可重复读）

MySQL InnoDB的默认级别。同一事务内，多次读取同一行数据，结果始终一致。不可重复读被消除了。

但写倾斜（Write Skew）仍存在——两个事务基于同一快照做不同决策并写入不同行时，RR无法检测。

实现机制：MVCC在事务开始时创建一次Read View，整个事务期间都用它。

Serializable（可序列化）

最强隔离级别。并发执行结果与串行执行完全一致。

实现机制一：2PL（两阶段锁）——传统做法，性能差。

实现机制二：SSI（Serializable Snapshot Isolation）——DDIA作者高度推崇。乐观执行，检测冲突，回滚。PostgreSQL 9.1开始支持。冲突率低时性能远优于2PL。

特性 2PL SSI
并发策略 悲观 乐观
阻塞行为 读阻塞写 不阻塞
冲突处理 等待/死锁 回滚重试
适合场景 高冲突 低冲突

二、MySQL RR vs PostgreSQL RC：为什么默认不同？

MySQL的历史路径：早期Statement-Based Replication下，RC会导致主从不一致。RR通过间隙锁保护了基于语句的复制。即使现在推荐RBR，惯性依然。

PostgreSQL的哲学：不给开发者”魔法”。RC是开销最小的正常级别，如果你需要更强隔离，显式设置SERIALIZABLE。

实际影响：

  • MySQL RR+间隙锁：死锁概率更高
  • PostgreSQL RC：开发者在应用层更主动处理并发

三、隔离级别速查表

隔离级别 脏读 不可重复读 幻读 写倾斜
Read Uncommitted 是 是 是 是
Read Committed 否 是 是 是
Repeatable Read 否 否 部分 是
Serializable 否 否 否 否

四、实战：订单中心的隔离级别选择

扣库存 → RR + 乐观锁（version字段）。RR保证事务内读到一致快照，乐观锁防丢失更新。

创建订单 → RR。多表操作需要一致的快照视图。

报表查询 → RC。长事务报表不要持有快照导致undo log膨胀，RC看到最新提交反而更接近”当前”状态。

余额扣减 → Serializable或严格乐观锁。余额扣成负数就是资损事故。

五、与DDIA第8章的呼应

DDIA第8章讨论的是分布式系统中的一致性和共识，事务隔离级别是单机一致性模型。理解单机隔离级别有两点关键意义：

  1. 它定义了”异常”的边界——很多人用着MySQL RR却不知道写倾斜的存在
  2. 分布式一致性是单机隔离级别的延伸——Read Committed变成”最终一致性”，Serializable变成”线性一致性”+序列化

Martin Kleppmann对SSI的高度推崇贯穿DDIA全书：与其用锁阻止冲突，不如让冲突发生然后处理它。

结语

如果你只记住一句话：永远不要假设数据库的默认行为能保护你——显式分析你的并发场景，显式设置你的隔离级别。
