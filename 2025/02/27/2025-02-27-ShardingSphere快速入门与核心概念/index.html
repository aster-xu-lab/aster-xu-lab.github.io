ShardingSphere-JDBC 快速入门与核心概念

问题的起点

cloud-order 的 or_sales_info 表已经逼近 6000 万条，单表查询越来越慢，DBA 天天催着拆分。但分库分表一直是个”听起来很厉害，做起来很痛”的事——手写路由、改所有 DAO、跨分片聚合…… 直到引入了 ShardingSphere-JDBC。

本文记录我对 ShardingSphere-JDBC 的学习笔记，从最核心的概念讲起。

核心概念：逻辑表 vs 物理表

ShardingSphere 最巧妙的一点，就是应用层永远只认识一张”逻辑表”，SQL 发来后在底层被改写路由到真实的”物理表”。

  • 逻辑表：应用代码里操作的统一表名，如 t_order
  • 物理表：数据库里真实存在的分片表，如 t_order_0 ~ t_order_3

业务代码完全无感，分片逻辑全部被 ShardingSphere 透明接管。

日志里看路由：sql-show

配置 props.setProperty("sql-show", "true")，执行时会打印改写过程：

  • Logic SQL = 应用写的原始 SQL
  • Actual SQL = 改写后真正执行的 SQL
  • 数据源名 + 物理表名一目了然

学习阶段务必打开它，直观观察路由。生产再关掉。

小结

ShardingSphere-JDBC 的核心就是：逻辑表 + 分片规则 + 透明路由。构建一个分片 DataSource，业务零改造，SQL 自动改写路由。这是分库分表落地的基础，后面的策略、兼容性、迁移都是在这个地基上展开的。
