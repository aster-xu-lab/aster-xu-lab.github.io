慢 SQL 治理一年复盘：从日均千条级到个位数

订单中心慢 SQL 从日均千条级（峰值 1124 条）降到个位数（6 条），DB 单次负载降 30-50%。这篇复盘一年治理的完整路径——不是一次优化，是持续体系。

一、现状：慢 SQL 是”慢性病”

订单中心日均处理几十万订单，慢 SQL 日志峰值日均 1124 条，系统可用性在 99.9% 附近徘徊，每次大促都心跳加速。

慢 SQL 的危害不只是”慢”——它占用连接、拖慢事务、引发雪崩。一条慢 SQL 打满连接池，整个订单链路就瘫了。

二、治理路径：从上到下，低成本手段优先

我遵循”从便宜到贵“的治理顺序：

① 索引优化（收益最大）

慢 SQL 里 80% 是索引问题：

  • 联合索引：查询条件多字段，建联合索引（注意最左前缀）；
  • 覆盖索引：查询的字段都在索引里，回表变索引扫描——订单查询高频字段，覆盖索引收益明显；
  • 区分度：区分度低的字段（如 status）不适合单独建索引。

② SQL 改写

  • 大 IN 拆批：WHERE id IN (上千个) 拆成多批，避免一次查太多；
  • 去掉 COUNT(*)：大表 count 全表扫描，用缓存计数替代；
  • 避免 SELECT *：只查需要的字段（配合覆盖索引）；
  • LIKE 优化：前置通配符不走索引。

③ 缓存

读多写少的查询，加缓存（Redis/Caffeine），把 DB 压力降下来——这是最直接的降载手段。

④ 连接池/架构

  • 连接池隔离（舱壁）：慢的查询隔离，不拖垮全局；
  • 复杂统计下沉 Doris：订单分库分表后，跨分片统计不扛在 MySQL。

三、体系化：不是一次优化，是持续机制

治理能持续，靠的不是”优化一次”，是机制：

  1. 慢 SQL 监控：慢日志自动收集，阈值内的都进监控；
  2. 定期扫描：每周看慢 SQL 列表，新增的立刻分析；
  3. 上线 SQL 评审：新需求带的 SQL 上线前走评审（看索引、看行数）；
  4. 大促前专项：大促前做一次慢 SQL 全量清剿 + 热点缓存预热。

关键认知：慢 SQL 治理是”存量清理 + 增量拦截”两条腿——只清存量，新的还会冒出来。

四、结果与数字

  • 慢 SQL：日均 1124 条 → 6 条；
  • DB 单次负载：降 30-50%；
  • 大促：DB 不再是瓶颈，配合限流降级扛住峰值。

（数字都有监控日志支撑，不是估的。）

五、复盘：最值的几个判断

  1. 优先索引而非改架构：80% 慢 SQL 靠索引就解决了，分库分表是最后手段——先便宜后贵；
  2. 覆盖索引是隐藏王者：订单查询”只查字段 + 高频”的场景，覆盖索引把回表变索引扫描，收益被低估；
  3. 增量拦截比存量清理重要：上线 SQL 评审挡住新增慢 SQL，比反复清存量有效得多。

总结

  • 慢 SQL 是”慢性病”：占连接、拖事务、引发雪崩；
  • 治理顺序：索引 → SQL 改写 → 缓存 → 连接池/架构，从便宜到贵；
  • 覆盖索引、大 IN 拆批、去 COUNT(*)、避免 SELECT *，是高频手段；
  • 体系化：监控 + 定期扫描 + 上线评审 + 大促专项，存量清理 + 增量拦截；
  • 结果：1124 → 6 条、DB 负载降 30-50%，数字有据。
