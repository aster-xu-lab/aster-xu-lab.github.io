分片扩容的无停机流程：存量回填、binlog增量追平与对账兜底

一、为什么 hash 分片扩容要 rehash

单号哈希分片的落片公式是：

片数从 8 扩到 16，% 16 的结果和 % 8 不一样了——原来落在 0 号片的数据，现在可能该落 2 号片。所以扩一倍的片数，意味着大约一半的数据要换物理分片。这就是 rehash。

这也是”单号 hash 分片”对比”时间/区间分片”的一个代价：时间分片扩容无感（新数据进新区间），但 hash 分片扩容必须迁移。

那怎么迁？一次对外无感的迁移，是分库分表最见功力的地方。

二、无停机迁移的五步流程

迁移的核心不是”把数据搬过去”，而是”搬的过程中业务不能停、不能丢、不能重“。我的流程是五步：

逐段解释：

① 存量回填：历史数据（累计约 6000 万行）分批从旧分片迁到新分片。分批 + 夜间低峰跑批，日均约 800 万行，每批小步提交、last_id 位点记进度、断点续跑——这是典型的迁库批处理范式。

② binlog/Canal 增量追平：回填期间业务还在写，存量回填的速度追不上新增写入，所以要靠 binlog 增量把新写入同步到新分片。这里的关键是位点对齐：记录切流点严格对齐 binlog 位点，作为对账基准。

③ 对账兜底：增量同步不是绝对可信的，按业务主键遍历两侧比对，差异按最新状态重写目标分片。连续两轮差异为 0 才允许切流——对账不过，绝不推进。

④ 灰度切流：先切一小部分（比如 1/16）验证稳定，再按渠道逐个切，约两周完成全量。灰度期间随时可回滚。

⑤ 删旧表：全量对账通过、稳定运行一段时间后，才清理旧表。

三、澄清”双写”：零侵入的 binlog 增量双写

“双写”这个词在面试里极易被误解，我在这里明确口径：

这里的”双写”= 新老分片并存期间，由 binlog/Canal 异步增量把新写补到新表的零侵入增量双写。业务只写老表，不在应用层改代码做双向写。

也就是说，”双写”不是应用层每个写操作写两遍，而是数据库层面的 binlog 捕获 + 异步增量。业务代码完全无感知，这是它”零侵入”的含义。

四、增量一致性：为什么不会”死漏”

双写期间，增量同步理论上存在两类不一致：

  1. 新建单：切换时点没对齐的单子；
  2. 中途变更单：同一单先更旧表、后更新表，顺序竞态。

这两类靠什么收敛？

  • ① 位点对齐：切流点严格对齐 binlog 位点，记对账基准位点；
  • ② at-least-once + 幂等：增量消费至少一次、不缺失，消费端幂等去重；
  • ③ 对账兜底：连续两轮差异为 0 才切流，差异按最新业务时间戳/版本号重写目标分片。

这里要诚实：瞬时不一致是存在的（”暂时”不是”死漏”），靠对账收敛成最终一致。对外承诺的是”最终一致 + 对账收敛 + 对外无感“，不是”零瞬时不一致”——那种承诺做不到，也不该做。

五、零停机切换：Nacos 配置热更

迁移里最容易翻车的环节是”切换路由那一刻“——如果切路由要改代码、重启应用，就是停机。

我的做法是配置驱动路由：

  • 业务代码只写逻辑表（or_sales_info）；
  • ShardingSphere 路由层把逻辑表映射到物理表（版本号前缀 t_sales_v8/t_sales_v16）；
  • 换表名/换数据源 = 改路由配置，不是改 SQL；
  • 数据源 + 分片规则放 Nacos 下发，应用不重启、连接不断。

这样”切流”本质上是改一个路由配置，配合 @RefreshScope 让配置生效。切流顺序：先灰度切读（按渠道/比例验证）→ 全量对账通过后 100% 切走 → 老表保留可回滚。

技术坑提醒：ShardingSphere 的 DataSource 默认不会自动 @RefreshScope 热置换，需要显式挂刷新逻辑，否则配置改了也不生效——这是”零停机”能否真正成立的细节。

六、真实口径

这是 2025 年下半年真实上线的项目，几个关键数字我固定下来，避免各渠道口径打架：

  • 当前 8 片，每片约 750 万行（6000 万 ÷ 8）；
  • 2025 下半年灰度上线；
  • 切流约两周（按渠道逐个切）；
  • 历史迁移约一周（存量回填 + binlog/Canal 增量追平，无停机）；
  • 扩容规划 8→16 片，同一套 rehash 流程。

七、为什么”对账不过不切流”是铁律

整个流程里，最容易被低估的是对账。回填快慢可以赶、增量追平可以等，但对账是唯一的”正确性证明”。没有对账兜底，回填和增量的任何一次失误都会变成静默的数据错误，而且在 Doris 里根本看不出来——查询照常返回，只是结果悄悄不对。

所以我把对账当成迁移的”关卡”而不是”可选项”：连续两轮差异 0，才允许切流；任何一轮不过，停下来查，而不是带着差异继续走。

总结

  • hash 分片扩容必然 rehash，落片会变，必须迁移；
  • 无停机流程五步：存量回填 → binlog 增量追平 → 对账兜底 → 灰度切流 → 删旧表；
  • “双写” = binlog/Canal 零侵入增量双写，不是应用层双向写；
  • 增量一致性靠 位点对齐 + at-least-once 幂等 + 对账兜底，瞬时不一致靠对账收敛成最终一致；
  • 零停机切换 = Nacos 配置热更（逻辑表 → 物理表映射，改配置不改 SQL）；
  • 对账不过不切流，是迁移的铁律。
