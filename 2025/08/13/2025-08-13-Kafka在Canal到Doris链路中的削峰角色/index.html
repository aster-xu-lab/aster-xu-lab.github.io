Kafka在Canal→Doris链路中的削峰角色：一次分库分表的真实配套工程

背景：分库分表后，复杂查询去哪儿

订单中台的销售信息表做了分库分表（单号主分片，8 片，每片约 750 万行），WHERE order_no = ? 这种主路径查询零广播，很舒服。

但分库分表有个必然的代价：按单号分片后，跨分片的复杂统计查询做不了——比如按用户、按时间段的聚合分析，散落在 8 个分片里，没法在 MySQL 层高效完成。

业界的标准解法是读写分离 + 异构存储：把 MySQL 的数据实时同步到分析型数据库（OLAP），复杂查询走 OLAP，MySQL 只扛事务。

我们用的组合是：MySQL → Canal → Kafka → Doris。

二、链路长什么样

每个环节的职责：

  • Canal：伪装成 MySQL 的从库，订阅 binlog，把每条数据变更解析成结构化事件发出去；
  • Kafka：消息的削峰缓冲层——Canal 抓到的变更瞬间可能很大（大促、批量操作），Doris 写吞吐有限，直接怼上去会压垮下游；
  • Doris：OLAP 宽表，承接所有跨分片的复杂统计查询。

三、为什么中间必须垫一层 Kafka

直接”MySQL → Canal → Doris”不行吗？不行，三个理由：

1. 削峰：binlog 变更的节奏是”突发的”——白天大量订单，深夜凌晨可能批量修正，瞬时流量能差一个数量级。Doris 按峰值去准备资源太浪费，按均值扛又会积压。Kafka 垫在中间，上游突发写进 Kafka，下游按自己的节奏消费，两边解耦。

2. 解耦/缓冲：Doris 短暂不可用（运维、扩容、故障）时，Kafka 的分区存储 + retention 兜住数据，不会丢，恢复后继续消费。这就是消息队列的经典价值：不要求上下游同时可用。

3. 数据量大：全量销售数据的持续同步，消息量是”大数据量”级别。Kafka 天生为这种场景设计——百万级吞吐，扛这种量级毫无压力。

四、Kafka 为什么能扛住：高吞吐的物理基础

Kafka 百万级吞吐不是吹的，底层是三个机制的叠加：

① 日志模型 + 顺序写
消息追加进分区的日志段文件，只在尾部顺序 append、不随机覆盖。机械盘顺序写远比随机写快（随机写要寻道，一次寻道约 10ms；顺序写是连续的）——这是吞吐的物理地基。

② PageCache
读写依靠操作系统页缓存，命中页缓存就不碰磁盘，性能”接近内存”。

③ sendfile 零拷贝
Broker 把日志段发给消费者时，用 sendfile 让数据从磁盘经内核直接 DMA 到网卡，不经过用户态——从 4 次拷贝降到 2 次 DMA。上一篇写零拷贝时专门讲过这块。

一句话主线：日志模型 + 顺序 append + PageCache + sendfile，把”落盘”和”网卡发送”都推到最省的道路上。

五、可靠性：这条同步链路不能丢

数据同步链路一旦丢消息，Doris 里就是静默的脏数据——比延迟更可怕。Kafka 侧用三件事兜底：

  • 生产端 acks=all：所有 ISR 副本都写成功才算成功，配合重试；
  • Broker 端副本 + min.insync.replicas：保证至少 N 个副本同步，副本落后太多被踢出 ISR；
  • 消费端手动提交 offset：Doris 写成功才提交消费位置，写失败不提交，重启后重新消费。

再往下还有一层：对账。这条链路依赖”增量消息不漏”，但增量本身有兜不住的概率（Canal 位点异常、消费积压超 retention 被清等）。所以除了 Kafka 侧的可靠投递，链路还要有定期对账补漏——按业务主键比对 MySQL 和 Doris 的数据，差异重投。增量 + 对账，才是完整闭环。

六、一个诚实的口径说明

这里涉及的”8 片、每片约 750 万行、2025 下半年灰度约两周、迁移约一周无停机”是我简历和面试里的定稿口径，写博客时我保持同一口径，避免各渠道数据打架。分库分表本身的选型逻辑（为什么单号主分片、为什么不用时间主分片）是另一篇的主题。

总结

  • 分库分表后的复杂查询，靠异构存储承接：MySQL 事务、Doris 分析；
  • Canal 抓 binlog → Kafka 削峰缓冲 → 写 Doris，Kafka 的角色是削峰 + 解耦 + 兜底；
  • Kafka 高吞吐 = 顺序写 + PageCache + sendfile 零拷贝；
  • 同步链路可靠性 = acks=all + 副本/ISR + 手动提交 offset + 定期对账补漏；
  • 增量 + 对账，才是”不丢”的完整闭环。
