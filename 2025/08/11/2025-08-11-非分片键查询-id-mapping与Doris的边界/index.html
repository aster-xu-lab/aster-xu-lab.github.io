非分片键查询怎么办：id-mapping索引表、Doris与ES的边界

分片键定了单号，那”按用户查订单”怎么办？

这是分库分表面试的经典深水区：你的分片键是 order_no，那按 user_id 拉某个用户的所有订单，怎么办？

很多人第一反应是”上 ES”或”上索引”，但这是方案先行的坏习惯。我踩过的坑告诉我，正确顺序是：先问业务要不要这个查询。

一、先立原则：分片后只支持业务真实需要的查询

分库分表的前提是：只支持业务真实需要的查询，不是所有”可能发生的查询”。

我的订单中台真实访问模式：

  • 下单到下游：创建订单，同步到外部系统；
  • 按订单号回传状态：外部系统处理完，按单号回传状态。

而 C 端用户不直接查中台的库——用户在自己 App 里看订单列表，那是商城/前端职责，它有自己的数据服务。中台对外暴露的是”按订单号下发/回传状态”的核心链路。

所以”按 user_id 拉全部订单”这种 C 端列表查询，中台基本不做，它根本不是预设要解决的问题。先把这个想清楚，后面一大半”怎么办”都不存在了。

二、真需要时：id-mapping 索引表（二次路由）

如果后台运营真需要”按用户查订单”（低频、内部），业界标准解法是索引表法（全局二级索引）：

这是二次路由：第一次用索引表把”非分片键”转成”分片键集合”，第二次用分片键走主路径。

这套方案的优点：主表不用动，分片体系不用改，只多一张小索引表。索引表本身要么不分片（量小）、要么按 user_id 分片，都便宜。

三、为什么不能用 Doris 做这个查询

可能会有人想：”我反正有 Doris 同步数据，直接查 Doris 不就得了？”

不行。Doris 是 OLAP 列存，强在聚合统计（GROUP BY），不适合精确点查。 原因：

  • Doris 没有二级索引，只有分区剪枝；
  • 按 user_id 精确点查时，如果没有按 user_id 分区，就得全分区扫描，反而慢；
  • 要让 Doris 支持点查，要满足 Unique Key + Merge-on-Write + 行存 + 短路路径一堆苛刻前提，为一个低频反查引进来，得不偿失。

所以分工很明确：Doris 管”跨分片的聚合统计”（按时间、按平台、按品类出报表），不碰”单用户精确点查”——那个用 id-mapping 索引表就够了。

四、为什么也不该无脑上 ES

ES 的适用场景是 C 端复杂搜索：模糊查询、多维组合筛选、相关性排序。中台的一个内部低频反查，用索引表两步就能解决，为它引入一整套路由、分片、高可用的 ES 集群，运维成本和复杂度都严重过剩。

分库分表后非分片键查询不是无脑上 ES/索引，先问”业务到底要不要这个查询”，按真实需求决定。 这句话是我复盘时最想记下来的。

五、关联表与独立引用表的边界

非分片键查询的话题，还延伸到”哪些表进分片体系”。我按两类区分：

“同生共死”的关联表（订单主表、订单商品表、订单地址表、售后退货）：全部用 order_no 分片。因为它们关联键本来就是 order_no，同键后一个订单的全部数据哈希到同一物理分片，订单详情页查主表+商品+地址是片内本地 JOIN，根本不是跨片查询，也没有跨片分布式事务。

独立”引用”表（商品主数据、用户主数据）：低频、稳定、总量可控，不分片，用冗余字段或单独存储，不塞进订单分片体系。它们和订单是引用关系，不是”同生共死”。

这条边界很关键：该同键的同键（消灭跨片 JOIN），不该同键的别硬塞（避免无谓分片）。

总结

  • 先问业务要不要，C 端列表查询不是中台职责，很多”怎么办”根本不存在；
  • 真需要的低频反查：id-mapping 索引表，先查索引拿 order_no 集合，再按分片键精准路由（二次路由）；
  • Doris 不适合精确点查（OLAP 列存、聚合强、点查弱），它管复杂统计；
  • ES 只留给复杂搜索，中台反查用索引表足够，不为它引集群；
  • 关联表同键分片消灭跨片 JOIN，独立引用表不分片。
