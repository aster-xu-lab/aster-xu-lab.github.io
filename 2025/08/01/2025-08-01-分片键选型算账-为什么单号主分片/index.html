分片键选型的算账：为什么单号主分片，而不是时间主分片

一、先回答”什么时候该分”

分库分表最容易被问倒的第一题是：为什么分？

我的判断信号有三个，缺一不可：

  1. 单表数据量逼近千万级：订单销售信息表累计接近 6000 万行、单月增量约 380 万行——索引、缓存、读写分离都扛不住的量级；
  2. 写入成为瓶颈：单库单库的写入能力到了上限；
  3. 目标是横向扩容，不是优化单点查询。

在到达这个信号之前，我们经历过一段”假分片”：早期是渠道垂直分表——拼多多一张表、京东一张表。问题很明显：手工拆分、没有分布式路由、每开一个新渠道要新建一套表、Schema 变更要同步 N 张表。这没有真正的扩容/路由能力，只是把数据”物理上拆开”了。

所以后来才做真正的水平分库分表：ShardingSphere-JDBC 路由到单物理表。

二、分片键选型：拿真实数据说话，不是拍脑袋

选分片键是分库分表最关键的决策，我的方法不是拍脑袋，而是拿真实数据做两件事：

  1. SQL 核查量级与访问模式：分析真实表，确认所有业务事件（创建/发货/取消/签收）的定位方式；
  2. 核对慢查询与执行计划：确认主路径是不是 WHERE order_no = ? 单点查询。

分析结果很明确：所有业务事件都按订单号定位。那么分片键的选择就水到渠成了。

三、为什么是单号，不是时间

两个候选摆上台面：

单号主分片：订单号唯一、天然均匀 → 按它分片，每条写入和状态流转精准路由到单物理表 → 写路径零广播。

时间主分片：按创建时间分片，对统计查询友好、按时间扩容天然无感——但有个致命问题：每条写事件会广播到全部分片。为什么？因为一个订单从创建到发货到取消，跨越很长时间，按时间分片的话，订单状态流转时它的分片在变，业务方根本不知道去哪查，只能广播所有分片。

写广播是分片方案里最严重的问题：分片后写是高频路径，写一条数据若广播到所有分片，等于所有分片都要处理——白分片，还引入跨片一致性难题。所以主分片键一定选高频查写的那一个。

一句话：单号对应”单点高频访问”，时间对应”范围统计访问”——前者是写路径的命脉，后者可以交给别处。 这就是”分片键匹配查询访问模式”（DDIA 第 6 章分区思想的精髓）。

四、复杂统计查询：不硬扛，下沉 Doris

选了单号分片，代价是按时间/多维度统计的查询变成广播。我的处理不是硬扛，而是异构存储：

OLTP 分片只解决”写入 + 分片键单点查询”，复杂查询给 OLAP。 这个分工清楚了，分片方案才站得住。

五、哈希算法：别裸用 String.hashCode()

单号是字符串，直接 orderNo.hashCode() % 8 是大坑——String.hashCode() 的分布特性差，特定前缀可能扎堆。我用的是 HASH_MOD（ShardingSphere auto-tables）/ FNV / Murmur 这类分布均匀的哈希。

而且不靠纸面公式选型，靠真实数据分桶说话：抽一段有代表性的真实单号（不同前缀/长度）→ 分别用 FNV/Murmur/HASH_MOD 对各桶取模 → 统计各桶数量极差/偏离均值比例，选最均匀的那个，同时检查特定前缀是否扎堆。

这里还有一个容易忽略的细节：平台字段字典归一化——淘宝/天猫/拼多多/PDD 的别名统一映射到标准字典码（TB/TM/PDD）。平台不是分片键、不参与路由，但统计/过滤必需，归一化保证跨分片聚合口径统一（下沉 Doris 时尤其重要）。

六、ShardingSphere 一次查询的底层五步

无论用什么分片工具，一次查询的底层原理都一样，这五步是核心：

  1. SQL 解析：把用户 SQL 解析，识别出分片键字段（order_no）和条件；
  2. 路由：根据分片键 + 分片算法，算出这条 SQL 落在哪些物理分片（hash(order_no) → 某个分片）；
  3. 改写：把逻辑表名改写为物理表名（逻辑 or_sales_info → 物理 or_sales_info_0/_1）；
  4. 执行：真的去分片执行改写后的 SQL；
  5. 归并：结果汇总——单片直接返回；跨片查询各片结果内存归并排序/聚合/分页。

跨片查询的代价也在这里暴露：跨片分页 ORDER BY create_time LIMIT 100 要每个分片各取 100 条再内存归并，page 越大取越多越贵。所以禁大页码、用游标分页。

七、选型与终局认知

工具选了 ShardingSphere-JDBC：JDBC 代理（嵌入式），不引入额外部署和网络跳点，贴合 Java 中台、逻辑简单、性能损耗小。相对 ShardingSphere-Proxy（独立代理、部署成本高）更适合。

行业格局上，分片有三大派：

  • 中间件派：ShardingSphere、阿里 TDDL、美团 Zebra（早期自研后来部分并入 ShardingSphere）；
  • 分布式数据库派：TiDB / OceanBase——原生分布式，是终局方向；
  • CDC 派：Canal/Debezium 同步 binlog 到数仓，用增量解决分表后的数据同步。

我的判断（诚实）：中间件是过渡态、分布式数据库是终局，但当前大多数公司还在 MySQL + ShardingSphere 阶段，因为运维生态更成熟。核心认知是：无论什么工具，SQL解析→路由→改写→执行→归并的原理都一样。

总结

  • 分库分表的信号：单表千万级 + 写入瓶颈 + 横向扩容目标；
  • 分片键选型拿真实数据 SQL 分析，不拍脑袋；
  • 单号主分片：唯一均匀、写路径零广播；时间主分片统计友好但写广播是致命伤；
  • 复杂统计下沉 Doris，OLTP 只解决”写入 + 分片键单点查询”；
  • 哈希用 HASH_MOD/FNV/Murmur，不裸用 String.hashCode，真实数据抽样验证分布；
  • 路由原理五步：SQL解析→路由→改写→执行→归并，工具不重要，原理一样。
