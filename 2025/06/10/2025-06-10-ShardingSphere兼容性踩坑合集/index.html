ShardingSphere 与 ORM 兼容性踩坑合集（分页 / 元数据 / 拦截器）

分片落地最痛的往往不是分片本身，而是与现有 ORM 的兼容性。我在把 ShardingSphere 接入 cloud-order（cloud-dal + MyBatis-Plus + PageHelper）时踩了一堆坑，整理成合集，帮你提前规避。

坑1：分页 —— PageHelper 与 ShardingSphere 二选一

现象：cloud-dal 的 PageUtils.startPage() 用的是 PageHelper 5.3.0（独立分页库），而 ShardingSphere 自己也带分页改写。两个分页机制叠加，SQL 被重复追加 LIMIT。

源码确认：PageUtils.startPage → PageHelper.startPage()；而 MybatisPlusAutoConfig 里 PaginationInnerInterceptor 默认 pagePluginEnable=false（关闭）。所以 cloud-dal 实际用 PageHelper 分页。

解法：分页必须二选一，不能两个分页拦截器并存。

  • 保留 PageHelper → 关闭 ShardingSphere 分页改写（不推荐）
  • 废除 PageHelper，改用 ShardingSphere 或 MyBatis-Plus 原生分页（推荐）

实测：MyBatis-Plus 的 PaginationInnerInterceptor 与 ShardingSphere 协同正常，total/pages 跨分片正确。这是我验证过最稳的组合。

坑2：物理表必须先建，再构造 ShardingSphere 数据源

现象：Spring Boot 里逻辑表报 Table or view 't_demo_order' does not exist。

根因：shardingDataSource() 这个 @Bean 在容器早期创建，ShardingSphere 扫描元数据时若物理表还没建，元数据是空白快照。而 @Component 的 CommandLineRunner 建表在容器 ready 后，太晚了。

解法：在 shardingDataSource() Bean 方法内部、构造数据源前先建物理分片表（幂等）。

坑3：非分片单表元数据不自动注册

现象：读写分离/影子库配置的单表报”表不存在”，但分片表正常。

坑5：cloud-parent 生态里 @SpringBootApplication 被中间件卡死

现象：order-service 加 @SpringBootApplication 启动报 Seata/Dubbo/Redis 找不到配置或连不上。

根因：cloud-parent 带入大量中间件，spring.factories 注册了自动配置，@SpringBootApplication 全部加载。

解法（二选一）：

  1. @SpringBootApplication(exclude={...}) 排除所有中间件自动配置（清单很长且会漏）
  2. 新建独立模块，parent 用 spring-boot-starter-parent，只依赖干净依赖（推荐）

坑6：Groovy 不兼容 Java 21

现象：INLINE 表达式里调 Java 对象方法报 Groovy 编译错。

根因：ShardingSphere 5.4.1 内置 Groovy 版本过老，不支持 Java 21 class 文件。

解法：INLINE 里只做简单的 % 运算；时间分片用 INTERVAL；字符串分片用 HASH_MOD。

排查手段总结

场景 手段
路由不对 sql-show=true 看 Logic → Actual SQL
版本冲突 mvn dependency:tree
API/SPI type 不确定 用 sources jar 反编译看
数据落库不对 底层 JDBC 直查物理表确认分布

小结

兼容性坑的共性问题就几个：分页二选一、物理表先建、元数据注册、逻辑数据源挂载。提前知道这些，能省掉大量调试时间。最推荐的生产组合：SpringBoot + MyBatis-Plus（原生分页）+ ShardingSphere，已在独立模块完整验证。
