DDIA-10-从线性一致性到因果一致性：一致性模型的阶梯

引言

分布式系统最令人头疼的问题之一就是：不同节点看到的数据不一致。

你刚在淘宝下了一个订单，刷新订单列表，订单没出来——你慌了，又下了一单，结果两个订单同时出现。这是用户体验的噩梦，也是分布式系统工程师的日常挑战。

在《Designing Data-Intensive Applications》第10章从单机到分布式的过渡中，Martin Kleppmann花了大量篇幅讨论一致性与共识。但坦白说，他给出的概念密度太高——线性一致性、顺序一致性、因果一致性、最终一致性，这几个词来回出现，容易让人迷失。

这篇文章的目标很简单：用一条阶梯，把四种一致性模型串起来，让你一次看懂。

一致性模型的阶梯

想象一座金字塔，从上到下约束越来越弱，性能越来越好：

这个阶梯揭示了分布式系统中一个永恒的权衡：你越想让系统表现得”像单机一样”，你就付出越大的性能和可用性代价。

下面我们一层一层来看。

第一层：线性一致性（Linearizability）

定义

线性一致性是最强的单对象一致性保证。它要求：所有操作看起来像是原子的、在一个全局时间线上的瞬时执行。

通俗地说：在你写入完成的那一瞬间之后，所有客户端都必须能看到你写入的新值。就好像整个系统只有一个数据副本，所有请求都在排队执行。

一个反例

假设你和一个朋友同时操作同一个银行账户（余额初始为100元）：

这就是线性一致性。关键特征：一旦写入完成（返回给客户端），后续所有读操作都必须返回新值。

为什么这么贵？

实现线性一致性需要共识协议。

在分布式系统中，多副本之间要达成”谁先写、谁后写”的一致意见，这就是 Paxos / Raft 存在的意义。Raft 通过 Leader 选举 + 日志复制，保证所有节点的操作顺序一致——从而对外呈现线性一致性。

代价是什么？

  1. 延迟高：每次写入需要多数节点确认（Quorum），跨机房延迟不可忽视。
  2. 可用性受 CAP 约束：网络分区下，你必须选择可用性（A）或线性一致性（C）。这里的 C 指的正是线性一致性——不是 ACID 里的 C（后者是事务原子性/一致性）。

Eric Brewer 的 CAP 定理指出，网络分区发生时，你只能在 C 和 A 之间二选一。所以在生产环境中，给关键路径加线性一致性，等于在可用性上押了注——你押的是网络不会频繁分区，或者你宁愿不可用也不愿数据不一致。

第二层：顺序一致性（Sequential Consistency）

定义

顺序一致性比线性一致性弱一层。它不要求操作在全局时间线上瞬时发生——只要求：所有节点看到的操作顺序一致，但允许操作有”生效窗口”。

区别在哪里？

关键区别：顺序一致性不要求”写入返回后立刻对所有人可见”。它只保证如果节点 A 看到了 op1 → op2 → op3 这个顺序，那么节点 B 也看到同样的顺序。但具体每个操作在什么时间点变得可见，顺序一致性不管。

这就是为什么它比线性一致性”便宜”一些：不需要全局同步时钟，不需要共识。

在现实中的应用

Zookeeper 提供的保证接近顺序一致性。它通过 Zab 协议保证所有事务按相同顺序提交，但客户端可能读到稍旧的快照。

第三层：因果一致性（Causal Consistency）

定义

因果一致性更进一步放松：有因果关系的操作保持顺序，但无因果关系的并发操作可以任意乱序。

这是分布式系统中极具实用价值的一致性层级——它抓住了大多数业务场景的本质需求。

什么是”因果关系”？

因果关系在分布式系统中的定义非常务实：如果一个节点先读到某个值，然后基于这个值做了写入，那么这两个操作之间就有因果关系。

或者更简单地说：某个操作的发生依赖于另一个操作的结果，它们就有因果关系。

读己之写是因果一致性的特例

“读己之写”（Read Your Writes）是最经典的因果一致性场景。

你发表了一条微博评论，然后刷新页面——你必须看到自己刚发的那条评论。这里的因果关系是：你点击”发表”触发的写操作，与你随后刷新页面的读操作之间，有清晰的因果链条——它们发生在同一个用户上下文中。

但有趣的是，其他用户发表的评论，你可能现在看到，也可能稍后看到——因为它们之间没有因果关系。哪怕 A 的评论比 B 早10秒，只要它们之间不存在依赖，一致处理也没关系。

因果一致性的实现

实现因果一致性，通常有两种思路：

  1. 显式追踪依赖：每个操作携带依赖信息（如版本向量的形式），系统根据依赖判断哪些操作必须排在前。
  2. 利用因果边界：如果一组操作之间隐含有因果关系（如相同数据库事务、相同 RPC 链），系统通过原子上传批量操作来保持因果顺序。

第四层：最终一致性（Eventual Consistency）

定义

最终一致性是底线：只要系统中不再有新的写入，经过足够长的时间后，所有副本最终会收敛到相同的数据。

这听着很弱——确实很弱。但绝大部分互联网系统的大部分数据都是最终一致。

适用场景

京东商品评论、微博点赞数、视频播放量——这些数据多等几秒钟再更新完全没问题。用户不关心某个视频播放量是 10230 还是 10231，过几秒看一样就行。

最终一致性的好处是极端可用：网络分区下照样能写，恢复后数据自动同步。

常用实现机制

  • 异步复制：主节点写入后立即返回，后台异步同步到备节点。
  • CRDT（Conflict-Free Replicated Datatypes）：数学上保证合并结果唯一的数据结构，适合离线协同编辑等场景。
  • Gossip 协议：节点随机交换差异日志，最终全局收敛。Dynamo/Cassandra 使用这套。

实战：电商系统中的一致性需求分层

理论聊了半天，回到我的主场——电商中台。在一个日订单130万的系统中，不同数据对一致性的要求截然不同。

库存扣减：线性一致性

库存是不能含糊的数据。超卖一次就是一次客诉。所以扣库存要走线性一致性路径：

  • Redis + Lua 实现：单线程 Redis 天然提供线性一致的单 key 操作。不过 Redis Cluster 跨槽操作无助。
  • DB 行锁 + 乐观锁：UPDATE inventory SET stock = stock - 1 WHERE id = ? AND stock >= 1，利用数据库行锁保证原子性。
  • 宁可慢不能错：库存扣减涉及资金安全，慢50ms换数据正确，完全值得。

订单列表：因果一致性

用户下单后，进入”我的订单”页面，必须看到刚下的订单。这就是读己之写——因果一致性的特例。

但用户在不同页面看到的订单列表，允许有秒级的延迟。比如订单中心、订单详情页、售后工单页面，后端的订单状态同步可以走异步消息，只要最终一致就行。

实现上：

  • 下单成功后同步写主库 → 立即返回订单ID。
  • 订单列表接口读主库（或读己之写的用户路由到主库）。
  • 其他旁路搜索/分析场景走ES异步索引，容忍几秒延迟。

商品评论：最终一致性

用户发表一条评论后，其他用户在几秒后才看到——这完全可接受。没有因果关系，也不需要全局顺序。ElasticSearch索引、Redis缓存的更新都可以走异步消息。

总结表

场景 一致性要求 代价 实现方式
库存扣减 线性一致 高延迟、分区可用性降低 乐观锁 + DB行锁 / Redis Lua
订单列表 因果一致（读己之写） 读路由复杂度 用户维度路由主库
商品评论 最终一致 几乎无代价 ES异步索引 + 缓存失效
商品详情 最终一致 几乎无代价 CDN + 缓存异步刷新

深度联结：SyncTask 引擎中的因果关系

这是我职业生涯中最得意的作品——SyncTask驿传引擎。它本质上是一个分布式任务编排引擎，核心能力是：将多个子任务按依赖关系串联执行。

afterExecute 编排

SyncTask 的核心模型是 DAG：任务A执行完毕后，触发任务B继续执行。

这里的因果关系非常清晰：

  • 风险控制依赖订单同步的输出（订单金额、用户ID），所以必须在订单同步之后执行。
  • 库存校验和风险控制之间没有依赖关系——它们的输入都来自订单同步，但彼此独立。所以它们可以并发执行。

这不正是因果一致性的完美体现么？

  • 有因果的操作（A → B）：保证顺序。
  • 无因果的操作（风控 vs 库存）：可以任意调度。

SyncTask 的设计怎么保证这点？

  1. DAG 解析：引擎在任务启动前解析依赖关系，生成拓扑排序——这确定了”必须有因果保序”的链路。
  2. 并发调度：同一层级的、无依赖关系的子任务同时提交给线程池——最大化并发。这在理论上可类比：无因果关系的写操作可以任意乱序。
  3. 失败传播：如果上游任务失败，下游所有依赖它的任务标记为”待补偿”——这也遵循因果链：上游的失败是下游无法执行的原因，不能无视为”成功了”继续往下走。

与 DDIA 的呼应

这个设计暗合了 DDIA 第10章和数据库中”因果一致性”的思想：不需要全局全序，只需要在局部因果关系链条上保序。如果强行要求所有子任务按照 N^2 个全局顺序依次执行（即线性一致的视角），性能将是灾难性的。

这正是 SyncTask 引擎的核心洞察：找到因果边界，在边界内保序，在边界外最大化并行度。

总结：从理论学习到工程实践

回顾这座一致性模型的阶梯：

做了七年后端，我的体感是：系统设计的本质不是选择”最强”的保证，而是为不同的数据、不同的路径、选择”恰好够用”的一致性层级。

库存扣减要线性一致，因为错了就是钱的问题。订单列表要因果一致，因为用户的心理模型就是”我做了什么应该能看到”。评论数、浏览数、点赞数——最终一致完全够用，成本几近为零。

最后，一致性不仅仅是一个分布式系统的学术概念——它已经渗透在 SyncTask 引擎的 DAG 调度里，渗透在 Redis Lua 脚本的原语里，渗透在每一个业务需求的架构选择里。而 DDIA 这本书的价值，正是帮你建立起这样一套思考框架。
