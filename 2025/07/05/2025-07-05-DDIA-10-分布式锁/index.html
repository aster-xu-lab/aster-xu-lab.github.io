DDIA-10-ZooKeeper与etcd：为什么分布式锁不应该自己实现

一、引子：一把看似简单的锁

假设你在写一个定时任务调度系统，需求很简单：多个服务实例部署在同一台机器上，每天凌晨2点跑一次对账，但只能有一个实例执行。

这不是虚构的故事。分布式锁是分布式系统中最容易让人产生“我已经搞定了”错觉的组件——代码量极少，概念极其简单，但正确实现的难度远超想象。

二、自己实现分布式锁的三个经典陷阱

陷阱一：SET NX 和 EX 不是原子的

在Redis 2.6.12之前，SET 命令不支持 NX 和 EX 同时使用。开发者需要先 SETNX，再 EXPIRE：

问题在于这两条命令之间不是原子的。如果客户端在 SETNX 成功之后、EXPIRE 执行之前崩溃，这把锁就永远不会过期——死锁。虽然Redis 2.6.12之后 SET key value NX EX seconds 解决了原子性问题，但它只是三个陷阱中最容易解决的那个。

陷阱二：锁过期比任务执行时间短

回到开头的场景。你给锁设了30秒过期，但任务偶尔跑了40秒。前一个实例还在执行任务，锁已经过期，后一个实例成功获取锁，两个实例同时操作共享资源。

你可能会说：“那把过期时间设长一点不就行了？”设多长？60秒？如果任务因为GC停顿、网络抖动、磁盘IO阻塞跑了70秒呢？在Java世界里，Full GC让线程停顿数秒甚至数十秒并不罕见。你永远无法保证任务一定在过期时间内完成。

陷阱三：主从切换导致锁丢失

这是最隐蔽的陷阱。假设你使用了Redis Sentinel或Cluster模式：

  1. 客户端A在Redis主节点上成功获取了锁 my_lock
  2. Redis主节点在将 my_lock 的写入同步到从节点之前宕机
  3. Sentinel触发故障转移，从节点被提升为新主节点
  4. 客户端B向新主节点请求 my_lock——因为数据没有同步过来，锁不存在，获取成功
  5. 现在A和B都认为自己持有锁

这就是典型的脑裂场景。Redis的异步复制模型决定了它无法保证数据在故障切换时完全一致。在主从架构下，任何基于Redis单节点的分布式锁方案在理论上都存在锁丢失的可能。

三、RedLock：一次著名的公开论战

面对主从切换的锁丢失问题，Redis作者Antirez在2014年提出了RedLock算法。

RedLock的核心思路是：不在单节点上获取锁，而是向N个独立的Redis节点（通常是5个）分别获取锁。客户端只有在多数节点（N/2+1，即3个）上成功获取锁，且总耗时小于锁的有效期时，才认为获取成功。

具体步骤：

  1. 获取当前时间戳（毫秒）
  2. 依次向N个Redis节点请求锁，使用相同的key和随机value，设置相同的过期时间
  3. 计算总耗时 = 当前时间 - 步骤1的时间。如果从多数节点获取成功且总耗时 < 锁有效期，则获取成功
  4. 锁的实际有效时间 = 锁有效期 - 总耗时
  5. 如果获取失败，向所有节点发送释放请求

看起来很美：没有单点故障，大多数节点同意了就算数。但DDIA作者Martin Kleppmann在2016年发表了一篇名为《How to do distributed locking》的文章，公开批评RedLock的设计。

Martin的核心论点是：RedLock依赖于时序假设。

RedLock的安全性建立在”锁的有效期大于操作耗时”这一假设之上。但在分布式系统中，时钟是不可靠的——NTP同步可能产生跳跃，虚拟机可能暂停，GC可能造成长时间停顿。如果一个客户端在获取锁后经历了长时间的GC停顿，等到它醒来继续操作共享资源时，锁可能早已过期并且被另一个客户端获取了。

Martin的关键洞见是：分布式锁的难点不在锁本身，而在锁与共享资源的交互。如果共享资源本身没有机制来检查锁的有效性，那么即使你的锁实现得再完美，也无法保证安全。

Antirez回应说，RedLock是一个实用的工程方案，在大多数生产环境中时钟漂移的影响是可控的。这场论战持续了多轮，两人谁也没有完全说服对方，但它揭示了一个深层次的问题：强一致性的分布式锁必须建立在共识协议之上，而不是基于过期时间的租约之上。

四、ZooKeeper：共识协议的正确打开方式

ZooKeeper用的是ZAB（ZooKeeper Atomic Broadcast）协议，一种类Paxos的共识算法。在ZK里实现分布式锁，靠的是临时顺序节点，而不是过期时间。

锁的获取与释放

基本流程：

  1. 所有竞争锁的客户端在ZK的某个路径下创建一个临时顺序节点，比如 /lock/request-0000000001、/lock/request-0000000002
  2. 客户端获取 /lock 下所有子节点，检查自己是不是序号最小的那个
  3. 如果是，获取锁成功
  4. 如果不是，对序号比自己小的上一个节点设置Watch，进入等待
  5. 释放锁时，删除自己的节点
  6. 由于是临时节点，如果客户端崩溃或会话超时，ZK会自动删除该节点，下一个客户端获得锁

这套机制有几个精妙之处：

第一，公平性。 顺序节点天然形成FIFO队列，先来先得，不会出现某个客户端永远抢不到锁的饥饿问题。

第二，羊群效应的避免。 如果所有等待者都Watch锁路径下的所有变化，每次释放锁都会唤醒所有等待者，造成惊群。ZK的”Watch上一个节点”策略确保每次只有一个客户端被唤醒。

第三，会话级别的安全保证。 临时节点的生命周期与会话绑定。如果客户端崩溃，会话超时后ZK自动清理节点，不会死锁。如果发生网络分区，客户端在分区一侧，ZK集群在另一侧——客户端无法通信，会话超时，节点被删除，锁自动释放，不会出现锁被永久持有的情况。

代价

ZooKeeper的代价也不小。它需要奇数台服务器组成集群（通常3台或5台），运维复杂度较高。所有写操作都要经过Leader，吞吐量受限于单台机器的网络和磁盘带宽。在Java生态中，Curator框架提供了 InterProcessMutex 等封装，但底层原理理解不足时排查问题依然困难。

更重要的是：ZK集群的部署和维护成本意味着，如果只是”需要一把分布式锁”，引入ZooKeeper是很重的依赖。这也是为什么很多团队宁愿在Redis上自己写锁的原因。

五、etcd：新一代的共识存储

etcd是CoreOS团队用Go语言开发的分布式KV存储，底层使用Raft共识算法。在分布式锁这个场景上，etcd可以被视为ZooKeeper的现代化替代品。

Raft vs ZAB

Raft和ZAB要实现的目标相同——在分布式系统中就操作顺序达成一致。Raft的设计更强调可理解性，把共识过程分解为Leader选举、日志复制、安全性三个相对独立的子问题。相比ZAB，Raft的论文更容易读，实现也更容易正确。

etcd的锁机制：Lease + 事务

etcd实现分布式锁主要依赖两个特性：

Lease（租约）： 客户端创建一个Lease并设定TTL，然后将key绑定到这个Lease。客户端需要定期续约（KeepAlive）。如果客户端崩溃或网络断开，Lease过期，etcd自动删除绑定的key——等价于ZK的临时节点。

相比ZooKeeper的优势

etcd的部署和运维比ZooKeeper简单得多。一个二进制文件，Raft集群的加入和移除通过API操作，不需要修改配置文件。再加上gRPC的HTTP/2协议、内置的Watch API，在云原生生态中，etcd已经成为Kubernetes的标配，团队通常不需要额外引入依赖。

当然，etcd也不是银弹。它的吞吐量同样受限于共识协议，不适合高频率的加锁/解锁场景。如果每秒钟要获取和释放上千次锁，不要用etcd——你可能需要重新审视你的架构设计。

六、Fencing Token：被忽略的关键拼图

现在我们已经有了强一致性的锁实现——ZK的临时顺序节点或etcd的Lease+事务。这够了吗？

Martin Kleppmann在DDIA中反复强调一个观点：锁本身只解决了”互斥”问题，但没有解决”共享资源是否知道锁的存在”的问题。

考虑这个场景：

  1. 客户端A获取了锁，拿到令牌编号33
  2. 客户端A因为GC停顿了60秒
  3. 在A停顿期间，锁过期，客户端B获取了锁，拿到令牌编号34
  4. 客户端A醒来，带着令牌33去写共享资源（比如数据库或文件存储）
  5. 共享资源无从得知33已经过期、34才是有效的，接受了A的写入

这就是Fencing Token（栅栏令牌）要解决的问题。锁服务在授予锁的同时，返回一个单调递增的令牌编号。共享资源只接受编号更大的写请求，拒绝编号更小的”僵尸”写入。

实现Fencing Token，ZooKeeper可以直接用顺序节点的序号（znode的cversion或序号后缀）；etcd可以用事务的ModRevision。Redisson本身不提供Fencing Token机制，但你可以基于Redis的 INCR 命令自己实现。

这个设计的深刻之处在于：它把”锁的安全性”从锁服务转移到了共享资源——如果共享资源有能力拒绝过期的请求，那么即使锁偶尔出问题，整体系统仍然是安全的。

七、实战：SyncTask驿传引擎的分布式锁

回到真实项目。SyncTask驿传引擎是我司的异步任务调度框架，日均处理130万订单的履约同步，部署了8个服务实例。核心约束是：同一个租户的任务，同一时刻只能有一个实例在执行。

我们选择了Redisson作为分布式锁的客户端库。不是因为Redis比ZooKeeper更安全，而是因为这是工程权衡后的最优解。

这完美解决了陷阱二（锁过期<任务执行时间）的问题，在绝大多数场景下足够了。

为什么没用ZooKeeper

不是没考虑。SyncTask的早期版本确实评估过Curator的 InterProcessMutex。权衡如下：

  • 运维成本： 公司运维体系已经管理着Redis Cluster，但不负责ZooKeeper。引入ZK意味着额外的3台服务器和运维培训。
  • 性能需求： 最高峰时每秒可能触发数十个锁操作。Redis单机的10万QPS能力绰绰有余；ZK的写吞吐量在数千QPS级别，理论上也够用，但余量较小。
  • 故障恢复复杂度： 如果Redis Cluster挂了，我们还有降级策略（单实例执行）；如果ZK集群出现Leader选举问题，影响面不只是SyncTask——风险集中度更高。
  • 锁丢失的实际概率： 主从切换导致的锁丢失在8个实例的高峰期确实可能发生。但我们评估下来，SyncTask有天然的重试和幂等保护（基于任务状态机），即使极低概率的锁丢失也不会造成数据不一致——最坏情况是多执行了一次任务，而任务是幂等的。

这个取舍背后的原则是：根据共享资源的性质选择锁策略。如果共享资源自身有Fencing或幂等保护，Redis锁的弱一致性就是可接受的；如果共享资源不能容忍任何并发写入，就必须上ZooKeeper或etcd。

八、回归DDIA：锁的本质是共识问题

DDIA第10章的标题是”领导者和锁”（Leaders and Locks），Martin把这两个概念放在一起不是偶然的。选主和加锁本质上是同一个问题：在同一时刻，只允许一个节点做某件事。

  • Raft选主：同一时刻只能有一个Leader处理写请求
  • ZooKeeper锁：同一时刻只能有一个客户端持有锁
  • Redisson锁：同一时刻只能有一个线程执行临界区

当你用 SET NX 实现锁时，你把Redis当成了真相的来源。当一个客户端向Redis问”锁在吗？”，Redis说”没人持锁”，客户端就认为无人持锁。但如果网络分区了、主从切换了、GC停顿了，真相就被扭曲了。

共识协议（ZAB/Raft/Multi-Paxos）的价值在于：它们不依赖单一的真相来源，而是通过多数节点投票来定义真相。即使少部分节点故障或网络断开，真相仍然是唯一的、一致的。这就是”强一致性”在分布式锁语境中的真正含义。

但强一致性不是免费的。共识操作有网络往返延迟，有磁盘写入开销，有集群规模约束。对于SyncTask引擎来说，100ms级别的锁获取延迟是可以接受的（锁的粒度是租户级别，并发竞争并不激烈）；对于每秒几千次的细粒度锁，共识的开销就太大了。

所以最终的选型框架是：

场景 方案 原理
单实例（JVM内） synchronized / ReentrantLock volatile + CAS，堆内存可见性
轻量分布式（可容忍锁偶尔丢失） Redis + Redisson 单节点租约 + Watchdog续期
严格强一致性（不可丢失） ZooKeeper / etcd 共识协议保证原子性
极致安全性 共识锁 + Fencing Token + 共享资源校验 多层防御，存储侧拒绝过期写入

九、结语

这篇文章的标题是”为什么分布式锁不应该自己实现”，但答案并不是”因为别人已经写好了库”。

真正的答案是：分布式锁的正确实现涉及共识协议、时钟不确定性、网络分区、GC停顿等分布式系统的核心难题，这些难题的交互方式反直觉、难以测试、且在生产环境中的表现往往与单元测试截然不同。自己写一把锁，你大概率会漏掉其中至少一个陷阱。

用Redisson不是因为它是最强的，而是因为它在工程成本和安全性之间找到了一个实用的平衡点，并且经过了大量生产环境的验证。用ZooKeeper或etcd不是因为它们更简单，而是因为它们内置了共识协议的保证，把正确性的责任从应用代码转移到了基础设施。

下次当你觉得”不就是一把锁吗”的时候，回想一下Fencing Token的设计——那把看似简单的锁背后，是整个分布式系统理论在支撑。
