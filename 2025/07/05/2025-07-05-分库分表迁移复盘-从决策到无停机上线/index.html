分库分表迁移复盘：从分片键决策到无停机上线

订单销售信息表累计逼近 6000 万行，2025 年上半年完成了分库分表落地。这篇复盘完整过程——从”要不要分”的决策，到分片键选型，到无停机迁移。

一、为什么要分：三个信号

分库分表不是一上来就分的。我的判断信号是三个：

  1. 单表数据量逼近千万级：订单销售信息表累计接近 6000 万行、单月增量约 380 万行——索引、缓存、读写分离都扛不住的量级；
  2. 写入成为瓶颈：单库单表写入能力到了上限；
  3. 目标是横向扩容，不是优化单点查询。

在到达这个信号之前，我们经历过”假分片”阶段：渠道垂直分表（拼多多一张表、京东一张表）——手工拆分、没有分布式路由、每开新渠道要新建一套表。这不是真正的水平分片。

二、分片键选型：拿真实数据说话

这是最关键的决策。我的方法不是拍脑袋，而是拿真实表做 SQL 分析 + 核对慢查询：

  • 确认所有业务事件（创建/发货/取消/签收）都按 WHERE order_no = ? 定位；
  • 所以分片键选单号（order_no），不用时间。

为什么是单号不是时间：

  • 单号唯一、天然均匀 → 每条写入精准路由单物理表 → 写路径零广播；
  • 时间主分片对统计友好，但每条写事件会广播到全部分片——写广播是分片方案里最严重的问题。

复杂统计查询怎么办：不硬扛，下沉 Doris（Canal + Kafka 同步）——OLTP 分片只解决”写入 + 分片键单点查询”，复杂查询给 OLAP。

三、无停机迁移：五步流程

迁移的核心不是”把数据搬过去”，而是”搬的过程中业务不能停、不能丢、不能重“：

  • 存量回填：历史近 6000 万行分批迁移，夜间低峰跑批，日均约 800 万行，last_id 位点记进度、断点续跑；
  • binlog 增量追平：回填期间的新写入靠 binlog 增量同步到新分片，位点对齐（切流点严格对齐 binlog 位点）；
  • 对账兜底：按业务主键遍历两侧比对，连续两轮差异为 0 才允许切流——对账不过不推进；
  • 灰度切流：按渠道逐个切，约两周完成，随时可回滚；
  • 删旧表：全量对账通过、稳定运行后才清理。

这里的”双写”= binlog/Canal 增量双写，零侵入——业务只写老表，不在应用层改代码双向写。

四、零停机切换：配置驱动路由

迁移最怕”切路由那一刻要重启”——我的做法是配置驱动路由：

  • 业务代码只写逻辑表（or_sales_info）；
  • ShardingSphere 路由层把逻辑表映射到物理表（版本号前缀）；
  • 换表名/数据源 = 改路由配置，不是改 SQL；
  • 数据源 + 分片规则放 Nacos 下发，应用不重启、连接不断。

切流顺序：先灰度切读（按渠道/比例验证）→ 全量对账通过后 100% 切走 → 老表保留可回滚。

五、上线后的数字

  • 当前 8 片，每片约 750 万行（6000 万 ÷ 8）；
  • 单号主分片写路径零广播，主路径查询精准路由；
  • 复杂统计查询走 Doris，不靠 MySQL 分片扛。

六、复盘：做对了什么

  1. 分片键匹配访问模式：先分析真实 SQL，再定分片键——这是 DDIA 分区思想的落地；
  2. 对账是铁律：连续两轮差异 0 才切流，把”正确性证明”当迁移的关卡而不是可选项；
  3. 零停机靠配置驱动：路由配置化 + Nacos 热更，切流不重启。

总结

  • 分库分表信号：单表千万级 + 写入瓶颈 + 横向扩容目标；
  • 分片键选单号（写零广播），不选时间（写广播）；
  • 无停机迁移五步：回填 → 增量追平 → 对账 → 灰度 → 删旧表，对账不过不切流；
  • 零停机切换靠 Nacos 配置热更，改配置不改 SQL；
  • 复杂统计下沉 Doris，OLTP 只解决”写入 + 分片键单点查询”；
  • 上线后 8 片/每片约 750 万，写路径零广播。
