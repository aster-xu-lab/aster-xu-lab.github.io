Sentinel 限流、熔断、降级：一个下游慢如何拖垮一片，怎么打断

一、三个词先分清

限流、熔断、降级是微服务最常被混的三个概念：

作用
限流 控制请求进入的量（按 QPS/并发线程数/热点参数），超出拒/排队
熔断 下游异常/慢时快速失败，不再调它（熔断开关），等恢复再试——护自己不拖垮
降级 放弃/简化非核心功能（如商品详情降级只返回基础字段）——主动

一句话：限流控制”进来多少”，熔断保护”自己别被拖垮”，降级放弃”非核心的”。

二、雪崩传导：为什么一个慢拖垮一片

这是微服务最经典的题，要能讲出链路：

打断三连（对应三个概念）：

  1. ① 超时：每个调用设连接/读超时，别无限等——不让线程被占死；
  2. ② 熔断：下游慢/错误超阈值 → 快速失败，不继续占线程——止损；
  3. ③ 限流/隔离：舱壁/线程池隔离，一个下游拖垮的是它的隔离池，不是全部。

这就是 Sentinel 那套”为什么这么设计”——超时是底线，熔断是止损，隔离是防扩散。

三、Sentinel 怎么玩

Sentinel 针对**资源（接口方法）**限流，不是按 IP：

  • QPS 模式：按接口 QPS 设阈值（如订单下单接口限 5w），令牌桶思想；
  • 并发线程数模式：控制同时处理线程数，超了排队/拒绝；
  • 热点参数限流：对某个具体参数值（如爆款商品 ID、某商家）单独限流——防一个热点 key 把整体流量打满；
  • 熔断策略：异常比例 / 慢调用比例 / 异常数；
  • 降级规则：接口异常比例高 → 降级返回兜底。

四、大促保障：四件套一起上

限流、熔断、降级、缓存是大促保障四件套，不是单讲一个：

  • 限流：入口控制”量”，按 QPS 限流防打爆；
  • 降级：非核心功能降级（二级缓存降级走 Redis、营销/推荐只保留基础）；
  • 熔断：下游仓储/SAP 异常时快速失败，保护自己；
  • 缓存：热点数据预热、缓存降级。

订单中心大促的做法：按 QPS 限流防打爆、下游异常熔断快速失败、非核心功能降级。配合”预热 + 风控 + 异步”，是完整的大促保障体系。

五、连接池隔离：舱壁模式

隔离是防雪崩的关键手段之一。连接池隔离（舱壁模式）：给每个下游分配独立的连接池/线程池——一个下游慢，占满的是它的隔离池，其他下游不受影响。

我在订单中心做过这个：给慢的下游单独隔离连接池，防止它拖垮全局。这是”隔离”思想在资源层的落地，和线程池隔离同理。

六、结合我的项目

订单中心真实用 Sentinel 护大促，这套是我可用性 99.99% 的组成部分。讲微服务治理，用订单中心的真实配置和治理经验（Dubbo + Nacos + Sentinel + 连接池隔离），就是差异化——比背概念强得多。

总结

  • 限流控制量、熔断护自己、降级弃非核心，别混；
  • 雪崩链路：下游慢 → 线程占死 → 堆积打满 → 整链崩溃，打断三连：超时 + 熔断 + 隔离；
  • Sentinel 按**资源（接口）**限流，QPS / 并发线程 / 热点参数；
  • 大促四件套：限流 + 降级 + 熔断 + 缓存，配合预热/风控/异步；
  • 连接池隔离（舱壁）防一个下游拖垮全局；
  • 订单中心真实在用，可用性 99.99% 的基础。
