微服务治理：超时重试、配置中心、链路追踪与优雅下线

一、治理的本质：让分布式系统可控

微服务拆完只是开始，真正难的是治理——超时重试、隔离、配置管理、可观测、发布安全。这篇把治理的几个关键面理清楚。

二、超时与重试

  • 超时：Feign/Dubbo 设置超时，分连接超时 + 读超时。每个调用都必须有超时——这是雪崩打断的第一道底线；
  • 重试：注意幂等——只有幂等接口才能重试，非幂等重试会造成重复扣款/重复下单。Dubbo 默认重试 2 次，非幂等要关重试。

一个坑（上一篇提过）：Dubbo 超时消费方优先——在 Reference 上配的 timeout 优先级最高，提供方配的会被覆盖。所以超时统一在消费方配。

四、隔离：舱壁 + 线程池隔离

隔离是治理的核心手段：

  • 线程池隔离：每个下游独立的线程池，一个慢不占满全局；
  • 连接池隔离（舱壁）：每个下游独立的连接池——我在订单中心给慢下游单独隔离连接池，防止拖垮全局。

六、优雅下线与灰度

发布时不能直接停服务（正在处理的请求会断）：

我有灰度切换经验：发布时逐步切流，验证稳定再全量。这和发布时的灰度切流是同一套思想——变更要可控可回滚。

七、一个加分认知：监控告警分级

治理的最后一环是监控告警。我的 SyncTask 引擎做了四级告警分层（SKIP / ONE / BATCH / MIN）——不同级别的异常用不同告警通道和频率，避免”全部轰炸”导致告警疲劳。

这是把”监控告警”当成系统设计的一部分，而不是事后加。

总结

  • 超时是底线（连接 + 读），重试要幂等；
  • 配置中心（Nacos）改配置不停机，@Value 不自动更新要 @RefreshScope；
  • 隔离：线程池/连接池舱壁，防一个下游拖垮全局；
  • 链路追踪：traceId 贯穿全链路，Zipkin 瀑布图定位瓶颈；
  • 优雅下线 + 灰度：先摘注册再停，逐步切流可回滚；
  • 监控告警分级，避免告警疲劳——我 SyncTask 的四级告警。
