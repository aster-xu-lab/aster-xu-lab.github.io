微服务注册发现与网关：Nacos、Dubbo、Feign 各管什么

定位：订单中心真实在用 Spring Cloud Alibaba（Nacos/Dubbo/Feign/Sentinel），这篇把”为什么用、怎么用、怎么治理”理成框架。

一、为什么拆微服务

单体 → 微服务，换来解耦、独立部署、独立扩展、技术栈灵活；代价是分布式复杂性：网络调用、事务、一致性、链路追踪。

Spring Cloud Alibaba 全家桶是我的栈：

组件 职责
Nacos 注册中心 + 配置中心
Dubbo 高性能 RPC
Feign/OpenFeign 声明式 HTTP 调用
Sentinel 限流 / 熔断 / 降级
Seata 分布式事务

二、服务注册与发现：Nacos

服务多了，调用方不知道 provider 在哪、有几个实例。注册发现的流程：

Nacos 同时是配置中心：改配置不用重启，动态刷新（后面展开）。

三、Dubbo vs Feign

Dubbo Feign
协议 RPC，自定义协议 HTTP
性能 高（二进制定制协议） 一般
特点 分组/泛化调用、服务治理强 声明式接口、简单、Ribbon 负载均衡
场景 内部高性能服务间调用 HTTP/和其他框架对接

订单中心的做法：服务间关键调用用 Dubbo（性能高），需要 HTTP 或对接非 Dubbo 场景用 Feign。Nacos 做服务发现 + 配置中心。

四、负载均衡与网关

  • 负载均衡：Ribbon（客户端）/ Nginx（服务端），把请求分到多个实例；
  • 网关（Gateway）：统一入口，做路由、鉴权、限流、跨域。外部请求先进网关，再分发到微服务。

网关 vs 注册中心的分工（别混）：

网关管”从外面进来“（外部请求统一入口、路由/鉴权/限流）；注册中心管”服务之间“（内部服务互相发现）。外部请求先进网关 → 路由到内部微服务 → 内部服务靠 Nacos 发现。

五、结合我的项目

订单中心是 Spring Cloud Alibaba 微服务，对接 20+ 平台：

  • 服务间用 Dubbo RPC 高性能调用；
  • Nacos 做注册中心 + 配置中心（配置动态刷新，改配置不用重启）；
  • 外部请求经网关路由；
  • Sentinel 限流熔断降级护大促（下一篇展开）。

这套 + 连接池隔离 + 全链路追踪，是可用性 99.99% 的基础。

六、一个踩过的坑：Dubbo 超时谁说了算

Dubbo 超时是”消费方优先“——调用方在 Reference 上配置的 timeout 优先级最高，提供方 Service 上配的会被覆盖/不生效。所以超时统一在消费方配，避免提供方坑消费方。重试默认 2 次，幂等才能重试，非幂等关重试。

总结

  • 微服务拆解耦、独立部署，代价是分布式复杂性；
  • Nacos = 注册中心 + 配置中心（不只是注册）；
  • Dubbo = RPC 高性能，Feign = HTTP 声明式，别答反；
  • 网关管”从外面进来”，注册中心管”服务之间”；
  • Dubbo 超时消费方优先，统一在消费方配，重试要幂等；
  • 订单中心真实用这套，是我稳定性的基础。
