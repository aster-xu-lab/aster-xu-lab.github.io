分片扩容不重来：反向索引表用双写 + 灰度切流优雅扩容

哈希分片扩容的痛：同单号落片变了

反向索引表按单号 outer_order_no 哈希分片。假设从 8 片扩到 16 片：

片数一变，同一个单号在新旧两套落到了不同分片。取模分片扩容 = 推倒重来，不能直接加片数。

扩容难点取决于分片方案

扩容难度和分片方案强相关（or_sales_info 已确认单号主分片）：

  • 时间分片：扩容 = 加月表，天然扩容，但”按单号处理的业务事件”会广播所有月表（写路径广播严重）
  • 单号分片：业务事件精准路由，但扩容（8→16片）需重列全部分片数据

交易系统（订单）通常选单号主分片（业务事件是主维度），所以扩容走下面的双写+灰度流程——这是单号分片的必要代价，换来所有事件的精准路由。

无感扩容：双写 + 回填 + 对账 + 灰度切流

业界标准四步（全程不停服）：

1. 双写（保证在线数据两边一致）

新增单号同时写旧8片 + 新16片：

2. 存量回填

扫主表，历史单号按新算法 rehash 到新16片：

3. 对账

抽样比对新旧索引一致性，不一致就补：

4. 灰度切读（表名带版本号避免冲突）

新旧表名用版本号前缀区分，避免编号撞名：

查询按开关切流 + 旧表兜底：

灰度比例从 20% → 100%，全程可回滚。

5. 收尾

100% 切走 → 停双写 → 对账确认 → 删旧表。

实测演示（8片 → 16片）

全程主表一单没迁，只迁移了映射表（小、可重建），配合灰度+兜底，切流期间一个查询都不错失。

两个关键决策点

  1. 表名带版本号：t_index_v8_* / t_index_v16_*，新旧并存不冲突，可回滚
  2. 查询新旧同查 + 新表兜底：灰度早期新表 miss 自动回旧表，绝不错数据

小结

场景 怎么办
时间分片扩容 按月加表, 天然扩容, 不用 rehash（但有”按单号写事件广播”缺陷）
单号分片扩容 双写 + 回填 + 对账 + 灰度切流（业务事件精准路由, 需 rehash）
表名冲突 带版本号前缀 v8/v16
切流不错数据 新表优先 + 旧表兜底

交易系统(订单)选单号主分片：换来所有业务事件（创建/发货/取消/签收）精准路由零广播，
代价是扩容需走”双写+灰度”流程。时间分片虽然扩容简单，但写命广播严重，不适合订单这类”事件按单号”的业务。
