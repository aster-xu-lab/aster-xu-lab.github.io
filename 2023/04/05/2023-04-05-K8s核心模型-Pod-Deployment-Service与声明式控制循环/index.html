K8s 核心模型：Pod、Deployment、Service 与"声明式控制循环"

定位：学习笔记。无 K8s 实操，目标是”概念清晰、能聊基础”——A 档大厂必问的短板补课。

一、七个核心概念

概念 是什么 类比
Pod 最小调度单位，一个或多个容器 一台”逻辑主机”
Deployment 管理 Pod 副本、滚动更新、回滚 应用部署
Service 稳定访问入口，负载均衡到 Pod 虚拟 IP / 负载均衡
Ingress 外部 http/https 入口，路由到 Service 网关 / nginx
ConfigMap / Secret 配置 / 密钥，注入 Pod 配置中心
PVC 持久化存储 硬盘
HPA 按 CPU/指标自动扩缩 Pod 弹性伸缩

一个最常被纠正的点：Pod 是最小调度单位，不是容器——一个 Pod 可以装多个容器（比如业务容器 + 边车），它们共享网络和存储。

二、总纲：声明式 + 控制循环

理解 K8s 一切行为的钥匙是一句话：

你下发”期望状态”（Desired State）给 apiserver（存 etcd），controller 不断比对”现状 vs 期望”，把系统收敛到期望。

自愈、滚动更新、自动扩缩，全是这个”控制循环”的推论——不是 K8s 特意做的功能，是”持续收敛到期望状态”的自然结果。

三、集群结构：控制平面 + 工作节点

为什么所有请求都走 apiserver：因为它是”期望状态”的唯一入口——所有变更经它写入 etcd，控制器从 etcd 读期望、去调谐。这是声明式模型的总纲。

四、探针：K8s 怎么知道容器挂了

三个探针，各有分工（高频考点）：

  • livenessProbe（存活探针）：容器活没死——死了就重启；
  • readinessProbe（就绪探针）：容器好了没——好了才进 Service 接流量；
  • startupProbe（启动探针）：慢启动容器用，启动期先别判死。

一句话：liveness 决定重启，readiness 决定要不要给流量——别混。

五、Service 为什么能”服务发现”

Pod 的 IP 会变（重建就换），Service 提供一个稳定的虚拟 IP（ClusterIP）+ DNS 名字：

这就是”K8s 内置服务发现”的底层：Pod 挂重建，Service 名不变。跨节点通信靠 CNI 插件（Calico/Flannel）。

六、K8s 的三个核心价值

  • 滚动更新：Deployment 更新不中断服务，逐步替换旧 Pod（minReady/maxSurge 控制）；
  • 自愈：Pod 挂了自动重建，节点挂了 Pod 调度到别的节点；
  • 弹性伸缩：HPA 按 CPU/内存/自定义指标扩缩 Pod 数。

再加一个：环境一致（Dev/Prod 同一套镜像和编排）。

七、选型认知：K8s 不是无脑上

K8s 带来标准化、自愈、弹性，但学习/运维成本高、架构更复杂——对小团队可能过度设计。

是否上 K8s 要看规模和团队能力，这是 trade-off 不是无脑上。 单体 → 容器 → K8s 是演进方向，但要衡量当前阶段值不值得。

八、诚实的边界

我目前用 Docker 部署，没有 K8s 实操。这篇是概念学习笔记：Pod/Deployment/Service 模型、声明式控制循环、探针、Service 发现，我都能讲清楚原理，但简历不写”精通 K8s”。被问到就如实说”了解概念、实操在补”——这是投大厂想补的一块，宁可这么说，别硬装。

总结

  • 核心概念：Pod（最小调度单位）/ Deployment（副本+滚动）/ Service（稳定入口）/ Ingress（外部入口）/ ConfigMap / PVC / HPA；
  • 总纲：声明式 + 控制循环——下发期望状态，控制器持续收敛，自愈/滚动/扩缩都是它的推论；
  • 探针：liveness 决定重启，readiness 决定给流量；
  • Service 发现：ClusterIP + Endpoints 让 Pod 重建 IP 变但服务名不变；
  • 价值：滚动更新 / 自愈 / 弹性 / 环境一致；代价：运维成本高，小团队要权衡；
  • 诚实：概念了解、无实操，不装精通。
