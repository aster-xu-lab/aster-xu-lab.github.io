DDIA-03-关系模型vs文档模型：电商订单该存MySQL还是MongoDB

一、一个真实的深夜选型会

凌晨一点，会议室白板上画满了框线。

CTO问了一个看似简单的问题：「订单数据用MySQL还是MongoDB？」

这不是技术选秀。这是过去三个月第三次线上故障复盘后，架构组必须给出答案的问题。

我们的系统当时跑着日订单峰值130万，MySQL单库已经扛不住了。有同事提议：订单JSON一把梭，存MongoDB，读得快、写得也快。

听起来很诱人。但真相远比直觉复杂。

这就是本文要讨论的核心：关系模型和文档模型的本质差异是什么？在电商订单这个具体场景下，你该怎么选？

二、关系模型：为「关联」而生的模型

2.1 订单不是一条数据，是一张关系网

电商订单长什么样？一个完整的下单流程涉及至少这些表：

这不是「一条订单数据」。这是一张以order_id为主键的关系网。

2.2 JOIN不是Bug，是Feature

关系模型的核心能力是什么？不是「存数据」，是在需要的时候关联查询。

举个例子——运营要拉一张报表：过去7天，支付成功但超48小时未发货的订单，且订单金额超过500元。SQL写出来：

三表JOIN，条件混合过滤。在关系数据库里，这就是一条SQL的事。

换成文档数据库？你得先查order表拿到order_id列表，再分别查payment和logistics，回到应用层做交集。把数据库的JOIN搬到了应用代码里——代码复杂、性能差、容易出错。

2.3 ACID事务：订单系统的底线

这点几乎没有争论空间。

一个下单操作至少涉及：

  1. 库存扣减（inventory表）
  2. 订单创建（order表）
  3. 订单商品写入（order_item表）
  4. 优惠券核销（coupon表）

这四步必须原子化——要么全成功，要么全回滚。

你想想：订单创建了但库存没扣，超卖。优惠券核销了但订单失败了，用户投诉。任何一个「一半成功」的状态，都是线上事故。

有人说MongoDB 4.0+支持多文档事务了。没错，但它的事务性能远不如MySQL/InnoDB——这是为其底层存储引擎的架构买单。在高并发写入场景下，MongoDB事务的吞吐量只有MySQL的1/3到1/5（来自我们压测的实际数据）。

2.4 Schema强约束：反混沌的护城河

订单系统跑了三年，接手过五拨人。如果没有Schema约束，order表里会出现：

  • status字段：有人写’PAID’，有人写’paid’，还有人写数字1
  • total_amount字段：有人存分为单位，有人存元
  • extra_info字段：JSON里面套JSON，嵌套三层，没人知道里面到底有什么

强Schema不是束缚，是团队协作的契约。它让你在凌晨三点被电话叫醒时，不用去猜数据库里到底存了什么。

三、文档模型：为「读一次」而生的模型

3.1 购物车：文档模型的黄金场景

现在我们换个场景——购物车。

购物车的数据结构天然是嵌套的：

如果用关系模型，你需要：

  • 一张cart主表
  • 一张cart_item子表
  • 每次读购物车都要JOIN
  • 每次加商品都要操作两张表

用文档模型，一次读取，拿到全部。性能更好，代码更简单。

3.2 商品描述：Schema灵活的正解

SKU的属性千差万别：

  • 手机：颜色、存储、网络制式
  • 衣服：尺码、材质、洗涤方式
  • 食品：保质期、储存条件、过敏原

关系模型怎么做？要么建一张巨大的宽表，要么走EAV模式（实体-属性-值），后者查询就是噩梦。

文档模型的灵活Schema在这里是真正的优势——每个类目的SKU描述存自己的字段，互不干扰，读一次全取。

3.3 小结：文档模型适合什么？

一个简单的判断标准——如果你的数据总是以聚合为单位被读写，很少有跨聚合的关联查询，文档模型就是正确答案。

购物车读的是「某个用户的完整购物车」，不是「所有含有iPhone的购物车」；商品描述读的是「某个SKU的完整信息」，不是「所有支持5G的手机的屏幕尺寸」——那是搜索引擎的事。

四、文档模型的暗面：多对多就是噩梦

DDIA里有个经典例子：LinkedIn的简历数据。

一个用户有多段工作经历，每段工作经历关联一个公司，一个公司有多位现任和前雇员。这是典型的多对多关系。

在文档模型里：

方案A：把工作经历嵌套在用户文档里。

  • 问题：你想查「这家公司所有前雇员」，得扫描所有用户文档。
  • 问题：公司信息更新了（比如改名），你得遍历所有用户文档去改。

方案B：把用户引用放在公司文档里。

  • 问题：反过来，你想查「某人所有工作经历」，得扫描所有公司文档。

方案C：两边各存一份。

  • 问题：数据冗余，一致性维护成本爆炸。

这就是文档模型的阿喀琉斯之踵：它天然适合一对多/一对一的关系树，但在多对多关系面前捉襟见肘。

回到订单场景：一个用户有多个订单（一对多），一个订单有多个商品（一对多），商品属于多个类目（多对多），订单关联多张优惠券（多对多），优惠券又关联营销活动（多对多）。

订单领域的多对多关系无处不在。这才是我们最终没有选MongoDB做主存储的根本原因。

五、实战：130万日订单，为什么最终选了MySQL

5.1 真实的性能瓶颈不在存储模型

很多团队遇到性能问题第一反应是换数据库。但我们的教训是：80%的性能问题出在索引设计、SQL写法和架构设计上，而不是存储引擎上。

130万日订单，峰值QPS大概在3000左右（订单写入）。MySQL 8.0 + InnoDB，合理分库分表之后，这点量根本不是瓶颈。

真正的瓶颈在哪里？

  • 促销活动期间的瞬时流量——秒杀场景，10万QPS冲进来
  • 运营后台的复杂报表查询——多表JOIN + GROUP BY + 聚合函数，慢查询打挂主库
  • 大数据量的历史订单检索——用户想看三年前的订单，扫全表

这些问题，换MongoDB也一样存在。秒杀该排队还是排队，报表该慢还是慢，历史数据该归档还是得归档。

5.2 JSON字段：关系型里的「文档模型」

MySQL 5.7+支持JSON字段。这是一个被低估的功能。

我们把订单的「可变属性」存为JSON——比如用户自定义字段、特定渠道的扩展信息、AB实验参数。这些字段不需要查询，不需要索引，只是透传。

这样就做到了：**核心数据走关系模型，灵活扩展走JSON。**两者不是对立的，是可以组合的。

5.3 事务不是可选项，是必要条件

这一点在第二章已经说过，但值得重复。

130万日订单意味着什么？意味着每天有几百万次库存操作、几百万次支付回调、几百万次优惠券核销。任何一个环节的不一致都会被放大成上千个用户投诉。

我们早期用过一个方案：订单主流程走MySQL，非关键流程（比如积分发放）异步走消息队列，最终一致性。结果呢？积分系统挂了三天，没人发现。用户来投诉，「我明明下单了为什么没有积分？」

最终一致性不是不行，但要分场景。和钱相关的，和用户直接感知相关的，必须强一致。

这就是为什么订单主存储必须是支持成熟ACID事务的关系数据库——不是因为MongoDB不好，是因为订单这个领域的事务要求太高了。

六、但也不是纯关系：多模型策略

选了MySQL不意味着只用MySQL。现代电商架构是多模型混合的。

6.1 ES：关系查询的补充

运营后台的复杂搜索——多条件筛选、模糊匹配、排序——全部走Elasticsearch。

MySQL负责写入，Canal监听binlog同步到ES，ES负责查询。读写分离在存储模型层面的体现。

6.2 HBase：冷数据归档

三年前的订单，99.9%的时间没人查。但你不能删——税务合规要求保存至少五年。

全部放在MySQL里？磁盘占用巨大，备份恢复慢，而且拖累Buffer Pool命中率。

我们的做法：6个月以内的热数据在MySQL，6个月以上的冷数据归档到HBase。查历史订单走专门的归档查询接口，用户查自己的订单时，先去MySQL查热数据，没有再去HBase。

6.3 多模型的真正含义

不是「选一个数据库统治一切」，而是让每个数据库做它最擅长的事：

场景 存储 原因
订单写/事务 MySQL ACID, JOIN
订单搜索/报表 Elasticsearch 全文检索, 聚合
购物车 Redis + MongoDB 读一次, 热数据
商品详情 MongoDB 嵌套结构, Schema灵活
历史订单归档 HBase 低成本, 海量存储
库存扣减 MySQL 行锁, 强一致

七、回到那个问题：到底怎么选？

如果今天一个新团队来问我这个问题，我给的决策框架是三个问题：

问题一：你的数据实体之间有没有多对多关系？

  • 有 → 关系模型（订单、CRM、ERP）
  • 没有，或只有一对多 → 文档模型可以考虑

问题二：业务需要跨实体的ACID事务吗？

  • 需要 → 关系模型（支付、库存、订单）
  • 不需要，或只需要单文档原子性 → 文档模型可以考虑

问题三：数据结构稳定吗？团队规模大吗？

  • 稳定、人多 → 关系模型，强Schema是协作契约
  • 迭代快、人少 → 文档模型，Schema灵活性是优势

这三个问题答完，答案基本上就出来了。

但还有一个不容忽视的现实因素：**团队的数据库运维能力。**MySQL的DBA好找，MongoDB的专家稀缺。一个700人的技术团队可能有5个MySQL DBA，但MongoDB可能一个专职的人都没有。这不是技术问题，是组织问题——但组织问题往往是最终决策的决定性因素。

八、写在最后

DDIA第五章有一句话我印象很深：

「数据模型的选择对系统能力有深远影响——它不仅影响软件的编写方式，也影响我们思考手中问题的方式。」

翻译成大白话：你用什么数据模型，决定了你用什么样的方式理解业务。

关系模型让你用「实体+关系」的视角看世界——订单是一个实体，用户是一个实体，它们通过外键关联。文档模型让你用「聚合」的视角看世界——购物车是一个聚合，它内部的结构是它自己的事，外部不关心。

两种思维模型没有高下之分。关键在于你的业务领域更适合哪种视角。

对于电商订单——需要关联查询、需要ACID事务、需要强Schema约束——关系模型是更自然的思维模型。但在购物车、商品描述、搜索索引等场景，文档模型同样不可替代。

所以最后的答案不是「选MySQL还是选MongoDB」，而是：「你的场景长什么样，就用什么模型。一个系统不够，就用多个。但核心交易链路，ACID和JOIN是不可妥协的底线。」
