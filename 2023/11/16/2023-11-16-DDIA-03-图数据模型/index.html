DDIA-03-图数据模型：当你的订单关联比二叉树还复杂

引言：当 JOIN 变成噩梦

去年双十一大促复盘时，运营问了一个问题：”最近30天，有多少订单是因为同一辆配送车超载导致拆单的？我们要评估运力不足对用户体验的影响。”

听起来是个合理的数据查询需求，对吧？

我打开 cloud-supplychain-planning 的数据模型，画了一张关联图：

要回答运营的问题，SQL 需要 JOIN 7 张表，而且还有自关联（一个波次拆出多个配送单，配送单之间互相关联）。写完这个查询，代码审查时同事问：”这 SQL 写了 80 行，能跑吗？”

能跑倒是能跑，但跑一次要 40 秒。而这个数据是运营每天早会都要的。

这个问题让我开始思考：我们一直在用关系数据库建模一切，但有些关系天然不是”表”，而是”网”。

供应链上下游、用户推荐关系、物料 BOM 结构——这些数据的内在形态是一张图。用表去模拟图，就像用螺丝刀当锤子使，能敲进去，但每次都很别扭。

一、图的本质：顶点和边

图数据模型的核心只有两个概念：

顶点（Vertex）：实体。比如一个用户、一个订单、一个仓库、一个 SKU。

边（Edge）：关系。比如”下单”、”包含”、”存放于”、”依赖”。

一条边连接两个顶点，可以有方向（有向图），也可以带属性（属性图）。比如：

这就是属性图模型——Neo4j 等主流图数据库的实现方式。每个顶点有标签（如 User、Order），每条边有类型（如 PLACED、CONTAINS），顶点和边都可以携带 key-value 属性。

还有一种学术上更严谨的三元组模型（RDF），用「主体-谓词-客体」表示所有关系，比如 (订单12345, 包含, SKU-789)。它的优势在于语义网的标准化，但在工程实践中，属性图因为更接近开发者直觉而占据了主流。本文后面的讨论都基于属性图。

二、什么时候图数据库比关系数据库更合适

不是说所有场景都应该用图数据库。选择存储模型要看查询模式。

图数据库的甜点区

场景 1：路径查找

“从供应商A到仓库B，经过哪些中转节点？”——这是典型的图遍历，每次走一条边、看相邻节点。图数据库的存储引擎针对这种访问模式做了优化：顶点和它的邻边在磁盘上通常存储在一起，一次 I/O 就能拿到。

关系数据库做同样的事，每次”走一步”都是一次 JOIN，而 JOIN 需要索引查找、可能跨页——随着跳数增加，代价指数上升。

场景 2：多跳关联查询

“这个缺陷零件影响了哪些成品，这些成品发给了哪些客户？”——从零件追溯到成品再追溯到客户，三跳起步。供应链里这种追溯查询非常常见。图数据库的遍历时间复杂度是 O(度数 × 跳数)，而 SQL JOIN 在缺少恰当索引时会退化到 O(n²)。

关于这个问题，DDIA 第二章引用了 Michael Stonebraker 等人的一篇经典论文《The End of an Architectural Era》，核心观点是：传统 RDBMS 的架构是为 1970 年代的商业数据处理设计的，行存储、B+树索引、基于 JOIN 的查询优化器——这些都假设数据以”记录”为单位被访问。而图遍历、列式分析、流处理这些现代场景需要完全不同的架构。图数据库就是这种”专用化”趋势的代表。

场景 3：推荐和模式发现

“买了这个 SKU 的用户还买了什么？”——电商推荐引擎底层是用户-商品二分图。用 Cypher 可以很自然地表达：

图数据库不应该做什么

坦率说，在我们的 130 万日订单场景里，图数据库不是主存储——也不会是。

原因很简单：订单本身是典型的”记录”模型，订单的核心操作是”增删改查单条记录”，偶尔做范围扫描（”某时间段内的所有订单”）。这些是关系数据库的强项。把订单数据全部灌进图数据库，写入性能不如 MySQL，生态工具也不如 MySQL 成熟。

所以图不是替代，是补充。主链路还是 MySQL + Redis + Elasticsearch，图数据库作为分析工具存在——离线把订单、用户、商品之间的关系导入 Neo4j，让数据团队用它做关联分析和模式发现。

三、实战：供应链 BOM 关系——递归 CTE 的维护之痛

回到我们的 cloud-supplychain-planning 项目。

供应链计划里最核心也最头疼的数据结构之一是 BOM（Bill of Materials，物料清单）。一个成品由多个半成品组成，半成品又由其他半成品或原材料组成——形成一棵多层的物料树。

这个结构在 MySQL 里的经典建模是「物料主数据表 + 物料关系表」：

问题来了：生产计划需要把成品需求展开到所有底层原材料。这叫 BOM 展开。

SQL 递归 CTE 方案

这个方案能跑。但现实中的问题不在查询本身，而在于：

  1. 数据质量问题：BOM 里偶尔会有循环引用——A 包含 B，B 包含 C，C 又引用了 A。递归 CTE 遇到循环直接报错或死循环，所以必须加 level < 20 这种防御。但问题是，循环本身是数据异常，查询不报错不代表数据没问题——这种异常就被默默地截断了。

  2. 中间层物料的需求合并：BOM 展开不只是”一直拆到底”，有时需要停在某些中间层物料上（因为该物料有独立库存）。SQL 方案只能”全拆”或”不拆”，做不到”条件性停止”。

  3. 维护成本：每次加一个业务规则（比如”跳过停用物料”、”考虑损耗率”），都要往递归 CTE 里加 JOIN 和 CASE WHEN。三个月后递归 CTE 膨胀到 120 行，维护它的同事已经转岗了。

实话实说

我们的生产环境并没把 BOM 全部迁移到图数据库——切换存储的成本太高，而且 BOM 的增删改查还是主链路。但我们用 Neo4j 建了一个BOM 分析副本：每天晚上把 MySQL 的 BOM 数据同步到图数据库，供计划团队做路径分析、循环依赖检测、影响面评估。效果超出预期——以前要跑 30 分钟的全链路物料追溯，现在秒级出结果。

四、130万日订单：图数据库的真实定位

写到这可能有读者想问：你们 130 万日订单的电商场景，图数据库到底怎么用的？

坦诚说：绝大部分流量走的是 MySQL + Redis。订单的创建、支付状态更新、用户查询订单列表——这些都是 Key-Value 或简单 JOIN，B+Tree 索引处理得非常好。图数据库不是来抢这个活的。

但在以下场景，我们把数据同步到了 Neo4j（离线 T+1）：

场景 MySQL 的痛点 图数据库的表现
供应链全链路追溯 7+ 表 JOIN，递归 CTE Cypher 十来行，秒回
仓库网络规划 需要计算”从任意仓到任意客户的距离” 图的最短路径算法天然支持
异常订单关联分析 分析拆单、缺货间的关联 图聚类和社区发现
欺诈检测 需要关联账号、设备、IP 多跳关系 图模式匹配，识别异常子图

这个架构的核心经验是：图数据库和关系数据库不是互斥的，而是分担不同查询模式的。 OLTP 走关系型，OLAP/图分析走专用引擎。这和 DDIA 一书的核心精神是一致的——没有银弹，只有合适的工具。

五、选型建议：图数据库值不值得学？

先说工具。目前图数据库领域 Neo4j 是事实标准，生态最完善。云上有 Neo4j Aura，也可以用 AWS Neptune、阿里云 GDB。如果你的数据量在千万级顶点、亿级边以内，单机 Neo4j 完全够用，部署成本很低。

查询语言方面，Cypher 已经被 ISO 采纳为国际标准（GQL），学起来不会白费。

一个常见的反对意见是：”我现在的项目没有图查询需求，学了用不上。” 我的经验是：不是你用不上，而是你还没学会用图的视角看数据。 一旦你理解了图模型，你会发现：

  • 用户的收藏、加购、下单行为天然形成了一张”用户-商品-行为”图
  • 权限系统的”用户-角色-资源”是典型的二分图
  • 微服务调用链天然是有向图

这些场景用图建模和查询，往往比用 SQL 更自然。即使你最终因为运维原因没有引入图数据库，理解图模型也会改变你设计数据模型的方式——你会更敏感于”这个关系是 one-to-many 还是 many-to-many”，会在建表时就考虑到未来可能的多跳查询。

结语：图不是银弹，但值得放进工具箱

这一篇是 DDIA 系列的数据模型章节。前两篇我们讨论了关系模型和文档模型，今天把目光转向了图模型——它不是新概念（图论的年龄比计算机科学还大），但在工程实践中被严重低估。

太多团队下意识地选 MySQL 建模一切，遇到多跳关联就写几十行的递归 CTE，然后抱怨”数据库慢”。问题不在数据库，在模型——你用错了抽象。

图数据库的价值不是”替代关系数据库”，而是提供了一种处理关联密集型数据的原生语言和存储结构。 当你的数据关系像供应链上下游、用户推荐网络这样”比二叉树还复杂”的时候，打开 Neo4j 试试——你会发现很多问题变得简单了。

把图数据库放进你的工具箱，总有一天它会帮你解决一个用 SQL 必须绕远路的问题。
