DDIA-06-主从复制：MySQL Binlog复制到底做了什么

一、为什么需要主从复制？

先看一个真实数据。

我们的订单中心，日订单130万，峰值QPS约8000。MySQL单机扛读还行，但问题是：(1) 机器总会挂，(2) 读写都在一台机器上互相抢资源，(3) 备份不好做。主从复制就是解决这些问题的标准答案。

DDIA第六章的主题就是Replication（复制）。Martin Kleppmann说得很直白：复制的核心动机有三——

  • 高可用：主库挂了从库顶上
  • 可扩展性：读写分离，读流量分流到从库
  • 延迟优化：地理上就近部署副本

但一提到”副本”，问题就来了：数据怎么同步？同步到什么程度？出了延迟怎么办？

本文从MySQL Binlog复制的实现细节出发，逐一拆解这些问题。

二、三种复制模式：同步、异步与半同步

DDIA把复制模式分为三种：同步复制、异步复制、半同步复制。它们的差异，本质上是一个trade-off：数据一致性 vs 写入性能 vs 可用性。

2.1 异步复制（Asynchronous）

MySQL默认就是异步复制。流程很简单：

  1. 主库执行事务，写入Binlog，提交事务，返回客户端OK
  2. 主库的Binlog Dump线程把Binlog事件推给从库
  3. 从库IO线程接收，写入Relay Log
  4. 从库SQL线程回放Relay Log

关键点：主库提交事务完全不等从库确认——这就是”异步”的含义。

优点：主库写入性能不受从库影响，高吞吐。
缺点：主库宕机时，未同步到从库的数据直接丢失——这也是DDIA说的”持久性风险（Durability Risk）”。

2.2 半同步复制（Semi-synchronous）

MySQL 5.5之后引入的折中方案：

  1. 主库执行事务，写Binlog
  2. 主库等待至少一个从库的ACK确认
  3. 收到ACK后才返回客户端OK

优点：比异步安全（至少一个副本有数据），比同步快（不必等所有从库）。
缺点：如果主库宕机时刚好没有从库收到最新事务，该事务仍会丢失。超时机制会在从库无响应时退化为异步——这在CAP理论里属于放弃了C，保了A。

2.3 同步复制（Synchronous）

MySQL Group Replication中的Paxos协议实现。DDIA对此的评价是：同步复制在实践中往往意味着只有一个从库是同步的，其他都是异步的。因为同步所有从库会导致——任意一个从库挂了，整个系统就无法写入。

对比总结：

模式 数据一致性 延迟 可用性
异步 可能丢失事务 低 高
同步 零丢失 高 低
半同步 丢失窗口≤1个事务 中 中

三、MySQL Binlog的三种格式

3.1 STATEMENT格式

记录的是SQL语句本身。

优点：日志量小。
缺点：严重依赖上下文——NOW(), UUID(), LIMIT不带ORDER BY会产生不确定结果，主从执行结果不一致。

3.2 ROW格式（推荐）

记录的是每一行数据的变化。DDIA中将这种实现称为”基于行的复制（Row-based Replication）”。

优点：确定性，安全，DELETE/UPDATE的行数完全一致。
缺点：日志量大——一条UPDATE影响了10万行就有10万条记录。

实战建议：生产环境直接用binlog_format=ROW。

3.3 MIXED格式

STATEMENT和ROW的混合。MySQL优化器自行决定。不可控，不推荐。

四、复制延迟与四种一致性保证

DDIA第六章最关键的价值，是提出了复制延迟下的四种一致性保证：

(1) 读己之写（Read-After-Write Consistency）

问题：用户提交操作后立即查看结果，读落到了还没同步完的从库——“刚发的评论消失了”。

解决方案：从主库读用户可能修改过的数据。

我们的实践：用户查询自己的订单列表一定走主库——因为用户刚下单后可能立即刷新看订单状态。

(2) 单调读（Monotonic Reads）

问题：用户先后两次从不同从库读取，数据”回退”了。

解决方案：基于用户ID哈希，让同一个用户始终路由到同一个从库。

(3) 前缀一致读（Consistent Prefix Reads）

问题：多个写入存在因果顺序，但不同副本回放顺序不一致。

解决方案：相关更新写入同一个分区。

我们的实践：订单所有操作（下单→支付→发货→收货）属于同一个order_id分片，天然满足。

(4) 最终一致性（Eventually Consistent）

最弱的保证：如果没有新的写入，所有副本最终会收敛。DDIA说得很清楚——“最终”到底是多久，谁也说不准。

六、经典故障：付了钱，订单还是未支付

  1. 用户支付成功，写入主库status='paid'
  2. 前端跳转订单详情页，SELECT status从从库读
  3. 从库还没同步完，读到status='unpaid'
  4. 用户以为支付失败，又付了一次 → 重复支付

解决方案：支付回调后订单查询强制走主库 + 业务层幂等兜底。

七、总结

  1. 三种复制模式本质上是CAP的权衡——异步牺牲C，同步牺牲A，半同步卡在中间
  2. ROW格式是MySQL Binlog的最安全选择
  3. 四种一致性保证是处理复制延迟的方法论，每种都有清晰的场景和解决方案
  4. 读写分离不是免费午餐——从库延迟是最大的坑，需要路由策略和业务幂等两层兜底

DDIA第六章最后有一段话我印象很深：“复制延迟是一个现实问题，应用程序必须准备好处理它——即使你今天用的是同步复制。”

延迟永远存在，关键不是消除它，而是在它存在的情况下，系统仍然正确。
