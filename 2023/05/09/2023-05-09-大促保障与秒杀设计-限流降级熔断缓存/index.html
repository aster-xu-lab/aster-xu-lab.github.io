大促保障与秒杀设计：限流、降级、熔断、缓存的组合拳

一、大促保障四件套

高并发场景（大促/秒杀）的保障，核心是四件套一起上：

  • 限流：入口控制量，按 QPS/并发线程限流，防止打爆；
  • 降级：非核心功能降级（营销/推荐只保留基础、二级缓存降级走 Redis）；
  • 熔断：下游异常快速失败，保护自己；
  • 缓存：热点数据预热、缓存降级。

我的订单中心大促：按 QPS 限流防打爆、下游仓储/SAP 异常时熔断快速失败、非核心功能降级只保留基础。配合”预热 + 风控 + 异步”，是完整的大促保障体系。

二、经典场景题：秒杀系统怎么设计

秒杀是系统设计的高频题，核心矛盾是瞬时超高并发 + 库存有限。分阶段设计：

① 提前：预热

  • 商品信息缓存预热（热点商品提前放 Redis）；
  • 库存缓存预扣：库存从 DB 预扣到 Redis，避免瞬间打爆 DB。

② 请求：限流 + 排队 + 异步

  • 限流：用户限频、IP 限流，防止脚本刷；
  • 排队：消息队列削峰——请求先进队列，后端异步消化；
  • 异步下单：真正的下单处理在队列消费者里，不阻塞前端。

③ 库存：Redis 预扣 + DB 最终扣减

  • Redis 预扣防超卖：DECR inventory 原子扣减，扣到 0 拒绝；
  • 最终 DB 扣减：异步把 Redis 的扣减落库；
  • 防止超卖：Redis 预扣是”能不能抢”的闸，DB 扣减是”最终账”。

④ 一致性：先扣 Redis 防超卖，异步 DB 对账

  • Redis 预扣 + 异步 DB 扣减，靠对账兜底收敛最终一致。

三、大促的完整保障套路

我的订单中心实战总结：

  1. 限流：Sentinel 按 QPS/并发限流，防止打爆；
  2. 降级：非核心功能降级（二级缓存降级走 Redis/cache）；
  3. 熔断：下游异常快速失败，保护自己；
  4. 缓存：热点数据预热、缓存降级；
  5. 异步：MQ 解耦耗时操作，削峰。

这套从”缓存到分库分表到 OLAP”的完整链路，就是我处理高并发/大促的方案——订单中台日均 15 万单（峰值 50 万），通天晓传统 OMS 双十一峰值 130 万日单，都是同一套。

四、为什么秒杀要”排队”

秒杀的本质是瞬时流量远超处理能力。如果不排队，所有请求同时打 DB，DB 直接挂。

排队（MQ）的价值：把瞬时尖峰平滑成持续流量——请求先落队列，后端按自己的吞吐慢慢消化。用户看到”排队中”，但不会丢请求。这就是”削峰”的落地。

五、防超卖的底层

超卖 = 卖出的比库存多。防超卖的关键在扣减的原子性：

  • Redis：DECR 是原子的，扣到 0 拒绝——保证不超卖；
  • DB：UPDATE stock SET num = num - 1 WHERE num > 0（条件更新）——保证不超卖；
  • 先 Redis 预扣（挡流量），再 DB 条件扣减（落账），对账兜底。

两层都”条件扣减”，才能既扛流量又不超卖。

六、和面试的连接

被问”设计一个秒杀系统”，就用这套：预热 → 限流排队异步 → Redis 预扣 + DB 条件扣减 → 对账。每一步都有 trade-off（比如 Redis 预扣可能和 DB 不一致，靠对账收敛），能讲清取舍就是 P7 水平。

总结

  • 大促四件套：限流 + 降级 + 熔断 + 缓存，配合预热/风控/异步；
  • 秒杀分阶段：预热 → 限流排队异步 → Redis 预扣 + DB 扣减 → 对账；
  • 削峰靠队列，把瞬时尖峰平滑成持续流量；
  • 防超卖靠原子扣减（Redis DECR + DB 条件更新），两层都不超卖；
  • 我的订单中心（日均 15 万/峰值 50 万）和通天晓大促（130 万日单）是这套的完整验证。
