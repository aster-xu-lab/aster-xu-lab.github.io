ShardingSphere 源码解析：一条 SQL 是如何被改写路由的

知其然也要知其所以然。前面用 ShardingSphere 把分片跑通了，我进一步读了源码，搞清楚一条 SQL 在 ShardingSphere 内部到底经历了什么。本文基于 5.4.1 源码，拆解调用链。

总入口：ShardingSQLRouter

所有分片路由的门口是 ShardingSQLRouter.createRouteContext()：

它自己不算，只是编排了”提取条件 → 校验 → 路由”三部曲。

① 提取分片条件：ShardingConditionEngine

从 WHERE / INSERT VALUES 里把分片键的值抠出来：

SELECT/UPDATE/DELETE 走 WhereClauseShardingConditionEngine，INSERT 走 InsertClauseShardingConditionEngine。

② 执行路由：ShardingStandardRoutingEngine

根据 SQL 是否带分片键，选不同的路由引擎（ShardingRouteEngineFactory）：

  • 带分片键单表 → ShardingStandardRoutingEngine
  • 不带分片键全表 → ShardingTableBroadcastRoutingEngine
  • 多表 JOIN → ShardingComplexRoutingEngine

按这个顺序追，链路最顺：

  1. ShardingSQLRouter.createRouteContext() — 总入口
  2. ShardingConditionEngine.createShardingConditions() — 提取分片键
  3. ShardingStandardRoutingEngine.route() + routeTables() — 算目标表
  4. TableTokenGenerator.generateSQLTokens() — 标记改写位置

小结

ShardingSphere 的核心链路：解析 SQL → 提取分片键 → 算目标表 → 改写 SQL → 执行。

  • ShardingSQLRouter 编排
  • xRoutingEngine 算路由
  • TableTokenGenerator 改写

弄懂这条链路，分片的”黑盒”就打开了，遇到路由不对、广播过多等问题时就知道往哪查。
