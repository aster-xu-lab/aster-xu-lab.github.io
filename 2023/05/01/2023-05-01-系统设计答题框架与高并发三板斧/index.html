系统设计答题框架：5 步走 + 高并发三板斧

一、设计题不考”完美答案”，考思路完整度

系统设计题最容易犯的错是一上来就画架构、甩方案。正确的打开方式是有框架地推进。我的万能套路是 5 步走：

最重要的第一步是澄清需求——面试官考的是”你会不会问清楚再动手”，而不是”你能不能直接给答案”。

二、高并发三板斧：缓存 + 异步 + 削峰

高并发设计的核心手段就三个：

手段 原理 我的案例
缓存 读多写少用缓存扛 Caffeine + Redis 二级缓存、大促降级
异步 耗时/可延迟操作异步化 MQ 解耦、阻塞队列批处理
削峰 平滑瞬时尖峰流量 限流 + 批次、大促分级降级
  • 缓存：把读压力从 DB 扛到 Redis/本地，读多写少场景立竿见影；
  • 异步：把”不一定要同步完成”的操作丢给 MQ，调用方不等，吞吐上来；
  • 削峰：瞬时尖峰（秒杀、大促）不硬扛，用限流 + 队列平滑。

我的订单中心日均 15 万单（峰值 50 万）就是用这套扛住；通天晓传统 OMS 双十一峰值 130 万日单也是同一套。

先低成本手段，不够再上分库分表/OLAP。我的慢 SQL 从千条级降到个位数（内部 1124 → 6）就是”索引 SQL 这层做到极致”。

四、高可用设计

高可用 = 不挂，手段：

  • 冗余：多副本、多机房、主从；
  • 故障转移：Redis 哨兵 / K8s 自愈 / MySQL 半同步；
  • 限流熔断降级：保护自己不拖垮；
  • 幂等重试：接口幂等 + 超时重试；
  • 监控告警：全链路追踪、指标监控、告警分级。

我的可用性做到 99.99%，关键在连接池隔离（舱壁）+ 监控告警及时。

五、别混三个词

  • 高性能：单次快（缓存/索引/异步）——QPS 高；
  • 高可用：不挂（冗余/故障转移）——99.99%；
  • 高并发：规模大也能扛（分布式/分片/削峰）。

三者常一起出现，但优化的手段侧重不同——被问”高性能和高可用什么关系”，把三者的手段说清楚就赢了。

总结

  • 设计题 5 步走：澄清需求 → 估规模 → 画架构 → 讲取舍 → 谈扩展，第一步最关键；
  • 高并发三板斧：缓存扛读、异步解耦、削峰平滑；
  • 数据库优化从索引低做起，别一上来分库分表；
  • 高可用 = 冗余 + 故障转移 + 限流熔断降级 + 幂等 + 监控；
  • 高性能/高可用/高并发手段侧重不同，别混；
  • 我的订单中心（日均 15 万/峰值 50 万）是这套的完整验证。
