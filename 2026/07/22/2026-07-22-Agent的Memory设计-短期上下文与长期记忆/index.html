Agent 的 Memory 设计：短期上下文与长期记忆的工程实现

Agent 三层架构里，Memory 是最容易被低估的一层。很多人以为 Memory 就是”把对话历史塞进 prompt”——但上下文窗口有限、历史一长就爆，跨会话更是无从谈起。这篇讲 Memory 的工程实现：短期上下文怎么管理、长期记忆怎么设计。

一、两个 Memory，两个问题

Agent 的 Memory 分两层，解决不同问题：

短期上下文 长期记忆
是什么 当前对话历史 跨会话的持久化信息
存在哪 内存 / 会话 Redis / 向量库 / DB
生命周期 一次会话 永久（可检索）
核心问题 上下文窗口装不下 怎么存、怎么检索

没有记忆的 Agent 每步都”失忆”——要么靠塞全量历史（贵且超窗口），要么跨会话完全没记忆。做好分层，Agent 才从”多步调用”变成”会积累的系统”。

二、短期上下文：窗口管理的四种策略

LLM 有上下文窗口上限（如 128K token），对话一长就装不下。四种策略：

① 截断（最粗暴）：只保留最近 N 轮，丢掉最老的。

缺点：早期关键信息（用户需求、约束）可能被丢。

② 滑动窗口（基础）：固定窗口滚动，比裸截断多了”始终保留第一条系统消息/用户目标”。

关键：用户目标要一直保留——它是 Agent 要完成的事，丢了就”跑偏”。

③ 摘要压缩（进阶）：把早期历史交给 LLM 生成摘要，用摘要代替原文。

省 token，但有损——摘要可能丢细节。适合”早期信息是背景、不重要细节”的场景。

④ 检索增强（Memory+RAG）：把”重要记忆”向量化，需要时检索，而不是全量塞。

选型：简单任务用滑动窗口（保用户目标），长任务用摘要，跨会话用检索增强。按场景选，不是越复杂越好。

三、长期记忆：怎么存、怎么检索

长期记忆解决”跨会话记住用户/任务”。两种实现：

① 结构化存储（DB/Redis）
适合确定性信息：用户偏好、任务状态、已处理记录。

② 向量库（语义记忆）
适合语义化信息：历史结论、背景知识。和 RAG 同一套基础设施。

记忆的 TTL 和隔离：

  • TTL：短期偏好设过期（如 7 天），长期知识不设——记忆也要”遗忘”；
  • 隔离：不同用户/任务的记忆要隔离（按 key 分），否则串记忆。

四、Memory 和 RAG 的关系（容易混）

RAG 和 Memory 都用向量检索，但来源不同：

RAG Agent Memory
数据来源 外部知识库（FAQ/文档） Agent 自己的历史（结论/偏好）
解决什么 知识过期、幻觉 跨会话连贯、个性化
生命周期 静态知识 动态积累

落地时共用一套向量基础设施（pgvector/Milvus + Embedding），只是写入的是不同内容。

六、诚实的边界

Memory 是 Agent 从 Demo 到生产的关键一环（我在《Agent 从 Demo 到生产》里列过”状态持久化”）。这篇是工程设计的梳理——生产级 Memory 还要考虑存储成本、检索延迟、记忆污染（写入了错误结论）。原理清楚、边界诚实。

总结

  • Memory 分两层：短期上下文（会话内）+ 长期记忆（跨会话）；
  • 短期管理四策略：截断 / 滑动窗口（保用户目标）/ 摘要压缩 / 检索增强，按场景选；
  • 长期记忆：结构化（DB/Redis）存确定性信息 + 向量库存语义记忆，注意 TTL 和隔离；
  • Memory 和 RAG 同基础设施，但数据来源不同（历史 vs 知识库）；
  • 工程三关键：主动写入、检索 gate、状态可恢复；
  • 没记忆的 Agent 每步失忆，做好 Memory 才是”会积累的系统”。
