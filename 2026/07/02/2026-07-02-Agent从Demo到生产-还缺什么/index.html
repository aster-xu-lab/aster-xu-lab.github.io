Agent 从 Demo 到生产：还差什么？我的可靠性清单

写完 30 行手写 ReAct、对比完 Spring AI 之后，最大的问题是：Demo 能跑，生产怎么上？ 这篇从可靠性工程视角，梳理 Agent 从 Demo 到生产要补的东西。

一、Demo 能跑 ≠ 能上生产

我的 30 行 ReAct 循环（think → act → observe）在本地跑得很好，但拿到生产环境，问题立刻暴露：

  • LLM 接口卡了，整个 Agent 卡死（没有超时）；
  • 某轮工具调用失败，直接断（没有重试）；
  • 多用户同时跑，状态全乱（没有隔离）；
  • 进程一重启，对话历史全丢（没有持久化）；
  • Agent 干了什么完全不可见（没有日志）。

这些不是”智能”问题，是工程问题——而工程问题恰好是我做任务编排引擎的老本行。

二、我的可靠性清单

1. 超时兜底

LLM 是不确定的：可能卡住、可能超时。每个 LLM 调用必须有超时，不能让 Agent 无限等。

2. 幂等

Agent 的 Tool 调用可能重复（LLM 重试、网络重试）。Tool 必须是幂等的——用唯一 key 查重。

这和消息消费幂等同源——分布式下重复是常态，幂等是兜底。

3. 状态持久化

Demo 的 history 在内存里，进程一死全丢。生产要持久化 Agent 的会话状态（Redis/DB），支持断点续传。

4. 可观测性

Agent 的推理是黑盒——LLM 为什么选这个工具、为什么停在这，不可见。必须记录全链路日志：

出问题才能复盘：”Agent 在第 3 轮选错了工具，因为工具描述有歧义”。

5. 人工确认点

涉及钱、库存、下发的关键 Tool 调用，必须有确认点——不能让模型直接拍板。这是安全底线。

6. 告警与降级

Agent 异常要有告警；LLM 不可用要降级（比如降到规则引擎、返回检索原文），而不是报错。

三、这些能力我有现成的

列完清单我发现：这套可靠性设计，我在 SyncTask 引擎里全做过：

Agent 需要 SyncTask 已有
超时兜底 任务超时 → 重试队列
幂等 分布式锁 + 二次查库双重防重
状态持久化 sync_task 表状态机
可观测性 全链路日志 + 四级告警
降级 失败重试 + 死信兜底

这解释了为什么我做 Agent 有信心：我不是从零学一个全新领域，而是把任务编排的可靠性经验迁移过来，补 LLM 这个”不确定的决策者”。

四、最大的新问题：LLM 的不可控

Agent 和 SyncTask 最大的区别：决策者从确定性的代码规则，变成了概率性的 LLM。

  • 规则引擎：if status == SUCCESS → next，输出确定；
  • LLM：可能输出”看起来合理但实际上是错的”的下一步。

所以 Agent 生产化多了一项核心工作：约束 LLM 的自由度：

  1. Tool 描述写精确——描述越清楚，选对率越高；
  2. 结构化输出——Function Calling / JSON Schema，比自由文本可靠；
  3. 关键路径人工确认——高风险操作不能全自动；
  4. 失败路径设计——LLM 答错/卡住时，有降级和兜底，不是硬撑。

五、诚实的边界

我在生产没有跑过 Agent 系统（这是学习阶段的认知）。但可靠性清单本身是真实工程经验的迁移——超时、幂等、持久化、可观测性、降级，这些我在 SyncTask 里都验证过，只是决策者从代码换成了 LLM。

总结

  • Demo 到生产差的是工程化：超时、幂等、持久化、可观测性、人工确认、降级；
  • 可靠性设计可迁移：SyncTask 的双重防重、状态机、告警、降级，Agent 全部适用；
  • 新问题是 LLM 不可控：约束工具描述、结构化输出、人工确认点、失败降级；
  • 我的迁移优势：懂可靠性工程的 Agent 开发者，是 ML 背景开发者缺的。
