七年 Java 后端之路：从企业开发到中台架构师

写在前面

2019 年 1 月入行，到 2026 年，整整七年。

从企业系统开发，到电商供应链，再到中台从 0 到 1。回头看，每个阶段真正留下的都是当时没分开记的判断。

这篇只保留还能复用的做法：基础怎么补、性能怎么证、事务和编排怎么选。

第一阶段：把基础啃透（2019-2021）

前两年做的是传统企业软件。这个阶段最大的收获是把基础打扎实了：

  • 从 Servlet 到 Spring Boot，一套一套地啃
  • 跟着视频系统学了 JVM（17 篇博客笔记，至今受益）
  • 把 23 种设计模式用 Java 写了一遍（23 篇博客笔记）

这段时间没有业务复杂度可以靠，能靠的只有把基础啃完。如果这两年只做 CRUD，后面的路会难走很多。

这个阶段的教训：前两年别急着追新技术，把 Java 基础、JVM、并发、设计模式啃透。这些东西十年都不会过时。

第二阶段：业务复杂度上来（2021-2024）

从传统软件转到电商供应链之后，订单和仓储扣在一条链路里，复杂度上了一个数量级。这段经历留下三件事：

1. 性能优化不是玄学

系统的 QPS 从 2000 优化到 8000+（当时的压测对比口径），不是靠”加机器”，而是靠：SQL 优化 + MQ 解耦 + 阻塞队列批处理 + 二级缓存。每次优化都有数据支撑，不是拍脑袋。

2. 分布式事务是绕不过去的坎

2024 年的 AT → TCC 迁移是我第一次独立做架构决策（该项目边界见分布式事务系列）。压测数据告诉我 AT 的全局锁在争用下撑不住，TCC 在冲突面更小的链路上表现更好；具体提升没有统一基线，不在这里报百分比。做技术选型最重要的不是”哪个方案好”，而是”哪个方案适合当前阶段”。

3. 带团队比写代码难

从一个人写代码到带一个小团队，最难的不是技术，而是分活。怎么让每个人做适合自己的事，怎么保证代码质量一致，怎么在 deadline 和代码质量之间做平衡——这些没有教程，全靠实操。

第三阶段：判断开始能复用（2024 起）

这一阶段留下的不是头衔，是三件能单独讲清楚的事：

1. SyncTask 引擎

从订单中台、仓储系统各数十个 Handler 的重复逻辑中抽离出 SyncTask 引擎。做了放弃 DAG 的架构决策——评估了 Temporal、Conductor、nFlow 等 6 个方案后选择了 Choreography 模式。这是我技术判断力最自信的时刻。

2. 稳定性治理

99.9% → 99.99%（监控统计口径，具体归因见大促复盘）；慢 SQL 在 2023 年已治理到个位数（1124→6），这一阶段做的是保持与复盘。不是惊天动地的创新，是 30+ 索引 + 大 IN 拆分 + 连接池隔离 + ThreadLocal 修复的具体工作。

3. Spec-Coding + AI 辅助

工单系统从 0 到 1——Spec→领域建模→API 设计→ADR→AI 加速编码。182 个文件、1.2 万行代码，3 周提测。证明了”先想清楚再动手”的效率远超”先写了再说”。

技术复盘：七年最值钱的五条经验

  1. 基础决定天花板：JVM、并发、设计模式这些”十年不过时”的东西，越早啃透越值钱；
  2. 性能优化靠数据不靠感觉：每次优化都要有监控数据支撑，QPS、慢 SQL、RT 都是证据；
  3. 架构决策是”选适合”不是”选最好”：AT→TCC、Choreography vs DAG、单号分片 vs 时间分片——都是”哪个适合当前约束”；
  4. 写 ADR 比写代码值钱：每次做完项目花 30 分钟记录”当时为什么这么做”，三年后回头看比代码本身有价值；
  5. 带团队的核心是分活：让每个人做适合自己的事、边界清晰、质量一致——这比技术难。

还在加码的三件事

  1. AI 工程化——编排经验迁到 Agent 上，重点是可控：成本、降级、评测、审计，而不是再写一个演示循环；
  2. 分布式与数据建模——分片之后的稳态、对账和扩容，继续按访问模式算账；
  3. 持续输出——把做过的决策写成讲得清的取舍。

写在最后

七年下来，最大的感悟：技术能力决定下限，决策能力决定上限。

能把功能做出来，和能做出正确的技术选型并讲清楚为什么，是两种能力。后者的跨越，不在于多会写代码，而在于能在一个模糊的技术场景下，做出最符合当前约束的决策，并且能说服别人。

如果只分享一条建议：每次做完一个项目，花 30 分钟写一份 ADR，记录”当时为什么这么做”。这份文档三年后回头看，比代码本身更有价值。
