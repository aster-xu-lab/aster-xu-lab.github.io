长跑采集的内存不是调大堆：从 2 GB OOM 到 350 MB 稳态

一条 1000 条的采集任务，跑到一百多条就开始 BROWSER4_EXIT_1。第一反应是「堆不够」或者「内存泄漏」，但 heap dump 里最大的对象不是业务数据，也不是缓存，而是一次导航命令顺手构建的 accessibility tree。这篇按三层归因讲：先分类错误，再找到具体命令的隐式副作用，最后处理跨进程的对象可达性。

一、EXIT_1 不是一种错误

采集进程退出码 1，日志里只留一行截断到 600 字符的 stderr。把所有 EXIT_1 都当成同一件事，会得到两个错误结论：要么以为全是风控，要么以为全是内存泄漏。

实际至少要分成三类：

类型 典型特征 处理方式
瞬时 eval / CDP 抖动 Ping timeout、WebSocket send timed out、MCP 工具请求超时 同会话延时 1 秒重试一次
引擎级故障 Java heap space、Internal Server Error、MCP 端点未就绪 重启 runtime 后重试
会话/导航失败 页面把浏览器会话带崩、CLI 自身退出 清理会话后重建

分类不是靠错误码本身，而是靠 errorCode + step + detail 三个字段一起判断。step 在流程里被显式标记成 opening / goto / eval / capture，因为同一个 EXIT_1 发生在导航阶段和发生在抽取阶段，含义完全不同。

瞬时失败的重试只允许一次，而且必须留在同一个 runtime 里：

这一步的收益不是「重试成功」，而是不要把可恢复的抖动升级成 JVM 重启。一个 URL 重启一次 JVM，1000 条任务的成本会完全失控。

分类做完，才轮到内存。

二、第一层：1.27 GB 是 byte[]

跑到 67 条时，JVM 堆已经 1.90 GB，G1 Old Gen 占 1.67 GB。heap dump 出来 1.87 GB，最大的对象类型是 byte[]：

  • 4,385,986 个实例，合计约 1.27 GB；
  • MergedDOMTreeNode 只有 26,231 个实例，约 2.7 MB。

直觉会往「是不是缓存了太多页面」「是不是图片没释放」上走，但 byte[] 的形态更像序列化后的 DOM 字符串和 JSON 缓冲区。这一步只能得出一个方向：内存在页面数据的表示层，不在业务对象层。

还有一个容易误判的指标：gc.overhead=0。它只说明 GC 没有频繁触发，不代表堆没问题。事实上 G1 在 OOM 之前没有做过一次 full GC——这一点后面还会再出现。

三、第二层：GC 能回收，所以不是「强引用泄漏」

下一步是手动触发一次 full GC，看堆能不能掉下来：

场景 GC 前 GC 后
跑 45 条 1.04 GB 490 MB
任务取消后 1.43 GB 60 MB
跑 130 条（不回收 session） 1.70 GB 1.09 GB

前两行说明：这些内存是垃圾，不是泄漏。任务取消、会话关闭之后，对象图断开，一次 full GC 就能回到 60 MB。

但第三行暴露了另一半问题：130 条时 GC 后仍有 1.09 GB live，而且从 45 条的 490 MB 到 130 条的 1.09 GB，大约是 每条 +7 MB 的 live 增长。也就是说：

  • 垃圾可以回收；
  • 但回收之后，仍然有一部分对象是可达的；
  • 这部分对象不随 GC 消失，只有关闭会话才断开引用。

这就是「内存泄漏」和「内存回收不及时」的分界。判断标准不是峰值，也不是单次 GC 能掉多少，而是每次 GC 后的 live 是否持续增长。

四、真正的垃圾源：goto 的 accessibility snapshot

沿着「页面表示层」这个方向查，最后落到一个看起来无关痛痒的命令上。

Browser4 的 CLI goto 在导航完成后，会自动构建一份完整的 accessibility tree，供后续的语义操作使用。对于 Amazon 这种页面，这棵树很大，而且 Browser4 会把它保留在会话里。每次导航都生成一棵，几轮之后就是：

  • MergedDOMTreeNode 2.8 万个；
  • byte[] 225 万个；
  • 20 条数据堆到 1.98 GB。

改用 eval location.href = url 导航后，同样的 20 条：

goto eval location.href
堆 1.98 GB 240 MB
MergedDOMTreeNode 2.8 万 36
byte[] 225 万 19 万
成功 20/20 20/20

导航本身没有变慢，也没有牺牲正确性。差异只是：eval 不会在命令结束后顺手构建并保留一份 accessibility tree。

现在的导航流程变成三步：

先读当前 URL 作为变化基准，再赋值导航，然后等 URL 变化、等 load 完成。这套组合比 goto 多几次 CLI 调用，但把最大的垃圾源直接拿掉了。

这是一个典型的「工具隐式副作用」问题。 命令的显式语义是「导航到某个地址」，隐式副作用是「构建一份完整的可访问性快照」。只看命令名，永远找不到它。

五、残余 live：session close 才断开引用

把 goto 换掉之后，垃圾少了，但 130 条时 GC 后仍有约 1.09 GB live。继续拆：

动作 结果
不关 session，直接 GC（195 条时） 只回落一部分，live 仍在
先 session close，再 GC 能压回 80–137 MB

原因不复杂：CDP 的对象图由会话持有，会话不关闭，Node 侧和 JVM 侧都还有引用链。GC 只能回收不可达对象，不能替你关闭会话。

于是加了 session 回收：每 50 条关闭并重建一次平台会话，再触发一次 GC。200 条验证：

  • 输入 198/200 ok，2 条失败都是列表里本来就无效的链接；
  • 0 OOM、0 次 JVM 重启；
  • 稳定阶段 PID 不变；
  • 堆在回收后回落到 258–363 MB。

但这里又撞上一个 G1 的行为：占用在 55–60% 时，G1 不会主动做 full GC。所以「每 50 条回收 session」只完成了一半，另一半必须由外部显式触发 System.gc()。应用进程没法直接让另一个 JVM 执行 GC，jcmd 是诊断工具，不能当产品依赖。

六、一个 2 KB 的 Java agent

解决方案是一个文件信号 agent：

  • 应用在关闭并重建会话后，往 <userData>/browser4/gc.request 写一个时间戳；
  • JVM 启动时挂上 -javaagent:.../GcAgent.jar -Dbrowser4.gc.request=<该文件>；
  • agent 起一个 daemon 线程，每 250 ms 轮询文件，存在就删除并调用一次 System.gc()；
  • jar 不存在时，应用回退到原来的「每 50 条重启 runtime」。

这个设计有几个刻意的取舍：

  1. 用文件信号，不用 RPC。 应用和 JVM 之间已经有一个 CLI 通道，但为了触发 GC 再走一次 MCP 没有意义；文件是最小侵入的跨进程信号。
  2. agent 可以缺失。 jar 没打进包，应用退回重启 runtime，功能不坏，只是更贵。
  3. 只在 session 回收后请求。 注释写得很明确：Call only after the platform session has been closed。会话没关，GC 收不掉那部分 live，触发也白触发。
  4. agent 不写业务日志。 它的 stderr 只进 runtime 的排空缓冲，验证以 jstat FGC、PID 和堆为准，避免把诊断信息混进应用日志。

验证结果：

跑次 结果
200 条（无外部 jcmd） 198 ok / 2 failed，0 OOM；agent 在 50/100/150/200 各触发一次 full GC，PID 不变，堆 304–368 MB
1000 条中途（5 h 14 min） 输入 839/1000 ok、0 failed、0 OOM、0 次 infra 重启；FGC 16，PID 全程不变，检查点堆 353 MB

1000 条这一跑没有跑完，剩下 161 条不在结论里。但「跑到 839 条、PID 不变、0 次重启」已经足够说明内存形态是稳态，不是缓慢泄漏。

七、另一条内存链：stdout 管道

堆之外还有一条更隐蔽的内存路径。

Browser4 的 JVM 每建立一个 session，会往 stdout 写约 94 KiB。Windows 的匿名管道缓冲大约是 64 KiB。如果父进程只接了 stderr、没有持续排空 stdout，管道写满后 JVM 的 write() 就会阻塞，所有 MCP 调用随之超时，CLI 退出 1，应用重启 JVM，循环往复。

当时的症状是「每 2 条崩一次」，墙钟被拉到正常值的 8.6 倍。修法不是调大缓冲，而是把 stdout 和 stderr 都接上并持续排空。

这条和堆没有关系，但它说明一件事：进程间缓冲也是内存，而且它的故障形态和 OOM 很像——都是子进程卡住、调用超时、退出码 1。排查时如果只盯着 heap dump，会漏掉这一类。

八、数据搬运：别让整页 HTML 走 stdout

还有一处不是「泄漏」、但会抬高峰值的地方：页面快照的落盘方式。

原来的做法是让 JVM 把整页 outerHTML 通过 eval 返回到 stdout，Node 再解析 JSON、写文件。平均每次 stdout 2,149,612 B。这意味着整页 DOM 要在 JVM 里序列化一次、在管道里传一次、在 Node 里再解析一次。

改成 htmlsnapshot export --file 之后，JVM 直接把文档写到 page.html.tmp，Node 读入后 gzip 成 page.html，再删临时文件。stdout 从 2.15 MB 降到 135 B，命令耗时只增加约 13 ms（496 ms → 509 ms）。

旧的 eval 路径保留为兜底，只在 export 不可用时触发。整体仍然是 best-effort：落盘失败不改变抽取结果。

九、边界

  • 不是所有 EXIT_1 都是内存。 先分类，再归因。把瞬时抖动当泄漏去调堆，只会让问题更晚出现。
  • 调大堆不是方案。 当前 -Xmx2048m 大约是观测峰值的 2 倍；调到 4 GB 只是把 OOM 推迟到更后面，垃圾源还在。
  • 平台默认值不同。 Amazon 默认每 50 条回收 session，eBay 默认不回收；这是页面规模和行为差异下的工程取值，不是通用最优解。
  • G1 的行为随 JDK 版本变化。 「55–60% 不主动 full GC」是这次观测到的行为，换版本要重新验证。
  • 1000 条只跑到 839 条，中途结论不能当成完整验收。
  • 外部 jcmd 只是诊断手段，产品路径依赖的是随包 agent；agent 缺失时回退重启 runtime。

总结

这次排查真正有用的不是「找到一个参数」，而是三层递进：

  1. 先分类：EXIT_1 混着瞬时抖动、引擎故障和导航失败，混在一起看就会得出错误结论；
  2. 再归因到具体命令：最大的垃圾源不是业务代码，而是 goto 顺手构建的 accessibility tree；
  3. 最后处理可达性：GC 能回收垃圾，但收不掉会话持有的对象图；关闭会话 + 外部显式 GC，才能把 live 压住。

内存问题的终点不是「堆设多大」，而是你知不知道自己每一层内存是谁持有的、什么时候会断开。
