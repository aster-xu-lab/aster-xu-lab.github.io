预填不是填空题：多源合并、来源溯源与可撤销

外部页面上的一个字段，往往不是一个值，而是多个来源、多个标签、多种格式的号码。把它们塞进一个输入框，用户看到的是拼接后的字符串，系统丢掉的却是「这个值从哪来」。更麻烦的是删除：用户删掉一个号，下一次重新识别又把它带回来。这篇讲一条预填管线怎么同时解决合并、溯源和撤销。

一、单值字段装不下多源

假设目标字段是「零件号」。来源页面上可能同时出现：

  • OE Part Number
  • Manufacturer Part Number
  • OEM Equivalent Part Number
  • 换行或逗号分隔的多值
  • 同一组里带空格、连字符、大小写差异的重复号

如果目标字段只有一个字符串，最直接的做法是全部拼起来。但这会带来三个问题：

  1. 来源丢失。 用户看到 12345;67890，不知道哪个来自哪个标签。
  2. 删除粒度错误。 用户想删一个号，实际删掉的是整个字段。
  3. 重跑复活。 预填是派生数据；下一次重新识别或模板重建，被删的号又回来了。

这三个问题不是 UI 问题，是数据模型问题。解决方式是把「一个值」改成「一组来源」。

复核对象里，这类字段被建模成组：

四、撤销：删除必须成为下一次派生的输入

用户删掉一个来源号码之后，系统要记住「这个号被删过」。如果只修改当前的 numbers，下一次重新识别会重新跑规则，被删的号又回来。

同类机制一共有三套，分别对应三种派生来源：

删除记录 作用对象 消费点
oeGroupRemovals 来源分组里的号码 复核归一化时扣减
removedCategoryAttributes 类目模板生成的属性行 模板重建时过滤
removedSourceAttributes 从来源页面自动写入的属性 自动写入时过滤

三个消费点对应三种「会重新生成数据」的时机。只要有一个消费点没接上，删除就会在某个路径上复活。

几个容易忽略的细节：

  • 只对 origin === 'source' 的删除写 tombstone。 手工组本来就是用户输入，删了就是删了，不需要防复活。
  • 「无此字段」要清空 tombstone。 用户明确表示这个字段没有值，如果还留着删除记录，下次重建会按删除记录再扣一遍，语义就乱了。
  • tombstone 的 key 必须稳定。 类目属性优先用 propertyDetailId，没有才退回名称；来源属性用 source:<name>:<value> 这种稳定 id。用展示文本当 key，改个标签就失配。

这里有一个更一般的结论：可撤销不等于「删掉当前值」，而是「把删除作为输入记录下来」。 只要数据是派生的，删除就必须参与下一次派生。

五、自动写入：克制比覆盖更重要

除了显式映射的字段，来源页面上还有大量未映射的结构化属性。一开始的想法很自然：既然有值，就都写成自定义属性。

实际做下来，必须加一长串排除条件：

  • 品牌、成色、原产国等已经有专门目标字段的；
  • 数量、零件号家族等会与目标字段重复的；
  • 车型、适配信息等走专门结构的；
  • 价格、库存、物流等交易字段；
  • 营销词、空值、含汉字的项；
  • 只接受结构化来源（item specifics / product details），不抓正文里的任意文本。

即使这样，仍然会有同名不同值的情况。处理方式不是覆盖，而是编号：

这样它既能被 tombstone 精确删除，也能在页面上保留原始标签：

sourceLabel 只存在数据层，不撑进复核表格；表格里显示的是编号后的名称。这样用户看到的是可区分的行，追溯时又能回到原页面的写法。

自动写入还有一个刻意的限制：只追加，不修改已有行。 类目模板已经生成的同名属性，不会被自动写入覆盖或合并。这是保守的选择——自动写入写错一条，用户要删一次；如果它还会改模板行，问题会变成「模板和来源打架」，更难排查。

六、完成门禁：空值和「未映射」不是一回事

预填做得再多，也不能保证每个必填项都有值。完成复核时的门禁分两层：

第一层是空值。 所有属性行的值为空都阻止完成，不管它是模板必填、模板非必填还是自定义属性。这条看起来严格，但它把「没填」和「填了空字符串」统一成了同一种状态。

第二层是长度。 自定义属性名称上限 100，值上限 2000。超长在提交前拦住，而不是等接口报错。

非必填的模板属性允许删除，但需要二次确认；必填属性不允许删除。删除记录进入 removedCategoryAttributes，类目模板重算时不会恢复。

这里要区分两个概念：

  • 发布完整度：还差哪些字段，用于提示；
  • 完成阻断：哪些问题不允许点「完成」，用于门禁。

两者分开计算。把提示当成阻断，会让用户在小问题上无法收尾；把阻断当成提示，会把不完整的数据送进下一步。

七、规则版本化：让「为什么预填成这个值」可复盘

预填规则会变。改了标签匹配、改了合并策略、改了排除词表，历史复核怎么解释？

做法是给规则包一个显式版本：

规则结果携带 ruleVersion，复核保存时持久化。旧复核保留旧版本，不回填；新复核写入当前版本。这样至少能回答「这条预填是按哪版规则生成的」。

版本号本身也承载信息：v1.5-oe-merge 表示这一版引入了多源合并。版本号不是给机器看的自增数字，是给人看的变更摘要。

配套的验证有两层：

  1. 脱敏样例：docs/samples/rules/*.json 固定输入与期望输出，断言版本、合并后的值、分组存在、必须省略的旧字段。
  2. 真实函数执行：check-input-layer.mjs 直接 import 真实的 applyEbayFieldRules / applyAmazonFieldRules，跑合并并断言版本与输出。

第二层很重要。只断言 JSON 结构，可能测的是「fixture 长得对」，而不是「规则真的这么跑」。直接执行真实函数，才能覆盖归一化、分组、去重这些实现细节。

这两层都挂在 verify:ready 里，规则变更不跑样例就过不了门禁。

八、任务默认值：快照和「上次填过什么」要分开

预填还有一类值不是来自来源页面，而是来自任务级默认值。这里有两份数据，职责完全不同：

存储 写入时机 用途
import_task_settings 任务创建时写一次，之后只读 该任务内所有商品复核的默认值快照
migration_task_defaults 上次成功创建任务时覆盖 新建任务表单的回显值

快照用 INSERT OR IGNORE，不可覆写；回显值用 UPSERT，可以覆盖。这样即使用户后来改了默认值，已经创建的任务仍按创建时的快照执行——任务内的行为不能被之后的表单修改悄悄改写。

应用到复核时，默认值只填空字段：

来源价优先，默认值不覆盖任何已有值。每写一项，把字段名加入 taskDefaultFields，UI 上标记「任务默认」。用户手动改过之后，该字段从标记里移除。

品牌兜底还有一个额外条件：只处理「缺失」，不处理「待确认」。待确认需要等已认证品牌列表加载后再判定，不能提前写一个看似确定的品牌。

解析层面也很克制：normalizeMigrationTaskSettings 对任何非法值返回 null，不做静默修复。价格必须大于 0 且最多两位小数。默认值写错会影响一整批任务，宁可让用户重填，也不要猜。

九、边界

  • 旧复核没有 oeGroups。 历史 review_json 仍走单个输入框，没有回填或迁移；分组只对新生成/重新识别的复核生效。
  • 自动写入词表还没用新样本校准。 当前排除词按已知示例实现，换一批页面可能需要调整，调整时应随规则版本一起升。
  • 自动写入只追加，不合并同名模板属性。 是否接受这个行为还需要产品确认。
  • replacementNo 没有长度上限。 平台字段长度未知，尚未补校验。
  • 规则样例的 eBay 部分只做结构自检。 真实执行由 check-input-layer.mjs 覆盖，两者不能互相替代。
  • 这些是「未验证/未做」，不是「已决定不做」。

总结

预填的产物不是一个值，而是四样东西：

  1. 值：归一化、去重、按来源组合并后的结果；
  2. 来源：每个号来自哪个标签、哪一组；
  3. 可撤销记录：用户删过什么，下一次派生要扣掉什么；
  4. 规则版本：这个结果按哪版规则生成。

只做第一样，得到的是一个「看起来填好了」的表单；四样都做，才得到一条能解释、能修改、能复盘的数据管线。
