从 URL 计数到商品实例：一次数据模型重做

旧模型里，一条 URL 对应一个商品，抓取失败就造一个占位商品。变体一展开，计数、归属和后续守卫全部失真。这一轮把「平台身份」和「任务内实例」拆成两层，失败只留在 URL 行。这篇讲模型为什么必须重做，以及迁移为什么选择一次性重置。

一、旧模型的三个失真

最初的模型很直观：一行输入 URL，一行商品；抓取成功就更新商品，失败就写一条失败商品占位。

在「一条链接 = 一个商品」的前提下，这个模型没有问题。但真实页面不是这样：

  1. 一次抓取可能展开多个变体。 一条父链接可能产出 N 个子规格，URL 数和商品数不再一一对应。
  2. 失败不是商品。 抓取失败、页面被拦截、链接失效，这些是输入层的事实，不应该在商品列表里占一行。
  3. 同一个平台商品可能被多个输入引用。 不同任务、同一任务的不同行，都可能有同一个商品身份；状态归属和后续守卫需要知道「这个实例属于哪一行输入」。

继续在旧模型上打补丁，会出现典型的症状：

  • 进度环按 URL 数算，商品列表按商品数算，两个数字对不上；
  • 失败占位混在商品列表里，用户以为「识别到了但有问题」；
  • 重试时不知道该重建哪个输入的商品；
  • 同一个商品在 A 任务已提交，B 任务又抓一遍。

这些问题不是计数 bug，是模型把三件不同的事压成了一行。

二、拆成三层

新模型把数据分成三层：

关系是：

三层各回答一个问题：

层 回答的问题
输入层 这条链接抓到了没有？失败原因是什么？
归属层 这次抓取是为了满足哪些输入行？
实例层 产生了哪些可处理/可提交的商品实例？

原来需要在一行里同时回答的三个问题，现在分开存。

三、两个键，职责不同

模型里有两个容易混淆的键。

source_key 是平台身份：

它回答「这是平台上的哪个商品」。Amazon 的 ASIN 在生成时统一大写，避免 B01ABC 和 b01abc 被当成两个商品。这个键用于跨任务判断「同一个商品是不是已经处理过」。

record_key 是任务内实例：

它回答「这是哪个任务、哪一行输入产生的实例」。同一个平台商品出现在两个任务里，会有两个 record_key，但共享一个 source_key。

为什么不能合成一个键？

  • 同一个商品在不同任务里需要独立的生命周期：A 任务已提交，不代表 B 任务可以跳过；
  • 同一个商品在同一任务的不同输入行下，也需要独立结算：放弃一行，不应该影响另一行；
  • 平台身份用于跨任务守卫，实例键用于任务内状态。

还有一条硬约束：task_id 永远不被 UPSERT 改写。 一个实例属于哪个任务，是创建时确定的，重抓只能更新内容，不能把它搬到另一个任务里。

四、失败不是商品

新模型最直接的收益，是把失败从商品层拿掉。

输入失败只写 import_task_urls：

采集期展开的派生链接失败，也写一条 origin = discovered、fetch_status = failed 的 URL 行。它不会创建一个 recognizing: 或 failed: 的商品占位。

随之而来的是完成门闩的变化：

任务完成需要同时满足：

  1. 抓取队列已排空；
  2. 所有可处理 URL 行都是 ok / skipped / abandoned，pending / failed 一律阻止；
  3. 所有已物化实例都是 draft / abandoned。

注意第二条对派生链接同样生效。衍生失败也阻止完成，必须重试成功并处理商品，或者明确放弃所属输入。这样「有失败但任务显示完成」的情况就不会出现。

旧模型里失败会造占位商品，所以「商品列表为空」和「全部失败」看起来差不多。新模型里，失败只在 URL 行，商品列表只包含真正物化出来的实例，两个概念不再混淆。

五、归属层：一次抓取，多个主人

import_task_instance_owners 是这次模型重做里最不显眼、但最关键的一张表：

它记录「这次抓取要满足哪些输入行」。物化时，同一份商品数据会为每个 owner 生成一个实例、发一个事件：

这样可以处理几种真实情况：

  • 不同写法、同一商品。 入队时按 source_key 合并成一次抓取，但每个输入行都登记 owner，最后各自得到实例。
  • 父链接展开变体。 派生链接继承根抓取的全部 owner，relation 改为 discovered。
  • 重试。 只重建「还没有实例、且输入未放弃」的 owner，不会重复物化。

放弃和提交也要按 owner 结算：

  • abandonInput(taskId, lineNo) 只结算该输入名下的非 draft、非 generating 实例；
  • 同一任务内先提交成功的实例获胜，同 source_key 的 ready / needs_action 兄弟实例自动 abandoned；
  • generating 不自动放弃，因为平台结果还未知，放弃会把「可能成功」写成「失败」；
  • 跨任务只把其他任务里尚未处理的 URL 行标 skipped，不搬移、不改写已存在的实例。

这几条规则的共同点是：结算的粒度是实例，不是「商品」这个抽象概念。

六、UPSERT 的边界

重抓同一个商品时，落库用的是 UPSERT。但更新列表是刻意收窄的：

原因很直接：

  • task_id 是归属，不能因为重抓就换任务；
  • workflow_status 是用户/流程状态，重抓不能把它打回初始态；
  • review_json 是人工复核层，来源证据更新不应该覆盖人的编辑。

状态只能通过显式的 updateProductStatus 改写，而且 abandoned 分支还禁止覆盖 draft。这让「重抓」和「状态变更」成为两个独立动作，不会互相踩。

七、迁移：为什么这次选择一次性重置

模型改到这个程度，旧数据无法平滑映射：旧的 record_key 是按商品生成的，新的是按「任务 + 输入 + 商品」生成的；旧的失败占位在新模型里没有对应物。

v8 阶段先做了一次带备份的迁移：

  • 迁移前用 VACUUM INTO 写一份 .bak-v7；
  • 备份失败就抛 IMPORT_DB_BACKUP_FAILED，中止迁移，原库不动。

这个原则是对的：破坏性迁移在备份不成立时不应该继续。

但到 v10，项目仍处于开发基线阶段，历史数据没有保留价值，迁移/回填代码本身成了负担。于是改成一次性重置：

打开数据库时：

  1. 版本 < 10（或没有版本但存在旧表）→ 删已知表、清同目录 captures/、重建；
  2. 版本 >= 10 → 保留数据；
  3. 写入当前版本；
  4. 修复中断任务。

关键在 LEGACY_RESET_BELOW 是固定值，不跟随 SCHEMA_VERSION。否则以后每次升版本，都会把用户数据当成「旧版本」重置一遍。

这条策略的边界写进了 schema 文档：这不是通用策略，后续 schema 变更必须写显式迁移，不得再提高这个阈值。 开发期可以销毁重来，发布后不行。

重置会连 captures/ 一起清掉，但只清同目录，不影响其他商家。清库也会丢本地已提交状态的守卫，所以文档里明确提示：清库后第一次提交前，先看目标平台的已提交列表。

八、验证与遗留

模型重做的验证主要靠离线回归：

  • 首商品成功 + 六个衍生失败：断言失败只落 URL 行、任务仍停在 processing；
  • 旧完成记录纠正：读取快照时把误标完成的任务拉回待处理；
  • 重试入口与放弃收尾：失败输入被放弃后，URL 行结算，任务才能完成；
  • 实例计数：一次抓取多个 owner 时，实例数按 owner 展开，不重复。

遗留项也明确记着：

  • 旧客户端兼容用的 failed:{taskId}:{lineNo} 过滤键还在，但不再创建对应行；
  • 部分类型注释和技能文档仍使用旧口径（例如 handleProductEvent），当前实现已经改名为 applyEvent 的 product 分支；
  • 这一轮是离线回归和 verify:ready，没有用真实 Electron 应用把新模型完整跑一遍。

九、总结

这次重做真正改的不是表结构，而是三个概念的归属：

  1. 身份：平台商品是什么（source_key）；
  2. 实例：这个任务、这行输入产生的商品是什么（record_key）；
  3. 失败：链接层的事实，不是商品（URL 行）。

三者分开之后，计数、重试、放弃、跨任务守卫才各有依据。至于迁移，判断标准不是「技术上能不能迁移」，而是「这批数据是否已经承诺给用户」：开发期可以销毁重建，发布后必须显式迁移。
