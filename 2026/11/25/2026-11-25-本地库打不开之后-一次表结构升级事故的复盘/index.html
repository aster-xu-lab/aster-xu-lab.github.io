本地库打不开之后：一次表结构升级事故的复盘

一次版本升级之后，应用能启动，窗口也在，但所有导入相关功能都没了：顶部显示「已登录」，任何操作都提示「请先登录」。卸载重装也没用——因为用户数据不在安装目录里。

最后在错误框里找到一行：IMPORT_IPC_INIT_FAILED: no such column: capture_rel_dir。这篇复盘讲三件事：旧库为什么会在升级后少一列，这一列为什么能让整块功能消失，以及最后怎么把「结构」变成一个可收敛的状态。

一、现象：不是功能坏了，是注册没跑完

第一反应通常是「某个查询写错了」。但现场有三条互相矛盾的线索：

  • 顶部商家芯片显示「已登录」；
  • 所有导入、任务、复核操作都提示「请先登录商家端」；
  • 删除应用、重新下载安装包，问题依旧。

第三条先排除了安装包的问题：桌面应用的用户数据在 userData 目录，卸载程序不会删它。旧库一直在，所以每次启动都在同一个地方失败。

真正的原因在第二条：异常发生在主进程注册 IPC 的阶段，而不是某个按钮的处理函数里。注册循环在第一处抛错就中断了，后面的三十二条 importer:* 通道一条都没注册。渲染层调用 getMerchantContext() 失败，被 catch 吞掉，merchantId 保持空字符串；界面据此判断「没有本地范围」，于是所有入口统一显示未登录。

一条 SQL 报错的最终形态，是「用户没登录」。 这个映射关系错得很彻底：真正的原因是本地库读不了，和登录状态没有关系。

二、为什么升级后才出现

根因可以压缩成两行代码：

CREATE TABLE IF NOT EXISTS 对已经存在的表是 no-op。它不会比对列，也不会补列。所以只要版本升级时在 DDL 里新增一列，老机器上的库永远拿不到它，第一次查询该列就会得到 no such column。

也就是说，v10 基线之后任何结构变化都没有迁移路径。这次事故只是第一个撞上来的列。

还有一层顺序问题：旧数据的迁移函数在仓储打开之前执行。它把旧库搬到商家目录后，直接 SELECT ... capture_rel_dir 改写路径——它假设新列已经存在。而真正会做结构升级的代码在更后面。先查新列，后升级结构，顺序反了。

三、三段各自正确的代码

把链路摊开，每一段单看都没问题：

环节 它假设什么 现实
旧库迁移 新列已经存在 旧库是更早的结构
仓储初始化 版本 < 10 才需要重建 版本 10 的库也可能缺列
IPC 注册 商家范围恢复不会失败 迁移失败会直接抛异常
渲染层 拿不到商家上下文 = 未登录 是本地库打不开

问题不在某一段，而在它们之间的契约：上游假设下游已经完成结构升级，下游又假设上游不会失败。任何一处例外都会向下游传播，最后被 UI 解释成一句最常见的提示。

这类事故的修复重点，不是给某个查询加个 try/catch，而是回答两个问题：

  1. 打开一个本地库时，如何判断它是不是当前结构？
  2. 判断与升级都失败时，应用应该怎么继续？

四、业界怎么做

查了一圈同类产品，结论比想象中保守：

做法 代表 适用
迁移失败拒绝启动 Room、Realm、Signal、Chrome/Firefox 持久业务数据
破坏性重建 Room fallbackToDestructiveMigration 缓存 / 可重建数据，且要显式 opt-in
只加列（additive-only） 多数本地库 向前兼容，旧版本代码不用改
逐版本迁移 Rails、Flyway、Room 迁移链 数据语义需要按序转换
更高版本门禁 Chrome/Firefox profile 防止旧程序改写新数据

两个容易被忽略的点：

  • 「程序可用」是对外壳的要求，不是对持久数据的授权。 外壳永远能起来；数据要么迁移成功，要么原样保留并明确告知，不能静默清空。
  • 加列本身在 SQLite 里有硬限制：不能加主键/唯一列，NOT NULL 必须带非空默认值。真到删列、改约束，官方给的是十二步重建表。

落到这次改造，目标就明确了：结构必须能收敛；收敛不了时，保留文件、保证应用可用、把原因告诉用户。

五、改造：打开时对齐，而不是相信版本号

新的做法是把「结构」当成一个可以反复计算的状态：唯一一份 canonical DDL，打开时把库对齐到它。

graph TD
  A["打开本地库"] --> B{"能读到 sqlite_master?"}
  B -->|否| Q["隔离为 .corrupt-(时间戳)<br/>新建空库 + 提示"]
  B -->|是| C{"版本 > 当前版本?"}
  C -->|是| R["拒绝打开<br/>文件原样保留 + 提示"]
  C -->|否| D{"版本 < 10 且缺实例模型两表?"}
  D -->|是| S["备份 .bak<br/>重建空库 + 提示"]
  D -->|否| E["结构对齐<br/>补表 / 补索引 / 按列重建"]

几个关键决定：

比对的是建表语句，不是版本号。 从 sqlite_master 读出每张表实际存储的 CREATE TABLE 文本，归一化空白后与 canonical DDL 比较。这样 UNIQUE、CHECK、索引变化也能识别——只比列名会漏掉约束。

漂移的表按列交集重建。 旧表重命名，按 canonical 建新表，然后用两边都有的列做 INSERT ... SELECT：

行保留，未知的旧列被丢弃，缺失的列按声明恢复。COALESCE 处理「旧表允许 NULL、新表 NOT NULL」的情况；整表重建后自增 id 的最大值会把 sqlite_sequence 带上去，后续插入不会撞号。

重置只针对真正的旧模型。 不能只看版本号——版本标记可能丢失。判定条件是「是否缺实例模型的两张表」，缺了才说明是 pre-v10 的结构；只是丢了标记、但结构已经是新的库，只补版本号，不重建。

更高版本不碰。 如果库的版本高于当前程序，说明它由更新的客户端写入。这时对齐等于降级，会丢掉未来列。正确做法是拒绝打开、文件原样保留，让用户去装对应版本。

失败也要分层。 读不了的文件隔离后新建；能读但不能升级的（比如约束冲突）也隔离，而不是让每次启动都失败。隔离前先移 -wal/-shm/-journal，再移主库——Windows 上连接没关就改名会 EBUSY。

备份用快照，不用裸拷贝。 VACUUM INTO 生成一致的 .bak，包含已提交的 WAL 帧；checkpoint 失败时直接拷贝主文件可能少数据。

最后一层是失败隔离：启动恢复商家范围失败，只记录一条降级提示，不再中断剩余通道的注册。渲染层也不再用商家上下文推断「本地库可用」——那两者在故障时本来就会分叉。

六、审查之后改掉的细节

第一版改完，离线用例全过。但让一个审查视角专门找反例后，发现了四个会真正丢数据的边界：

  1. 丢了 schema_meta 的库被判成旧库。 版本号返回 0，结构其实已经是新的，结果整库被重置。修正为按实例模型判定。
  2. 更高版本的库被「对齐」回当前版本。 版本号从 99 改回 11，未来列被丢弃。修正为拒绝打开。
  3. 重建违反 NOT NULL 时直接抛错。 旧表某列允许 NULL，新表不允许，整库每次启动都失败。修正为 COALESCE，兜不住时走隔离。
  4. 隔离只移了主文件。 残留的 WAL 会跟着新库被重放。修正为先移 sidecar 再移主库。

还有一条是审查同时否掉了过度设计：一开始想保留多份带时间戳的备份目录。后来确认本地任务与采集产物都可以重新生成，单槽 .bak 加重命名隔离已经够用；备份目录带来的磁盘增长、清理策略和隐私问题，收益不成比例。取舍的依据是数据能不能重建，不是备份看起来多完整。

七、验证：按「起始形态」造夹具

这次没有只测「从空库开始」。新增的离线校验按库的起始形态造夹具，共十七组：

  • 空文件、损坏文件；
  • v10 缺一列、多一列、缺一张表；
  • 自增表重建（检查 id 与序列）；
  • 丢失版本标记但结构完整；
  • 更高版本（必须拒绝且不改文件）；
  • 重建会违反 NOT NULL；
  • 约束冲突导致无法升级（必须隔离）；
  • 旧库迁移的两种形态（pre-v10 与 v10 缺列）。

另外用真实应用跑了七组构造的 userData：正常库、缺列库、旧库迁移、损坏文件、更高版本、丢版本标记。每组都在退出后直接读 SQLite 和备份文件核对，而不只看界面。

已经验证的：结构收敛、行保留、备份与隔离文件、未来版本不被改写、应用在所有故障形态下都能启动。

没有验证的：真实安装包从旧版本升级的完整路径、Windows 上的坏库恢复、以及登录后提示的补发。这三项单独列在测试报告的「未验证」里，不用离线通过去替代。

八、几个可以带走的判断

  • CREATE TABLE IF NOT EXISTS 不是迁移。它只负责「表不存在时建表」，不负责「表存在时对齐」。
  • 版本号可以帮你判断，但不能替你决定删除。丢失标记的库和真正的旧库，要用结构特征区分。
  • 失败时的第一优先级不是「让开」，而是「别丢」；第二优先级才是「能开」。两者都要，但顺序不能反。
  • 单个组件的异常，不要让它沿着调用链变成另一种语义。SQL 错误不该显示成「未登录」。

总结

  1. 本地库升级的核心不是写一条 ALTER，而是让「任意起始结构」都有确定的收敛路径。
  2. 判断是否重置，依据结构特征而不是单一版本号；判断是否降级，依据版本方向而不是「能不能打开」。
  3. 应用可用与数据安全可以同时满足：读不了就隔离、保留文件、说清原因；能做就重建、保留行、留好备份。
