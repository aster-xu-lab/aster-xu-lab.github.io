包内包外：桌面应用不该从 PATH 找自己的工具

开发时一切正常，打包后行为却变了——这类问题通常不在业务代码里，而在「运行时到底加载了哪个文件」。这轮修了两个边界：发布日志被打进 app.asar，以及打包版会从 cwd / PATH 找到用户自己装的同名 CLI。它们都不是功能 bug，而是包内包外的信任边界。

一、两个真实事故

第一个：不该进包的东西进了包。

发布运维脚本会在仓库根目录生成日志和临时产物。electron-builder 的默认收集规则把其中一部分打进了 app.asar，结果是安装包变大，而且这些日志本来就不应该分发给用户。

第二个：打包版从 PATH 找到了别的工具。

应用依赖一个随包分发的 CLI。旧的解析顺序是：

  1. process.resourcesPath/browser4/bin/...
  2. process.cwd()/resources/browser4/bin/...
  3. 裸命令 browser4-cli（走 PATH）

开发态下，这三条都能工作；打包态下，如果第一条因为路径或平台问题没命中，应用会去 cwd 或 PATH 找。用户机器上可能装着另一个版本，甚至另一个同名程序。应用启动的是谁，变成了环境决定的事。

二、asar 不是「源码压缩包」

app.asar 是 Electron 应用的资源归档。它不需要包含仓库里的所有文件，只应该包含运行时真正需要的内容。

最后一条容易忽略：Browser4 运行时不走 asar，而是走 extraResources。如果两边都收，安装包里会有两份，一份在 app.asar 里、一份在 Resources/browser4 下，体积和版本一致性都会出问题。

asarUnpack 和 extraResources 解决的不是同一个问题：

机制 用途
asarUnpack 文件仍属于应用资源，但需要以真实文件形式存在（原生模块、可执行文件）
extraResources 完全放在 app.asar 之外，按目录结构放到 Resources/

Browser4 需要被外部进程执行，所以走 extraResources，并且从 asar 的收集范围里显式排除。

这类问题的麻烦之处是它不报错：多打进去几个文件，应用照常启动，只有安装包大小和分发内容在悄悄变化。

三、可执行文件的解析顺序

修复后的解析规则是：

三条边界：

  1. 打包态只认 process.resourcesPath。 找不到就返回预期路径，让后续启动失败并报错，而不是去别处碰运气。
  2. cwd 回退只给开发态。 process.defaultApp 为真表示当前是 electron-vite dev 这类开发启动，不是安装包。
  3. PATH 回退彻底移除。 产品行为不能依赖用户环境里恰好有同名命令。

仍然保留一个显式覆盖入口：BROWSER4_CLI_PATH 环境变量。这是运维/诊断用的，不是自动回退——显式配置和「碰巧找到」是两回事。

还有一个相关的打包约束：如果包内 Browser4 的平台/架构和当前进程不匹配，直接抛 BROWSER4_BUNDLE_PLATFORM_MISMATCH，而不是尝试运行一个错误的二进制。macOS 和 Windows 必须在各自平台构建，不能交叉出包。

四、为什么这类问题容易漏

三个原因叠加：

  1. 开发态永远能跑。 cwd 和 PATH 都能命中，开发者看不到差异。
  2. 打包后只在特定机器复现。 干净机器上没有同名 CLI，问题不出现；开发者的机器上恰好有，问题也不出现；只有「装了另一个版本」的机器才会露馅。
  3. asar 污染没有功能症状。 包变大、内容变多，但应用能用，没人会主动去查。

所以验证不能只看「应用能不能启动」，要看「包内到底有什么、运行时到底解析到哪个路径」。

五、验证方式

打包验证按平台分发，至少覆盖三件事：

  • asar 内容：排除项是否生效，安装包大小是否回到预期量级；
  • extraResources：Browser4 目录、CLI、GC agent jar 是否在 Resources/browser4 下；
  • 解析路径：打包态启动后，日志里实际使用的 CLI 路径是否落在 Resources/browser4/bin。

这些检查放在 verify:package 里，而不是靠人工打开安装包看。verify:ready 负责源码层的类型检查、lint 和离线回归；verify:package 负责产物层。两者不能互相替代。

六、边界

  • Windows Authenticode 本期未做。 未签名安装包可能触发 SmartScreen 警告，这和资源解析是两个问题。
  • 构建必须分平台。 macOS arm64 与 Windows x64 各在对应平台出包，跨平台产物不做兼容承诺。
  • BROWSER4_CLI_PATH 是显式覆盖。 它不是自动回退路径，误配会让应用启动失败，而不是静默换一个 CLI。
  • 这一轮没有重新出包和装机验证。 结论来自代码、打包配置和既有产物检查；新安装包的真实行为仍需在目标平台确认。

七、总结

桌面应用的运行时依赖只有两种合法来源：

  1. 随包分发：路径固定、版本固定、平台匹配；
  2. 显式配置：用户或运维明确指定，配置错误就失败。

cwd 和 PATH 不属于这两种。它们能让开发更顺，但不能成为产品行为的一部分。应用应该知道自己从哪里启动自己的工具，而不是碰巧找到谁就用谁。
