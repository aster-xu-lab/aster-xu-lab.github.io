拆掉 2800 行之后：没有测试框架时怎么验证行为没变

一个 2829 行的仓储类、一个 3044 行的采集服务、一个 1818 行的复核组件。项目没有测试框架，只有一组验证脚本。这篇讲我们怎么把这三个文件拆到千行以内，以及怎么验证拆分前后的关键行为。每一轮都有可复现的代码对照和回归探针。

一、先决定「不做什么」

这次重构的输入很明确：文件太大、职责太杂、改一处要读半天。但「拆」有很多种做法，我们先把边界钉死：

  • 不重写。 只搬方法体，不顺手改逻辑、不改命名、不优化。
  • 不改公开调用面。 调用方、验证脚本里的桩点都保持原样。
  • 不追求「更优雅」。 抽出来的模块长什么样是次要的，等价才是第一目标。
  • 不碰没有缺陷对应的文件。 App.vue 还有 2437 行，但审查清单里它只对应「可选」，于是明确不做。

最后的结果：

文件 拆分前 拆分后 拆出
import-repository.ts 2829 行 939 行 9 个域模块
browser4-service.ts 3044 行 1043 行 8 个模块
ReviewFieldsColumn.vue 1818 行 117 行 7 个分节组件
import-ipc.ts 1016 行 606 行 5 个模块

二、按域拆，不按行拆

最容易犯的错是「前 500 行抽一个 utils，后 500 行再抽一个 helpers」。这样拆完，模块之间仍然互相调用，只是把一个大文件变成了几个大文件。

每个模块用工厂函数注入 DatabaseSync 和它真正需要的回调，不持有服务类引用：

仓储类最后只保留四类东西：

  1. schema 与版本重置；
  2. 启动自愈与中断终结；
  3. 名称分配、snapshot() 聚合；
  4. 每个域的薄转发。

薄转发不是多余的。验证脚本会直接调用并桩掉一部分实例方法，比如 persistRobotCheckDiagnostic、ensureRuntime、runCli。如果把这些方法从类上删掉，脚本会先坏，而不是代码先坏。

三、怎么缩小差异排查范围

没有单元测试，就不能只靠「我读了一遍，应该一样」。每一轮抽取后，我们做的是去空白逐字符对拍：

  1. 从改前基线里按方法签名切出正文；
  2. 从新模块里切出对应正文；
  3. 去掉空白后逐字符比较；
  4. 把允许的差异列成固定清单，逐条解释。

允许的差异只有三类：

  • this.database → database；
  • 跨方法调用去掉 this.、注入回调改名；
  • Prettier 去掉冗余的联合类型前导 |。

四、脚本会替你发现「等价」的漏洞

去空白对拍能快速找出方法体的差异，也可能掩盖字符串字面量中的空格变化。调用关系和运行结果要靠回归探针检查。

抽 browser4-service 时，check-import-flow.mjs 用 crashService.detectPlatform = () => { throw PROBE_BOOM } 做桩。抽取脚本把两处 this.detectPlatform( 直连成了模块内函数，绕过了桩，结果崩溃边界用例失败：

修复方式不是改测试，而是把 detectPlatform 作为依赖注入，保住原来的桩点。

同类问题还出现过两次：

  • 抽取脚本按旧索引切片，误删了相邻的 4 个方法。靠「方法清单与 HEAD 对齐、括号平衡为 0、typecheck 通过」发现并补回。
  • 对服务文件执行了 prettier --write，产生上千行格式噪音。最后从改前基线整体回滚，只格式化新模块。

这些都不是理论上的风险，是实际发生的返工。验证脚本本身就是契约的一部分，重构时不能把它当成可以随便改的附属品。

五、拆到什么程度停

import-repository 拆到 939 行时，剩下的部分是 DDL、版本重置、启动自愈、名称分配、snapshot() 聚合和各域转发。这些要么是跨域的入口，要么是生命周期逻辑，再拆只会制造回边。

我们给这次拆分定的停止条件是：类内没有待拆的跨域模块。不是「行数降到多少」，也不是「看起来顺眼」。

App.vue 的 2437 行同理：审查认为它没有对应缺陷，拆它属于「可选」，于是不做。重构的边界应该由风险决定，而不是由行数决定。

六、验证到了哪一步

已经做到的：

  • 每一轮方法体逐字符对拍，差异逐条解释；
  • typecheck、lint:errors、prettier、verify:ready 全部通过；
  • 验证脚本的桩点保持可用，崩溃边界、导入流程、输入层用例没有退化。

没有做到的：

  • 抽出的方法没有独立单测，部分分支只被现有脚本间接覆盖；
  • 没有跑真实采集、没有出包、没有做 UI 手测；
  • 对拍与现有探针覆盖了已列出的改动和路径，未覆盖的调用组合仍需按实际场景验证。

总结

  1. 没有测试框架时，可以先限定允许的代码差异，再用可复现的探针验证关键行为。
  2. 按域拆、从叶子拆、保留薄转发；验证脚本的桩点就是公开契约。
  3. 停止条件应该是「没有跨域模块可拆」，不是「行数好看」。
