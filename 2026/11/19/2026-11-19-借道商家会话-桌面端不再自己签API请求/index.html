借道商家会话：桌面端不再自己签 API 请求

桌面端要读商家后台的目录、上传图片、提交草稿。最早我们走 OpenAPI 签名通道；这一版改成在嵌入式商家页里，用页面自己的会话发请求。变化不只是「少维护一套签名」，而是把会话变成了一个有代次、有作用域、有失效时机的运行时对象。这篇讲它怎么工作，以及哪些边界仍然没被证明。

一、签名通道的问题不在签名

最初的方案很自然：桌面端作为 OpenAPI 客户端，自己持有凭据、自己签名，直接调平台接口。读目录是一条链路，提交草稿是另一条链路，和浏览器里的商家后台互不相干。

问题出在「互不相干」。同一份数据，浏览器里走的是商家会话，桌面端走的是 OpenAPI 客户端；两套身份、两套权限、两套错误模型。目录的可见范围、字段的枚举、草稿的归属校验，只要有一边变了，另一边就可能悄悄对不上。签名本身不是难点，难的是让两条链路长期保持同一个语义。

所以这次的方向反过来：桌面端不再自己证明「我是谁」，而是借用已经登录的商家页面，让请求以页面自己的身份发出去。

二、请求在页面里发，token 不出页面

WebContentsView 里加载的就是商家站点。页面登录后，ACCESS_TOKEN、tenantId、visitTenantId 都在它自己的 localStorage 里。我们要做的，是把一段脚本送进页面执行：

有三条边界是刻意守住的：

  1. 主进程不读 token。 它只接收 { status, text }，或者一个错误标记。token 从页面读、在页面用，不跨进程。
  2. 身份头在页面里拼。 商家、店铺、租户这些头部字段和页面当前会话保持一致，不依赖主进程缓存。
  3. 先校验 origin。 脚本执行前确认页面还在商家域名下，避免在错误的页面上发起请求。

这和之前那篇《把商家后台嵌进桌面端》里的登录判定守的是同一条边界：token 不跨进程。 那篇只判断「登录没有」，不读值；这篇要在登录之后真正用会话，读值也只在页面内发生。

代价也很直接：

  • 页面必须活着、加载完、且停在商家域名下。页面导航走或视图销毁，在途请求就应当失败。
  • 返回值只能是可序列化的文本。响应体、上传文件都要跨一次进程边界。
  • 文件上传得用 base64 把字节送进页面，再由页面构造 FormData。内存占用会翻倍，所以图片按 8 个一批上传，每批 120 秒超时，并核对返回的 URL 数量。

一旦变化，页面内的 AbortController 会中断在途请求。主进程侧另有一个代次（generation）计数器：每次会话失效就加一，并终止当前代次的所有请求。每个关键 await（上传、提交）之后都要重新确认代次和 webContents 没变，否则丢掉结果并返回 MERCHANT_SESSION_CHANGED。

这里有个容易被写错的细节：token 值变化不等于会话变化。

商家前端在遇到 401 时会自己调用刷新接口，重写 ACCESS_TOKEN。如果守卫把「token 变了」一律当成切账号，一次正常的刷新就会把已经成功的提交标成「结果未知」。我们最后只认三种真正的会话变化：

  • token 消失（退出登录）；
  • 商家 / 店铺身份变化；
  • 租户或访问租户变化。

同身份、同租户下的 token 轮换，放行。

四、迟到结果比失败更危险

异步请求最怕的不是报错，而是结果回来得太晚。用户已经切了商家，旧的读请求才返回；或者已经退出登录，旧的写请求才成功。此时如果直接采用结果，数据会落到错误的作用域里。

我们的处理分两层：

  1. 页面内的守卫在会话变化时 abort，尽量让请求不要完成。
  2. 主进程在 await 之后再次核对代次；即使页面已经把结果送回来，只要代次变了，也按 SESSION_CHANGED 丢弃。

第二层是兜底。abort 是尽力而为，网络请求可能已经到达服务端，响应也可能已经在路上。只有主进程的代次检查能保证「迟到的结果不会被采用」。

失效的触发点也列清楚，避免漏掉：

  • 主 frame 的整页导航（isInPlace 的页内跳转不算）；
  • webContents 销毁；
  • 切商家 / 切店铺 / 换登录账号；
  • 会话重建。

每次失效还会把页面里登记的请求统一 abort 掉。请求在页面里用一个随机 key 注册到 window 上的 Map，清理时连同定时器一起删掉，避免长会话里越积越多。

五、失败先分类，再决定重试

借道之后，失败可能来自四层：网络、HTTP、业务信封、会话。把它们压成一个 catch，重试策略就只能靠猜。我们的分类大致是这样：

现象 归类 处理
HTTP 401 或信封 code=401 MERCHANT_SESSION_EXPIRED 清理当前 token，触发登录探测
HTTP 403 MERCHANT_PERMISSION_DENIED 不重试，提示权限
HTTP 404 MERCHANT_ENDPOINT_NOT_FOUND 路径或版本不匹配
413 / 502 / 503 / 504 MERCHANT_BAD_RESPONSE:<status> 保留状态码，按服务端异常处理
其它 4xx / 5xx <failCode>:HTTP <status> 带业务动作前缀，便于定位
超时 MERCHANT_TIMEOUT 写操作按「结果未知」处理
信封矛盾 / 缺 data MERCHANT_BAD_RESPONSE 拒绝，不猜

业务信封的校验比 HTTP 状态更严格。成功码只认 0、200、"0"、"200"、"0000"；success 必须是布尔值，为 false 直接失败；data 字段必须存在（哪怕是 null）。早期那种「HTTP 200 就当成功」的写法，会把服务端的业务失败静默吞掉。

草稿提交还多一条：返回值必须是严格的布尔值，只有 true 才算成功。字符串 "false"、缺字段、null，全部按异常处理。原因很简单：这是写操作，误判成功的代价比误判失败大。

六、批量提交：一条会话错误毒化整批

草稿是批量提交的。一批几十条，如果第 3 条发现会话已经失效，继续把剩下的逐条打一遍，只会得到一串一模一样的失败记录，还会让用户误以为每条都单独出过问题。

所以会话级错误直接中止整批：

另一类要单独处理的是「结果未知」。上传完成、batchAdd 已发出，但客户端超时、网关返回 5xx、或者信封无法解析——这时服务端可能已经建了草稿，也可能没有。平台并不保证同一个 outGoodsNo 的幂等，客户端不能把它当成「没生成」：

同时保留本次使用的 outGoodsNo。重试时复用原标识，至少让平台侧的去重逻辑有东西可比对，而不是每次生成一个新的。

同一商品身份的并发提交也要收口：一个来源在生成中时，其它兄弟记录不再提交，也不直接放弃——因为生成中的结果同样是未知的，先等结果，或者让用户去后台核对。

Windows 更新安装走的是同一个入口。旧卸载器会把数据目录改名，任何还开着的 SQLite 连接或 Browser4 进程都会让改名失败，安装目录就可能停在半新半旧的状态。

八、验证到了哪一步

这次没有只靠「手动点一遍」。

离线回归用两套探针：

  • 一个探针把真实的 MerchantApiClient 放进 VM 页面环境执行，只替换 WebContents、origin 和网络响应。覆盖矛盾信封、false、缺字段、401/403/404/413、身份与 origin 不匹配、读正文过程中切账号、显式取消、导航、销毁、超时和 multipart 上传。
  • 另一个探针使用真实草稿服务和 SQLite，覆盖字符串 false 不标成功、上传/提交延迟期间关闭旧库、迟到成功被丢弃、未知结果落库。

实机验证在测试环境的真实商家页面上完成：

  • 10 个读接口（类目、品牌、车系、车型、批量车型、配件匹配、公共元数据、运费模板、属性字段、商家上下文）返回的 source 都是 merchant；
  • 注入真实 401 后，返回 MERCHANT_SESSION_EXPIRED，token 被移除、登录页出现，重新登录后数据恢复；
  • A → B → A 切商家，B 看不到 A 的任务和商品，回到 A 后数据恢复；
  • 一次真实草稿写入，通过主进程日志、SQLite 和商家后台草稿箱三方核对。

没有被证明的部分也要写清楚：

  • 没有等到 token 自然过期，401 是故障注入；
  • 没有验证真实 403 权限矩阵；
  • 没有在生产账号、安装包和 Windows 上验证；
  • token 轮换的守卫语义由离线探针覆盖，没有在真实刷新发生的瞬间做端到端复验；
  • 没有在真实 batchAdd 写入过程中切商家。取消只能停止客户端等待并尽力中断传输，不能撤回已经到达服务端的写入。

九、代价与边界

借道不是免费的：

  • 强耦合。 桌面端的接口行为跟着商家前端走。前端改路径、改信封、改刷新逻辑，桌面端都可能受影响。这是选择复用会话的代价，不是意外。
  • 前提是信任商家页面返回的数据。 请求在页面里发，主进程拿到的 status / text 由页面所在的环境产出。如果商家页面被注入或被篡改，返回值就不再可信，数据完整性也不再保证——我们能防的是”主进程不读 token、不把本地能力交给页面”，防不了”页面撒谎”。这和《把商家后台嵌进桌面端》的登录闸门、《LLM Key 不下渲染进程》的密钥边界是同一条信任边界的另一面：前两篇守的是”本地能力不外泄”，这一篇承认的是”业务数据的完整性依赖远程页面”。
  • 页面是运行前提。 页面没加载完、导航走了、视图销毁了，请求就应当失败。我们接受这个前提，而不是偷偷绕过它。
  • 上传要多一次编码。 base64 和分批是明确的内存换安全；如果以后要传更大的文件，需要重新设计这一层。
  • 服务端的责任没有消失。 客户端能做的只是「不采用错误结果」和「不谎报成功」。草稿归属、权限校验、重复提交的幂等，仍然必须由服务端自己保证。

总结

  1. 会话不是一个布尔值，而是「身份 + 租户 + 代次 + 失效时机」的组合；只判断登录与否，撑不起写操作。
  2. 迟到结果必须用主进程的代次检查兜底，页面里的 abort 只能算尽力而为。
  3. 借道换来的是一致性，付出的是耦合；把未验证的边界写清楚，比把它包装成「已完成」更有用。
