IPC 不该有 45 种入口：单一注册缝与运行时校验

渲染进程调主进程，四十多个通道散在 4 个文件里（整改时是 45 个），有的校验、有的不校验，有的手写 if，有的直接信类型。TypeScript 在进程边界就失效了——ipcMain.handle 收到的 unknown，编译器不会替你检查。这篇讲我们怎么把注册收成一个缝，并让脚本保证「有参数的通道一定带校验」。

一、类型系统止于进程边界

平时写主进程代码，类型很好用：

但 IPC 不是函数调用。渲染进程传过来的是结构化克隆后的普通对象，ipcMain.handle 的第二个参数在类型上可以被写成任何东西。开发期有类型提示，运行时没有任何保证：

  • preload 拼错了字段名，主进程读到 undefined；
  • 渲染进程升级后多传了一个字段，主进程静默忽略；
  • 恶意或异常帧传入 null、字符串、数组，代码在深处分不清是哪种错误。

类型只能约束「我们自己的代码怎么写」，约束不了「对面实际发来什么」。

「无参数」不是「忘了校验」，而是一个明确的分类。

三、校验形状，不校验业务

schema 用 Zod，只做三件事：

  1. 类型对不对（number / string / boolean / array）；
  2. 必填字段在不在；
  3. 值的范围是否明显非法（例如分页必须是正整数）。

业务规则不放在 schema 里。比如分页参数只校验「正整数或缺失」，越界仍由服务层 clamp：

这样 schema 不会随着业务规则变化而频繁改动，也不会因为「分页 500 条」这种可恢复的输入把请求直接拒掉。

有一个细节值得单独说：z.object 默认会 strip 未声明的键。如果 schema 漏写一个字段，它不会报错，而是悄悄消失。所以补 schema 时，我们用脚本比对了请求类型的字段集合与 z.object 的键集合，确认没有被静默丢弃的字段。

四、把规则变成脚本

人不靠谱，脚本靠谱。check-ipc-boundary.mjs 做四件事：

  1. 唯一缝：扫描 src/main，除 register.ts 外任何文件出现 ipcMain.handle( 或 ipcMain.on( 就失败。
  2. preload 与 main 通道集合一致：preload 里 ipcRenderer.invoke/send 用到的通道，必须在主进程注册；主进程注册的通道，也必须被 preload 使用。
  3. 有参数必须有 parser：preload 调用时带了参数，注册就必须是 registerValidated*，且解析函数名以 parse 开头。
  4. 无参数不允许挂 parser：反过来也要一致，避免「看起来校验了，其实参数永远为空」。

六、运行时校验不替代类型

两者解决不同问题：

手段 挡住什么 挡不住什么
TypeScript 开发期写错字段、漏传参数 运行时实际收到的数据
Zod schema 运行时形状错误、异常帧 值是否业务合法
边界脚本 新通道漏校验、通道集合不一致 解析器写得对不对

三层都要有。只靠类型，等于假设所有调用方都诚实；只靠运行时，开发体验会很差；只靠脚本，挡不住语义错误。

七、代价与边界

  • schema 与类型是两份定义。 目前靠字段集合比对控制漂移，但没有自动生成，新增字段时两边都要改。
  • 脚本是文本匹配。 它识别不了动态拼接的通道名，也识别不了通过别名调用 ipcMain 的写法；这是用简单换可维护性的取舍。
  • 不校验业务语义。 一个合法的数字仍然可能是错误的商品 ID，这属于服务层职责。
  • 没有覆盖所有 Electron 入口。 只覆盖 handle / on / invoke / send，没有涉及 ipcRenderer.sendSync 等未使用的路径。

总结

  1. 类型系统止于进程边界；跨进程的参数必须做运行时校验。
  2. 单一注册缝让规则可 grep、可脚本化；「无参数」也要显式分类。
  3. 脚本负责防止退化，schema 负责挡住异常帧，类型负责开发体验——三者不能互相替代。
