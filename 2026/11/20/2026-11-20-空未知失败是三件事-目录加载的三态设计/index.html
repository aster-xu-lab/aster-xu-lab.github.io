空、未知、失败是三件事：目录加载的三态设计

「没有数据」和「加载失败」看起来都是列表为空，但用户该做的事完全不同：一个是去后台建数据，一个是重试或重新登录。更麻烦的是第三种：我们不知道是空的，还是没加载全。 这篇讲一次目录加载的三态改造，以及为什么「空」不能被当成「用户删除了全部」。

一、一个 source: 'error' 装不下三种情况

改造前，目录接口的返回只有两种来源：

于是所有「没有拿到数据」都落进 error：

  • 请求成功，但后台确实没有模板；
  • 搜索关键词没有命中；
  • 会话失效，接口返回 401；
  • 翻页到一半失败，只拿到前 50 条；
  • 还没开始加载。

渲染层只能统一显示「加载失败，请重试」。用户按提示重试，结果还是空；或者更糟，切了账号导致会话失效，界面却让他一直点重试。

loading 仍然是独立布尔值。它和 source 不是一回事：加载中不是失败，也不该显示失败文案。

二、空不是删除

这是整条链路里最反直觉的一点。

一个目录返回空数组，可能有三种原因：

  1. 这个商家/店铺确实还没有任何数据；
  2. 当前筛选条件没有命中；
  3. 请求其实没成功，只是被折叠成了空。

只有第一种是「用户看到的真实状态」，但即使是第一种，也不能证明用户想删除之前的选择。

早先的修复走过一次弯路：目录变空时，把上次保存的默认模板和销售区域一起清掉，理由是「这些值已经不存在了」。结果用户只是切到一个新店铺，回来发现自己的默认设置没了。

现在的规则是：

  • 只有 source === 'merchant' 的目录才是权威的；
  • empty 保留上次设置，提示用户核对，不把删除写回；
  • 目录为空时拦住「创建任务」或「生成草稿」，而不是悄悄用空值继续；
  • 会话失效时中止整批提交，不要退回本地兜底值继续写。

最后一条尤其重要。原产国枚举拿不到时，代码里有一个 ISO 兜底分支；如果会话失效后继续走兜底，草稿可能带着一个用户没选过的值提交成功。失败可以重试，写错要人工清理。

三、翻页：什么叫「拿全了」

目录是分页的，每页 50 条，最多翻 20 页。判断「完整」不能只看「这一页有数据」：

这里有两个容易写错的地方。

第一，total = 0 不等于「没有数据」。 它可能表示「服务端没报总数」。所以不能一看到 0 就停止翻页，要继续读到空页为止。

第二，短页不等于结束。 如果服务端报了总数，而当前累计行数还差一截，短页只能说明中间有行被丢掉了，不能当成最后一页。

失败时的处理也要分位置：

失败位置 处理
第一页就失败 清空列表，source: 'error'
后续页失败，已有行 保留已得行，但标记不完整，不能当权威目录
达到翻页上限 保留已得行，标记不完整，提示去后台核对

早期版本在后续页失败时把前面拿到的模板也清空了，用户看到的是「什么都没有」；修复后保留已得部分，但不把残缺列表当成完整目录去裁剪默认值。

四、加载中不是失败

三态之外，还有一个独立维度：loading。

改造前，目录还在加载时，复核页会先渲染一次「加载失败」。原因是初始值就是 error，而加载完成前没人改它。用户看到一闪而过的红字，以为出了问题。

修复分两步：

  1. 渲染时先看 loading，再看 source。初始值仍然可能是 error，但加载期间不再把它渲染成失败文案；
  2. 切商家/切店铺时用代次（generation）丢弃旧响应，避免 A 的加载结果落到 B 的界面上。

loading、empty、error、merchant 四个状态，对应四种文案和四种可执行动作，不能互相顶替。

五、提交前再校验一次

界面拦住「未确认的模板」，不代表主进程也拦住了。任务页的批量提交、失败重试都可能绕过复核页的按钮。

这里的关键是「目录完整」这个前提。如果只拿到部分列表，就不能因为「没找到」而判定模板无效——那会把一个合法模板误杀。不完整时宁可不校验，也不能用残缺数据做否定判断。

同时，这个校验只拦当前条，不毒化整批。用户修正后可以重试，而不是整批失败。

六、把状态写清楚

最后整理成一张表，作为后续改动的约束：

状态 含义 能否覆盖上次设置 界面动作
loading 请求进行中 否 显示加载中，不显示失败
merchant 权威目录，可能为空也可能非空 是（按新目录校验） 正常选择
empty 请求成功但没有数据 否，保留并提示核对 引导去后台建数据或稍后重试
error 请求失败或只拿到部分 否 重试 / 重新登录

这张表的价值不在于好看，而在于以后再遇到「列表为空」时，先问一句：它到底是哪一种空？

七、验证与边界

已经验证的：

  • 目录服务对「成功但无数据」返回 empty，会话错误不再折叠成 error；
  • 翻页用例覆盖「有总数 / 无总数 / 短页 / 后续页失败 / 达到上限」；
  • 复核页在加载中不显示失败文案；
  • 主进程提交前的模板校验有独立跳过码和失败文案；
  • 相关断言进入 verify:input-layer 与 verify:ready。

没有验证的：

  • 没有在真实大数据量下跑满 20 页；
  • 没有覆盖所有目录类型，只重点改了分页与可空的那几类；
  • 会话失效时的兜底分支只做了离线用例，没有在真实服务端过期时复验。

总结

  1. empty、error、loading 是三种不同的事实，不能用同一个布尔值表达。
  2. 空目录不能证明用户想删除；只有权威目录才能覆盖上次设置。
  3. 翻页的「完整」需要明确终止条件；不完整时可以做提示，但不能拿残缺数据做否定判断。
