事件就是状态：用一个事件流驱动 UI 与数据库

采集任务有进度、有失败、有重试、有暂停。状态一多，最容易出的问题是”界面显示的和数据库里存的对不上”。我的做法是：只让一个事件流当真相，UI 和数据库都是它的投影。

一、问题：状态到底从哪来

如果界面自己算一套状态、数据库自己存一套状态，那它们迟早会漂移。最典型的一个反例：早期把”失败项”放在内存里，界面重开就没了；数据库里其实有失败的记录，但界面读不到。

根本原因是没有回答一个问题：这个系统的状态真相在哪？

我的答案是一句话：

事件就是状态（Events are state）。

二、一条事件流，两个投影

具体做法：

  • 启动时，界面拉一次快照（snapshot()），拿到所有任务的当前状态；
  • 此后，主进程只推事件，界面只消费事件；每个事件同时驱动两件事：更新 UI、更新本地数据库。

于是 UI 和数据库不再是两个”各自算状态”的东西，而是同一个事件流的两个投影——它们理论上永远一致。

这条约束有一个必须记住的推论，也是我们真踩过的坑：给事件加字段时，必须同时改持久化类型和渲染层的事件处理。只改一处，UI 和数据库就会静默不一致——和后端”改了 DTO 忘了改 DAO”是同一类 bug，只不过这里的一致性检查更弱。

三、两条轴：任务状态 ≠ 商品状态

状态复杂起来的根源是：一个采集任务里，每个商品也有自己的生命周期。这两者不是一回事：

轴 存哪 展示成什么
采集 任务表上的 stage 文案：采集中 / 已暂停 / 需人工 / 采集结束 / 已中止
处理 由商品状态派生（不落任务表） 徽标：处理中 / 部分完成 / 全部完成 / 已放弃

关键设计是第二条轴不落任务表——它是从商品的 workflow_status 实时派生的。

为什么？因为商品状态会因为”人工复核””放弃””生成草稿”等界面动作而变化，如果任务表也存一份，就会立刻出现”改了商品、忘了改任务”的同步问题。派生就没有这个问题：永远只有一个真相源。

UI 上因此有两条进度：一条采集进度条，一条处理进度条（我们后来还做成了”三环”）。它们各自独立，不会互相掩盖。

四、占位行：让”识别中”也能落库

一个具体的设计：商品还没抓到，界面上却要显示”识别中”。如果这个”识别中”只存在内存里，重启就丢。

做法是落一个占位行：key 形如 recognizing:{taskId}:{lineNo}，等抓取成功 / 失败时，再用真实商品行替换它。失败时同理，落一个 failed:{taskId}:{lineNo} 的占位。

两个好处：

  1. 重启可恢复——快照就能读到”识别中”，不依赖内存；
  2. key 空间隔离——占位行的 key 前缀和真实商品（平台 + 商品 ID）不同，互不干扰。

这也是”事件就是状态”的延伸：连”正在识别”这种瞬时状态，也落了库、成了事件流的一部分。

五、派生（derive）的单一真相源

商品状态不是谁想写就写，而是派生出来的：

有两个刻意的设计：

① 落库时由主进程重新派生。 渲染层提交复核时也会带一个状态，但主进程会用自己派生的结果覆盖它。这就是”单一真相源”——界面不能信誓旦旦地把状态写成别的值。

② 终态保护。 draft / abandoned / failed 是终态，派生遇到它们时直接返回原值，不重算。比如”已生成草稿的商品”不能再被改成别的状态。

这里还有个容易被误判成 bug 的地方：已生成草稿的商品，不能被改成”放弃”，这是有意为之（在数据库层的更新语句里就带了条件）。所以回归测试时如果发现”设放弃没生效”，那是预期行为，不是缺陷。

还有一个踩过的坑值得记：一开始把”识别中”也放进了终态集合，而占位行确实会落库，结果导致”识别中”的行一旦被复核保存就永久冻结。后来缩小了终态集合——“瞬时态”和”终态”不能混在一个保护列表里。

六、失败也要语义分离

单条商品失败，不等于任务失败。所以：

  • 单条失败：failedCount++，不把任务的 stage 写成失败，不设置任务的完成时间；
  • 失败的语义分成两层：fetch_status（URL 采集层：成功 / 失败）和 workflow_status（商品层：识别失败）。

这样”任务还在跑，但有几条失败了”和”整个任务崩了”就是两种不同的表达，界面能把它们分开显示（失败可筛、可重试）。

一个实测确认过的细节：中途失败一条、后面继续跑完，任务的 finished_at 应该是整单结束的时刻，而不是第一次失败的时刻——早期版本被”首败”钉死过，后来修掉了。

七、诚实的边界

有一个已知的、故意的界面边界：如果用户把”曾有问题的商品”（进过冲突 / 待补 / 识别失败）放弃掉，那条”处理问题”的环永远到不了 100%——因为环的分母包含”曾进入过问题状态的”商品，而分子只认”就绪 / 草稿”。用户视角已经没有待办了，环却还显示”待处理 N”。

这不是 bug，是当前口径的后果，被记录了下来（后续可选：让”已放弃”计入分子，或在环旁加个小标记）。把它写进文档，比假装它不存在好——否则下次一定有人当 bug 报。

总结

  • 核心原则：事件就是状态——启动拉一次快照，之后只推事件，UI 与数据库是同一事件流的两个投影；
  • 推论：加事件字段必须同时改持久化与渲染层，否则静默不一致；
  • 两条轴：采集状态落任务表，处理状态从商品状态派生、不落任务表（避免同步问题）；
  • 占位行让”识别中 / 失败”也落库，重启可恢复，且与真实商品 key 空间隔离；
  • 状态的单一真相源：落库时由主进程重新派生，并保护终态；瞬时态不能进终态保护列表；
  • 失败要语义分离：单条失败 ≠ 任务失败；fetch_status 与 workflow_status 分开；
  • 已知边界（放弃”曾有问题的”商品后处理环到不了 100%）写进文档，而不是留给下一个人当 bug 报。
