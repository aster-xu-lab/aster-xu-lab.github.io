LLM Key 不下渲染进程：Electron 里的密钥边界

桌面应用里接 LLM，绕不开一个问题：API Key 放哪？放渲染进程最方便，也最危险。这篇文章讲 Electron 里的密钥边界怎么划，以及为什么”模型建议”必须和”采集证据”分开。

一、为什么 Key 不能进渲染进程

回顾一下上一篇讲过的进程模型：渲染进程不被信任，它是个可能被远程内容污染的浏览器环境。而我们还内嵌了一个远程的商家后台页面。

如果 Key 出现在渲染进程里，就意味着：

  • 任何运行在渲染页里的脚本（包括被注入的）都能读到它；
  • 内嵌的远程页面一旦被污染，Key 直接泄露；
  • 前端代码、日志、错误上报都可能把它带出去。

Key 是”能力凭证”，不是”界面数据”。 界面数据可以下放，凭证不行。

二、Key 只在主进程

做法是彻底的三段式：

环节 在哪 谁能看到
存 主进程的配置，用系统安全存储加密 只有主进程
用 主进程发 HTTP 请求 只有主进程
显示 渲染层只拿到一个布尔 hasApiKey 渲染层

界面能做的事只有两件：判断”配没配 Key”（决定设置页怎么显示），提交”新 Key”（转给主进程保存）。它永远读不到已保存的 Key——连回显都不给。

这和”输入密码框不该回显密码”是同一个道理，只不过这里回显的话泄露面更大。

三、设置项也要校验

Key 这类设置从渲染层传进来，主进程落库前要校验（用 schema 校验库，比如 Zod）。这不只是格式问题——它挡住了”渲染层塞进一个畸形对象”这类输入，等于在主进程侧再设一道边界。

原则和 IPC 一样：渲染层的输入不可信，主进程要自己验。

四、模型输出必须与证据分离

安全边界之外，还有一个语义边界，同样重要。

采集到的商品数据（SourceProduct）是证据：它要可溯源、要持久化、要能回答”这个值是从哪个页面、哪个字段来的”。而 LLM 产出的是建议：候选值 + 置信度 + 依据。

如果把模型输出直接写进证据结构，会同时毁掉三件事：

  • 可溯源性——证据里混进了”猜”出来的值，就分不清真假；
  • 可回退性——模型输出已经落到持久化结构里，想关掉模型都关不干净；
  • 可审计性——审计时无法区分”抓来的”和”模型给的”。

所以建议必须是独立结构，好处是它能可开关、可缓存、可重算、可拒绝。这是”建议层”这个词的全部意义：它永远平行于证据，从不并入证据。

五、可开关的真正含义：关掉模型 = 行为不变

“建议层可开关”不是一句场面话，它有具体的验收标准：

关掉模型开关时，系统行为与”完全没接 AI”时完全一致**。**

怎么验？用一条固定样例跑冒烟，断言事件流和落库字段一字不变。这条回归测试的意义在于：它把”AI 能力”钉死成一个附加项，而不是必经之路——模型出问题、Key 欠费、接口超时，都不影响主链路。

这也是”确定性链路 + 可选建议层”这个架构的核心价值：AI 挂了，产品照常能用。

六、诚实的边界

  • “用户自配 Key、用户自费”是产品层面的取舍（谁承担成本、数据发给谁），不只是技术问题——它需要合规口径落到文档，否则不该在演示里展示。
  • Key 的加密依赖系统的安全存储能力。一个要警惕的设计陷阱是：不要把密钥安全的设计，依赖在一条尚未交付的链路上（比如某个还没做好的登录 / 凭证服务）——否则安全边界会跟着它一起延期。
  • 这套边界解决的是”Key 不泄露“和”模型不污染证据“，它不解决“模型输出对不对”——那要靠人工确认和验证，不是靠边界。

总结

  • Key 是能力凭证，不下渲染进程：存（主进程 + 系统安全存储）、用（主进程）、显示（只给 hasApiKey 布尔）；
  • 设置项的输入由主进程校验，因为渲染层输入不可信；
  • 模型输出必须与证据分离：建议是独立结构，才能可开关、可缓存、可重算、可拒绝，不毁掉证据的可溯源性；
  • “可开关”要落到验收：关掉模型，事件流与落库字段与没接 AI 时完全一致——AI 是附加项，不是必经路；
  • 诚实的边界：Key 安全不要依赖未交付的链路；合规口径要先落到文档。
