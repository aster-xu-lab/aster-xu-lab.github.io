DDIA-12-流批一体：为什么Flink在同时讨好两拨人

引子：两拨人的对立

在大数据团队里，向来有两拨人。

一拨人写离线批处理。他们每天凌晨跑 MapReduce 或 Spark SQL，把前一天的数据全量算一遍，早上出报表。等数小时是常态，延迟以天计，但数据靠谱——只要隔天早上结果一致，没人找他们麻烦。

另一拨人写实时流处理。他们接 Kafka，写 Storm 或 Spark Streaming，秒级延迟，大屏上数字跳得飞起。但数据老是对不齐——不是多算就是少算，凌晨一看，和离线报表差了好几个百分点。

两拨人用两套引擎、两套代码、两套口径。离线工程师不懂流，流工程师嫌批太慢。 Data Infra 团队更痛苦——要维护两套集群，两套监控，两套运维体系。

Flink 想做的事很疯狂：让这两拨人用同一套东西。

DDIA 的论断：批处理是流处理的特殊形式

Martin Kleppmann 在《Designing Data-Intensive Applications》第12章”流处理的未来”中，写下了一个至今读来仍然犀利的论断：

批处理引擎和流处理引擎之间的区别正在模糊。批处理不过是**处理有界数据（Bounded Data）**的流处理。

这句话不是文字游戏。它的逻辑链条非常清晰。

流处理（Stream Processing） 处理的是无界数据（Unbounded Data）——数据源源不断到来，你不知道什么时候结束，也不能等它结束再算。窗口、水印、状态管理，这些机制都是为了在”不知道全貌”的情况下给出一个近似正确的结果。

批处理（Batch Processing） 处理的是有界数据（Bounded Data）——数据就这么多，全部给你，你算完就行。不需要水印，不需要考虑延迟到达，因为”全部”的定义就是你手里的这些文件。

两者看似完全不同，但 Martin 指出了一个关键点：处理逻辑本身是一样的。 无论是在流的增量数据上做 SUM，还是在批的全量数据上做 SUM，你写的那段聚合代码没有本质区别。

那么，如果有一种引擎，能够把”有界”和”无界”这个区别从运行时剥离到输入定义上，会怎么样？

Flink 的核心洞察：批 = 流 + 有界输入

这就是 Flink 的架构洞见。

Flink 从一开始就选择了一条与众不同的路——它没有在流处理引擎外面包一层”微批”的壳（像早期的 Spark Streaming 那样拉长 mini-batch 间隔），也没有在批处理引擎上挂流处理的钩子。它做了一个更底层的决定：

流处理是 Flink 的一等公民，批处理是其特例。

这个设计体现在 Flink 运行时的两个模式：

维度 流模式（Streaming） 批模式（Batch）
输入数据 Unbounded（无界） Bounded（有界）
计算策略 持续增量计算 一次性全量计算
排序与聚合 事件时间 + Watermark 全局排序 + Hash/范围分区
容错 Checkpoint + 重放 中间结果物化 + 阶段重算
延迟 毫秒~秒级 分钟~小时级

关键是：这两个模式用的是同一套 API。 你的 DataStream API、Table API、Flink SQL 代码一行不改，只换一个配置（execution.runtime-mode），就能在流和批之间切换。

同一段 SQL，同一套语义，区别只在于数据源是有界还是无界。

这里的关键点有三层：

第一层：连接器抽象。 Flink 用同样的 Table Schema 描述 Kafka 流和 Hive 表。开发者在写聚合逻辑时，不需要关心数据来自何处、是有界还是无界——“我就要一个 orders，剩下的交给 Connector。”

第二层：SQL 语义统一。 GROUP BY + SUM 的语义在流模式和批模式下一致——最终得到的结果相同。流模式的底层实现是通过状态后端（RocksDB）维护增量聚合，批模式是通过全量 Shuffle + Reduce 完成，但对用户透明。

第三层：覆盖写能力。 redis_sink 的 upsert 模式在流模式下做增量更新（user_id=1001 的新订单来了，原子性地加到 Redis 里的 total_amt），在批模式下做全量覆盖（凌晨跑完后，Redis 里的数据被整体替换为精确计算值）。

这就是流批一体的本质：运行时自适应，语义保持一致，开发者不需要学两套东西。

架构演进：Lambda 的终结与 Kappa 的诞生

要理解流批一体的价值，必须回到 Lambda 架构的痛点。

Lambda 架构：双轨制的原罪

Nathan Marz 在2011年提出 Lambda 架构时，出发点是务实的：既然单一引擎不能同时满足”低延迟”和”高精度”，那就用两套——Speed Layer 负责快但不准，Batch Layer 负责准但慢，Serving Layer 把两者合并。

这个架构在一些大厂跑了十年，但痛点也越来越清晰：

  1. 两套代码，两套逻辑，两份维护成本。 Speed Layer 用 Storm/Flink，Batch Layer 用 Spark/Hive，同一个业务指标要写两次、改两次。
  2. 合并逻辑复杂且脆弱。 Serving Layer 要把两个结果 merge，谁覆盖谁、手动修正还是自动回填，这些问题在几百个指标规模下就是运维灾难。
  3. 数据口径天然不一致。 流算和批算的逻辑如果有一丁点差异，凌晨对账就一堆”数据不一致”工单，最终变成 Data Infra 部门的无底洞。

Kappa 架构：只用流处理引擎

Jay Kreps（Kafka 作者）在2015年提出 Kappa 架构时，给了一个激进的答案：

别搞两套了。只用流处理引擎。批处理只是流处理在有界数据上的重放。

Kappa 架构的核心思想：

在 Kappa 架构下，当需要”离线全量重算”时，不再是起一个 Spark 任务跑 Hive——而是让 Flink 把 Kafka 里保留的历史数据从某个 offset 开始全部重放一遍，用完全相同的流处理代码，得到精确结果。

而 Flink 的流批一体能力，让 Kappa 架构的实现更优雅：你甚至不需要在 Kafka 里存一个月的数据——直接用批模式读 Hive，用同一段 SQL 跑全量计算。

实战场景：订单实时统计的日夜双模式

用一个电商场景来收束。

白天——流模式（毫秒级延迟）：

用户在 App 下了一单，1秒内大屏上的”今日GMV”就能跳动一下。运营团队看到的是实时数据，虽然可能有 0.5% 的偏差（窗口边界 + 延迟到达），但作为实时看板足够了。

凌晨 2:00——批模式（全量校准）：

凌晨，Flink 同一个 JAR、同一段 SQL、同一个 GROUP BY user_id 聚合逻辑，只是数据源从 Kafka 切到了 Hive，运行模式从 STREAMING 切到了 BATCH。跑完之后 Redis 里的值被精确覆盖，财务团队也能直接用。

对比 Lambda 架构，这个方案把维护成本从”两套引擎 + 两套代码 + 数据对账脚本”压缩到了”一套引擎 + 一套代码 + 零对账”——因为流和批的聚合逻辑保证一致，不存在逻辑差异导致的口径偏差。

这就是 Flink 流批一体最直接的业务价值：不是理论上”可以统一”，而是运维成本断崖式下降。

总结：不可逆转的融合趋势

回到 DDIA 第12章的那句话——“流处理和批处理的融合是不可逆转的趋势。”

这不是预言，而是正在发生的事。

Google Dataflow 在2015年提出”流批一体”的 Beam 模型，Flink 在2018年做到生产级可用，Spark 从 2.x 开始用 Structured Streaming 弥补了微批的延迟劣势。现在主流引擎都在向”一套 API，多种模式”收敛。

但 Flink 走得更彻底——它不是给批处理引擎加流处理的壳，也不是给流处理引擎加批处理的补丁。它的运行时从第一天就把”有界/无界”作为数据源的属性而非引擎的属性。这让它的流批一体不是”兼容”，而是原生的统一抽象。

对于团队来说，流批一体带来的不是”新技术”的焦虑，而是减负：少学一套框架、少维护一套集群、少了凌晨的对账脚本。把省下来的精力花在业务理解上，这才是工程师该做的事。
