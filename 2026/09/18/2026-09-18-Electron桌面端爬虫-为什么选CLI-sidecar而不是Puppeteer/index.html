Electron 桌面端爬虫：为什么我用 CLI sidecar 而不是 Puppeteer

在 Electron 里做网页采集，最自然的想法是”直接 npm i playwright 跑”。我没有这么做——随包分发的是一个 CLI + JVM + Chromium 的 sidecar。这篇文章讲这个取舍，以及”随包 sidecar”引出的一堆跨平台构建硬约束。

一、候选方案其实有三条

要在一个桌面应用里采集网页，至少有三条路：

  1. 应用内直接跑 Playwright / Puppeteer：最轻，npm i 就能用，但等于自己实现”打开页面 → 处理状态 → 抽字段 → 重试”的整条链路。
  2. 依赖用户机器上的 Chrome：不用随包浏览器，但要处理”用户没装 / 版本不对 / 被插件干扰”，故障面不可控。
  3. 随包一个完整的采集 sidecar：体积大，但环境完全自持、版本完全可控。

我选了第三条，随包的是一个浏览器自动化 CLI（含 JVM 运行时与固定版本 Chromium）。

二、为什么不用方案 1（自己写 Playwright）

不是 Playwright 不好，而是它只是一个库，不是一套采集能力。真正耗时的从来不是”怎么开页面”，而是：

  • 页面状态判定（正常 / 验证码 / 已下架 / 布局不认识）；
  • 字段抽取的优先级（结构化数据 → 页面内 JSON → meta → 固定选择器 → 认不出就报错，而不是猜）；
  • 会话复用、限速、熔断、崩溃后重试；
  • 崩溃诊断：到底崩在”打开页面”、”抽取字段”还是”JVM 挂了”。

这些如果从零写，工作量远大于”接一个现成引擎”。随包 CLI 直接提供了会话模型、抽取命令、页面状态分类和诊断输出，我只需要在上面做编排——这也是后面几篇会反复提到的”把失败分类”的前提。

方案 2 被我直接排除：桌面软件不能把核心能力押在”用户机器上恰好有个可用的 Chrome”上。

三、sidecar 怎么进包

随包不是简单地把文件拷进去，而是有一套 staging 流程：

  • 一个 stage 脚本从本机抽取当前平台的 CLI + 固定版本运行时 + Playwright 系 Chromium（版本来自 playwright-core 的 browsers.json），并生成 manifest.json，里面写清楚每个文件的平台、架构与 SHA-256 校验和。
  • 打包时用 electron-builder 的 extraResources 把整个目录放到 asar 之外——因为里面是可执行文件（JVM、Chromium），不能被塞进 asar 归档。
  • 首启时校验 manifest：平台、架构、校验和都对得上，才原子复制到用户数据目录；对不上就返回一个明确的失败码（缺包 / 平台不匹配 / 校验和失败 / Chromium 缺失 / Chromium 校验和失败），而不是让用户看到一个语焉不详的崩溃。

关键点是校验和与平台一起进了 manifest，这直接引出下一节的硬约束。

四、跨平台构建的硬禁令

因为 sidecar 是按构建机平台嵌入的，就有了一条不能商量的规则：

绝不在 macOS 上打 Windows 包，也绝不在 Windows 上打 macOS 包。

在 mac 上构建 Windows 包，会把 darwin 的 CLI / JVM / Chromium 打进安装包，用户装到 Windows 上首启就报”平台不匹配”。这不是理论风险，是我们实际撞过的坑——错误码就是上面那个 BUNDLE_PLATFORM_MISMATCH。

配套的做法是各平台在各自的机器 / runner 上出包，产物按平台 + 渠道分目录（mac-arm64 / win-x64 × test / production），互不覆盖。

五、运行时目录绝不写回安装目录

一个容易踩的坑：sidecar 会写日志、缓存、profile。如果这些路径继承调用方的当前目录，打包版会把产物撒得到处都是——甚至打进 asar。

做法是把可写目录全部固定在用户数据目录下：运行时、状态、数据、日志、工作区各一个子目录，且显式指定工作目录（引擎会往 cwd 写自己的元数据目录）。打包版默认的 cwd 是只读的根目录，不指定就会失败或写出奇怪的东西。

原则一句话：安装目录只读，所有可变状态进用户数据目录。

六、诚实的边界

  • 体积大：随包 JVM + Chromium，安装包远大于”只跑 Playwright”。这是自持环境的必然代价，换来的是”用户机器上环境永远正确”。
  • 和平台绑死：sidecar 是二进制，升级引擎等于重建各平台产物，跨平台构建不能偷懒。
  • 供应链风险：我们依赖的引擎后端在开发期是快照（SNAPSHOT）构建，存在”版本漂移”和”升级必重测”的问题——这是选第三方引擎要接受的一类债。
  • 如果需求只是”抓几个静态页面”，这套方案是过重的。它适合的是”要长期稳定跑电商强站商品页”的场景。

总结

  • 桌面端采集有三条路，我选了随包 sidecar：环境自持、版本可控，代价是体积；
  • 拒绝”应用内直接跑 Playwright”不是因为库不好，而是它只给了一个库，没给采集能力（状态判定 / 抽取优先级 / 会话 / 熔断 / 诊断）；
  • sidecar 用 staging + manifest（含 SHA-256）+ extraResources（不进 asar） 进包，首启按平台 / 架构 / 校验和校验；
  • 由此产生硬禁令：不能跨平台打对方的包，否则平台不匹配；
  • 安装目录只读，运行时状态全部进用户数据目录，且必须显式指定工作目录。
