用 node:sqlite 替掉 better-sqlite3：Electron 里告别原生模块

Electron 里做本地数据库，默认答案通常是 better-sqlite3。我最后用的是 Electron 内置的 node:sqlite。这篇讲为什么——核心不是”性能”，而是”不想让主进程背上原生模块”，以及随之而来的几个 schema 设计取舍。

一、better-sqlite3 的隐性代价

better-sqlite3 很好用，但它是原生模块（native addon），这意味着：

  • 要按 Electron 的 ABI 重编译（electron-rebuild 那一套）；
  • 打包时要处理 .node 二进制、不同平台 / 架构各一份；
  • Electron 升级小版本，可能要重新编译；
  • 构建流水线多一步”依赖原生工具链”的环境要求。

这些代价平时不明显，但一旦进了打包链路，就会变成”换个 Node 版本就构建失败”这类烦人问题。

代价是：API 比 better-sqlite3 朴素，生态工具（迁移框架、ORM）也少。但对”桌面端本地库”这个场景，这些都不是刚需——本地库不需要连连接池、不需要分布式、不需要复杂迁移框架。

关键点是：不要用版本号去 gate 迁移。工程里有个 schema_meta.version，但它只是给人 / 运维看的标记，真正的迁移靠的是”每次启动都跑一遍幂等操作”。原因很实际——版本号是单点状态，一旦中间某个版本失败或手动改过库，靠版本号判断就会卡死或漏跑。

配套一条纪律：DDL 的真源文档和代码要保持同步，否则文档就成了过期地图。

四、存储模型：证据与人工修改分离

表结构上有一个刻意的设计：证据和人工复核分开存。

  • product_json：采集到的原始证据，不伪造、可溯源；
  • review_json：人工复核的编辑。

两者分开的直接好处是：人工改字段不会污染原始证据。这对”可审计”和”可回算”很重要——任何时候你能回答”这个值是人填的，还是抓来的”。

也有历史债：早期为了让表长得像上游商品的形状，加了一批投影列（商品名、来源标题之类）。后来发现这些列是冗余的——列表和快照都直接解析 JSON 列就行——于是停止写入投影列，但保留列定义以兼容旧库。这是一个典型的”不删列、只停写”的兼容策略。

五、反规范化计数器的陷阱

为了工作台列表快，任务表上放了三个计数列：总 URL 数、完成数、失败数。这是反规范化——它们不保证等于 URL 行数或商品行数。

漂移的来源有：

  • 重试：重试会重新计数，累计和本轮要分开；
  • 占位行：识别中 / 失败占位行也会占 key；
  • 跨任务同商品的 UPSERT：同一个商品换了任务归属，行会”搬家”。

所以文档里明确写了一条：不要拿计数列去”对账”商品行。它们是给列表排序 / 展示用的，不是真相源。这个坑在状态机那篇里还会碰到（”识别环”的分母问题）。

六、外键的取舍

schema 里写了一句 PRAGMA foreign_keys = ON，但实际上没有任何外键约束声明——所以这条 PRAGMA 目前是个 no-op，孤儿清理全靠应用层 SQL（比如替换任务 URL 时显式删）。

这是个有意的取舍：加真外键就需要配套的”删任务”设计（级联还是阻止），而我们还没定型删除语义。先留 PRAGMA、不声明约束，并在注释里写清楚”这是有意省略，不是忘了”——避免下一个人以为数据库会级联清理。

七、诚实的边界

  • 选内置 SQLite 换来的是”构建简单”，代价是”生态简单”——没有成熟的迁移框架和 ORM，schema 演进全靠幂等约定，需要团队自律。
  • 反规范化计数器是性能换一致性，一旦有重试 / 占位 / 迁移这类”非直线”操作，就会和真实行数偏离，必须靠文档约定而不是靠直觉。
  • 这套存储设计是按”桌面单机、按商家隔离”的场景做的（每个商家一个库文件、每库一套捕获目录）。它不适合”多端共享一个库”的场景。

总结

  • 选 node:sqlite（内置） 而不是 better-sqlite3：主进程零原生依赖、npmRebuild: false，构建链路干净；代价是 API 朴素、生态少；
  • schema 演进靠幂等操作（ensureColumn / CREATE INDEX IF NOT EXISTS），不靠版本号 gate；DDL 文档与代码必须同步；
  • 证据（product_json）与人工复核（review_json）分开存，人工编辑不污染证据；投影列停写不删列做兼容；
  • 任务计数列是反规范化，不保证等于行数（重试 / 占位 / UPSERT 会漂移），不要拿来对账；
  • 外键有意不声明（PRAGMA 是 no-op），孤儿清理走应用 SQL——要在注释里写明”有意省略”。
