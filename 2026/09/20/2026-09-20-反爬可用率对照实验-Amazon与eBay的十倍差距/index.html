反爬可用率对照实验：同一份代码，Amazon 与 eBay 差十倍

同一套采集引擎、同一台机器、同一批种子链接，Amazon 的可用率是 8%，eBay 是 90%。这篇文章讲这十倍差距是怎么测出来的、差距到底在哪，以及为什么”看起来更快的批量方案”是个陷阱。

一、先把实验设计说清楚

结论要站得住，前提是实验可比。这次对照做了三件事：

  • 种子统一：两份已保存的真实商品全页 HTML，从中提取内链（Amazon 44 个 ASIN、eBay 29 个 /itm/），再按各自方案扩链。
  • 统一跳过项：批测一律跳过 DOM 快照与图片下载，只测”能不能把商品页打开并抽出关键字段”。
  • 三套方案跑同样的输入：
方案 一句话 采集方式
A 应用等价 改造前的实现 Amazon 每条 open --fresh --headless；eBay 每条开新窗口
B crawl / swarm 引擎自带的批量模式 并行 crawl / swarm + X-SQL
C 推荐模式 现在的产品实现 按平台复用 session + 持久 profile，同平台只 goto 换地址

三种方案用的是同一个底层浏览器引擎，差别只在”怎么组织会话”。这样测出来的差异，才归因到策略而不是工具。

二、实测数字

Amazon

指标 A 应用等价 B 批量并行 C 推荐模式
目标 / 尝试 100 / 100 10 crawl / 20 swarm 100 / 62（扩链中断）
可用成功 86 crawl 10→1；swarm 20→1 7
风控信号 第 82 条起连续 14 次验证码 大量验证码壳页 连续 55 次验证码
墙钟 42 min 10 条约 30 s 20 min（未满 100）

eBay

指标 A 应用等价 B 批量并行 C 推荐模式
目标 / 尝试 100 / 29（扩不动） 批量 100 / 100
可用成功 真商品约 18 / 29 0（Error Page） 100
风控信号 每条新窗口高频触发”检查您的浏览器” 直接 Error Page 抽检无异常
墙钟 5.6 min（仅 29 条） 秒级失败 29 min

同样的引擎，Amazon 在 IP 干净时能跑到 86/100，一旦出口 IP 被”打伤”，方案 C 也只能到 7/100。而 eBay 在方案 C 下是 100/100。

三、结论一：不要用批量模式（crawl / swarm）做商品导入

B 方案最迷惑人的地方是墙钟好看：10 条大约 30 秒，比串行快了约 5 倍。但可用产量是 crawl 10→1、swarm 20→1，eBay 直接是 0。

原因不神秘——批量模式为了吞吐会开高并发、少等待，正好撞在强站的风控点上。规模化 ≠ 能过强站。在我们这个场景里，B 不是”更快”，是”更快地拿到验证码”。

所以产品路径最终没有采用引擎自带的批量能力，而是坚持串行 + 会话复用的方案 C。

四、结论二：Amazon 的瓶颈是出口 IP，不是浏览器可见性

直觉上会觉得”有头浏览器更像真人，应该更不容易被封”。实测否定了这一点：

在同一台已受伤的机器上 可用率
无头（headless） 约 9%（5 / 56）
有头（headed） 约 8%（3 / 40）

有头并不抬产量。 也就是说，”人手在 Chrome 里能打开 Amazon 页面”和”程序能采集 Amazon”是两件事：页面对人的风控松，对自动化流量的判定另有依据，出口 IP 的声誉是主因。

结论是：Amazon 这条线要提可用率，主杠杆是换网络 / 上代理池，而不是继续调浏览器参数。IP 被打伤之后，任何客户端的策略调整都救不回来。

五、结论三：eBay 能稳，靠的是”暖会话 + 复用”

eBay 的对比更能说明策略的价值。方案 A（每条开新窗口）会高频触发浏览器的安全检查，29 条就扩不动了；方案 C 先访问一次平台首页”暖场”，之后在同一个 profile、同一个会话里反复 goto 换商品页，扩链直接从 29 走到 1233。

会话复用之后，eBay 的单条耗时 p50 大约 5 秒，100 条约 25 分钟、可用率 90% 以上。

这里有个反直觉的细节值得记：同样的”复用会话”思路，对 Amazon 收效有限，对 eBay 立竿见影。所以策略不能跨平台照搬，必须按平台单独标定。

六、和业界量级对照一下

事后我找了电商商品详情采集的经验区间做参照（同一指标：墙钟 / 100 条）：

形态 粗估 / 100 条
高并发 API + 多代理池 约 1–5 min
浏览器渲染 + 代理池 约 5–15 min
刻意限速串行（保成功率） 约 15–40 min
无代理池、单出口、串行真浏览器 约 20–60 min

我们 eBay 的 ~25 min 正好落在”无池串行”这一档，说明优化已经到位——想进”几分钟级”那一档，靠继续挤本地间隔是没用的，必须上代理池 + 适度并发。

七、诚实的边界

  • 以上全部是单机、无代理池的结论。有代理池时，速度和可用率的瓶颈都会转移。
  • 批测不接入人工验证：验证码在批测里直接计为失败。而在真实产品里，验证码会弹框请用户手动过一次，所以产品的实际可用率会高于批测数字，两者不能直接等同。
  • 这套结论只对公开商品详情页成立，且样本量是百条级，不是全站统计。

总结

  • 同一引擎，Amazon 8–9%、eBay 90–100%，差距不在”工具”而在”策略 + 出口”；
  • 不要用 crawl / swarm 做商品导入：墙钟快 2–5 倍，可用产量崩到个位数，eBay 直接为 0；
  • Amazon 的主杠杆是出口 IP：有头 vs 无头 ≈ 8% vs 9%，无增益，换网络才是解；
  • eBay 靠”暖会话 + 会话复用”稳定：29 → 1233 扩链，p50 ≈ 5 s、100 条 ≈ 25 min；
  • 策略不可跨平台照搬，必须逐平台标定；无池串行 20–60 min / 100 条已是该档位的合理水平。
