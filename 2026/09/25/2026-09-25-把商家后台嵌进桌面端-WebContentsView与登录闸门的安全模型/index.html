把商家后台嵌进桌面端：WebContentsView 与登录闸门的安全模型

桌面端要嵌入一个已有的商家后台网页，还要用它当登录闸门。这篇文章讲 WebContentsView 的用法，以及内嵌远程页面时”怎么判定登录状态”这个看似简单、实则全是坑的问题。

一、为什么是 WebContentsView

要在 Electron 里显示一个外部网页，历史上有几种做法：<iframe>（跨域限制多）、<webview> 标签（已不推荐）、以及 WebContentsView。WebContentsView 是独立的一个 WebContents，有自己的进程、自己的会话，是现在推荐的做法。

这里有个朴素的设计值得记住：一个 View 身兼两职。

  • 未登录时，它铺满内容区，显示的就是登录页——它本身就是”闸门”；
  • 登录后，同一个 View 变成商家后台页面。

关键操作是改 bounds，不重建。切换登录状态时只调整这个 View 的位置和大小，而不是销毁再创建。重建会丢会话、丢状态、闪屏。

二、登录判定：只判 token 存在，绝不读值

“页面到底登录没有”是这个方案里最讲究的地方。我们最终的规则只有一条：

只看 localStorage.ACCESS_TOKEN 是否存在，永不读值。

具体有三层含义：

  1. 不读值：只判存在性。token 的内容不进内存之外的任何地方，不落日志、不转发、不显示。
  2. 不按 URL 判：这是最容易犯的错。登录前的商家站是营销站，/home、/about 这类路径在未登录时也存在，按路径判会把”未登录”误判成”已登录”。路径不是登录凭证。
  3. 探测失败 = 未登录（fail closed）：页面没就绪、加载出错，一律按未登录处理。宁可多要求一次登录，也不放一个未登录的人进去。

还有一个细节：导航安定之后再补一次校验（延迟几百毫秒，只补一次），因为单页应用登录后可能有一次导航过渡，太早探测会读到中间态。

三、远程页面的安全姿态

内嵌的商家页是远程内容，所以要按”不可信”对待：

  • contextIsolation + 无 nodeIntegration + sandbox；
  • 不挂 preload——远程页拿不到任何 window.api；
  • 观察用 webContents 的事件，动作走主进程方法，不通过注入脚本。

这样即使商家后台页面被注入，它也够不到本地能力——它只能在自己的沙箱里蹦跶。

四、导航拦截：两个事件都要挂

内嵌页面里的链接怎么处理，是一组容易漏的规则：

场景 处理
内嵌白名单域名内的链接 就地导航（留在内嵌视图里）
主窗口里的链接 一律 openExternal（交给系统浏览器）
target="_blank" / window.open 一律 openExternal
法律条款页（如服务协议、隐私政策） 也交给系统浏览器

注意这里有个反差：主窗口的规则是”一律 deny + 外部打开”，而内嵌视图的规则是”白名单内就地导航”。两套规则方向相反，很容易写混。

技术上的坑是：will-navigate 和 will-redirect 都要挂，重定向可以绕过只挂一个的防护。而且这两个事件的回调首参是 details 对象，用的是 details.url 和 details.preventDefault()——不少老示例里用的是已废弃的第二参数，照抄会踩坑。

target="_blank" 那条尤其重要：登录页上的”用户协议”链接如果被 loadURL 顶掉了当前文档，用户就回不到登录页了。所以这类必须 openExternal。

五、加载状态的三个事件，一个都不能少

判断”页面是否加载完成”看起来简单，实际要用三个事件配合，少一个就有坑：

  • did-start-loading：开始加载；但页面内导航也会触发它，且不一定有配对的 did-finish-load；
  • did-fail-load：加载失败；
  • did-stop-loading：加载停止——用它来判定”就绪”，但要在状态确实是 loading 时才置位。

最阴的一条是：加载失败后，Chromium 仍会提交一个错误页面，于是事件顺序变成”失败 → 完成 → 停止”。如果只看后两个事件，会把一个错误页当成”加载成功”。所以必须让后两个事件先检查”是否已经 loadFailed“。

六、一个踩过的坑：浅色模式校正不能用 debugger

商家后台的 SPA 会把深色模式持久化在 localStorage 里。桌面端想强制浅色，光设 Electron 的主题是不够的——得在商家的文档里把那个持久化标记清掉、把 html 上的 dark 类摘掉，必要时还得多一次重载。

但有个陷阱：做这件事的时候不要用 webContents.debugger。在同时开着远程调试端口的情况下，debugger 会挂住，把 loadURL 一起阻塞。改成直接执行脚本就好。这是一个”手段选对了，但用错场景”的典型坑。

七、诚实的边界

  • 登录判定用”token 存在性”是基于这个商家后台的实现约定的，换一个后台未必成立；它的好处是不碰 token 值，坏处是依赖对方把 token 放在那个位置。
  • 一个 View 同时当闸门和内容，是为了省一个窗口的取舍；如果登录页和内容页差异极大，拆成两个 View 会更清晰。
  • 隔离和沙箱能防”远程页拿到本地能力”，但防不住商家后台自己的权限模型问题——那是另一层的事。

总结

  • 用 WebContentsView，一个 View 身兼登录闸门与商家页，改 bounds 不重建；
  • 登录判定只判 token 存在性：不读值、不按 URL 判、探测失败按未登录（fail closed）；
  • 远程页按不可信处理：无 preload、无 Node、sandbox，观察走事件、动作走方法；
  • 导航规则是两套相反的：内嵌白名单就地导航，主窗口一律外部打开；target="_blank" 与法律页都外部打开；will-navigate 和 will-redirect 都要挂；
  • 加载状态要三个事件配合，且注意”失败后仍会提交错误页”的顺序陷阱；
  • 浅色校正不要用 debugger（会在远程调试下挂住）。
