DDIA-13-事件溯源与CQRS：把数据库当成事件日志来设计

一、起点：你的数据库里存的到底是什么？

打开任何一个业务系统的数据库，你大概率会看到类似这样的表结构：

用户充值50元，你就 UPDATE account SET balance = balance + 50 WHERE id = 1。用户消费30元，Balance变成-30。一切看起来天经地义 —— 毕竟数据库课本就是这么教的。

但仔细想想，这条 UPDATE 执行后，余额从100变成70这个事实是记录下来了，但”它为什么从100变成了70”这个信息却永远丢失了。你不知道这笔消费发生在什么时间、通过什么渠道、购买了什么商品。你的数据库里只有一个冷冰冰的数字：70。

这就是传统CRUD的本质：它回答的是”当前状态是什么”，而不是”状态是怎么变成这样的”。

如果有一天，财务团队跑过来问你：”上个月用户A的余额为什么对不上？中间到底发生了什么？”你翻遍数据库，只能看到一条又一条被覆盖的Balance值，中间的变化过程早已湮灭在 UPDATE 的尘埃里。

这时候，事件溯源（Event Sourcing）提供了一个完全不同的思路。

二、事件溯源：不存结果，存过程

事件溯源的核心思想朴素得近乎偏执：不存储当前状态，而是存储所有导致状态变更的事件。

还是那个账户的例子。在事件溯源的世界里，你的数据库是这样的：

Martin Kleppmann 在 DDIA 第11章举过一个经典的类比：Git 版本控制系统。Git 不存储文件的”当前内容”—— 它存储的是一系列 commit（事件），每个 commit 记录了谁在什么时间做了什么修改。你看到的”当前文件内容”是这些 commit 按序应用的结果。你可以 git checkout 回到任意一个历史版本，可以 git blame 追溯每一行代码的来源，可以 git revert 回滚任意一个操作。这不就是事件溯源吗？

三、和传统CRUD的本质区别

很多人在第一次接触事件溯源时会有一个疑问：这不就是多了几张日志表吗？我在 MySQL 里加一张 account_log 表，每次操作先插日志再更新余额，和事件溯源有什么区别？

区别在于谁是真相的来源（Source of Truth）。

在传统方案中，”日志表+余额表”的架构下，余额表是真相。日志表只是辅助记录，丢了也不影响业务 —— 你仍然可以从余额表读到正确的余额。日志表是”影”，余额表是”身”。

在事件溯源中，事件流是唯一的真相来源。不存在余额表。如果事件流丢了，整个系统就永远无法恢复当前状态。事件是”身”，余额是”影”—— 由事件”投射”出来的物化视图（Materialized View）。

这个反转带来了一系列深远的影响：

第一，天然审计。没有额外的日志表，没有 binlog 解析，没有触发器。你的业务数据本身就是完整的审计日志。任何合规审查、问题排查，只需要查询事件流。

第二，任意时刻回溯。想知道三天前下午3点零7分的账户状态？传统系统可能需要回放 binlog 到那个时间点。事件溯源只需要从零回放到那个时间点（配合快照优化）即可。

第三，Bug修复后数据修正。这是事件溯源最优雅的能力之一。假设你发现3月1日到3月15日之间，余额计算逻辑有一个 Bug，导致所有 refund 事件的金额少算了10%。传统方案的做法是：写一个补偿脚本，逐行修正余额表，祈祷不要出问题。事件溯源的做法是：修正计算逻辑的 Bug，然后重新回放事件流。数据不需要动，改的是逻辑。这也是 Martin Kleppmann 反复强调的观点：你修复的不是数据，而是数据产生的过程。

四、CQRS：读写天生就应该分离

如果只有事件溯源而没有CQRS，你会遇到一个现实问题：每次查询余额都要回放全部事件。随着事件数量增长，这个操作会越来越慢。

CQRS（Command Query Responsibility Segregation）说：写模型和读模型应该分开。写端（Command Side）处理业务命令，产出事件并追加到事件流。读端（Query Side）监听事件流，构建和维护专门为查询优化的物化视图。

回到账户的例子：

  • 写端：接收”充值50元”的命令，校验业务规则，产生 DepositEvent(amount=50)，追加到事件流。
  • 读端：监听事件流，每当出现 DepositEvent 或 WithdrawalEvent 或 RefundEvent，就更新一个 account_balance 表（或Elasticsearch索引，或Redis缓存）。

查询余额时，直接从读端查询，零毫秒级响应。

更重要的是，一个事件流可以投射出多个读模型。财务部门需要按月统计收入？监听同一个事件流，构建一个 monthly_revenue 物化视图。风控团队需要实时监测大额交易？再投射一个 large_transaction_alert 视图。事件流是唯一的真相来源，但消费方式是多样的。

这其实正是DDIA第13章”从数据系统到流系统”的核心思想之一：把数据库看成流处理器。传统的数据库是一个”持有当前状态的盒子”；在流式思维下，数据库是一个持续消费事件流并维护物化视图的流处理系统。Kafka Streams、Apache Flink、Materialize 等流处理框架本质上都在做这件事 —— 消费事件，维护状态，响应查询。

如果某个 Handler 的计算逻辑有 Bug，你不需要修复已经处理过的”数据”，只需要修正 Handler 的逻辑，然后重新执行编排链。这不就是事件溯源”修逻辑不修数据”的哲学吗？

更进一步，如果我们把每个 Handler 的输出事件持久化到事件存储中，SyncTask 的编排链就变成了一个完整的 CQRS + Event Sourcing 管道：Handler 链条是 Command 处理端，每个 Handler 产出的事件追加到事件流，物化视图构建器（可以是独立的 Handler）订阅事件流并更新外部查询视图。

这种思维的转变不是技术选型的差异，而是对”数据”这个词的重新理解。

七、慎重：不是银弹

事件溯源不是万能的。在决定采用之前，有几个现实问题需要认真评估：

最终一致性。写端追加事件后，读端的物化视图更新可能有延迟。如果你的业务场景要求”写入后立即可读”，你需要接受这个延迟，或者选择同步更新读模型（但也因此牺牲了读写分离的部分好处）。

事件Schema演进。随着业务演进，事件的结构会变化。OrderPaidEvent 一开始只有 orderId 和 amount，后来需要加上 paymentChannel。你需要一套策略来处理新旧事件格式的兼容（Upcasting）。

查询复杂度。简单的聚合查询（如余额）通过回放可以轻松处理，但复杂的跨实体关联查询（如”过去一个月购买了母婴类目商品的用户的平均客单价”）在事件溯源模型下并不直观。这时候读端的物化视图设计就变得至关重要。

团队认知成本。事件溯源和CQRS的思维模型与传统的CRUD有根本差异。团队成员需要理解”事件是真相来源””状态是事件的投影”这些概念，否则容易写出”既存事件又存状态”的缝合怪代码。

Greg Young 说过一句很经典的话：事件溯源不是一种技术选择，而是一种领域建模的选择。如果你的领域天然适合事件驱动的思维 —— 如订单流转、合同审批、库存变动、账户交易 —— 事件溯源会让你的系统获得传统CRUD难以企及的灵活性和可追溯性。但如果你的业务就是简单的表单录入和展示，强行引入事件溯源只会增加不必要的复杂度。

八、与DDIA第13章的呼应

回到DDIA这本书。第13章的标题是”The Future of Data Systems”，Martin Kleppmann 在这一章中反复强调一个观点：数据系统正在从”持有状态的被动存储”演化为”处理流数据的主动系统”。

传统的数据库是一个被动的状态容器 —— 你往里存数据，它帮你记着。流式数据库（Stream-native Database）则是一个主动的事件处理器 —— 它持续消费事件，维护物化视图，并对外提供查询能力。

事件溯源+CQRS正是这种演化的实践形态。当你把数据库当成事件日志来设计时，你获得的不只是”当前数据是什么”，而是”数据从哪里来、经过什么变化、到哪里去”的完整画卷。你可以在任意时刻回放历史，可以投射出任意维度的查询视图，可以在逻辑修复后重算全部数据 —— 这些都源于一个根本性的设计决策：不再把数据库当成状态的最终容器，而是把数据库当成事件日志的投影。

这就是DDIA第13章想告诉我们的：流不是数据的副产品，流就是数据本身。
