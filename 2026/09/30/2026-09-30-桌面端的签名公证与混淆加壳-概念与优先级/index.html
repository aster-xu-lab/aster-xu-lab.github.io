桌面端的签名、公证与混淆加壳：先分清这三件事

商用桌面端外发前，一定会被问：要不要混淆、要不要加壳？这三个词经常被混为一谈，但手段、成本和真实收益差很多。这篇文章把它们拆开，讲清楚”加固”到底该先做什么。

一、三个概念先分清

概念 在干什么 实际效果
代码混淆 改 JS 可读性（改名、平坦化、字符串加密） 抬高逆向成本；逻辑仍在客户端
加壳 静态看起来不像明文，运行时解开 容易触发杀软误报、破坏签名和更新；对 Electron 收益有限
加固（真正该做的） 让应用更难被系统拦截、更难被滥用 / 篡改 代码签名、完整性校验、sandbox、密钥不放客户端

关键认知：app.asar 不是加固，它只是打包格式。asar 是归档不是加密，可以被原样提取出来。把代码打进 asar 带来的安全感，是错觉。

二、”加固”应该优先理解为三件事

对这个产品，”加固”优先做的是：

  1. 平台信任链：mac 的 Developer ID + 公证 + staple；Windows 的 Authenticode + 时间戳；嵌套的二进制（运行时 / JVM / Chromium）从内到外逐层签。
  2. 运行时边界：维持 sandbox / IPC / 密钥不下渲染进程。
  3. 秘密不上客户端：假定”打包出去的策略、白名单、业务规则都能被拆包看到”，真正不能泄漏的放服务端。

至于混淆和加壳，都在这个”优先”之后——先把签名链做出来，再谈藏代码。业界对 B 端商户工具的常见顺序也是：签名与分发信任 → 客户端不放真秘密 →（可选）轻度混淆 → 很少上商业壳。

三、一个容易说错的细节：mac 的”残缺签名”不等于”未签名”

这是我自己踩过的认知坑。当前产物是 adhoc / 残缺签名，不是”没签名”，两者行为完全不同：

  • codesign --verify --deep --strict 能通过，但 spctl 失败（没有开发者身份、Sealed Resources 缺失）；
  • 带 quarantine 标记的副本双击会报”已损坏”，而且系统设置里没有“仍要打开”选项，只能手动 xattr -dr com.apple.quarantine 去掉隔离标记；
  • 有意思的是，完全未签名的包反而能在图形界面放行——因为系统对它没有”签名但无效”的判断。

所以”签名残缺”和”未签名”必须分开说，把两者混为一谈会导致排查方向完全错。

四、嵌套二进制的签名顺序

一个真实发布前必须解决的难点：随包资源（运行时、JVM、Chromium）不在打包器的签名范围内，因为它们被放在 asar 之外。要签名，得自己写 afterSign / afterPack 钩子，从内到外逐层签：先签最里层的二进制，再签外层的 .app，最后签 dmg 并公证 + stapler staple。

还有 entitlements 的坑：

  • mac 的 entitlements 里现在只有 JIT 相关项；
  • 开了 hardened runtime 之后，JVM 的 dlopen 很可能还需要 disable-library-validation；
  • 这些必须在公证之前先验证，否则会出现”签完了、公证过了，但应用起不来”。

五、Windows Authenticode：三个要点

  • 私钥必须在硬件（证书 + 硬件令牌 / HSM）；
  • 签名必须带时间戳，否则证书过期后历史签名失效；
  • SmartScreen 不因签名立即放行——签名只是让它有资格被”学习”为可信，新证书仍可能弹警告。

对内部分发来说，未签名的安装包触发 SmartScreen 警告是可以预期的；正式外发才必须完整签名。

六、优先级：把精力放在决定”能不能发出去”的事上

优先级 做什么
P0 完整签名 / 公证 / Authenticode + 嵌套二进制
P0 维持 IPC / sandbox / 密钥主进程
P1 生产产物完整性 / 防篡改（可选）
P2 轻度 JS 混淆（可选，且只在生产 channel）
不做 UPX 等 PE 壳、重度控制流混淆、指望客户端藏住采集逻辑

一句话口径：Electron 商户端打包默认不做混淆加壳；”加固” = 签名 + 运行时边界 + 秘密不上客户端。

一个重要的区分：test / 内部分发和 production / 外发在”签名、是否混淆”上可以不同（测试包留可读日志、签名可残缺），但在sandbox / IPC / 产物结构上必须相同——禁止”测试包松、生产包紧”，否则测试就失去了意义。

七、诚实的边界

  • 签名、公证依赖外部周期（证书申请、平台审核），时间不在自己的排期里，需要提前推。
  • 加了壳 / 重度混淆会破坏崩溃栈和调试体验，也会和公证、自动更新校验冲突——收益低、风险高，所以我们明确不做。
  • 客户端加固永远只是抬高成本，做不到”无法逆向”。真正的秘密只有一条路：放到服务端。

总结

  • 三个词分清：混淆改可读性、加壳骗静态、加固才是该做的（签名 + 运行边界 + 秘密不上客户端）；
  • app.asar 不是加密，不是加固；
  • mac 的**”签名残缺” ≠ “未签名”**：codesign 通过但 spctl 失败，行为和完全未签名相反；
  • 嵌套二进制要从内到外逐层签，并注意 hardened runtime 下 JVM 的 dlopen 可能需要 disable-library-validation；
  • Windows 签名：私钥在硬件、必须带时间戳、SmartScreen 不立即放行；
  • 优先级：签名与公证 P0 → 完整性 P1 → 轻度混淆 P2 → 壳不做；test / prod 在签名与混淆上可不同，在 sandbox / IPC / 产物结构上必须相同。
