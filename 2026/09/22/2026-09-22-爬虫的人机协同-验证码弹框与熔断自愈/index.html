爬虫的人机协同：验证码弹框，而不是硬刚

反爬最难受的不是”被拦”，而是”不知道被拦了还是代码坏了”。这篇文章讲怎么把采集失败分类、把验证码做成一次人工确认、把会话崩溃做成自愈，而不是无限重试或者静默把失败当成功。

一、第一步：把失败分类，而不是一锅端

采集失败的原因很多，但处理方式只有几类。所以第一件事是让每种失败都有独立的错误码，而不是笼统的”采集失败”：

类别 处理方式
验证码 / 机器人检查 人工确认（HITL）
页面错误 / 网络异常 冷却后重试
商品已下架 / 被删除 标记失败，不重试
缺标题 / 缺商品 ID 直接报错——不猜
布局不认识 标记失败，等人看一眼选择器

这里有一条贯穿始终的原则：绝不把失败伪装成成功。验证码、下架、页面错误、缺关键字段——一律显式报错，带上中文提示，而不是返回一个字段残缺的”成功”产物，让错误往下游传。

分类的价值在下一步才显现：只有分对了，才谈得上”哪一类该弹框、哪一类该重试、哪一类该放弃”。

二、验证码走人机协同（HITL）

验证码是采集里最尴尬的一类：程序过不去，但人可以轻松过去一次。

所以产品路径不是”硬刚”，而是把控制权交还给用户：

  1. 采集线程检出验证码，发出一个 awaiting_human 事件；
  2. 应用弹出模态框，提示用户去浏览器里过一次验证；
  3. 有个细节很关键——默认无头的平台，遇到验证码会临时切换到有头窗口打开那个页面，让用户看得见、点得到；
  4. 用户过完验证，点”已完成验证”（或”跳过”），采集继续。

这样验证码就不再是”这条采集失败了”，而变成”这条采集等了一下人”。批测里验证码被直接计为失败，但产品里大部分都能救回来——这也是为什么批测的失败率和产品的实际可用率不能直接等同。

三、会话复用：先暖个场

在验证码之外，更常见的是”同一批请求被识别为异常流量”。应对的核心是会话复用：

  • 每个平台一个持久会话 + 一个持久 profile；
  • 打开时先访问一次平台首页”暖场”，避免从空白页冷启动；
  • 之后换商品只做 goto 换地址，不再反复开新窗口。

前面那篇讲过效果的对比：同一条 eBay 链路，每条开新窗口的旧方案 29 条就扩不动；改成暖场 + 复用之后扩到了 1233 条。

四、限速与熔断

复用会话还不够，节奏也要控制：

  • 健康状态下间隔约 1 秒：不空等，保证吞吐；
  • 刚出现风控后间隔约 4 秒：给站点退让一点；
  • 连续 8 次风控 / 页面错误：判定该平台会话已”脏”，冷却约 90 秒并重建这个平台的会话（磁盘上的 profile 保留）。

熔断的粒度是按平台的——Amazon 出问题和 eBay 出问题是两回事，不能一起停。

五、崩溃自愈：重启，而不是死磕

引擎和本地服务进程偶尔会崩。我的处理很简单粗暴，但有效：

引擎进程异常退出 / 超时 → 直接重启本地服务 → 重试本条一次。

为什么是”重启”而不是”原地重试”？因为实测发现：能修好的崩溃，重启服务就能修好；重启服务都修不好的，原地重试也白搭。重试一次还不行的，就按失败处理，不无限纠缠。

反过来，我**关掉了”每 N 条主动回收会话”**这个看起来很合理的策略。原因是它非但没消除崩溃，还把崩溃固定在了”回收后第 1～2 条”。这件事值得单独看一眼诊断。

六、一次崩溃诊断：崩在哪，比崩了几次更重要

关掉主动回收之后，我盯了三件事：崩在哪个步骤、崩的周期、进程输出。

诊断结果（100 条对照）：

  • 崩点几乎都在”抽字段”这一步（failStep = eval），不是打开页面；
  • 关掉主动回收后，崩溃出现在第 11、22、33、55… 条——大约每 11 条一次，这个周期和”每 10 条回收”几乎同量级；
  • 进程输出（stdout）里反复出现的是 browser_evaluate 的 HTTP 30 秒超时，不是验证码。

结论就清晰了：主矛盾不是会话太老，而是长会话下”抽字段”这个调用会周期性超时。主动回收消不掉它，但”重启服务 + 重试”能把永久失败压成可恢复失败。

这个诊断也直接否定了两个直觉：一，”崩得多肯定是会话太久”（不是）；二，”崩得多肯定是验证码”（不是，是超时）。

七、诚实的边界

  • 上面这套是单机、无代理池的工程。有代理池时，很多风控问题会前移到代理层，客户端策略的权重会下降。
  • HITL 意味着采集不是完全无人值守的——一批里出现验证码，得有人在旁边点一下。这是刻意的取舍：宁可要一次人工，也不做绕过。
  • “抽字段超时”的根因（为什么长会话下会周期性超时）我们只做到了”缓解 + 可恢复”，没有根治——更细的字段抽取、上游排查都还留着。

总结

  • 采集失败先分类：验证码 / 页面错误 / 已下架 / 缺字段 / 布局未知，各有各的处理，绝不把失败当成功；
  • 验证码走 HITL：发事件 → 弹框 →（无头平台）临时切有头 → 人工过验证 → 继续；
  • 会话复用 + 暖场是稳定性的地基，同平台只 goto 换址；
  • 限速分级 + 按平台熔断：健康 1s、风控后 4s、连续 8 次冷却 90s 重建会话；
  • 崩溃处理是重启 + 重试一次，不做无限重试；”每 N 条主动回收”实测有害，已关闭；
  • 诊断的价值在于定位崩点（崩在抽字段、周期约每 11 条、根因是 30s 超时），而不是数崩溃次数。
