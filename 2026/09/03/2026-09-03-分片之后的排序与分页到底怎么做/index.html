分片之后的排序与分页，到底怎么做

学习 ShardingSphere 分片后，一个很现实的问题是：分片之后排序和分页怎么办？ 单表一条 LIMIT 搞定，分片后却要先改写、再归并，深分页更是性能灾难。本文讲透原理和几种解法。

本地单表：最朴素

单表最简单——MySQL 走索引排序 + 分页，一次查询搞定，ORDER BY + LIMIT 天然配合。

注意 ShardingSphere 会把每个分片的 LIMIT 扩展（offset+limit），保证归并正确。

深分页：性能灾难

假设 LIMIT 1000000, 10（跳过 100 万条）：

OFFSET 越大，拉到大内存的数据越多，性能爆炸。 这是分片分页最痛的点。

解法1：游标分页（推荐）

避免 OFFSET，用 WHERE id > lastId ORDER BY id LIMIT n：

  • 每次都是浅分页，不随页码变深
  • 分片下：即使广播所有分片（id 不是分片键），每个分片只取少量，性能可控
  • 适合”按顺序翻”，不适合”任意跳页”

解法2：ES/Doris 承接复杂排序

如果排序维度复杂（多字段、跨平台聚合、任意组合过滤），不要在分片表上做：

  • Doris MPP 引擎本地聚合、本地排序，深分页扛得住
  • ES 做复杂条件检索 + 排序

这是 OLAP 分离方案的落地点。

结合 or_sales_info 的双查询入口

查询 分页方式
按时间翻页（后台列表） 游标分页：WHERE trade_time < 某时间 ORDER BY trade_time DESC LIMIT n
按单号查（客服详情） 单号精准路由，单条，不分页
复杂条件排序统计 走 Doris/ES
  • 后台列表用游标分页（时间递减 + WHERE trade_time < lastTime），契合月表
  • 避免 OFFSET 深分页，它是分片分页性能杀手

小结

场景 处理
分片浅分页 ShardingSphere 改写 + 归并，能行
分片深分页 OFFSET 大性能爆 → 必须游标分页
复杂排序 走 ES/Doris，别在分片表硬扛

核心铁律：深分页 = 游标分页（keyset / search_after），全行业统一。 分片场景下更要如此。
