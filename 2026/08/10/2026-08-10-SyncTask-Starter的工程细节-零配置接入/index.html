SyncTask Starter 的工程细节：零配置接入是怎么做到的

SyncTask 引擎的核心卖点是”接入一个业务任务从数天降到数小时”。这个目标靠的不是引擎本身，而是 Starter 的零配置接入。这篇讲 Starter 背后的工程细节。

一、接入方要做什么

业务方接入 SyncTask，只需要三件事：

没有一行 @Configuration，没有 XML。其余（调度、锁、存储、通知、归档）全部用 Starter 默认实现。

二、三个工程机制

1. 自动配置：@EnableAutoConfiguration

Starter 的核心是一个自动配置类：

Spring Boot 启动时从 AutoConfiguration.imports 读到这个配置类，自动装配引擎。接入方零配置。

2. 默认实现可覆盖：@ConditionalOnMissingBean

引擎有 10 个 SPI 扩展点（TaskStore / LockService / NotifyChannel …），Starter 给每个 SPI 提供了默认实现（adapter-xxljob / adapter-mybatis / adapter-redisson）。

默认实现都标了 @ConditionalOnMissingBean——容器里已经有同类型 Bean 时，默认实现自动不装：

接入方零配置覆盖：不用写 @Primary、不用排除、不用改配置——只要 @Bean 一个同类型实现，Spring 发现已有就自动不装默认的。这就是”约定优于配置“的落地。

3. 参数驱动：param-class 配置

业务 Handler 怎么被路由？靠参数配置：

Starter 根据 param-class 自动选择参数解析器（默认 Jackson），把调度参数反序列化成业务 Handler 需要的类型。新增任务 = 新增配置，不用改代码。

三、为什么这样设计

这套设计的核心目标：把”接入成本”压到最低。

差距来自三件事：

  1. 自动装配——引擎该有的 Bean 全部自动建好；
  2. 约定优于配置——默认实现 + @ConditionalOnMissingBean，业务方只在”要换”时才写代码；
  3. 参数驱动——任务通过配置声明，不通过代码注册。

四、和 ShardingSphere SPI 的交叉

我在复习时发现：ShardingSphere 也有一套 SPI（配置文件声明 + 反射加载），和 Spring 的 @ConditionalOnMissingBean 是同一思想的两个实现——“核心不动、扩展可插拔”。

Spring 自动装配 ShardingSphere SPI
默认实现 @Bean + @ConditionalOnMissingBean 配置文件声明 + 反射加载
覆盖方式 业务方 @Bean 提供新实现 + 改配置
思想 约定优于配置 依赖倒置 + 扩展点

理解了一个，另一个就通了——框架的”可插拔”都是这套路。

五、踩过的坑

1. @ConditionalOnMissingBean 的覆盖时序

如果业务方的自定义 Bean 和 Starter 的默认 Bean 同一批注册，顺序可能导致默认实现先注册、自定义的反而被跳过。

解法：默认实现放自动配置类（@AutoConfiguration，后于业务 @Bean 注册），保证自定义 Bean 先注册、默认的检测到后跳过。

2. 自动配置类的加载顺序

多个自动配置类之间可能有依赖。用 @AutoConfigureAfter/Before 控制顺序，避免”引擎要用的 Bean 还没建好”。

3. 参数解析器的扩展

默认 Jackson 解析器不满足时，业务方实现 SyncTaskParamParser SPI，通过 @ConditionalOnMissingBean 覆盖——解析器也能插拔。

六、复盘：Starter 的价值

Starter 不是”多一个 Maven 模块”那么简单，它是引擎从”库”变成”产品”的关键：

  • 库：你 import 依赖、自己 new、自己组装——引擎还是”你的代码”；
  • Starter：你只写业务——引擎是”开箱即用的产品”。

“接入成本从数天降到数小时”不是靠引擎的算法，是靠 Starter 的工程化——自动装配 + 约定优于配置 + 参数驱动。

总结

  • 接入方只做三件事：引 Starter、实现 Handler、配一行参数；
  • 三个机制：@EnableAutoConfiguration 自动装配、@ConditionalOnMissingBean 默认可覆盖、param-class 参数驱动；
  • 目标：接入成本从数天降到数小时，零配置、零代码；
  • 与 ShardingSphere SPI 同一思想：核心不动、扩展可插拔；
  • 坑：@ConditionalOnMissingBean 覆盖时序、自动配置顺序、解析器扩展；
  • Starter 让引擎从”库”变”产品”。
