DDIA-03-实战：订单中心的多模型存储策略——MySQL主库+ES搜索+HBase归档

一、一个存储引擎打天下的时代过去了

2019年我刚接手cloud-order订单中心时，所有东西都在MySQL里。订单明细查询、商家后台列表、运营报表导出——全部走MySQL，靠加索引、分库分表、读写分离硬扛。那时候团队的共识很简单：出问题就加索引，再不行就分表，分表不行就上缓存。

直到2020年双十一，峰值冲到一天80万单，商家后台某个”订单详情列表”页面撑不住了。SQL里带了8个WHERE条件、3个JOIN，MySQL执行计划走不了索引，每一页翻页都要全表扫描几十万行，CPU直接飙到90%以上。加缓存只缓解了热点订单的重复查询，但商家对历史订单的任意组合检索——比如”最近3个月、已完成、金额大于500的退款单”——缓存命中率低得可怜。

然后我们引入了Elasticsearch，把订单搜索场景从MySQL剥离到ES，问题迎刃而解。这是第一刀。第二刀是2021年初，订单表涨到了快2亿行，DBA三天两头喊磁盘告警。我们分析了一周的查询日志，发现超过60%的SQL只查最近3个月的数据，而3个月以前的订单，除了偶尔的售后和财务对账，几乎没人碰。于是我们把冷数据迁移到HBase做归档，主库只保留近3个月的热数据，表空间砍掉了70%。

这篇文章记录了这次存储架构的演进过程。我写得不只是”怎么用”这些存储引擎，更想讲清楚”为什么要这么用”——以及踩过的坑。

二、MySQL主存储：订单为什么不能没有ACID

任何架构决策，第一个要回答的问题是：这个数据的核心属性是什么？ 订单的核心属性是”不能丢、不能错、不能不一致”。

2.1 订单写入的”铁三角”：库存扣减 + 订单创建 + 优惠券核销

一个用户下单，后端至少要做三件事：

  1. 扣减商品库存（库存服务）
  2. 创建订单记录（订单服务）
  3. 核销优惠券（营销服务）

这三个操作要么全部成功，要么全部回滚。如果订单创建成功但库存没扣，商家会超卖。如果库存扣了但订单没生成，用户付了钱却看不到订单。这类问题的根因不在QPS、不在响应时间，而在”部分失败”——一个分布式系统里最棘手的问题。

如果换成NoSQL呢？ 大部分NoSQL不支持跨行事务或多文档事务。你可以用分布式事务框架（Seata等），但那就引入了新的协调节点、全局锁、两阶段提交的性能损耗。在130万日订单峰值——也就是每秒约15单、每单涉及5-10次数据库操作——用Seata的AT模式平白多出一轮分支事务注册和全局锁等待，RT从80ms涨到200ms以上。这不是一个好选择。

2.2 JOIN的价值被严重低估了

业界有个声音喊了好几年：”不要用JOIN，在应用层组装。” 这个建议在某些场景是对的，但一刀切式地不用JOIN，会让代码变得不可维护。

什么时候不JOIN？ 当数据跨越不同存储引擎（比如订单在MySQL、商品图片在ES），或者JOIN的表数据量巨大且扫描范围广（比如报表聚合），那就不要勉强。

2.3 分库分表后的JOIN限制与解决

cloud-order用的分库分表是ShardingSphere-JDBC，以buyer_id分片。这带来一个天然限制：跨分片的JOIN不能做。我们的解法是：

  1. 单分片内的关联查询：order和order_item用同一个分片键（buyer_id），订单和明细保证落在同一分片上，可以本地JOIN。
  2. 跨分片数据不JOIN：比如商家查订单列表（跨buyer_id分片），走ES而非MySQL。MySQL只服务”当前用户查自己的订单”这类精准命中分片的查询。
  3. 广播表：订单状态字典、支付方式字典这类”读多写少、数量小”的维度表，每个分片存一份，JOIN无压力。

3.1 典型场景：商家后台的订单列表检索

  • 商品名称（模糊匹配）
  • 收货人手机号
  • 买家昵称

  • 是否包含某SKU

3.2 ES的倒排索引恰好解决这个痛点

Elasticsearch的倒排索引天然适合”多条件检索+模糊匹配+排序+分页”组合。每一列独立建立倒排索引，查询时多个索引的倒排列表取交集——效率远高于MySQL的索引合并。

3.3 ES的一个关键坑：不要用它做主存储

ES被设计为搜索引擎，不是数据库。它在写入一致性、事务隔离级别上与MySQL有本质差别。ES的近实时特性（refresh_interval默认1秒）意味着数据写入后不是立即可见的。cloud-order的原则很明确：ES永远只做”镜像”，不做”权威”。 任何写入永远以MySQL为准，ES数据丢了可以全量重建，MySQL数据丢了就是事故。

四、HBase归档存储：冷数据迁移，给主库减负

4.1 冷热分离的核心思路

数据有天然的生命周期。订单创建后前7天是高活跃期（支付、取消、发货），1个月内是问题高发期（退款、投诉），3个月后基本进入沉寂。cloud-order的查询日志分析显示：

时间段 查询占比 说明
近7天 45% 支付、发货、物流跟踪
7天-1月 30% 退款、售后、评价
1月-3月 20% 售后复查、商家对账
3个月以上 5% 财务审计、年度报表

75%的查询集中在近1个月内，95%在3个月内。而存储侧，3个月以上的订单占了总数据量的65%以上。让65%的存储服务5%的查询，ROI极低。

4.2 为什么选HBase而不是继续拆MySQL分表或冷热分区？

有人会说：MySQL分表也能冷热分离，按时间分表不就完了？技术上可行，但有几个实际困难：

  1. 冷热分离后的查询路由：按时间分表意味着每个查询都要知道时间范围。商家查”最近3个月的待发货订单”，OK，路由到热表。但如果查”某用户的所有订单”（没有时间条件），就要遍历所有分片——性能和复杂度都不小。
  2. 跨表UNION/排序：如果冷热表结构一致，查询需要UNION ALL然后ORDER BY，性能会随分片数增长而恶化。
  3. 存储成本：MySQL单行存储开销（包括索引）远高于HBase。同样存储1亿行订单，MySQL的存储成本是HBase的3-5倍。
  4. 运维负担：5000万活跃行的MySQL实例和2亿行的实例，备份、主从同步、DDL的时间完全不是一个量级。

HBase的宽表模型和按rowkey顺序存储的特性，恰好适合”已知rowkey（订单ID），扫一批连续记录”的场景。而且HDFS作为底层存储，三副本冗余，成本低于MySQL的主从+备份存储。

4.3 HBase的设计：rowkey和列族

cloud-order的HBase订单表设计：

整个订单的所有子表数据，拍平成一个大JSON，存到一个RowKey下。单次Get操作就拿回整条订单的所有信息，不需要跨表关联。HBase不支持JOIN，那就在写入时把关联数据提前聚合好，以”空间换时间”——这也是宽表设计的核心思想。

为什么不用对象存储（OSS/S3）归档？ 很多人都提过这个方案：把订单序列化为JSON存到OSS，成本更低。但OSS只支持通过key获取对象，不支持扫描、范围查询。当财务需要”导出2024年Q3所有订单”时，OSS方案只能全量拉下来自己过滤——这不是归档，是扔进黑洞。HBase支持scan和范围查询，即使响应速度不如MySQL，也远比OSS实用。

五、数据同步策略：Canal + MQ 的准实时同步

5.1 同步架构

Canal模拟MySQL slave的交互协议，监听binlog变更，解析出INSERT/UPDATE/DELETE事件，推送到Kafka。下游消费者根据不同存储引擎的特性做适配。

5.2 同步延迟的来源

这个链路不是实时的，延迟来自几个环节：

  1. Binlog写入延迟：MySQL的事务提交后才写binlog，正常情况下毫秒级，网络抖动时可能延迟。
  2. Canal解析延迟：Canal解析binlog事件有一定开销，高并发写入时可能积压。
  3. Kafka端到端延迟：生产者写入+消费者拉取+消费处理。
  4. ES refresh延迟：ES写入文档后，默认1秒后refresh才能被搜索到。

综合下来，P99延迟在1-3秒，极端情况下（秒杀峰值）可能到5-10秒。

六、数据一致性：ES查不到是回源还是等待？

当一个用户在ES里搜自己的订单发现搜不到时——因为同步延迟——你有两个选择：

方案A：回源MySQL

ES没查到，降级到MySQL再查一次。mysqlRetry开关控制。

优点是用户总能查到。缺点是：如果ES大面积延迟（比如同步消费者挂了），MySQL又被大量降级查询打爆——也就是说，ES没兜住流量时，MySQL可能要承受双倍压力。

方案B：等待重试

查不到时，前端提示”请稍后重试”，客户端3秒后自动重新查询。

我们的选择是方案A + 熔断保护：正常情况下走ES，空结果时触发一次MySQL回源。但如果MySQL回源的比例超过5%（说明ES大面积异常），自动关闭MySQL回源，走”请稍后重试”提示。这个熔断阈值由Sentinel控制，避免级联故障。

HBase归档的一个一致性细节

归档到HBase后，MySQL中对应的订单记录会被删除。如果删除操作先于HBase写入完成，查询”3个月前刚归档的订单”会两边都查不到。我们的解法是：先写HBase，确认写入成功后再删MySQL，且删除是逻辑删除（is_deleted=1），物理删除由定时任务每天执行一次，并加2小时的buffer——HBase写入成功2小时后才真正物理删除。 这道安全垫在几次归档事故中救了我们。

七、运维成本：130万日订单规模下的必要性分析

多一套存储就多一套运维。Elasticsearch的集群、Kibana监控、索引生命周期管理；HBase的HMaster、RegionServer、HDFS上的数据均衡；Canal的HA切换——这些都是运维的代价。在日订单只有几万条的时候，MySQL单库就搞定了，上ES和HBase纯粹是过度设计。

什么规模值得上多存储？

以cloud-order的经验（没干到”必须”的时候不要加组件，每加一个组件就多一个故障点）：

规模 推荐架构 说明
日订单 < 5万 MySQL单库 + 索引优化 没必要引入额外复杂度
日订单 5-50万 MySQL分库分表 + Redis缓存 缓存解决90%的查询热点
日订单 50-200万 MySQL + ES（搜索） ES接手多条件检索场景
日订单 > 200万 MySQL + ES + HBase归档 冷热分离降本，全链路可扩展

cloud-order在生产环境跑了3年，架构成本大概是这样：MySQL 3台（1主2从），ES 3台（数据节点），HBase 5台（1HMaster + 3RegionServer + 1备份），Kafka 3台，Canal 2台（一主一备）。总机器数16台，运维团队2人（轮值）。

ES的运维痛点：索引容量规划和分片设计。订单量每年翻倍，索引如果没有提前规划好shard数量，后期拆分困难。我们按”每个shard 50GB以内，每天一个索引”做lifecycle管理——7天内的热索引保留在SSD节点，30天内的温索引迁到HDD节点，超过30天自动关闭（数据可删，需要时从HBase重建）。

HBase的运维痛点：Region分裂和合并。数据量增长时Region自动分裂，大量小Region影响性能。我们设置了预分区策略（按buyer_id hash分200个Region），并监控Region大小，在HBase负载低峰期手动触发major_compact。

运维成本 vs 业务价值

如果只算机器和人力成本，多存储架构大概每年多花12-15万（云服务器+运维DBA分摊）。但如果不做存储拆分，维持一个能扛住130万日订单的MySQL集群：1主N从 + 超大规模磁盘 + 更贵的商业数据库服务（如RDS的高配PolarDB），成本不会比多存储低，而且随着数据持续膨胀，单点瓶颈会越来越突出。

核心问题的关键不是成本，而是”单存储架构的能力天花板”。MySQL不是设计来干”全文搜索”和”海量数据归档查询”的。你让一个人干三个人的活，他能撑一阵子，但早晚会出事。

八、结语：多模型存储不是为了炫技，是被业务逼出来的

这篇文章写到最后，我想回到这个标题：“一个存储引擎打天下的时代过去了”。

我不是说MySQL不够好。事实上，7年了，cloud-order的核心业务逻辑始终跑在MySQL上，从未动摇。没有哪个NoSQL能替代它在事务处理和关联查询上的位置。但它有它的边界——当查询模式从”按ID精准定位”变成”多维度自由组合检索”，当数据量从”几千万”膨胀到”十几亿”，当你发现大部分数据常年没人碰却占着最贵的存储——你就需要其他工具来填补空白。

这个演进过程是渐进的，也是一步步被业务倒逼的：商家要更快更灵活的订单检索→上ES；DBA报警磁盘不够→冷热分离上HBase。没有哪一次决策来自”新技术很酷我们用一下吧”，而都来自”现有方案扛不住了我们得想个办法”。

如果要用一句话总结这次存储架构的演进，我会说：选择存储引擎的依据不是它有多强，而是它刚好能解决你眼下最难的那个问题——而其他的问题，留给其他引擎去解决。
