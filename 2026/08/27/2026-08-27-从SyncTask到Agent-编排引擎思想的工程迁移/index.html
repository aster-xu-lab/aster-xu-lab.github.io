从 SyncTask 到 Agent：编排引擎思想的工程迁移

学 Agent 时我最大的优势不是 Python、不是 Prompt，而是 SyncTask 引擎的编排经验。这篇文章讲怎么把任务编排引擎的工程思想真正迁移到 Agent——不是概念对照（那篇讲过），而是具体的工程做法。

一、迁移的前提：Agent 和 SyncTask 是同构的

Agent 的本质是 think → act → observe 循环，SyncTask 的本质是”调度 → 执行 → 状态机”。剥掉 LLM 这层”思考”，剩下的是同一套编排骨架：

SyncTask Agent
Handler 注册表（声明可用能力） tools 清单（声明可用工具）
handlerKey 路由到实现 LLM 推理 → 选 Tool
参数解析/校验（SPI） JSON Schema 校验
executeCore() 执行业务 Tool 被调用 → 返回结果
afterExecute 决定下一跳 LLM 决定下一步
sync_task 表状态机 Memory / 会话状态

区别只有一个：决策者从代码规则变成了 LLM。这个区别带来新问题（LLM 不可控），但编排的可靠性工程是可以直接迁移的。

二、迁移一：工具层，从 Handler 到 Tool

SyncTask 的 Handler 设计可以平移到 Agent 的 Tool：

迁移要点：

  1. description 要写”给 LLM 看”：SyncTask 的 description 给代码看（路由用），Agent 的 description 给 LLM 看（决策用）——写得越清楚，LLM 选对率越高；
  2. 参数 schema 用 JSON Schema：SyncTask 用自定义参数解析器，Agent 统一 JSON Schema（LLM 按 schema 填参）；
  3. 注册表思想保留：ToolRegistry 就是 HandlerRegistry 的复制，@ConditionalOnMissingBean 那套可插拔设计照搬。

三、迁移二：可靠性，从任务状态机到会话状态

SyncTask 最值钱的是可靠性设计，全部可以迁移：

① 双重防重 → Agent 幂等

SyncTask 用”分布式锁 + 二次查库”防重复执行。Agent 的 Tool 调用同样可能重复（LLM 重试、网络重试）：

② 状态机 → 会话/记忆

SyncTask 的 sync_task 表状态机管任务生命周期；Agent 用 Memory 管对话状态：

  • 短期记忆 = 对话历史（上下文）；
  • 长期记忆 = 持久化会话（Redis/DB），支持断点续传——进程挂了能恢复，和 SyncTask 任务表一样。

③ 告警分级 → Agent 可观测性

SyncTask 的四级告警（SKIP/ONE/BATCH/MIN）迁移到 Agent，就是分级记录：

Agent 推理是黑盒，出问题必须能复盘——和 SyncTask 排查任务失败一个思路。

四、迁移三：编排，从 afterExecute 到 LLM 决策

SyncTask 用 afterExecute 埋点做 Choreography（任务完成后触发下一步）。Agent 把这个”决策者”换成了 LLM：

结构一样，决策者不同。这带来一个必须处理的差异：LLM 可能选错。

约束 LLM 自由度的做法：

  1. Tool 描述精确——描述越清楚，选对率越高；
  2. 结构化输出——Function Calling / JSON Schema，比自由文本可靠；
  3. 关键路径人工确认——涉及钱/库存的 Tool 调用必须确认点；
  4. 失败兜底——LLM 卡住/答错时，有降级路径（超时、重试、返回原文）。

五、一次真实的”迁移演练”

我做过一个小实验：把 SyncTask 的一个链式同步（下单 → 通知仓储 → 回传状态）用 Agent 重新实现：

  • 三个 Tool：createOrder、notifyWarehouse、updateStatus；
  • 让 LLM 编排三步，而不是 SyncTask 的 afterExecute 链；
  • 发现：LLM 在工具选择上基本正确，但偶发会跳过步骤（比如直接 updateStatus 忘了 notifyWarehouse）。

结论：Agent 适合”探索性”任务（不确定下一步），SyncTask 适合”确定性”任务（流程固定）。混合方案最优：确定性的链（下单→通知→回传）用 SyncTask 保证不跳步，不确定的决策（比如”这个订单该走哪个处理流程”）交给 LLM。

六、诚实的边界

这是学习阶段的迁移思考（SyncTask 是生产实践、Agent 是学习实践）。但迁移的方法论是真实的：工具层、可靠性层、编排层的每一块，都是 SyncTask 里验证过的工程做法，只是把决策者从代码换成 LLM。

总结

  • Agent 和 SyncTask 同构：Handler↔Tool、状态机↔Memory、afterExecute↔LLM 决策；
  • 工具层迁移：Handler → Tool，description 给 LLM 看、schema 用 JSON Schema；
  • 可靠性迁移：双重防重 → 幂等、状态机 → 会话记忆、四级告警 → 可观测性；
  • 编排迁移：规则决策 → LLM 决策，要约束自由度（描述精确/结构化输出/人工确认/失败兜底）；
  • 混合最优：确定性链用 SyncTask，不确定决策交给 LLM；
  • 迁移优势：懂可靠性工程的 Agent 开发者，是 ML 背景开发者缺的。
