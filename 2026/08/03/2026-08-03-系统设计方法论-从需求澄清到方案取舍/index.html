系统设计方法论：从需求澄清到方案取舍，一套可复用的打法

做过订单中台、分库分表、任务编排引擎之后，我发现系统设计有一套可复用的打法。这套方法论从”需求澄清”到”方案取舍”，每一步都有明确的目的——尤其是每个关键选择都要有 trade-off 依据。

一、系统设计看四件事

设计一个系统，本质上是在回答四件事：

  1. 需求是什么（最重要的第一步：先问清楚再动手）；
  2. 规模多大（量级感：QPS、数据量、带宽）；
  3. 架构怎么分（分层、组件）；
  4. 每个关键选择为什么（trade-off：这是”深”和”浅”的分水岭）。

二、五步法：从澄清到扩展

第①步最容易被忽略但最重要——不澄清就动手，等于在错误的前提下做设计。我的习惯是开口先问：”这个系统的 QPS 量级？数据量多大？一致性要求？可用性要求？”

三、一个完整示例：设计一个图片资源中心

用”图片资源中心”完整走一遍五步法：

① 澄清需求

  • 上传量：日增图片 1000 万张，单张 0.5~5MB；
  • 访问量：峰值 QPS 5 万（大促）；
  • 一致性：图片不可变（上传后不修改），删除可延迟；
  • 可用性：99.9%。

② 估算规模

  • 日存储增量：1000 万 × 2MB ≈ 20TB/天；
  • 访问带宽：5 万 QPS × 500KB ≈ 25GB/s——这个数字立刻说明：不能全走业务服务器，必须 CDN。

③ 核心架构

④ 关键设计（trade-off 在这里）

  • 分片上传 + 断点续传：大图拆 5MB 分片并发上传，失败重传分片而不是整张重传；
  • 存储选型：OSS 还是自建 MinIO？ 选 OSS——因为图片量大、20TB/天，自建对象存储的运维成本（机架、副本、扩容）远超 OSS 的费用，且 OSS 天然多副本高可用。自建只在”数据合规/私有化”时才值得；
  • 图片处理：实时处理 vs 预生成？预生成多尺寸（大促前批量生成缩略图）——因为实时处理（每次请求压缩）会打爆 CPU 且 CDN 缓存命中率低；预生成后 CDN 缓存每个尺寸，回源率极低；
  • CDN 缓存：图片不可变 → 永久缓存 + 版本化文件名（改图 = 新文件名），回源率从 30% 降到 1% 以下。

⑤ 扩展与优化

  • 瓶颈：CDN 回源 → 对象存储带宽 → 上传服务；
  • 扩容：上传服务无状态水平扩；对象存储按分区扩展；
  • 大促：提前预热热点图片到 CDN，上传链路限流。

四、深 vs 浅：关键差异

同样一个设计，”浅”的方案是：分层架构 + 分片上传 + CDN。“深”的方案是给每个选择 trade-off：

选择 浅 深
存储 “用 OSS” “用 OSS，因为 20TB/天自建运维成本远超 OSS 费用，且天然高可用”
图片处理 “做压缩” “预生成多尺寸，因为实时压缩打爆 CPU 且 CDN 缓存命中率低”
CDN “上 CDN” “图片不可变 → 永久缓存 + 版本化文件名，回源率降一个数量级”

架构评审要的是”为什么选这个”，不是”选了什么”。

五、真实案例：高并发订单系统

方法论最稳的用法是落到自己做的真实系统。设计高并发订单系统，直接拿订单中台讲：

订单中台日均 15 万单（峰值 50 万），支撑体系是：Caffeine+Redis 二级缓存扛读、MQ 解耦异步、Sentinel 限流熔断降级、慢 SQL 从千条级降到个位数、分库分表（单号主分片、6000 万行）、复杂查询下沉 Doris。

真实案例 + 具体数字 + 完整链路，比任何虚拟设计都更有说服力——因为每个选择都有真实依据。

六、trade-off 的三条底层原则

复盘大量设计，trade-off 的底层就三条：

  1. 先便宜后贵：缓存能解决的不上分库分表，索引能解决的不换架构——成本递增；
  2. 隔离防雪崩：一个下游慢要能隔离（连接池/线程池舱壁），不拖垮全局；
  3. 可回滚优先：任何大变更（迁移、扩容、切换）要能灰度、能回滚——“对外无感”靠的是可控。

总结

  • 五步法：澄清需求 → 估规模 → 画架构 → 讲 trade-off → 谈扩展，第一步最关键；
  • 深 vs 浅的分水岭是 trade-off：每个选择讲”为什么选这个不选那个”；
  • 完整示例：图片资源中心的存储/图片处理/CDN 三个 trade-off；
  • 真实案例：订单中台（15万/50万/分库分表/Doris）是方法论的最好验证；
  • 底层原则：先便宜后贵、隔离防雪崩、可回滚优先。
