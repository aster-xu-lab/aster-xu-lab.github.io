DDIA-11-实战：电商日报表的批处理设计——从MySQL全量扫描到增量快照

一、从一个慢查询说起

凌晨 3:00，告警响了。

日报表的批处理跑了 11 分钟还没结束，CPU 使用率飙到 90%。运营同事早上 8 点上班要看昨天的销售日报——这张表必须在凌晨算完。这不是一次两次的事，随着订单量突破 200 万/天，全量扫描的代价正在指数级增长。

问题出在哪？

最初的日报表设计很朴素：每天凌晨跑一个存储过程——

每天 SELECT 全量订单表（JOIN 订单详情、商品、用户、仓库），在 Java 应用层聚合计算后写入报表。逻辑简单直观，但当订单量从 10 万涨到 200 万，这个”简单直观”就变成了灾难现场。

二、问题拆解：全量扫描为什么不可持续

先把这个方案的病灶拆开来看。

第一，全表扫描的成本是 O(n)。n 是历史总订单数，而不是当天新增订单数。表里有半年的数据，每天却要扫描全部 6000 万行——99.5% 的行跟今天的报表毫无关系。MySQL 的 Buffer Pool 被大量冷数据污染，命中率断崖式下跌。

第二，批处理跑在主库上。凌晨 3 点虽然业务低谷，但海外仓订单、异步任务、定时结算仍然在运行。批处理的磁盘 IO 和锁竞争拉高了所有请求的延迟，P99 从 50ms 飙到 200ms。

第三，没有容错机制。如果凌晨 4:00 因为网络抖动导致写入失败，整个批处理必须从头重跑——再扫描一遍全表，再等 8 分钟。更糟糕的是，重跑可能产生重复数据，因为 INSERT 不是幂等的。

第四，数据膨胀不可控。业务要求保留 3 年数据，6000 万行的主库扛不住。不解决冷热分离的问题，前面的所有优化都只是延缓死刑。

这些问题的根源不是”报表逻辑写错了”，而是批处理的设计模式没有适配数据量级的增长。DDIA 第 11 章开篇就讲：批处理的本质是读一组输入、做转换、写一组输出，而输出的设计决定了系统的可靠性。我们的输出是追加写（append）、不可幂等、没有分区切分意识——这是所有问题的起点。

三、改进一：读写分离——先止血

第一步不是优化算法，而是降低爆炸半径。批处理再慢，不能影响业务主库。

方案很直接：日报表的所有查询切到从库。

改动只涉及连接串切换，一个小时上线。效果立竿见影：主库凌晨 CPU 从 70% 降到 30%，P99 延迟恢复到 50ms 以内。

但读写分离只是把问题转移了，没有解决问题本身。从库仍然要扫 6000 万行，批处理仍然要跑 8 分钟。而且带来了新的隐患：主从延迟。凌晨是主库写入的低谷期，延迟通常在 1 秒以内，暂时不是问题。但在大促期间，主库批量结算可能导致从库延迟 10-30 秒，这意味着日报表可能漏掉刚刚支付的订单。

这是 DDIA 里说的「读自己的写」问题在批处理场景的变体。对于日报表这个 T+1 场景，30 秒延迟可以接受——我们只要在凌晨 2:30 之后启动批处理，确保前天最后一笔订单已经同步到从库。这个延迟窗口的确认，后续会通过监控主从同步位点来保证。

四、改进二：增量快照——从百万级到万级

止血之后，开始治本。

日报表的输入有个关键特征：只关心昨天的数据。每天 200 万订单，正常情况下的日增量只有 200 万行，但我们却要扫描 6000 万行——3000% 的浪费。

改全量扫描为增量扫描的核心思想很简单：

  1. 记录水位线（watermark）：每次批处理完成后，把最后处理的订单 updated_at 存到一张 batch_checkpoint 表。
  2. 下次只查增量：WHERE updated_at > last_checkpoint
  3. 合并增量到快照：把增量数据 MERGE 到日报表的快照分区中。

每天的扫描量从 6000 万行下降到 200-300 万行，批处理耗时从 8 分钟降到 40 秒。

但这里面有个细节必须处理好：边界问题。updated_at > last_watermark 会漏掉在 last_watermark 同一秒内插入/更新的订单（MySQL DATETIME 精度到秒）。所以实际实现是：每次把 watermark 往前推 30 秒（overlap window），然后在写入报表时用 ON DUPLICATE KEY UPDATE 或 MERGE 做去重覆盖，保证同一行数据不会因为边界被遗漏。

这就是 DDIA 第 11 章强调的：批处理的输出应该是幂等的。增量扫描 + 覆盖写意味着同一批数据可以安全地重复处理——即使上次执行到一半失败了，重跑也不会产生脏数据。同时也满足了「断点续传」的要求：不管从哪个 watermark 开始跑，最终结果一致。

五、改进三：HBase 冷热分离——根治数据膨胀

增量快照解决了计算量的问题，但没解决存储量的问题。3 年的订单数据都放在一张 MySQL 表里，索引维护、备份恢复、DDL 变更都是噩梦。

于是引入 HBase 做冷数据归档：

每月 1 号凌晨，扫描 created_at > 3 个月 的订单，批量写入 HBase（RowKey 设计为 {warehouse_id}_{yyyyMMdd}_{order_id}），HBase 写入确认后再从 MySQL 删除。

HBase 在这个场景下比 MySQL 更适合，原因有二：一是 HBase 天然按 RowKey 范围分区，按仓库+日期做范围扫描性能极好；二是 HBase 的存储成本远低于 SSD 上的 MySQL，适合放低访问频率的归档数据。

一个容易被忽视的坑：HBase 写入保证。MySQL 删数据之前，必须确认 HBase 写入成功且数据可读。我们的做法是先写 HBase → flush → 校验 RowCount → 再删 MySQL。不是”Write-Ahead”而是”Write-Confirm-Then-Delete”。

六、容错设计：批处理不能只跑得动，还要能救得回

生产环境不会按你的预期运行。凌晨 3:15 网络闪断、3:30 从库主从切换、3:45 磁盘空间不足——批处理被中断是常态，不是意外。

我们的容错三板斧：

第一，幂等重跑。日报表的写入从来不用 INSERT，而是 INSERT ... ON DUPLICATE KEY UPDATE（或者用 REPLACE INTO）。同一个 (biz_date, warehouse_id, product_id) 组合如果有两条数据，后者覆盖前者。这意味着同一个批次的处理可以安全地重跑任意次。

第二，checkpoint 断点续传。batch_checkpoint 表不仅记录 watermark，还记录当前水位和状态。批处理中断后，重试时从上次成功的 checkpoint 继续，已处理完的部分不需要重跑。

第三，可观测性。再好的容错设计，如果不能”看见”问题就形同虚设。我们给每个批处理任务加了三个核心指标：执行耗时、处理行数、watermark 偏移量。Grafana 面板上一条线往下走，马上能判断是该扩容还是该排查数据倾斜。

七、与 DDIA 第 11 章的呼应

回头来看，这一路演进背后的设计理念在 DDIA 第 11 章里都有清晰的阐述：

批处理的输出应该被设计成一个不可变的数据集，可以通过重新运行整个输出来完全替换。

实际上这个原则决定了我们每一版设计的走向：

  • 全量扫描 + INSERT ——违反这个原则。INSERT 不是幂等的，重跑产生重复数据。
  • 增量扫描 + UPSERT ——开始符合这个原则。覆盖写意味着”重新运行输出”的结果是一样的。
  • HBase 归档 ——进一步体现了”数据文件不可变”的思想。历史数据一旦写入 HBase，不再修改，只有物理删除。

DDIA 还区分了两种批处理输出模式：

  • 为搜索优化的输出——搜索引擎倒排索引、全文搜索。日报表本质上就是一种为”查询”优化的输出：预聚合、按维度分组、存储冗余以换取查询速度。
  • 为事务处理的输出——把批处理结果写回到实时系统。这个我们刻意避免了，让批处理的输出保持单向流动（MySQL 订单表 → 日报表），不反向污染在线事务表的稳定性。

另一方面，日报表的演化也印证了第 11 章的另一个核心观点：可重复执行（repeated execution）是批处理可靠性的基石。不是”确保不失败”，而是”失败了可以安全重来”。网络、磁盘、内存、时钟——分布式系统里的一切都可能出错。确定性、幂等的输出设计让你不需要祈祷不出错，只需要在出错时按下重试。

八、效果总结与下一步

阶段 扫描数据量 耗时 主库影响
全量扫描 6000万行 8分钟 CPU 70%
读写分离 6000万行 8分钟 无影响
增量快照 200万行 40秒 无影响
+HBase归档 200万行(热表仅600万) 40秒 无影响

从 8 分钟到 40 秒，从全库扫描到增量快照，日报表的设计迭代了 4 个版本。但比性能提升更重要的，是建立了一套可以复用的批处理范式：水位线 + 覆盖写 + 冷热分离 + 可观测性。这套范式后来被应用到了周报表、月报表、商品画像、用户行为分析等所有 T+1 批处理场景中。

下一步面临的问题是：日报表的 40 秒耗时会随着日订单量继续增长，而增量扫描的量就是单日订单量。如果日订单达到 500 万，单次批处理会接近 2 分钟。解决的思路是分区并行——按 warehouse_id 分成 N 个分区，每个分区独立拉取、独立聚合、独立写入，最后不需要合并（因为不同仓库的数据天然不重叠）。这在 DDIA 的 MapReduce 章节有完整的理论支撑，我们后续单独写一篇来讲。
