DDIA-05-编码与演化的艺术：JSON/Protobuf/Avro在电商系统中的真实选择

前言

不知道你有没有注意过这样一件事：在分布式系统中，数据只有两种状态——在内存里，或者在传输中。

当你写下一行 orderService.createOrder(orderDTO) ，数据在JVM堆内，这是内存状态。当你把这个订单通过HTTP发给下游、通过MQ推给消费者、通过RPC调用远程服务——数据就进入了传输状态。而传输的前提，是编码（Encoding），也就是我们常说的序列化。

DDIA第五章的标题叫”Encoding and Evolution”，但我觉得它真正在讨论的话题是：当系统需要演化的时候，你的数据格式扛得住吗？

这个问题我踩过坑。订单中心最初所有接口都用JSON，风平浪静。直到有一天，供应链系统说：”你们返回的金额字段，BigDecimal 72.00 到了我们这变成了 7.2E+1，财务对不上账了。”

你看，编码从来不是”选个序列化库”那么简单。它是分布式系统的毛细血管——MQ消息体、HTTP响应体、RPC请求体、日志格式、缓存Value——一切跨进程通信最终都要落在编码上。毛细血管堵一条，整个肢体都会坏死。

今天这篇文章，我会结合7年电商中台的实战经验，聊清楚三件事：

  1. JSON的舒适区和它悄悄埋下的雷
  2. Protobuf和Avro到底解决了什么问题，又带来了什么新问题
  3. 在我们的订单中心架构中，编码格式的真实选择逻辑

一、编码的本质：结构化数据如何在字节流中存活

先回到问题原点。为什么需要编码？

因为内存中的数据结构是”活的”——有指针、有引用、有类型信息。但网络传输或磁盘存储只能接收字节序列。编码就是把内存中的数据结构”翻译”成字节流，解码则是反向操作。

DDIA中将编码分为两大类：

  • 语言内置编码：Java的Serializable、Python的pickle。优点是方便，缺点是绑死了语言，而且Java序列化有严重的安全漏洞——反序列化时可以执行任意代码。生产环境请永远不要用java.io.Serializable做跨系统通信。

  • 语言无关编码：JSON、XML、CSV（文本格式）；Protobuf、Avro、Thrift、MessagePack（二进制格式）。这是我们今天讨论的重点。

选择编码格式时，有三个维度的考量：

维度 说明
空间效率 编码后的字节数。在130万日订单的体量下，消息体缩小50%就是每天节省几十GB带宽
Schema支持 有无显式数据结构定义。Schema = 契约 = 编译期类型安全
演化能力 数据结构改变时，新老版本能否共存。这是DDIA第五章最核心的主题

二、JSON：最熟悉的陌生人

2.1 为什么我们都爱JSON

JSON是HTTP API的默认语言。无论是前后端分离的REST接口、还是xxl-job的任务参数、还是Elasticsearch的查询DSL，JSON几乎无处不在。

它最大的优势就八个字：人类可读，生态最好。

调试的时候，你在Postman里看到的就是最终数据，不需要任何解码工具。日志打出来直接能读。测试用例写起来不需要编译.proto文件。这对中小团队来说意味着极低的认知负担。

在订单中心，我们内部REST API全部用JSON。为什么？因为内部API的消费者是同团队的同事，当他们凌晨两点排查线上问题时，能看到原始JSON远比盯着一串十六进制二进制数据要高效。可调试性是分布式系统最重要的非功能性需求之一——这一点很多”性能至上”的文章不会告诉你。

2.2 JSON的五大暗坑

但JSON的”简单”是有代价的。以下每一个坑我都亲身踩过：

第一坑：数字精度丢失

JSON规范（RFC 8259）中只有一个Number类型，不区分整数和浮点数。而JavaScript的Number是IEEE 754双精度浮点数，整数安全范围只有 -(2^53 - 1) 到 2^53 - 1。

更致命的是，Java的BigDecimal序列化为JSON时，很多库默认行为是转为科学计数法：

解决方案是Jackson配置 WRITE_BIGDECIMAL_AS_PLAIN 或在字段上加 @JsonFormat(shape = JsonFormat.Shape.STRING)。但这不是技术问题，而是契约问题——你的下游可能用的是Node.js、Python、Go，它们对科学计数法的处理各不相同。

第二坑：没有Schema

JSON最大的便利也是它最大的隐患：没有Schema。

接口文档说 userId 是Long，上游某天不小心传了个String "12345"，你反序列化时会不会炸？如果你的Jackson配置了 DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES，上游加了新字段，你的服务直接500？

没有Schema意味着所有校验都发生在运行时。这在内部API里可控（你骂隔壁组的同事一顿就行），但对外部系统就是一颗定时炸弹。

第三坑：二进制数据编码膨胀

JSON是文本格式，二进制数据（如图片、文件）需要Base64编码，体积膨胀约33%。虽然订单中心不传文件，但如果你用JSON传批量数据——比如一次性同步500条订单给下游——体积差异就非常明显了。

实测：500条订单对象，JSON序列化约850KB，同样的数据用Protobuf约220KB，相差将近4倍。

第四坑：解析性能

JSON解析需要逐字符处理——跳过空白、匹配引号、处理转义。而二进制格式的解析是字段编号+长度前缀的跳读，不需要扫描整个消息。在日处理百万级的场景下，这点差异会放大为CPU成本的显著差距。

第五坑：注释不标准

JSON规范不支持注释。你在JSON配置文件里加个 // TODO，有些解析器直接报错。所以在生产配置中，我们团队统一用YAML替代JSON做配置文件。

2.3 JSON在订单中心的真实位置

既然有这么多坑，我们还在用JSON吗？当然在用，而且用在最合适的位置：

  • 内部REST API：可读性 > 性能。团队小，排查效率优先。
  • xxl-job任务参数：xxl-job原生就是JSON传参，我们的SyncTask引擎寄生在xxl-job之上，消息体用JSON是唯一选择——这是兼容性决定的技术选型，不是性能分析的结果。
  • 配置数据：虽然我们用YAML写配置，但运行时很多配置以JSON格式存储在DB中，因为MySQL 5.7+原生支持JSON类型和JSON函数。

一句话总结：JSON适合人类频繁接触的边界——API调试、日志分析、配置文件。这些场景下，效率和可读性的价值远大于几个字节的节省。

三、Protobuf：Schema驱动的内部RPC利器

3.1 核心设计：字段编号而非字段名

Protobuf最精妙的设计是：编码时不存字段名，只存字段编号。

序列化后的二进制数据中，order_id 只占用 (field_number << 3) | wire_type = (1 << 3) | 0 = 0x08 一个字节作为tag，然后是varint编码的值。而JSON需要存完整的 "orderId": 字符串（10字节）。

这意味着什么？意味着字段名可以随便改，不影响兼容性。 order_id 改成 order_identifier，只要字段编号保持1，新老系统互发消息完全没问题。这在演进频繁的电商系统中是巨大的工程优势。

3.2 向后兼容的契约

Protobuf的兼容性规则非常清晰：

操作 兼容性 说明
新增字段（新编号） ✅ 完全兼容 老代码忽略新字段，新代码读到老消息时新字段取默认值
删除字段（保留编号） ✅ 注意编号 字段编号必须永久保留（标记reserved），否则会被新字段复用而导致”幽灵数据”
改字段名 ✅ 完全兼容 编码依赖编号不依赖名称
改字段类型 ❌ 灾难 int32改string——看起来不可能，但真实发生过的故事
改字段编号 ❌ 灾难 等于换了一个字段

收到老消息时，新字段取默认值。这个默认值的语义至关重要：int32默认0，string默认空字符串，bool默认false。设计Schema时，必须确保默认值是”安全的”。

举个例子：如果消息体新增了 bool need_retry = 10，默认值是false，老系统发来的消息不带这个字段，新系统解析出来默认false——“不需要重试”，这是安全行为。但如果是 int32 max_retry_count = 10，默认值是0，新系统收到老消息后会认为”重试0次”，如果业务逻辑是0次=无限重试——这就是隐性Bug。

默认值设计原则：默认值应该等同于”不做新行为”。

3.3 Protobuf在电商系统中的合适位置

Protobuf最适合的场景：内部微服务之间的高频RPC通信。

  • 发送方和接收方都属于同一组织，可以同步升级.proto文件
  • 通信频率高，二进制格式的解析效率优势明显
  • 字段变更频繁，Schema的向后兼容机制保证平滑升级

在我们订单中心的架构推演中，以下是Protobuf的理想落点：

  • OrderService → InventoryService（订单中心调用库存中心）：高频、内部、PB可以显著减少序列化开销
  • OrderService → NotificationService（订单状态变更通知）：异步消息，PB的消息体积优势明显

但我们目前还没有全面切换到Protobuf，原因在第五节会展开。

3.4 Protobuf的代价

不会藏着掖着，Protobuf也有实打实的代价：

  • 可读性差：二进制格式，调试时必须工具解码。凌晨线上排查时盯着一串十六进制，心态容易崩。
  • 构建流程增加：需要protoc编译器，.proto文件管理，多语言代码生成。对小团队是额外负担。
  • Schema分发：消费者需要.proto定义才能反序列化。如果没有Schema Registry（Confluent的或自建的），Schema版本管理就是一个容易出错的手工流程。

四、Avro：数据管道的动态类型引擎

4.1 Avro的设计哲学：Schema不是代码，是数据

Protobuf将Schema编译成代码。Java中你会得到一个OrderMessage类，直接.getOrderId()。这是静态类型绑定。

Avro走了一条完全不同的路：Schema独立于代码存储，可以是JSON文件、可以存在Schema Registry中、甚至可以直接嵌入数据文件的头部。

Avro序列化的数据文件中，Schema和数据存储在一起。这意味着：

  • 读取方不需要提前知道Schema
  • Schema可以动态解析
  • 写入时的Schema和读取时的Schema可以不同（Schema演化解析）

这个设计使得Avro天然适合数据管道——Kafka中可能堆积了数天的消息，消费方可能是昨天才上线的服务，但只要Schema Registry中有对应的版本历史，消费方就能正确解析。

4.2 Avro的Schema演化规则

Avro没有字段编号，它靠什么做兼容？答案是字段名匹配 + 默认值。

Avro解析时，用Writer的Schema解码字节，用Reader的Schema重建对象。字段名相同的直接映射。Reader有而Writer没有的字段，用默认值填充。

这比Protobuf更灵活，但也更危险：如果你改了一个字段名（不是新增，是改名），Avro找不到匹配——而Protobuf靠编号，改名没问题。

4.3 Avro在电商架构中的可能落点

在我们团队的技术雷达上，Avro标记为”评估中”，目标场景是：

场景一：订单状态变更的Kafka消息

目前订单状态变更靠定时任务轮询DB，这是一个典型的”技术债到期日永远在明天的方案”。如果未来迁移到事件驱动架构（订单状态变更推Kafka），Avro + Schema Registry会是消息格式的优先选项：

  • Kafka Connect（Hadoop生态）原生支持Avro
  • 消息可能被多个异构消费者消费（Java/Go/Python），Schema独立存储避免了多端同步的问题
  • 数据管道中可能有数小时的延迟消费，Schema演化解析是硬需求

场景二：数据归档到HBase/数据仓库

日130万订单，MySQL中热数据保留3个月，历史数据需要归档。如果未来接入大数据平台（Hadoop/Flink生态），Avro是行级存储的事实标准。

4.4 Avro不适合什么场景

  • 同步RPC：动态解析Schema有额外开销，对延迟敏感的同步调用不如Protobuf
  • 小团队：Schema Registry的运维成本、Kafka生态的学习曲线，都是现实的团队能力约束

五、实战：订单中心编码格式的选择逻辑

5.1 我们现在的选择

场景 编码格式 原因
内部REST API JSON 可读性 > 性能，调试效率优先
SyncTask消息体 JSON xxl-job原生JSON传参，兼容性决定
跨系统HTTP回调 JSON 外部系统技术栈不可控，JSON是最大公约数
内部RPC JSON（现阶段） 团队规模小，Protobuf收益不抵运维成本
Kafka消息 规划中Avro Kafka Connect + Schema Registry生态优势

这不是什么高大上的”架构决策”，它就是实事求是：团队4个人，运维能力覆盖JSON已经很好，引入Protobuf的构建流程和Schema管理是多一个人的工作量。

5.2 如果切换到Protobuf，需要什么条件？

坦白说，我在设计SyncTask引擎的独立版本时，已经为Protobuf预留了扩展点。引擎的SPI体系中，消息解析接口SyncTaskParamParser是策略模式的，当前只有一个JSON实现。如果未来切换到Protobuf，只需增加一个PB实现类，注册到Spring容器即可。

切换的先决条件不是”性能瓶颈出现了”，而是：

  1. 团队熟悉protoc工具链，能独立维护.proto文件仓库
  2. 内部RPC调用方数量和调用频率达到一定规模，二进制格式的收益覆盖构建流程的额外成本
  3. Schema Registry或等价机制建立，避免.proto文件散落在各仓库的”野Schema”现象

在满足这些条件之前，JSON的”够用就好”是这个规模下最理性的选择。

5.3 Schema演化策略：几条铁律

不管是JSON、Protobuf还是Avro，Schema演化都遵循相同的铁律。这些规则来自血迹斑斑的生产经验，来自那个BigDecimal科学计数法的凌晨：

铁律一：加字段永远设默认值

JSON场景下，接收方用Jackson反序列化，未知字段默认忽略（取决于配置），新字段的默认值是null/0/false。你必须保证代码能正确处理这些null值。

铁律二：删字段先标记废弃，不直接删除

如果你想删掉oldField，正确步骤是：

  1. 当前版本：oldField标记 @Deprecated，代码中不再使用，但序列化时不忽略
  2. 下一个版本：确认无消费者依赖后，忽略序列化（Jackson的@JsonIgnore）
  3. 下下个版本：从DTO中删除字段

不要跳步。直接删字段意味着：当老版本的上游发消息时，你的新版本服务可能因为反序列化失败而拒绝消费。而在电商系统中，”拒绝消费”= 订单丢失 = P0事故。

铁律三：改字段类型 = 灾难，唯一正确做法是新增字段替代

BigDecimal改成String？int改成long？——不要改，新加一个字段：

这个方案的代价是：一段过渡期内，消息体同时包含新旧两个字段。等所有消费者都升级后，再删除旧字段。过渡期可能是一个月，但在130万日订单的体量下，这个成本是必须支付的。

铁律四：枚举值可以加，不能改不能删

订单状态枚举 PENDING → PAID → SHIPPED → COMPLETED，新增一个 REFUNDING 没问题。但如果把 PAID 改成 PAYMENT_CONFIRMED，或者删除 SHIPPED——所有依赖枚举值做逻辑判断的代码都会出错。

5.4 SyncTask引擎的Schema演化挑战

我们SyncTask引擎管理着cloud-order的49个Handler和cloud-wms的44个Handler，合计93个Handler。每个Handler有独立的消息体格式。当某个Handler的消息体需要新增字段时，挑战在哪？

挑战不在代码层面——Handler接口有getParamClass()方法声明消息体类型，新增字段只要设了默认值就是安全的。

挑战在运维层面——93个Handler的消息体，有没有一个中央注册表？目前没有。消息体的定义分散在各Handler的Java类中。如果未来引入Protobuf，.proto文件的管理和Schema Registry的搭建，将是比编码本身更重要的工程任务。

这也是为什么我在SyncTask引擎独立版本中，把SyncTaskParamParser抽象为SPI——它不只是”支持多种序列化格式”的技术噱头，而是为未来的Schema管理留了一道门。

六、选择的本质：不是benchmark，是团队能力和运维成本

人们喜欢做技术选型时看benchmark——序列化速度、反序列化速度、消息体积。这些数据很重要，但它们不是决策的核心因素。

核心因素是团队能力和运维成本。

一个真实的故事：某电商团队（比我们大得多）全面推行Protobuf做内部RPC，.proto文件散落在20+个Git仓库中，没人维护统一的Schema Registry。半年后两个团队联调，A团队用的.proto是3月版本，B团队用的.proto是2月版本，中间加了一个字段但编号冲突。联调搞了两天，最后发现是版本不对称。

这不是Protobuf的问题，这是工程治理能力跟不上技术选型的问题。

另一个故事：某团队用JSON传所有数据，包括定时的全量订单同步（每次50000条）。JSON消息体动辄几十MB，MQ消息积压时带宽被打满。运维加了机器，但不解决问题——问题在消息格式。

总结

DDIA第五章讲的是编码与演化，但我读完最大的体会是：编码格式的选择，本质上是你在为未来留多少余地的思考。

JSON告诉你：只要能跑就行，演化的事以后再说。它的可读性让你在调试时很舒服，但留下的坑（精度、无Schema、体积）会在某个凌晨让你不舒服。

Protobuf告诉你：我们先把契约定好（Schema），然后严格遵守。它适合控制力强的内部系统，但需要团队有版本管理的能力。

Avro告诉你：Schema和数据一起走，消费者自己会解析。它适合数据管道，但需要Schema Registry这样的大数据基础设施。

在我们的订单中心，当前的选择可以总结为一句非常不性感的话：JSON能覆盖的场景就用JSON，JSON扛不住的场景评估是否到了引入新基础设施的临界点。

这也正是”架构师”和”写代码的”的区别——不是你会用多少种技术，而是你知道什么时候不该用什么技术。
