DDIA-10-两阶段提交与共识的边界：电商库存扣减为什么不能偷懒

一、一个真实的线上事故

2019年双十一，我们的订单系统出现了一批”幽灵库存”——订单状态显示已取消，但库存没有恢复。排查发现，订单服务和库存服务分别部署在两套独立的MySQL集群上，当天凌晨主库发生了一次HA切换，正好压在了订单写的间歇期上。几十个事务处于in-doubt状态，等DBA手动介入时，已经过去了四个小时。

这个场景对我们来说是再熟悉不过的现场了——跨库操作、分布式事务、故障恢复，全是课后留堂的经典题目。当时团队讨论了一个看似合理的问题：能不能用Raft把订单库和库存库做成一个复制组，让它自动脑裂恢复，然后就不用管2PC了？

这个问题听起来有理有据。Raft提供强一致性、自动故障切换，Log Replication保证了复制组内所有节点的操作顺序完全一致。如果让订单和库存都在同一个Raft组里，提交就变成了一次分布式日志追加——这和2PC的”所有人同意才提交”听起来是一回事。

但这个直觉是错的。Raft和2PC解决的是完全不同层次的问题，把其中一个当另一个的替代品，就像用电焊修水管——工具很牛，但用错了地方。今天这篇文章，就从这个边界开始聊起。

二、2PC的本质：原子提交，不是共识

很多人（包括当年的我）把2PC理解为一个投票协议——协调者（Coordinator）问所有参与者（Participant）：准备好没？所有人都说OK就提交，有人说不OK就回滚。这个理解不算错，但它掩盖了2PC最核心的本质：2PC是一个原子提交协议（Atomic Commit Protocol），它要做的是让一组参与者对一个”要么全部提交、要么全部回滚”的决定达成一致。

关键词是”原子提交”，不是”共识”。

我们看2PC的执行流程：

  1. Phase 1（Prepare）：协调者向所有参与者发送Prepare消息。参与者执行事务到”即将提交”的状态，锁定资源，将Undo和Redo日志写入磁盘，然后回复YES或NO。回复YES意味着参与者承诺：后续协调者让我提交我就一定能提交，让我回滚我就一定能回滚。

  2. Phase 2（Commit/Abort）：协调者根据所有参与者的投票结果，发送Commit或Abort。参与者按照指令执行最终操作并释放锁。

DDIA第9章有一个精确的表述：“两阶段提交将一个分布式事务的提交拆分为一个关键的、不可逆的决策点。” 这个决策点就是协调者收到所有YES之后、发送Commit之前的那一刻。从那一刻起，结果已经锁定，无法反悔。

这里有一个容易混淆的点：2PC确实也有投票和多数派的概念（所有参与者都YES才提交），这和Paxos的Prepare/Promise机制看似相似。但区别在于——2PC的”投票”是为了原子性的决策（全局是commit还是abort），而Paxos/Raft的”投票”是为了在多个副本之间选出一个值，保证读到同一个值的人不会读到不同版本。目标和语义完全不同。

三、2PC的致命弱点：容错

DDIA用了一整节讲2PC的容错问题，核心就一句话：2PC在协调者故障时，参与者会陷入in-doubt状态，无法自主恢复。

具体展开一下。假设协调者在发送了”YES”投票后崩溃，参与者就处于一个尴尬的位置：

  • 它不知道其他参与者投了什么票。
  • 如果它自己投了YES，它既不能单方面提交（万一别人投了NO，协调者最终要Abort），也不能单方面回滚（万一所有人都投了YES，协调者最终要Commit）。
  • 它只能等。在等的时候，它持有的锁不能释放。因为放锁意味着其他事务可能读到未决数据，破坏了ACID的隔离性。

这个状态就是in-doubt。在实际系统中，in-doubt事务会一直持有行级锁，导致其他事务在争抢同一行时阻塞。如果协调者长时间不可用，阻塞会像雪崩一样扩散——库存表的某几行被锁死，扣减请求全部超时，上层重试再叠加，整个库存链路雪崩。

这就是2PC的核心矛盾：它把系统正确性绑定在了协调者这一个单点上。 在CAP框架里，2PC是一个典型的选择C而放弃A的方案——网络分区时，为了保证一致性，多个分区会拒绝服务。协调者不是网络分区，但它的故障等同于网络分区：参与者联系不上协调者，必须阻塞。

有人会问：数据库厂商不是有XA事务的自动恢复机制吗？MySQL的在in-doubt超时后可以自动回滚或提交，Oracle有DBA手动的COMMIT FORCE。这些是工程上的补救手段，但不是协议层面的解决方案。它们在超时后假设一个结果（通常是rollback），这已经违反了2PC的语义（协议上说必须等协调者通知）。

这就是DDIA那句经典总结的出处：“2PC是一个共识协议——但它是一个容易受单点故障影响的、不完整的共识协议。” 这句话很妙，后面我们会回来。

四、Raft/Paxos解决什么问题？

现在看共识协议这一边。

Multipaxos和Raft要解决的问题可以概括为：在一个有节点故障和网络分区的异步系统中，让多个节点对一系列值的顺序达成一致，并且保证任何时刻，任意多数的节点中至少有一个拥有全部已提交的日志。

典型的应用场景：一个Redis Cluster的三节点复制组，主节点接受写入，同步到两个从节点。当主节点宕机时，剩下的两个节点通过Raft选举出新的Leader，新的Leader保证它拥有所有已提交的日志条目，不会丢数据。

关键点：Raft操作的是同一个状态机的多个副本。每个副本运行的是完全相同的状态机逻辑，它们的差异仅限于日志的先后顺序。Raft保证的是这些副本的日志顺序一致，从而保证状态机输出一致。

这和2PC的差异就非常明显了：

维度 2PC Raft/Paxos
目标 原子性：多个参与者要么全提交、要么全回滚 一致性：多个副本对状态机日志顺序达成一致
参与者 异构的：每个参与者操作不同的资源（订单表、库存表） 同构的：每个副本运行相同的逻辑
容错 协调者故障→in-doubt阻塞 Leader故障→重新选举，继续服务
提交条件 所有参与者都YES（100%同意） 多数派确认（Quorum，过半数同意）
核心场景 跨数据库/跨服务的分布式事务 单状态机的多副本容灾

表里最关键的一行是”提交条件”。2PC要求100%的参与者同意，而Raft只需要多数派（过半数）。这决定了Raft可以容忍少数节点故障——因为多数派里一定有最新的日志。2PC的”全或无”使其在面对任意节点故障时直接卡住。

现在回头看那句话——“2PC是一个不完整的共识协议”——DDIA的意思是说：如果把共识定义为”让多个节点对某个值达成一致”，那2PC也算是共识的一种特例，只是它的容错设计不完整。标准的共识协议（Paxos/Raft）经过Lamport/Ongaro等人的严格证明，在节点故障和网络故障下依然满足safety（不会返回错误结果），只是可能牺牲liveness（在极端分区下暂时不可用）。而2PC的safety依赖协调者不宕机——这个假设在工程现实中是一道巨大的裂缝。

五、库存扣减到底需要什么？

回到文章开头的问题：完成一笔电商订单，需要同时更新订单库（订单状态从”待支付”变”已支付”）和库存库（库存数量减1）。这是一个典型的异构跨库原子操作——两个操作属于不同的业务实体，存储在不同的数据库实例中，但它们必须同生共死。

Raft能解决这个问题吗？不能。

Raft可以保证订单库的三个副本之间数据一致（Master宕了Slave顶上，不会丢数据），也可以保证库存库的两个副本一致。但Raft不能保证订单库和库存库之间的一致性。这是两个独立的Raft复制组，两个Leader各管各的日志。一个提交了另一个没提交，Raft协议完全没有能力干预。

这就是”层次边界”的核心洞见：Raft解决的是基础设施层的状态机复制问题，2PC/TCC解决的是应用层的跨资源原子性问题。

用建筑学的比喻：Raft是打好每个房间的地基，保证每间屋子的地面不会塌陷。但客厅和卧室之间需不需要一个门，门该往哪开，这不是地基能决定的。跨库事务就是那个门的位置——它是业务逻辑层面的协调工作。

回到我们的库存扣减场景，能选的技术方案有三个：

方案一：XA两阶段提交（最直接但最危险）

通过JTA（Java Transaction API）管理跨库的XA事务。订单库和库存库各自作为XA资源参与同一个全局事务。Prepare阶段两个库分别执行SQL并在本地写日志，Commit阶段一起提交。

优点：语义正确，ACID保证完整。缺点：in-doubt问题前面已经分析透了，库存这种热点表一旦有行锁死，下游全部阻塞。即使有自动化恢复，超时窗口内的锁等待也足以在流量高峰期搞垮库存服务。

方案二：TCC补偿型事务（我们的选择）

TCC（Try-Confirm-Cancel）是我们最终落地的方案。它的思路是用”预留→确认/取消”的两阶段模式替代数据库层的锁：

  • Try：在订单表中写入一条状态为”冻结中”的订单记录，同时在库存表中执行UPDATE stock SET frozen = frozen + 1, available = available - 1 WHERE sku_id = ? AND available > 0。这一步不会让其他请求拿不到库存（因为available已经扣了），但库存真正的”归属”还没定。如果Try失败（库存不足），订单侧直接返回失败，两边状态一致。

  • Confirm：订单表状态改为”已支付”，库存表执行UPDATE stock SET frozen = frozen - 1 WHERE sku_id = ?。两个操作都是幂等的——重试不会导致重复扣减。

  • Cancel：如果在Try之后、Confirm之前出了问题（比如支付超时），执行Cancel：订单表状态改为”已取消”，库存表执行UPDATE stock SET available = available + 1, frozen = frozen - 1 WHERE sku_id = ?，释放预留。

这里有一个必须澄清的点：TCC不是共识协议。Try阶段只是锁定了业务资源（调低available、调高frozen），不需要跨节点的数据一致性保证。Confirm/Cancel是两次独立的幂等更新，失败了可以重试。这里的核心假设是：Confirm和Cancel最终一定会成功（通过本地事务+重试机制保证）。这在共识协议的术语里叫”最终达成一致”，但TCC没有用任何Quorum、Leader选举、Log Replication——它只是在业务层面用状态机保证最终一致性。

方案三：Saga（异步解耦场景）

如果业务允许库存扣减可以晚几秒甚至几分钟完成，还可以考虑Saga。订单服务发送”库存扣减”消息到MQ，库存服务消费消息执行扣减。如果失败，发送”补偿”消息反向操作。但这里有个坑：正向操作可能因为网络抖动延迟了几分钟才成功，此时订单已经超过了支付超时窗口自动取消了。Saga的补偿顺序需要业务方自己处理，设计复杂度比TCC高。

六、共识在分布式事务中的真实角色

既然TCC里不需要共识，那共识算法在电商系统里到底用在哪？

第一层：元数据管理。 我们的任务调度集群有四个节点，通过Raft选出Master来分配任务。这个场景是Raft的教科书用例——Leader选举、元数据状态机复制。它的核心要求是”任意时刻只有一个Master”，和TCC的业务事务没有直接关系。

第二层：配置中心。 配置下发需要保证每个服务实例看到的配置是一致的。Apollo用Eureka做注册、数据库做存储，但新一代配置中心（如K/V Store生态）用Raft做配置更新的原子广播。这不是事务，但确实依赖共识来保证一致性。

第三层：事务协调器本身。 这个比较有意思。如果你的TCC框架里有一个统一的”事务协调器”维护全局事务状态，那这个协调器的高可用可以用Raft来保证——多个协调器实例之间通过Raft复制状态，任意一个挂了其他的顶上。但这是为了让协调器不成为单点，而不是用Raft替代TCC。 协调器做了高可用之后，执行Confirm/Cancel的还是TCC协议本身。

把这个图景画出来就是：

每一层都由不同的协议支撑，顶层和下层的关注点完全不交叉。这就是”偷懒”想用一层协议解决所有问题的荒谬之处——它把不同抽象层次的问题强行坍缩成了一个。

七、DDIA第9-10章的中心论题：从原子提交到共识的跃迁

DDIA的第9章”一致性与共识”和第10章”原子提交与共识”其实是一个递进结构。第9章的结论是：需要线性一致性的场景（唯一ID、Leader选举、加锁）依赖共识。第10章则把这个结论反过来：原子提交是共识问题的特例——让多个节点对一个二值结果（commit/abort）达成一致。

这句话很漂亮，但需要细品。它不是说2PC可以当共识协议用（因为2PC不解决容错），而是说如果有一个足够健壮的共识协议，原子提交可以转化为共识问题。DDIA举的例子是ZooKeeper的原子广播（ZAB）和Google Spanner的TrueTime+Paxos组合。这些系统的做法是：把”所有参与者是否同意的决策”变成”把决策写入共识日志”——只要共识层保证了日志的一致性和容错，上层就不再需要协调者了，也不用担心in-doubt。

换句话说：2PC的协调者是集中式的单点，而基于共识的原子提交把这个单点替换成了一个Raft Group。我们的TCC协调器做HA就是这个思路的具体落地——只是我们的共识范围仅限于协调器自身，没有囊括全部参与者的业务数据。

这也解释了一个面试高频问题：”2PC和Raft都是两阶段协议，它们到底是什么关系？” 标准答案不是”没关系”，也不是”一回事”，而是：2PC是原子提交协议（不保证容错），Raft是共识协议（保证容错）。当你在一个容错的共识层上实现原子提交时，你就得到了一个没有单点故障的2PC。

八、为什么这个区分对工程有实际价值

聊了这么多理论，最后回到工程的实用层面。在我的经验里，这个”2PC vs 共识”的混淆在团队中反复出现，粗略估计有以下几个典型变种：

“RocketMQ的事务消息是不是就是不阻塞版的2PC？”——不是。RocketMQ事务消息是两阶段，但第一阶段是发半消息（不投递），第二阶段是确认/回滚。它没有”所有人投票”的语义，而是生产者单方面决定提交或回滚。这是异步的最终一致，不是原子提交。

“用一个大Raft组管理所有数据库节点不就完了？”——Raft写日志的Latency和跨地域的网络延迟成正比。把订单库和库存库放在一个Raft组里，每次写入都要等多数派跨机房确认，吞吐量会降到不可接受。而且跨库SQL的优化器在这种架构下基本报废。

“用分布式锁不就行了？先锁库存再写订单？”——先锁后写是ACID里”掉电丢数据”的典型反例。如果锁库存成功、写订单前进程崩溃，库存被锁死死在谁手里都不知道。分布式锁做幂等还凑合，做原子性保证是南辕北辙。

“用Saga不就够了？”——Saga对隔离性的保证是弱隔离（读未提交），中间状态对外暴露。如果库存扣减和订单创建之间有几秒窗口，在这个窗口里另一个事务读到库存已扣但订单还没创建，数据层面就是不一致的。TCC用Try阶段的frozen字段解决了这个问题（预扣让available数立即可见地减少），隔离性远好于Saga。

这些问题的共同根源，就是没有厘清”我的问题到底是在哪一层”——是需要多副本一致（Raft），还是需要跨资源原子操作（2PC/TCC），还是需要异步最终一致（Saga/MQ）。层次分不清，方案就选不对。

九、总结

回到标题——“电商库存扣减为什么不能偷懒”。这个”懒”指的是企图用一个单一协议解决所有分布式问题。实际操作中：

  • Raft/Paxos 负责每个数据库集群内部的副本一致性——让你放心地知道订单数据不会因为主库宕机而丢。
  • TCC/2PC/Saga 负责跨数据库、跨服务的业务事务一致性——让你放心地知道库存和订单要么一起成功、要么一起失败。
  • 两者解决的是不同层次的问题，无法相互替代。

DDIA整本书的一个核心方法论，就是反复强调**”理解你的抽象”** 。分布式系统的每一层抽象都有其适用边界和失效模式，跨层”偷懒”的结果往往是把一层的失效模式泄露到另一层——就像把2PC的in-doubt问题用Raft掩盖起来，出问题时的排障图表会比代码量还大。

技术决策的价值不在于用了多高级的协议，而在于选对了适合当前问题层次的协议。这大概就是Martin Kleppmann写这两章的初衷。
