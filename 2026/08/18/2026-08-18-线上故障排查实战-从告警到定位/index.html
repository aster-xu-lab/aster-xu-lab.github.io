线上故障排查实战：从告警到定位，一次完整的高 CPU 排查

线上出问题，最考验功底的不是”会背命令”，而是从告警到定位的完整排查思路。这篇用一次真实的高 CPU 排查，讲透我的排查方法论。

一、告警来了，先别慌

凌晨两点，告警群响了：订单服务 CPU 持续 90%+。

我处理线上问题的第一步永远是”保现场 + 看整体“，而不是一头扎进代码：

二、一步步定位

① top 看进程

确认是 Java 应用的问题（不是数据库、不是 IO）。

② 定位线程

④ 看线程栈

⑤ 反查代码

定位到代码：订单处理里有一个重试循环没有上限——某个订单状态异常时，代码会无限重试，把 CPU 烧满。

三、根因与修复

根因是：对某个一直失败的订单，重试逻辑没有设置最大次数和退避，导致 while(true) 空转。

四、排查方法论：四个场景的通用套路

高 CPU 只是线上问题的一种。我把常见场景整理成套路：

场景 1：高 CPU

场景 2：内存溢出（OOM）

场景 3：GC 频繁 / 停顿

场景 4：慢 SQL

五、最值钱的一句话

线上排查最值钱的经验是：先保现场再动手，先整体后聚焦。

  • 一上来就翻代码 = 大海捞针；
  • 一上来就重启 = 现场没了，永远定位不到根因；
  • 正确顺序是”资源 → 进程 → 线程 → 栈 → 代码”，层层缩小范围。

六、诚实的复盘

这次排查能快速定位，是因为平时做了三件事：

  1. 启动参数加了 dump 和 GC 日志（保现场能力）；
  2. 熟悉 jstack/jstat/jmap 的用途（工具熟练度）；
  3. 对订单处理链路熟（业务理解）。

排查能力不是背命令，是”工具 + 现场 + 业务”三者的结合——这也是我 99.99% 可用性背后的真实支撑。

总结

  • 排查顺序：保现场 → 看整体 → 定位进程 → 定位线程 → 定位代码；
  • 高 CPU：top → top -Hp → 线程转 hex → jstack；
  • OOM：先加 dump 参数保现场 → MAT 分析；
  • GC 频繁：jstat 看趋势，老年代增长 = 泄漏；
  • 慢 SQL：EXPLAIN 看索引；
  • 核心心法：先保现场再动手，先整体后聚焦。
