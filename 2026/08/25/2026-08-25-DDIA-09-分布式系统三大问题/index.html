DDIA-09-分布式系统的三大问题：不可靠网络、不可靠时钟、部分失效

DDIA-09-分布式系统的三大问题：不可靠网络、不可靠时钟、部分失效

《Designing Data-Intensive Applications》第 9 章「一致性与共识」是全书最硬核的章节之一。但在讨论一致性算法和共识协议之前，Kleppmann 花了大量篇幅铺垫一个更根本的问题：分布式系统为什么会出错？ 答案藏在三个相互纠缠的概念里——不可靠网络、不可靠时钟、部分失效。理解这三者，是理解一切分布式理论的起点。

一、核心命题：分布式与单机的根本区别

一个刚接触分布式系统的程序员，最容易犯的错误是：把分布式系统想象成单机系统的放大版。

在单机上，函数调用要么成功、要么失败，CPU 执行指令要么对、要么错，内存数据要么完整、要么崩溃。这种「确定性」让单机编程成为一个相对可控的智力活动——你可以通过调试器一步步追踪状态变化，用单元测试覆盖边界条件。

分布式系统完全不同。想象你现在要把一个订单状态更新同步到下游 WMS 系统：你的服务发了一个 HTTP POST，等了三秒没有响应。请问——

  • 请求真的发出去了吗？
  • 对方收到并处理了吗？
  • 是网络断了，还是对方进程挂了，还是对方在处理但太慢了？
  • 你该重试吗？重试了会不会导致重复处理？

在单机上你永远不需要回答这些问题。但在分布式系统中，这恰恰是每一天都要面对的日常。

Kleppmann 把这种根本差异归结为一个概念：部分失效（Partial Failure）。单机系统的失效是确定性的——要么全好，要么全坏；分布式系统的失效是非确定性的——有些节点正常运作，有些节点异常，而你能获得的信息总是滞后和不完整的。

二、不可靠网络：消息可能丢失、延迟、乱序

2.1 TCP 并不能解决所有问题

很多人有一个直觉：「既然我们用的都是 TCP 协议，TCP 有重传和确认机制，那网络不就是可靠的吗？」

这是一个危险的误解。

TCP 确实能在一段连接中保证：如果对端确认收到了数据，那数据一定到达了；如果连接断开，你一定会知道。 但 TCP 不能回答一个关键问题：你发了一个请求，在对端确认之前，数据到底有没有被处理？

典型场景如下：

客户端发了一个扣减库存的请求，然后 TCP 连接断了。此时客户端的 TCP 栈告诉你「连接已断开」，但它不能告诉你：服务端到底有没有执行这次扣减。

  • 可能请求在到达服务端之前就丢了——库存未扣减；
  • 可能请求到达了，服务端处理完成，但 ACK 包在返回途中丢了——库存已扣减；
  • 可能请求到达了，服务端处理完成并发送了响应，但响应包在网络中丢失——库存已扣减。

结论：TCP 提供的是「连接内」的可靠，而不是「语义上」的可靠。 应用层必须自己处理这种不确定性。

2.2 超时重试的两难困境

面对不可靠网络，最自然的应对策是超时重试。但重试本身会引入新问题——

  • 重复执行：如果第一次请求实际成功但响应超时了，重试会导致同一个操作被执行两次。
  • 加重故障：如果下游已经在高负载下挣扎，重试会雪上加霜。Kleppmann 在书中特别提到了这个问题，并建议采用**退避（backoff）**策略，以及更重要的——全局限流。

实战提醒：不要只在单节点上做 local retry + exponential backoff，你还要防止 100 个上游节点同时对同一个下游做退避重试——它们的退避窗口很可能撞在一起。这时需要一个 client-side circuit breaker + retry budget 的组合策略。

2.3 网络拥塞和时间的不确定性

在真实生产环境中，网络问题往往不是「通」或「不通」的二元状态。最常见的故障模式是——

  • 长尾延迟：P99.9 的网络时延可能是 P50 的 10 倍甚至 100 倍。
  • 丢包：交换机缓冲区溢出导致的数据包丢弃。
  • 网络分区：一部分节点和另一部分节点之间完全无法通信，但每组内部仍然正常运行。

这种「半死不活」的状态，比彻底挂掉更难诊断。

三、不可靠时钟：两个节点的时间无法直接比较

3.1 两种时钟，两种误差

分布式系统中的时钟按用途分为两类，但它们都不靠谱——

墙上时钟（Wall-clock Time / Time-of-day Clock）：

  • 即 System.currentTimeMillis() 或 new Date() 返回的时间。
  • 问题一：NTP 同步误差。 两个节点的墙上时钟可能相差几百毫秒甚至几秒——取决于 NTP 同步频率和网络状况。
  • 问题二：NTP 回拨。 如果 NTP 发现本地时钟比服务器快了，它会跳回到正确时间。你的代码可能看到时间「倒着跑」——刚才还是 10:00:05，现在突然变成了 10:00:01。
  • 问题三：闰秒。 闰秒调整可能让同一秒出现两次（正闰秒）或跳过一秒（负闰秒），直接破坏了「时间线性递增」这个基本假设。

单调时钟（Monotonic Clock）：

  • 即 System.nanoTime() 返回的时间（Linux 上的 CLOCK_MONOTONIC）。
  • 它保证一直往前进，不会回拨。
  • 但问题在于： 单调时钟的频率可能漂移。同一台机器上，1ms 间隔的 nanoTime 差值可能偏好几微秒；不同机器之间，根本无法比较。
  • 单调时钟只适用于测量同一节点上的时间间隔（比如计算超时），绝对不能用于跨节点的时间比较。

3.2 时钟顺序信任的危害

一个典型的反模式：用 created_at 时间戳来推断事件的全局顺序。

如果两个订单分别在机房 A 和机房 B 创建，机房 A 的 NTP 慢了 500ms，那你按 created_at 排序出来的结果就是错的——先创建的订单可能排在了后面。

Kleppmann 为此提出了一个关键建议：将时间戳视为置信区间，而非精确值。 比如 Google 的 Spanner 用原子钟 + GPS 将 uncertainty 控制在 7ms 以内（TrueTime API），从而可以用时间戳安全地做出全局顺序判断。但对于绝大多数没有原子钟的普通系统，时间戳只能用于展示，不能用于决策。

3.3 「等待固定时间」vs「等待逻辑条件」

另一个因为时钟不可靠导致的典型 bug：「sleep + 假设数据已经可用」。

在分布式系统中，正确的做法不是等「物理时间」，而是等「逻辑条件」——用消息通知、回调、轮询检查标识位等方式。Kleppmann 明确指出：时钟只能用于测量超时（告诉你可以放弃等待），不能用于保障状态（断言数据已经就绪）。

四、部分失效：分布式系统中最难处理的场景

4.1 不是挂，而是「半挂」

单机系统最常见的两种失败：进程崩溃（确定性的停止工作）或 OOM Kill。分布式系统还有一种独特的失败模式：部分失效。

  • 服务节点还活着，但只对一部分请求无响应（GC 停顿、线程池满）。
  • 数据库主库正常写入，但从库因为磁盘 IO 拥塞同步延迟 30 秒。
  • Redis 集群中两个分片正常、一个分片网络闪断后刚刚恢复（数据可能不一致）。

这些场景的共同特征是：你永远只能从外部观察到间接信号（超时、错误码、延迟上升），而无法像调试单机程序那样直接检查系统内部状态。

4.2 信息的不完整性

Kleppmann 反复强调的一个观点：分布式系统中的节点只能通过消息交换来感知彼此状态，没有共享内存，没有全局时钟，没有「上帝视角」。

这意味着：当你作为节点 A 发现节点 B 没有在规定时间内回复时，你无法区分以下情况——

  1. B 已经挂了。
  2. B 没挂，但网络断了。
  3. B 没挂，网络也没断，但 B 负载过高，处理慢了。
  4. B 没挂，网络也没断，但你的超时阈值设得太短了。

你做出的每一个决策，都是基于不完整的本地信息。这就是分布式系统为什么这么难。

4.3 错误处理的层次

很多系统在设计时只考虑了「正常路径」，错误处理是一个 catch (Exception e) { log.error(...) } 的补丁。Kleppmann 的建议是：把部分失效当作一等公民，而不是异常路径。

具体来说——

  • 配置超时不只是一个运维参数，它是一个设计决策：选择了什么超时阈值，就等于选择了「宁可被误判为故障（false positive）」还是「宁可延误发现故障（false negative）」。
  • 死信队列和人工补偿工单不是失败的设计，而是必须存在的后备手段——因为有些部分失效机器无法自动判断意图。
  • 回滚不一定可行（下游已经消费了消息、第三方已经扣了钱），此时需要**补偿事务（Saga Pattern）**而非简单的 try-catch。

五、应对策：超时检测、幂等操作、租约

面对这三个问题，业界沉淀出了一套经过大规模生产验证的应对模式。以下是经过实践检验的组合拳。

5.1 超时检测：心跳 + Phi Accrual Failure Detector

简单的「ping 三次超时就判死」策略有一个明显问题：短暂的网络抖动会导致频繁的误判和 failover。Cassandra 社区推广的 Phi Accrual Failure Detector 是一个更优雅的方案——

  • 不用固定阈值，而是用动态的可信度。 每次心跳到达或丢失，更新一个「怀疑级别」（Phi 值）。Phi 值越高，表示节点出故障的可能性越大。
  • 自适应网络抖动。 如果某段时间网络整体延迟升高，检测器会自动调整 baseline，不会因为网络拥塞而误判大量节点死亡。
  • 实现核心： 维护一个心跳到达时间的滑动窗口，用指数分布建模，计算当前采样在这个分布中的「异常程度」。

在没有引入 Phi Accrual 的场景下，至少也要做到：

  • 心跳间隔和超时判断解耦（间隔 3s，至少要等 3 个间隔以上才判死）。
  • 增加重连试探阶段（判死后先尝试 re-establish connection，失败再确认）。
  • 判死和判活的阈值不对称（恢复需要更多次连续成功，避免「飘变」）。

5.2 幂等操作：at-least-once + 去重

既然网络不可靠，那不重试是不可能的。但如果你要重试，就必须让操作幂等。

让一个非幂等操作变成幂等，有几种常见手段——

方案一：唯一 ID 去重。
在请求中携带唯一的幂等键（idempotency key），接收方在数据库中记录每个 key 的处理结果。重复的 key 直接返回已有结果，不执行实际逻辑。

方案二：状态机约束。
操作声明前置条件（比如「仅当订单状态为 PAID 才能进入 SHIPPING」），利用状态机的确定性来保证重复执行不会产生副作用。

方案三：端到端幂等。
在下游链路的每一个环节都保证幂等性，使得重试可以在最上游安全地进行。这需要每个接收方都明确支持去重。

5.3 租约（Lease）：带 TTL 的临时授权

锁在分布式系统中如果不带超时是危险的——持有锁的节点可能宕机或 GC 停顿，导致锁永远无法释放。租约（Lease） 通过给锁加上 TTL，确保锁一定会在特定时间后自动释放。

要点：

  • 租约是「权限 + 有效期」的组合，不是锁的简单替代。 持有租约的节点必须在有效期内完成操作，否则应该主动放弃。
  • fencing token 的配合： 在基于锁 + 租约的方案上，还需要一个递增的 token（fencing token），每次获取新租约时 token +1。写操作时携带 token，存储端拒绝比记录中更小的 token——防止一个过期但仍认为自己持有租约的「僵尸节点」做出错误写入。

这就是 Chubby / Zookeeper 底层思想的核心。

六、实战：订单系统时钟漂移的全链路排查

说点亲身经历的。

我们有两个机房（可以理解为两个数据中心的逻辑隔离区），分别叫 S-1 和 S-2。订单系统做了跨机房双活，两个机房的订单服务各自独立接收请求、写本地缓存。

某天客服反馈：「一个用户下了两单，第二单的时间显示比第一单还早。」

排查链路如下——

  1. 确认问题范围： 不是偶发，而是高频出现，且全部集中在「第一单在 S-2 创建、第二单在 S-1 创建」的组合上。
  2. 查看服务器时间： S-1 和 S-2 全部运行 NTP 服务，且都配置了同一个 NTP 服务器。但用 ntpq -p 检查发现，S-2 的 offset 稳定在 +450ms 左右（即 S-2 的时钟比 NTP 服务器快 450ms），而 S-1 的 offset 在 ±50ms 范围内。
  3. 根因定位： S-2 所在的物理机（当时还是混合部署）有一个老化硬件时钟（RTC），NTP 在校准时可以补偿 offset，但 NTP 不能修改硬件时钟本身。每次 NTP 服务重启（部署时偶发），会短暂地用硬件时钟初始化，然后又慢慢修正回来——导致墙上时钟在一个区间内来回跳动。
  4. 为何 NTP 没完全修正： 我们配置的 NTP 采用 slew 模式（ntpd -x），即通过调节时钟频率而非直接跳变来修正偏差。450ms 的 offset 需要数分钟才能完全恢复。在这个恢复窗口内产生的订单，created_at 就不可靠。

解决方案：用全局有序 ID 替代时间戳排序

短期止血：

  • 统一到单个 NTP 时间源（两台机器的 NTP server 一致），加大同步频率。
  • 监控各个节点的 NTP offset，超过 200ms 告警。

长期解法（根本性解决）： 不再依赖墙上时钟做排序。

我们引入了基于雪花算法（Snowflake）的全局唯一 ID 作为订单的主键和排序依据：

  • 41 位毫秒时间戳 + 10 位机器 ID + 12 位序列号。
  • 毫秒时间戳来自单调时钟（用服务启动基准时间 + System.nanoTime() 差值推算），不受 NTP 回拨影响。
  • 即使两个节点的时间存在微量偏差，机器 ID 的差异也能保证 ID 的全局唯一性。
  • 订单列表排序改为 ORDER BY id DESC，时间复杂度不变，可靠性质的飞跃。

这次事故的教训：永远不要在分布式系统中把墙上时钟当作因果顺序的依据。 时间戳可以作为辅助信息展示（用户看到的「下单时间」），但不能参与任何业务逻辑判断——排序、幂等判定、因果推断，都不能依赖它。

七、回到 SyncTask：超时控制与幂等设计的工程落地

这部分是我在 SyncTask 驿传引擎中的实际工程实践，刚好对应了 DDIA 第 9 章对超时和幂等的论述。

7.1 V2 版本的 CompletableFuture 超时控制

SyncTask 引擎最初的 V1 版本是基于 XXL-JOB 的分页拉取 + 同步串行处理。一个显著的痛点是：如果某个 Handler 调用下游超时或者死循环，整个执行线程会被卡住。

V2 版本的架构修复了这个问题。核心设计：

  • 每个 Handler 的执行被包装为 CompletableFuture，放入线程池异步执行。
  • 主线程用 get(timeout, unit) 整体等待，超时后主动中断未完成任务。
  • 超时的 Future 会被标记为 FAILED，对应的批次记录写入 task_execution_log 表，方便后续人工补偿或自动重试。

这里也暗合了 Kleppmann 提到的「超时不只是一个运维参数，而是设计决策」——我在 V2 中把超时值从常量改为了按 Handler 可配置的字段。为什么？因为不同的下游有不同的 SLA，一个调用「华为 ERP」的 Handler 和调用「金蝶财务」的 Handler 的超时阈值绝不可能是同一个数字。

7.2 幂等设计的落地

SyncTask 引擎的任务模型天然支持幂等：每个任务有唯一 taskId，关联了 businessKey（业务唯一键）和 taskStatus。关键设计如下——

  • 状态机保护： 任务状态流转严格遵循 PENDING → PROCESSING → SUCCESS/FAILED。幂等判断前置在 PROCESSING 之前的 PENDING 状态——如果任务已经在 PROCESSING 状态，重复触发直接返回已有结果。
  • 分布式锁 + 状态双重保护： 即使锁因为 Redis 租约过期而释放（5.3 节讨论的问题），状态机的约束也能拦截「拿到了过期锁的僵尸节点」——因为状态已经不是 PENDING 了。
  • rentry-safe 的业务执行： 所有 Handler 的执行都被鼓励设计为可重入的，即如果被中断后重新调度，不会产生副作用。做不到的地方，用 task_execution_log 记录完整上下文，由人工兜底。

7.3 回看 DDIA 的「真相由多数派决定」

第 9 章后半部分讨论了 Quorum、两阶段提交、共识算法，Kleppmann 的核心论点是：在分布式系统中，单个节点不能宣判自己是正确的——真相必须由多数派决定。

这和 SyncTask 引擎的设计有直接呼应：

  • afterExecute 编排模式（Choreography）取代 DAG： 放弃集中式编排者的原因之一，就是不想把「这个任务链的下一步是什么」的决定权交给单一节点——如果一个节点挂了，整条链的状态就消失了。afterExecute 模式让每个 Handler 自行决定「我完成后把接力棒交给谁」，相当于每个参与者都参与了决策。
  • 任务状态被持久化到数据库（TaskStore），而不是内存： 这意味着即使执行节点完全挂掉，状态不会丢失，新节点可以从数据库读取状态后继续。数据库成了「多数派」的代言人——只有 commit 到数据库的状态才是真实的。
  • 可插拔的 LockService（默认 Redis）： 锁本身可以被替换（比如换成 Zookeeper 的 ephemeral node），但锁的语义不变——被锁保护的那个资源，其当前状态的真相必须经过这个锁的仲裁。

八、总结：三个问题的统一思想

把不可靠网络、不可靠时钟、部分失效串起来，它们指向同一个核心思想——

分布式系统中的节点，没有全局视图，没有同步时钟，网络随时可能割裂。你能做的，不是消除不确定性（这不可能），而是设计能在不确定性中仍然正确运行的系统。

具体而言：

  1. 对于网络： 接受「消息可能丢 / 可能晚到」，用超时 + 幂等 + 退避来兜底，而不是假设网络一直通畅。
  2. 对于时钟： 永远不用墙上时钟做逻辑决策（排序、因果、幂等）。用逻辑时钟（版本向量、事务 ID）替代物理时钟。
  3. 对于部分失效： 设计系统时默认「任何节点随时可能部分失效」。状态机、租约、fencing token、重试和补偿都是基础设施级的必需品，而不是「可选异常处理」。

DDIA 第 9 章用一个很妙的话收束了整章：「分布式系统的问题，最终都是信息问题。」（原话是说共识问题的本质是「达成一致的过程就是一种信息传递」，我引申一下。）你设计超时、重试、租约、幂等，本质上都是在设计如何在不完整信息的条件下做出安全决策。

理解这一点，比记住任何具体算法都重要。因为具体算法你随时可以查到，但这个思维框架——在不确定性中做安全决策——必须长在骨子里。
