分库分表上线一周年复盘：稳态运营、对账与扩容规划

2025 年下半年分库分表上线，到 2026 年 8 月正好一年。这一篇复盘”上线之后”的事——不是迁移怎么做（那篇讲过），而是稳态运营、对账机制、以及 8→16 扩容的推演。这才是分库分表真正见功夫的地方。

一、稳态现状

  • 当前 8 片，每片约 750 万行，累计 6000 万行；
  • 分片键单号（order_no），写路径零广播；
  • 复杂统计查询下沉 Doris（Canal → Kafka 同步）。

上线的”那一刻”不难，难的是一年里每天的对账、监控、扩容规划。

二、稳态运营：三件事

1. 对账是常态，不是一次性

分库分表后，正确性不能靠”迁移时对一次账”就完了——数据每天在变，对账要常态化。

我的对账机制：

选型边界：纯比对用 XXL-JOB 单选跑（迁库批处理、无编排需求）；差异重投才走 SyncTask（要可靠投递、可能重试）。

2. 监控：分片健康度

分库分表后要盯的监控变了：

  • 分片数据倾斜：每片行数/写入量是否均匀（单号哈希分布，理论上均匀，要验证实际）；
  • 跨片查询：是否出现意外广播（应该是 0）；
  • 慢 SQL 分布：慢 SQL 落在哪个分片、是否某片热点。

3. 踩坑的持续修复

上线一年遇到的兼容性问题：

  • PageHelper 分页冲突：跨分片分页会内存归并，深分页贵 → 禁大页码、改游标分页；
  • 非分片键查询：按用户查订单 → 建 user_id → order_no 索引表，二次路由；
  • 跨分片 JOIN：关联表同键分片（订单主表/商品表/地址表都用 order_no），片内本地 JOIN。

三、扩容规划：8→16 的推演

单号哈希分片，扩容必然 rehash——hash(order_no) % 8 变成 % 16，落片变化，大约一半数据要迁移。

关键推演：

  1. 要动多少数据：8→16，约一半行数（3000 万行）需要换分片——这是个大工程，不能停机；
  2. “双写”是零侵入增量双写：新老分片并存期间，binlog/Canal 异步把新写补到新表，业务只写老表，不应用层改代码双向写；
  3. 零停机切换靠 Nacos 配置热更：业务写逻辑表，路由层映射物理表，换表名 = 改路由配置（Nacos 下发），应用不重启；
  4. 对账不过不切流：连续两轮差异 0 才切，灰度按渠道逐个切，随时可回滚。

为什么现在规划而不是等数据满了再想：扩容的推演（数据量、流程、工具）提前验证过，真到触发时是按流程走，不是现场发明。

四、一个诚实的算账

扩容的代价要算清楚：

  • 8→16 要迁移约一半数据，磁盘、网络、时间成本都高；
  • 能不能不加片？比如清理历史数据（终态订单归档）、优化压缩比——先试便宜手段，扩容是最后手段（和”先索引后分库分表”一个原则）。

所以现在的策略是：能归档的先归档、能优化的先优化，8→16 作为已推演好的后备方案，触发条件（单表逼近千万级/写入瓶颈）到了才上。

五、复盘：上线一年最大的收获

  1. 分库分表不是”上线即结束”，是”持续治理的开始”——对账、监控、兼容性修复是常态；
  2. 扩容的难不在”搬数据”，在”无停机 + 对账 + 可回滚”——提前推演、按流程走，比现场发明可靠；
  3. 先便宜后贵：归档、优化能拖后扩容，就不要急着加片。

总结

  • 稳态：8 片 / 750 万每片 / 6000 万行，写路径零广播；
  • 对账常态化：定期比对 MySQL vs Doris，连续两轮差异 0 才一致；比对用 XXL-JOB、重投用 SyncTask；
  • 监控：分片倾斜、跨片查询、慢 SQL 分布；
  • 扩容 8→16：rehash 约一半数据，回填 + 增量追平 + 对账 + 灰度 + 删旧表，Nacos 热更零停机；
  • 先归档/优化拖后扩容，扩容是最后手段；
  • 收获：分库分表是持续治理，不是一次性上线。
