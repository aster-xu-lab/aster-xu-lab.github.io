DDIA-01-从130万日订单看架构权衡：没有银弹只有取舍

AsterXu Lab · DDIA实战笔记第1篇
作者技术背景：7年Java后端，技术主管，电商供应链中台
核心资产：SyncTask驿传引擎（独立组件，5模块/10 SPI/93 Handler），V2版本作者
系统指标：日订单峰值130万，可用性99.9%→99.99%，日均慢SQL 1124→6条，QPS 2000→8000+

130万日订单：并发到底多大？

面试官最爱问：「你说130万日订单，那并发是多少？」

这里得把数字算清楚。130万订单不是均匀分布在24小时的，我们电商平台有明确的高峰规律：早10点到晚10点是活跃时段，其中晚7点到9点是巅峰。经验数据是 80%的订单集中在30%的时间段内。

算一下：

  • 日均130万 → 高压时段（7h）订单量 ≈ 130万 × 80% = 104万
  • 高压时段平均QPS ≈ 104万 ÷ 7 ÷ 3600 ≈ 41 QPS
  • 峰值QPS（经验系数 35 倍）≈ 41 × 5 ≈ **200210 QPS**

看起来不高对吧？但魔鬼都在细节里：

  1. 订单创建本身不是瓶颈——一个下单接口平均耗时120ms，210 QPS 需要约25个Tomcat线程就打发了。
  2. 真正的瓶颈在「下单后」：库存扣减、营销锁券、支付通知、履约拆单、物流调度、短信推送……一个下单操作触发的是10+个下游服务调用，实际系统负载是表象的10倍以上。
  3. 数据库才是杀手：210 QPS的订单写入，带上库存、营销、支付等关联读写，DB的实际承载轻松到 3000~5000 QPS。在这个量级，不当的索引设计、长事务、锁竞争都会把DB拖垮。

我们当时日均慢SQL 1124条的现状，就是这么来的。

带着这个真实压力，下面拆解4个我们亲手做过的架构权衡。

权衡1：同步vs异步——支付通知为什么必须用MQ？

场景还原

用户支付成功后，支付宝/微信会回调我们的支付通知接口。收到通知后需要做：

  1. 更新支付单状态
  2. 更新订单状态（待支付→已支付）
  3. 触发分账结算
  4. 触发履约（拆单→仓库→WMS）
  5. 推送通知（App推送+短信）
  6. 埋点上报

如果同步执行这些逻辑：

  • 接口响应时间至少 800ms~1.5s
  • 支付渠道有超时重试机制，响应慢会触发重复通知
  • 任何一个下游服务抖动，支付回调就失败了
  • 回调失败→渠道重试→重复通知→幂等逻辑复杂

我们的选择：同步收，异步发

实际的实现是：

支付回调接口只做两件事：验签 + 落库，然后发一条MQ，50ms内返回。

代价是什么？

代价1：用户看到「支付成功」但订单仍显示「待支付」

这是最终一致性的经典场景。用户在支付完成页面点「返回商家」，看到订单还是「待支付」——我们约定的SLA是 支付成功后3秒内订单状态必须刷新。实际监控P99是1.2秒，可以接受。

代价不是不处理，而是设定一个业务上能容忍的SLA。

代价2：消息丢失风险

MQ不是100%可靠的。Broker宕机重启前未刷盘的消息会丢。我们的应对：

  • 支付通知接口在发MQ后会落一条「支付事件」记录（同一个本地事务）
  • 定时任务每5分钟扫一遍「支付成功但订单状态未更新」的支付事件，补偿处理
  • 这就是 事务发件箱模式的简化实现

代价3：消息顺序性问题

同一个用户的连续操作（支付→退款→重新支付），如果消息乱序到达，订单状态可能错乱。我们的解法是：订单状态机 + 乐观锁版本号。状态只能正向流转（待支付→已支付→已发货→已完成），非法转换直接丢弃+告警，而不是依赖消息顺序。

这个权衡的本质

DDIA第五章讲复制滞后的时候提过一个观点：异步复制带来的是滞后，但只要SLA在业务容忍范围内，它就不是Bug而是Feature。 支付通知的异步化完全同理。

如果追求同步调用链——收银台回调→RPC调订单→RPC调履约→RPC调通知——系统耦合度会爆炸，任何一个下游慢都会影响支付体验。而支付体验是电商的命门，绝对不能碰。

结论：对于支付通知这种「通知方等不起，处理方可延迟秒级」的场景，MQ异步是压倒性的正确选择。代价用补偿机制兜底，而不是用同步来回避。

权衡2：强一致vs最终一致——库存超卖的天花板在哪？

这个问题的起源

库存扣减有个经典争论：用Redis扣库存还是直接查库扣？

Redis方案：预热库存到Redis，下单时先decr，高性能，但数据不一致时会出现超卖。
数据库方案：UPDATE inventory SET stock = stock - 1 WHERE stock >= 1，绝对正确，但高并发下DB扛不住。

多数文章说到这就结束了，给出一个结论：「用Redis+Lua保证原子性就行」。实际远没那么简单。

我们踩过的坑

我们一开始也是Redis方案。逻辑很简单：

运行三个月后，库存对账发现：实际超卖率约 0.03%。210 QPS场景下，每天超卖约 39单。每一单都要客服介入、赔优惠券、用户体验极差。

排查原因：不是Redis原子性问题，而是 缓存与DB不同步。场景如下：

  1. 运营在后台改库存（例如从100改成50）
  2. 改库后缓存刷新有延迟（即使是50ms）
  3. 这50ms内，Redis里还是100
  4. 下单扣成功，但实际库存应该是50，超卖了

运营操作不是高并发场景，但它是 人工操作，频率低影响大。

最终方案：读Redis+写DB双重检查

我们最后的实现是：

关键点：

  • Redis只是预扣，不是最终扣减的真相来源
  • DB是最终裁决者，乐观锁保证不会超卖
  • Redis DECR成功但DB UPDATE失败时，INCR回滚，代价极小（多一次Redis往返）
  • 库存对账任务每10分钟跑一次，用DB库存校准Redis

代价又是什么？

Redis预扣 + DB双重检查，每次扣库存比纯Redis方案多了 一次DB UPDATE（约8~15ms）。但因为我们用连接池 + HikariCP，210 QPS场景下，库存DB的QPS约是 210 × 2（Redis+DB）= 420 QPS，数据库完全扛得住。

如果QPS到5000+呢？那就要引入 库存分片——按SKU ID hash到不同库存实例。但我们目前不需要，就不引入。

这个权衡的本质

DDIA第七章（事务）讲隔离级别的时候说：Serializable是最安全的隔离级别，但性能代价最大。Read Committed有各种异常，但用得最广。 选什么隔离级别，取决于你能否承受那些异常。

库存扣减同理：Redis纯扣方案就是Read Committed级别——大部分时间正确，偶尔出问题。DB双重检查是Repeatable Read级别——更安全，代价略高。 我们没有追求强一致（Serializable级别，也就是DB独占锁扣库存），因为业务上不需要——允许短暂的不一致，用最终一致性补偿。

结论：库存扣减的正确答案不是「选Redis还是选DB」，而是「用Redis做性能层，用DB做正确性层，两层协作」。超卖的本质不是技术选型问题，是没有为不一致场景设计兜底方案。

权衡3：单体vs微服务——订单中心拆不拆？

当时的状态

我们在做供应链中台时面临一个决定：订单中心要不要从大单体里拆出来变成独立微服务？

当时的现状：

  • 订单业务已经相对独立，有20+张订单相关表
  • 订单团队4人，基本是独立迭代
  • 其他服务（商品、营销、支付）和订单有大量联表查询
  • 大单体是一个Spring Boot应用，war包部署，启动一次要90秒

我推翻了拆分的提议

团队里有人建议直接拆，因为「微服务是趋势」。我拦住了，原因是：

1. 联表查询的杀伤力

订单列表接口需要联表查商品名称、SKU规格、营销活动名称、店铺名称。单体里一个SQL：

拆成微服务后变成：查订单→RPC查商品→RPC查SKU→RPC查营销→组装返回。原本20ms的SQL变成4次RPC调用，正常跑100ms+，P99能到300ms。这不是优化，是劣化。

2. 分布式事务是买一送十

拆之前，订单创建 + 库存扣减 + 营销锁券在一个本地事务里，1秒搞定。拆之后：

  • 订单服务写order表
  • RPC调库存服务扣库存（分布式事务）
  • RPC调营销服务锁券（又一个分布式事务）

当时我们用Seata AT模式做2PC（两阶段提交）。

然后就爆了：

  • 全局事务超时设30秒，高峰期锁持有时间长，锁竞争严重
  • AT模式依赖全局锁 + undo_log，undo_log表膨胀到2000万条
  • 一次订单创建涉及3个RM（资源管理器），任何一个超时，全局事务回滚
  • seata-server挂了整个分布式事务体系瘫痪

日均超时事务437个，用户看到的报错率飙升。

分布式事务从2PC改TCC

AT模式不行，我们决定上TCC（Try-Confirm-Cancel）。对于订单创建场景：

TCC没有全局锁，也没有undo_log膨胀问题。但代价是代码复杂度翻倍——每个服务要写Try/Confirm/Cancel三套逻辑，还要处理空回滚、幂等、悬挂这些TCC的经典坑。

效果：事务超时率从 3.7% 降到 0.1% 以下，整体性能提升约 40%。

那到底拆不拆？

我们最终的策略是：不拆订单中心，拆履约引擎。

为什么？

  • 订单查询场景大量联表，拆了性能劣化明显
  • 履约（订单→拆单→调度仓库→WMS）是异步链路，天然适合拆分，且无联表查询
  • 订单中心保留在单体里，履约独立为微服务

这是一个务实的选择。DDIA第四章（编码与演化）讲向后兼容的时候提到：架构演进的目标不是追求某个技术名词的正确性，而是让系统在可控的代价下持续交付业务价值。

结论：微服务拆分不是判断题（拆or不拆），而是选择题（拆哪个）。评价标准只有一个：拆了以后，性能和数据一致性代价能否被业务价值覆盖？订单中心拆了是负收益，履约引擎拆了是正收益——这就是决策的全部。

权衡4：自研vs开源——SyncTask为什么寄生在xxl-job上？

SyncTask是什么

同步任务驿传引擎是我们的核心组件。本质是一个异步任务编排调度框架，负责处理电商履约链路的复杂任务流转：订单拆单→仓库匹配→WMS下发→物流回传→签收完成。

V2版本的核心设计：

  • 5个核心模块：Core、Scheduler、Handler、SPI、Monitor
  • 10个SPI扩展点，93个Handler
  • 放弃DAG编排，用 afterExecute Choreography模式（架构减法）

为什么不从零造轮子？

这是团队里争议最大的一个决定。有人说：「我们业务这么特殊，xxl-job能hold住吗？不如自研一个分布式调度引擎。」

我的判断逻辑很简单：

第一问：xxl-job能解决我们多少问题？

任务调度、失败重试、分片、管理后台——这些xxl-job全有，而且久经考验。我们不是在做调度引擎的公司，我们的核心价值在「任务编排逻辑」上。

第二问：如果基于xxl-job改造，改造成本多大？

xxl-job提供了标准的IJobHandler接口，extend它并注入我们的编排逻辑即可。核心代码不到500行，对接成本极低。

第三问：自研的额外收益是什么？

几乎没有。调度器本身不产生业务差异化——调度策略、重试策略、分片策略这些都是标准需求，行业有成熟的实现范式。自研一个，功能不会比xxl-job多，但bug一定比xxl-job多——因为xxl-job有几千个生产环境在验证。

「寄生」而不是「从零」

最终方案：SyncTask作为xxl-job的一个执行器寄居在xxl-job调度中心上，xxl-job管调度，SyncTask管编排。

架构图简化：

我们只做了自己必须做的事情——编排引擎。调度、分片、重试、监控面板全部复用xxl-job。

后来为什么放弃了DAG？

这其实是我们做过的另一个关键权衡。任务编排普遍做法是DAG（有向无环图），但我评估后认为：

  1. 我们的履约链路本质上是线性流程：拆单→仓库匹配→WMS→物流→签收，不是复杂的图结构
  2. DAG需要定义节点和依赖，90%的场景我们只用到了它的线性子集
  3. DAG的节点定义依赖、循环检测、图遍历，给调试和排查带来了大量心智负担
  4. 运维看到DAG配置一脸茫然，出了问题排查路径不直观

所以V2版本直接用 afterExecute Choreography模式——上一个Handler执行完后，通过 SPI 回调链决定下一个Handler是谁。没有图，没有依赖定义，代码即文档：

DDIA的作者Martin Kleppmann说过一句话我很认同：「好的架构不是做了多少加法，而是敢做减法。」放弃DAG是一次减法，寄居xxl-job是另一次减法。

代价是什么？

  • xxl-job版本升级时可能需要适配
  • 调度逻辑依赖于开源项目Roadmap，但我们fork了稳定版，影响可控
  • 社区版功能上限——比如我们想要的分片策略社区版不提供，只能自己拓展

这些代价和「从零自研一个调度引擎+持续维护两年」相比，不值一提。

结论：自研vs开源的选择标准不是「能不能做」，而是「做了以后的长期维护成本，值不值得现在省下来的改造成本」。用寄居模式把自研部分压缩到最小，是我们最正确的架构决策之一。

结尾：没有银弹，只有场景下的最优解

《人月神话》里Fred Brooks提出了「没有银弹」这个论断。DDIA这本书本质上就是在讲同一件事——分布式系统涉及的每一个问题（复制、分区、事务、共识），都没有放之四海而皆准的解法。

回顾我们四个核心权衡：

权衡 我们的选择 付出代价 为什么值
同步vs异步 支付通知MQ异步 最终一致性3秒窗口，消息丢失风险 支付接口50ms响应，不被下游耦合
强一致vs最终一致 Redis预扣+DB双重检查 每次多一次DB UPDATE 超卖率降到零，DB扛得住
单体vs微服务 不拆订单中心，拆履约引擎 订单模块仍在单体中 避免联表查询劣化，分布式事务可控
自研vs开源 SyncTask寄生xxl-job 依赖开源版本迭代 专注编排引擎，不改造成调度

如果把架构决策比作投资：

  • 纯技术驱动是赌博——因为新技术而用新技术，大概率亏钱
  • 纯业务驱动是保守——永远不动架构，债务越积越多
  • 好的架构决策是在技术投入和业务收益之间找到平衡点，并且为每一种代价设计兜底方案

130万日订单这个量级，既不是小打小闹（不需要考虑分布式问题的阶段），也不是巨头级别（需要完全自研基础设施的阶段）。正因如此，架构权衡才显得格外重要——资源有限，每一次选择都意味着放弃另一个方案的全部收益。

DDIA教会我的不是某个具体的技术方案，而是一种思维习惯： 做任何架构决策之前，先问三个问题：

  1. 这个方案的代价是什么？我能不能兜住？
  2. 如果不做，业务能跑多久？
  3. 今天的最优解，3年后还是最优解吗？

如果你也在做架构决策，建议把这3个问题贴在显示器上。

毕竟，架构师的核心竞争力，从来就不是「知道多少种方案」，而是「在什么场景下选什么方案，以及对代价心知肚明」。
