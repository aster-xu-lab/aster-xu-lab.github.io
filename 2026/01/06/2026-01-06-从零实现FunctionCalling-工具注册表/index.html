从零实现 Function Calling：一个 39 行的工具注册表

定位：这是一篇学习笔记——我为了搞懂 Agent 原理，自己动手实现了一遍 Function Calling 基础设施。它是个 demo，不是生产框架。

一、Function Calling 到底在做什么

概念上，Function Calling 是”让 LLM 输出结构化 JSON，声明要调用哪个函数、传什么参数”（原理我在另一篇《Function Calling：结构化输出的工具调用》里讲透了）。

二、Tool 接口：一个工具就是 4 个方法

4 个方法各有各的受众：

  • name() 和 description() 是给 LLM 看的——模型根据描述决定”该不该调、调哪个”；
  • parameters() 是给 LLM 和程序共用的——LLM 按 schema 填参数，程序按 schema 校验；
  • execute() 是给 程序执行的——LLM 只输出”调用声明”，真正干活的是这里。

一个工具就类比一个 Service 方法，只是调用者从代码变成了 LLM。

三、ToolRegistry：Agent 的工具箱

核心是 getDefinitions() 和 execute() 两个方法，正好对应 Function Calling 的两个方向：

  • 告诉模型”我有啥”：getDefinitions() 把所有工具转成 name/description/input_schema 清单，随请求发给 LLM；
  • 模型说”我要用 X”：execute() 按名字从注册表查到工具，把 LLM 填的参数传进去执行。

四、LlmClient：大脑的连接

chat() 接收对话历史和工具清单，返回一个 LlmResponse。这个响应的设计是整个调用链的关键——它把”模型的两个意图”暴露出来：

模型每次响应只做两件事之一：要么完成任务输出文本（end_turn），要么想调一个工具（tool_use）。 把这两件事判出来，Agent 的循环逻辑就成立了。

五、设计洞察：注册表模式，我在 SyncTask 里见过

写完 ToolRegistry 我有种强烈的既视感——它和我做的 SyncTask 引擎的 HandlerRegistry 是同构的：

SyncTask HandlerRegistry Agent ToolRegistry
注册 register(handler) register(tool)
路由 handlerKey 找实现 toolName 找工具
执行 handler.execute(param) tool.execute(args)
暴露 给调度器 给 LLM（工具清单）

“定义能力 → 按需调度 → 可扩展”这套骨架，和决策者是代码还是 LLM 无关。 这也是我理解 Agent 最快的捷径——我不是在学一个全新概念，而是在用一个熟悉的架构模式套一个新的决策者。

六、诚实的边界

这套代码是学习 demo：没有超时、没有重试、没有并发控制、没有日志链路。生产级的 Function Calling 基础设施要补的东西很多，但骨架是同一副——Tool 接口 + 注册表 + 客户端。把骨架看懂了，再看 Spring AI、LangChain 的实现，就是看它怎么把这个骨架武装起来了。

总结

  • Tool 接口 4 个方法：name/description/parameters/execute，前两个给 LLM，后两个给程序；
  • ToolRegistry 两个关键方法：getDefinitions()（告诉模型有啥）、execute()（执行模型选中的工具）；
  • LlmResponse 判定：end_turn = 完成，tool_use = 想调工具——这是 Agent 循环成立的前提；
  • 注册表模式与 SyncTask 的 HandlerRegistry 同构，是迁移理解 Agent 的捷径；
  • 学习 demo 的骨架，生产级要补超时/重试/并发/日志。
