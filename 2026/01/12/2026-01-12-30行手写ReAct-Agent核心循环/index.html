30 行手写一个 ReAct Agent：每一行都看得懂

定位：学习笔记。我把 ReAct 循环亲手写了一遍，整个 Agent 核心就是 30 行 Java——不多不少，每一行我都知道它为什么在这。

一、Agent 的本质是 3 行伪代码

先把”Agent 很神秘”的滤镜摘掉。Agent 的本质就 3 行：

  • think：LLM 思考下一步做什么；
  • act：决定调用工具（或直接输出最终答案）；
  • observe：拿到工具结果，丢回对话，继续循环。

用 Java 类比：一个带反馈控制的工作流引擎——LLM 判断下一步要调哪个 Service 方法，调用后根据返回值决定继续还是结束。

二、完整代码：30 行

三、逐段讲：每一行为什么存在

① 初始化 history

对话历史是 Agent 的”短期记忆”。第一行把用户目标放进去，之后的每一轮思考都基于完整的 history。

② for 循环 + maxTurns 安全阀

没有循环上限的 Agent 是危险的——如果 LLM 一直想调工具（比如逻辑错误），会无限循环烧 token。maxTurns = 10 就是保险丝：10 轮还完不成，直接返回”任务未完成”。

③ LLM 思考

把完整对话历史 + 工具清单一起发给 LLM。注意是”完整历史”——每一轮的工具调用结果都要回填，模型才能基于前面的观察做下一步决策。

④ 两个分支：结束 or 调工具

这就是上一篇文章里 LlmResponse 的两个判定：end_turn = 模型认为任务完成，输出最终文本；tool_use = 模型想调工具。

⑤ 执行工具 + 回填结果（关键）

这是 ReAct 循环的闭环：LLM 说”调用 get_current_time” → 程序执行拿到时间 → 把”工具执行结果”以 tool 角色的消息加回 history → 下一轮 LLM 就能看到这个结果，继续推理。

没有这一步回填，Agent 就是个”只说话不干活”的对话机器人。

四、三个设计点

回头看，30 行里藏着三个关键设计：

  1. 安全阀：maxTurns 上限，防无限循环烧 token——生产级要更细（超时、token 预算）；
  2. history 手动管理：每一轮的工具结果主动回填，显式、可控、每一步可见——这是自实现最大的价值：调试时你能看到 Agent 每轮在想什么、调了什么、拿到了什么；
  3. 判定靠 stopReason：end_turn / tool_use 两个状态驱动分支，模型每轮只有这两种意图，逻辑就简单了。

五、诚实地看：这和”生产级 Agent”差什么

30 行是”最小可跑”的 Agent 循环，离生产差得远：

  • 没有超时：LLM 接口卡住，整个循环就卡死；
  • 没有重试：某轮工具调用失败，直接断；
  • 没有并发/隔离：多用户同时跑就乱；
  • 没有持久化：history 在内存里，进程一死全丢。

但这些差距恰好说明一个道理：Agent 的”智能”在 LLM 里，不在 Agent 框架里。 框架要解决的，是循环、状态、可靠性这些”工程问题”——而这正是我做 SyncTask 任务编排引擎的老本行。

总结

  • Agent 本质 = think → act → observe 循环，30 行 Java 即可跑通；
  • 三个关键设计：maxTurns 安全阀、history 手动回填、stopReason 双分支判定；
  • 自实现的最大价值是每一步可见——调试时清楚知道 Agent 在想什么；
  • 离生产差的（超时/重试/并发/持久化）都是工程问题，不是”智能”问题；
  • 学习 demo，诚实标注。
