SyncTask 引擎设计复盘：为什么主动选择"不做 DAG"

订单中台 49 个同步 Handler、仓储系统 44 个同步 Handler，两套业务同步逻辑 80%+ 重复。SyncTask 引擎从重复中抽离。这篇复盘它的核心设计决策——尤其是”为什么主动不做三件事”。

一、背景：80% 重复的同步逻辑

订单中台和仓储系统都有大量”对异构下游同步”的任务：取参 → 拉数 → 加锁 → 执行业务 → 更新状态，这套流程两套系统完全一样，只是业务不同。

解法不是”再写一套”，是抽离引擎：把重复的执行逻辑抽成 SyncTask Engine，业务方只实现 Handler，其余用默认。

二、评估过的 6 个开源方案

动手前评估了 6 个方案，各有各的”不适配”：

方案 不适配的原因
Temporal 需独立 Server + Cluster，运维成本高
Conductor 依赖 ES 存储，重
nFlow 学习成本高
Flowable BPMN 审批领域，和任务同步场景不同
DBOS Transact 要求 Postgres
xxl-job 只管调度，不管编排

结论：要么重、要么领域不匹配。于是决定自己做一个”恰好够用”的引擎——并主动选择不做三件事。

三、三个”不做”决策

1. 不引入 DAG 编排引擎

90% 的同步任务之间无依赖关系——每个任务独立跑就行，DAG 的”依赖编排”能力根本用不上。

有依赖的少数场景（比如”先同步库存、再同步订单”），用 afterExecute 埋点（Choreography 模式）实现：

为什么 Choreography 而不是 DAG：

  • DAG 适合”流程预先可确定”——但同步任务的执行链是事件驱动的，一个任务干完才知道要不要触发下一步；
  • Choreography 用 sync_task 表作为事件载体，context.properties 透传上下文，零引擎、零 DSL、零维护成本；
  • 11 个 Handler 覆盖链式同步场景，DAG 在这里是过度设计。

2. 不引入独立调度 Server

引擎寄居在 xxl-job 之上（@XxlJob 桥接），通过 SchedulerAdapter SPI 解耦——可替换为 PowerJob 或手动触发。

为什么复用 xxl-job：公司已有 cron 基础设施，为编排引擎再引入一套调度 Server（Temporal 那样），运维成本不划算。SPI 解耦保证了”今天用 xxl-job，明天想换 PowerJob，只改适配器”。

3. 不引入引擎内部延迟队列/退避算法

用”多 Job 分工 + 差异化 cron“实现每种状态独立的差异化重试心跳：

本质是用组合现有基础设施替代写代码——不自己实现延迟队列，而是用多个 Job 的分级频率模拟。

四、可靠性的两个核心设计

双重防重

分布式锁 + 二次查库：先拿 Redisson 锁保证同一任务不被并发执行，执行前再查一次库确认状态没变。即使锁偶尔异常，重复执行也会被幂等收敛。

双层权重调度

  • 第一层：Job 内状态配额（INIT:WAIT:FAIL = 4:1:1）；
  • 第二层：多 XXL-JOB 实例分级（高频/中频/低频）。

分层时间轮思想：让每种状态有独立的处理节奏，互不阻塞。

五、10 个 SPI 扩展点

引擎核心零框架依赖（仅 SLF4J + Hutool），所有可变点都是 SPI：

SPI 默认实现 可替换
SchedulerAdapter xxl-job PowerJob/手动
TaskStore MyBatis-Plus JPA/Mongo
LockService Redisson DB 行锁
NotifyChannel 企微机器人 飞书/钉钉
TaskArchiveService MyBatis-Plus 定时物理删除
… … …

接入方通过 @ConditionalOnMissingBean 零配置覆盖默认实现——引擎核心不动，扩展可插拔。

六、复盘：这个设计值不值

值：接入一个业务任务从数天降到数小时（只实现 Handler + 配置 + 建表）；两个系统复用同一套引擎，维护成本减半。

取舍：SyncTask 是 Temporal 的能力子集——没有持久化工作流、没有内置 DAG。但场景匹配度更高、运维成本更低。不做三件事换来了零引擎零维护，比”功能全但没人会用”更符合中台的实际需求。

总结

  • 背景：80% 同步逻辑重复 → 抽离 SyncTask 引擎；
  • 评估 6 个方案都不适配 → 自研”恰好够用”的引擎；
  • 三个”不做”：不引入 DAG（Choreography 够用）、不引入独立 Server（复用 xxl-job + SPI）、不引入延迟队列（多 Job 分级频率）；
  • 可靠性：双重防重 + 双层权重调度；
  • 10 个 SPI 扩展点，@ConditionalOnMissingBean 零配置覆盖；
  • 取舍：能力子集但场景匹配、运维成本低——架构减法比堆功能更难也更值钱。
