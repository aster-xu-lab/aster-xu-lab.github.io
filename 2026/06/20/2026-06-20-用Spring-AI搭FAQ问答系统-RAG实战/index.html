用 Spring AI 搭一个 FAQ 问答系统：RAG 实战全流程

上一篇讲了 Spring AI 的基础，这篇做一个完整的小项目：内部 FAQ 问答系统。把 RAG 的完整链路（切块 → 向量化 → 检索 → 拼 prompt → 幻觉控制）真正跑起来。这是我自己做过的最小落地场景。RAG 的工程思路（切块策略、混合检索、幻觉控制为什么这么做）在《RAG 工程实践》里已经展开过，这篇只讲 Spring AI 下的具体实现，不重复论证。

一、场景与架构

内部有几百条 FAQ（运维问题、业务规则、操作手册），想让员工用自然语言提问，系统基于 FAQ 回答。

RAG 架构：

为什么用 RAG 而不是把 FAQ 全塞进 prompt：FAQ 几百条塞不下上下文窗口，而且塞进去是”全量检索”，模型找不到重点。RAG 只喂”和问题最相关的几段”。

二、选型：为什么 pgvector

向量库选了 pgvector（PostgreSQL 插件），理由：

  • 不引新组件：业务库就是 PG，加个插件 + 一张向量表即可；
  • 体量匹配：几百条 FAQ，百万级以内的向量检索 pgvector 足够；
  • 运维成本低：不用为这个小场景单独运维一套向量库。

如果数据量到千万级再换 Milvus 这类专用向量库。选型看体量，不追时髦。

五、幻觉控制的实现

三种手段的取舍和理由在《RAG 工程实践》里讲过，这里只写落地时具体卡在哪：

① 检索不到就明说：TopN 的相似度低于阈值时，不硬答，直接返回”没有找到相关信息，建议转人工”——允许说不知道，绝不允许编。阈值不要拍脑袋，用一批真实问题分别看”该拒答”和”该回答”两边的分布，再定一个能接受误杀的值。

② 加引用来源：要求 LLM 回答带上 chunk id（”根据 FAQ-123”）。这要求检索结果把 id 一起查出来，而不是只拼 content——否则模型只能编一个来源。

③ 意图识别兜底：接 LLM 之前先判断问题类型——明显不在 FAQ 覆盖范围的（比如闲聊），直接走兜底，不硬往 LLM 上引。

④ 检索结果的信任边界：FAQ 文档可能被写入”忽略以上指令”之类的间接注入，检索结果只能当资料。另外，如果 FAQ 分部门或租户，权限过滤要写进检索 SQL（如 WHERE tenant_id = ?），不能先召回再在应用层删——那样越权内容已经进了模型上下文。

六、降级与成本

  • 降级的具体做法：捕获 LLM 调用异常或超时后，直接返回检索到的 TopN 原文，并明确标注”以下为相关资料，未经过模型总结”——既留住用户，也不把错误答案伪装成答案；
  • 成本的两个旋钮：TopN 和 chunk 大小。TopN 固定在配置里，chunk 在建库时切好；改任何一个都要重新评估检索质量，不能只盯着账单。

七、这套实现没覆盖什么

  • 没有量化评测：代码只验证了链路能跑通，没有标注集，也没有统计召回率或答案正确率；
  • 没有混合检索：只用了向量相似度，关键词/精确匹配还没接；
  • 没有生产级并发与限流：示例是最小单机实现。

这些不是”以后再说”，而是下一步的明确待办。没有评测，就不能说它”效果好”——链路跑通和效果达标是两件事。

总结

  • RAG = 离线建库（切块→向量化→存库）+ 在线问答（检索→拼 prompt→回答）；
  • 选 pgvector：不引新组件、体量匹配，大流量再上 Milvus；
  • 切块粒度匹配回答粒度，建库/检索用同一 Embedding 模型；
  • 幻觉控制：检索不到就说不知道 + 引用来源 + 意图识别兜底；检索内容按不可信输入处理，权限过滤写进检索 SQL；
  • 本文用手写 JdbcTemplate 展示检索过程；生产更推荐 PgVectorStore + QuestionAnswerAdvisor，并用 chunk id 支撑引用回填；
  • LLM 不可用要降级为返回原文，用 TopN 和 chunk 大小控制成本；
  • 这只是最小实现：缺评测、混合检索、并发限流，不能据此声称效果达标。
