用 Spring AI 搭一个 FAQ 问答系统：RAG 实战全流程

上一篇讲了 Spring AI 的基础，这篇做一个完整的小项目：内部 FAQ 问答系统。把 RAG 的完整链路（切块 → 向量化 → 检索 → 拼 prompt → 幻觉控制）真正跑起来。这是我自己做过的最小落地场景。

一、场景与架构

内部有几百条 FAQ（运维问题、业务规则、操作手册），想让员工用自然语言提问，系统基于 FAQ 回答。

RAG 架构：

为什么用 RAG 而不是把 FAQ 全塞进 prompt：FAQ 几百条塞不下上下文窗口，而且塞进去是”全量检索”，模型找不到重点。RAG 只喂”和问题最相关的几段”。

二、选型：为什么 pgvector

向量库选了 pgvector（PostgreSQL 插件），理由：

  • 不引新组件：业务库就是 PG，加个插件 + 一张向量表即可；
  • 体量匹配：几百条 FAQ，百万级以内的向量检索 pgvector 足够；
  • 运维成本低：不用为这个小场景单独运维一套向量库。

如果数据量到千万级再换 Milvus 这类专用向量库。选型看体量，不追时髦。

五、幻觉控制：RAG 的生死线

这是整个系统最重要的部分，三个手段：

① 检索不到就明说：TopN 的相似度低于阈值时，不硬答，直接返回”没有找到相关信息，建议转人工”——允许说不知道，绝不允许编。

② 加引用来源：要求 LLM 回答带上来源（”根据 FAQ-123”），用户可核验，模型也更不容易瞎编。

③ 意图识别兜底：接 LLM 之前先判断问题类型——明显不在 FAQ 覆盖范围的（比如闲聊），直接走兜底，不硬往 LLM 上引。

六、降级与成本

  • LLM 超时/不可用：降级为”直接返回检索到的 TopN 原文”，保证用户至少看到相关内容，而不是报错；
  • 成本：TopN 控制在 3-5 条，长 FAQ 答案切短，控制 prompt token。

七、诚实评估

这是一个最小落地场景，没有大规模生产数据，也没有量化指标（没有”召回率 88%”这种数字）。它的价值在于把 RAG 完整链路跑通了：切块、向量化、检索、拼 prompt、幻觉控制、降级——每个环节该踩的坑都踩了一遍。原理清楚、链路跑通、边界诚实，是我现在能对 AI 工程化说的最准确的话。

总结

  • RAG = 离线建库（切块→向量化→存库）+ 在线问答（检索→拼 prompt→回答）；
  • 选 pgvector：不引新组件、体量匹配，大流量再上 Milvus；
  • 切块粒度匹配回答粒度，建库/检索用同一 Embedding 模型；
  • 幻觉控制三件套：检索不到就说不知道 + 引用来源 + 意图识别兜底；
  • LLM 不可用要降级为返回原文，TopN 控制成本；
  • 最小落地场景，链路完整、边界诚实。
