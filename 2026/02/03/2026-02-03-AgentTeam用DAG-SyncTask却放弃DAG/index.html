Agent Team 用 DAG，SyncTask 却放弃 DAG：两种编排的决策逻辑

定位：学习笔记 + 复盘。这个对照特别有意思——我在做 SyncTask 引擎时放弃了 DAG 选了 Choreography，而学习 Agent Team 时发现它反而用 DAG。同一个决策，两个答案，值得想清楚为什么。

二、关键认知：DAG 是人定义的，不是 LLM 编排的

这里有一个容易被误解的点，也是我学习时最值钱的认知：

Agent 之间的调用链（DAG）是”人”定义的，不是 LLM 编排的。LLM 只负责单个节点内部的”思考→行动”。

“产品经理 → 架构师 → 工程师”这个顺序，是我在代码里硬编码的——它代表的是业务流程，不是模型自己想的。LLM 的职责被限定在每一步内部：产品经理 Agent 内部做 ReAct，架构师 Agent 内部做 ReAct，但它们之间的交接是程序控制的。

这意味着：Agent Team 的”编排”和”智能”是分开的。 编排（谁先谁后、谁给谁输入）是确定性代码；智能（每个节点内怎么做）是 LLM。

三、对照：SyncTask 为什么放弃 DAG

我在 SyncTask 引擎里做的恰恰是反方向的决定——评估了 6 个开源方案之后，主动不做三件事，其中第一条就是”不引入 DAG 编排引擎”。

当时的决策逻辑：

  1. 90% 的同步任务之间无依赖关系——每个任务独立跑就行，DAG 的”依赖编排”能力用不上；
  2. 有依赖的少数场景（比如”先同步库存、再同步订单”），用 afterExecute 埋点（Choreography 模式）实现——任务完成后触发下一个，sync_task 表作为事件载体；
  3. 零引擎、零 DSL、零维护成本。

为什么能这么做：同步任务的执行链是”事件驱动”的——一个任务干完了，自然知道下一步该干嘛，不需要一个中央 DAG 把全流程预先画好。

四、两个决策的逻辑对比

SyncTask 引擎 Agent Team
任务间关系 90% 无依赖 强依赖（PRD→设计→代码）
编排方式 Choreography（事件驱动） DAG（人定义流水线）
执行链来源 运行时动态（afterExecute 触发） 编译期固定（代码硬编码）
为什么 依赖少，DAG 是过度设计 流水线明确，DAG 直观
决策者 代码规则 代码（LLM 只管内节点）

核心分界线是：任务间的依赖关系到底是不是”预先可确定的”。

  • 可确定（Agent Team：产品→架构→工程，流程固定）→ 用 DAG/流水线，直观、可控；
  • 不可确定（SyncTask：任务完成才知道下一步要不要触发什么）→ 用 Choreography，事件驱动，避免预先画死。

五、这是同一个架构问题的两面

有意思的是，这两个项目回答的是同一个问题：“多个步骤之间怎么协调”。

  • SyncTask 的角度：为了省运维，砍掉重量级 DAG，用轻量事件驱动替代；
  • Agent Team 的角度：为了流程清晰，显式画出 DAG，让多 Agent 协作可预期。

两个答案都对，因为约束不同。架构决策没有银弹，只有”场景匹配”——这也是我在 D2 面试手册里反复说的：不是哪个模式高级，是哪个匹配当前场景。

六、延伸：为什么 Agent 世界也分两派

在 Agent 领域，”编排”同样是分派别的：

  • DAG 工作流（扣子、Dify）：拖拽节点串联，流程预先定义——适合业务流程明确的场景；
  • Agent 间直聊（Claude Code Agent 团队）：Agent 通过队列互相投递任务，动态协作——适合不确定、需探索的场景。

和我 SyncTask 的 Choreography 是同一枚硬币——只是把”afterExecute 事件触发”换成了”Agent 之间投消息”。底层思想完全一致。

总结

  • Agent Team 用 DAG：多 Agent 流水线，DAG 是人定义的，LLM 只管节点内部；
  • SyncTask 放弃 DAG：90% 任务无依赖，用 afterExecute 埋点（Choreography） 替代，零引擎零成本；
  • 分界线：依赖关系能否预先确定——能则 DAG 直观，不能则 Choreography 灵活；
  • 两者是同一架构问题（多步骤协调）的两面，场景匹配比模式先进更重要；
  • 学习 demo 笔记，不涉及生产数据。
