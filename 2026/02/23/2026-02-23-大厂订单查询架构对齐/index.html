大厂订单查询架构对齐：淘宝、京东、拼多多、抖音是怎么处理的

说明：大厂订单核心分片细节高度保密。本文基于公开技术分享与行业通用演进整理。标「确信」的是行业共识；标「推断」的具体某家口径请以官方技术分享为准。

一、核心共识：大厂订单查询都是「三层解耦」

不管淘宝京东拼多多抖音，电商订单查询几乎都长这样：

二、订单主库：按 order_no 分库分表（确信度较高）

订单库几乎都直接按单号 hash 分库分表（比如 32 库 × 32 表）：

  • 好处：单号详情 = 天然精准路由，0 广播，也不需要”单号反向索引表”
  • or_sales_info 已确认同此选型（业务事件都按单号）→ 与业界一致

三、”我的订单”维度：不是建 user_id 索引表，而是上 ES

这是大厂与自建方案最大的差异：

  • 中小(无ES)：维护 user_order_index（按 user_id 分片）→ 写冗余
  • 大厂：“我的订单”根本不查 MySQL，查 ES/Doris 宽表（已存 user_id/order_no/时间/金额/状态）

原因：

  1. WHERE user_id=? ORDER BY 时间 正是 ES 擅长的
  2. 免去 user_id 反向索引表的写冗余
  3. ES 天然支持 search_after 做游标深分页

「确信」：用查询库扛维度查询、减少写冗余，这是大厂共性。（某家具体内部口径为「推断」）

四、C端深分页：游标 + search_after（确信，行业统一）

C端下拉深分页，大厂几乎不用 OFFSET：

技术 说明
MySQL 场景 WHERE id > lastId ORDER BY id LIMIT n（keyset 游标）
ES 场景 search_after（ES 官方游标，替代 from/size）

深分页 = 游标（search_after / keyset）是行业铁律。

五、B端深分页：不拉 MySQL，Doris/ES 扛（确信）

B端（运营/客服）复杂筛选排序，大厂绝不裸查订单主库：

  • B 端查 ES 或 Doris/ClickHouse 宽表
  • 深分页：ES search_after、Doris ORDER BY + LIMIT（MPP 本地排序）
  • 导出：流式 Scroll / 分页拉批

为什么 B 端不查 MySQL：多条件组合在分片表上广播所有分片，深分页直接爆。

六、同步时效：Canal/binlog → Kafka → 宽表（确信，秒级）

大厂订单宽表的同步链路标准就是 CDC 流式：

  • 时效：秒级（Canal 毫秒解析 + 消费批量写）
  • 本质：流式 CDC，不是定时 job
  • 部分大厂（如抖音部分场景）订单写主库事务内发 MQ（事务消息/本地消息表），减少查询数据延迟

注意：写入主线 + 异步同步，存在秒级不一致窗口。C端详情拿”最新状态”通常回源 MySQL。

七、具体到各家（标注置信度）

平台 置信度 做法
淘宝 中(有公开) 订单库按单号散列；查询靠索引/搜索底层；B端查询系统
京东 中(架构文章) 订单明细库 + 搜索/聚合库分离；C端列表走宽表，详情回订单库
拼多多 较低(少公开) 极致成本，推断：主库按单号分片，”我的订单”走宽表/ES 减写冗余
抖音电商 中(部分分享) 订单体系 + 消息驱动同步（事务内发MQ保证实时），宽表/ES 查询

八、你的方案对齐大厂

你的设计 大厂做法 结论
单号主分片（2026-09确认） 单号 hash 分库分表 ✅ 与业界一致
业务事件按单号 单号主分片天然精准 ✅ 一致
user_id 冗余列+游标 ES/Doris 宽表 有查询库就不建 user_id 索引
时间统计 Doris/ES 宽表 ✅ 一致（不裸查 MySQL 分片）
C端深分页游标 search_after/keyset 铁律 ✅ 一致
Canal→Kafka→宽表 正是大厂做法 ✅ 一致

小结

大厂订单查询共性：

  1. 主库按单号 hash 分片（详情零路由成本）
  2. “我的订单”等维度丢给 ES/Doris 宽表，不建过多反相索引 → 写冗余最小
  3. C端深分页用游标（search_after）
  4. B端复杂查询走 Doris/ES，不裸查 MySQL
  5. Canal binlog + Kafka 流式同步，秒级时效

核心：能用查询库解决的维度，就不在 MySQL 侧建反向索引。
