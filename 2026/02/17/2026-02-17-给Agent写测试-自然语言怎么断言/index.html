给 Agent 写测试：输出是自然语言，怎么断言？

定位：学习笔记。Agent 的输出是自然语言，不能像普通代码那样 assertEquals。这篇记录我怎么给 Agent 搭测试脚手架（Harness）。

一、问题：普通测试的假设在这里不成立

给普通代码写测试，核心假设是输出是确定性的：

但 Agent 的输出是自然语言，同样的输入，两次生成的文本大概率不一样。而且 Agent 还会调工具、有多轮循环，状态在变。所以：

  • 不能 assertEquals——你不知道模型会输出哪句话；
  • 不能断言具体内容——只能断言”应该包含什么”、”结构对不对”；
  • 工具行为不可控——真实工具会打外部接口，测试不稳定。

那怎么测？我的做法分三层。

二、第一层：工具测试——Agent 的地基要先测

Agent 的确定性部分其实是 Tool：给定参数，返回结果应该是确定的。所以工具层用传统方式测：

工具是 Agent 里唯一确定的部分，先把它测稳——工具错了，上面的 Agent 循环再对也没用。

三、第二层：Mock 工具——给测试可控的输入

真实工具（查数据库、调外部接口）会让测试不稳定、还可能花真钱。所以要一个可控、可预测的 Mock 工具：

echo 工具不做任何 IO，输入什么回显什么——测试时用 MockEchoTool 替换真实工具，Agent 的行为就完全可预测了。这是测试里最常用的技巧：把不确定性隔离在可控的替身里。

四、第三层：验收测试——对自然语言做”软断言”

五、三层测试的完整图景

原则一句话：越接近 LLM 的输出，断言越”软”；越接近确定性代码，断言越”硬”。 把能确定的部分（工具、注册表、Mock）测扎实，对不确定的部分（Agent 自然语言输出）用关键词/结构做验收。

六、为什么这很重要

Agent 落地最大的阻力不是”跑不起来”，而是**”怎么证明它干得对”**。LLM 是概率性的，没有测试保障，你不敢让 Agent 去处理真实业务——因为没法判断它这次是不是又”一本正经地胡说”。

Harness 的价值就是给 Agent 装上”质量护栏”：工具层保证能力正确、Mock 层保证测试可控、验收层保证输出达标。这和我在消息系统里做对账兜底是同一个思路——不能证明正确性的系统，不敢放上生产。

总结

  • Agent 输出是自然语言，不能 assertEquals，要分三层测；
  • 工具测试（硬断言）：工具是确定性部分，先测稳；
  • Mock 工具：用可控替身隔离不确定性，测试可预测；
  • 验收测试（软断言）：关键词 + 长度，验证”该干的事干了没”；
  • 原则：越接近 LLM 越软，越接近代码越硬；
  • Harness = Agent 的质量护栏，让概率性输出可验证。
