MCP：工具调用的"JDBC"——从零看一个 JSON-RPC 协议

定位：学习笔记。MCP（Model Context Protocol）是 2024 年底由 Anthropic 提出的工具调用标准化协议。我为了搞懂它，自己实现了一个最小版 Server/Client。

一、MCP 解决什么问题

在 MCP 之前，每个 LLM 应用连工具都是自己造的轮子：协议自己定、格式自己定、连自己的 Agent 是这套、换一个框架又得重写。

MCP 的定位一句话：工具调用的 JDBC。

JDBC 干的事，是让任何 Java 程序用同一套接口连任何数据库（换个驱动即可）。MCP 干的事，是让任何 LLM/Agent 用同一套协议连任何工具（换一个”驱动”即可）。

二、协议核心：JSON-RPC 2.0 over stdio

MCP 的传输层用 JSON-RPC 2.0，传输通道用 stdio（标准输入输出）。关键就两个方法：

  • tools/list：列出所有可用工具（名字、描述、输入 schema）；
  • tools/call：调用指定工具，传参数，拿结果。

为什么用 stdio：MCP Server 通常作为一个子进程被 Agent 拉起，两边通过 stdin/stdout 交换 JSON 行——不需要开端口、不需要网络配置，进程内通信最简单可靠。

真实协议在 tools/list 之前还有一个握手：Client 先发 initialize（协商协议版本、声明 capabilities），Server 返回 initialize 结果；Client 再发 notifications/initialized 通知，之后才能正常调用 tools/list、tools/call。下面为了突出工具调用的骨架，把这段生命周期省掉了——本文的 demo 不是可互操作的完整 MCP 实现。

五、MCP vs Agent：两个容易混淆的角色

学习时我一度分不清 MCP 和 Agent 的关系：

MCP Server Agent
角色 工具提供者（被调用） 任务执行者（主动调）
做什么 暴露工具，等待调用 拆任务、做决策、调工具
进程 常驻，等请求 常驻，跑循环

类比：MCP Server 像一个”工具服务”（被调），Agent 像一个”调度大脑”（调用）。Agent 进程是调用方，MCP Server 是被调用方——Agent 通过 MCP 协议拿到 MCP Server 暴露的工具。

六、诚实的边界

我的 demo 只实现了 MCP 的”工具调用”部分（tools/list、tools/call），跳过了 initialize / notifications/initialized 握手，也忽略了资源（resources）、提示词（prompts）等高级特性。MCP 官方协议更完整，还有 Streamable HTTP 等传输方式。它是理解协议形状的最小演示，不能当成可互操作的 MCP Server 使用。

但核心骨架——JSON-RPC 请求/响应 + 工具注册——就是上面这几行，看懂了就理解了这个协议的设计思想。

还有一个必须明确的信任边界：MCP 把”工具提供者”和”调用方”拆成两个进程，Server 暴露什么工具、工具能碰到什么数据，等于把相应权限交给了调用方。接入第三方 MCP Server 时，要把它当成不可信代码——限制它能访问的文件和网络，对写操作和敏感数据做人工确认，不要因为”协议标准化了”就默认它安全。

总结

  • MCP = 工具调用的 JDBC，任何 LLM 用统一协议连任何工具；
  • 协议核心：JSON-RPC 2.0 over stdio，两个方法 tools/list + tools/call；
  • 剥开协议外壳，核心还是 Tool 接口 + 注册表，MCP 只是包了层标准化通信；
  • Client 与 Server 通过子进程管道通信，发一行 JSON 等一行 JSON；
  • MCP Server 是”工具提供者”，Agent 是”任务执行者”，角色别混；
  • 概念年代：MCP 2024 年底提出，这篇是 2026 年 2 月的学习记录；
  • 真实协议需要 initialize + notifications/initialized 握手，本文 demo 省略了，仅为非完整实现。
