桌面应用不能留孤儿进程：Chromium、JVM 与退出语义

用户关掉窗口，任务栏里还留着 Chromium；再打开一次，机器上多一份 JVM。这类问题不会立刻报错，但会一直吃内存、占端口，最后表现成「应用越用越卡」。这篇文章讲三类孤儿是怎么产生的，以及退出路径应该怎么设计。

一、孤儿从哪来：时序窗口

这个应用启动时会拉起一个 Browser4 运行时（JVM），JVM 在启动后几秒内会自己开一个默认上下文的 Chromium。而平台 session 要到 10–20 秒才真正打开。

最初的清理逻辑是在 session 打开时缓存 Chromium 路径，退出时按这个路径杀残留。问题就出在中间那个窗口：

结果就是 Chromium 留在后台。修法有两条：

  1. 缓存提前：runtime 一解析出来就记下 Chromium 路径，不等 session；
  2. 同步兜底：缓存仍为空时，退出路径同步推导出随包 Chromium 目录，不依赖异步工作。

杀进程时按路径前缀匹配，所以传目录就能覆盖目录下所有 revision 子目录。

二、按路径杀，不按进程名

这是最容易写错的一步。如果按 chrome.exe 或 Google Chrome 匹配，会误杀用户自己的浏览器。

正确做法是只杀随包的 Chromium：

  • Windows：匹配随包目录下的 chrome.exe；
  • macOS：匹配 .app 内进程，needle 用 lastIndexOf('.app/')，避免打包态命中外层 Electron 的 .app 而自杀；
  • 跳过当前进程的 pid / ppid；
  • 不碰系统 Google Chrome。

实测证据：

场景 结果
session 已开 34 个 Chromium → 0
首次 session 打开前 8 个 Chromium → 0
退出后 随包 Chromium 0、Browser4 JVM 0
用户自装 Browser4 未被误杀
系统 Google Chrome 未被误杀

两条路径都在 1 秒内退出干净。

三、日志要打出「杀的是哪个路径」

第一版还有一个隐蔽问题：如果 kill 被跳过，日志里什么都没有。症状看起来和「kill 失败」一模一样——都是关窗后 Chromium 还在跑。

现在退出路径会明确记录它正在杀的路径。没有日志的跳过，是最难排查的失败。

四、退出语义：关窗不等于退出

两个平台的约定本来就不同：

  • Windows：关闭主窗口 = 整退；但要先关掉独立的复核/查看窗，再走 before-quit；
  • macOS：关闭红灯不退出，必须 Cmd+Q。这是平台习惯，不要「帮用户」改成关窗即退。

五、监听地址也属于生命周期

另一个「进程问题」其实出在网络绑定上。JVM 开了两个 socket：

  • Spring 主 server：默认绑 0.0.0.0；
  • Browser4 自己的 MCP-over-HTTP server：默认 0.0.0.0:8088。

后果有两个：

  1. Windows 防火墙每次启动都弹「Windows 安全警报」；
  2. 一个能驱动浏览器的服务暴露在局域网里。

只设 --server.address=127.0.0.1 不够——实测这只把 Spring socket 绑到回环，MCP 那个仍停在 ::。两个都要绑回环。

防火墙弹窗还有一个放大器：打包版首启会把 runtime 拷到带版本号的目录，一升级路径就变，所以用户点了「允许」下次还会再弹。看起来像「一直在弹」，实际是路径变了导致规则没命中。

六、边界

  • 退出清理只覆盖随包进程；用户自己安装的 Browser4 不归应用管，也不应该被管；
  • 强制杀进程是兜底，不是正常路径。正常路径应该先让 CLI / session 自己关闭；
  • 崩溃退出的情况没有经过 before-quit，只能依赖下次启动时清理或系统回收，这一块没有做成强保证；
  • 长跑后的进程数量与句柄泄漏，还没有单独做长时观察。

总结

孤儿进程的根因通常不是「杀不掉」，而是清理逻辑依赖了一个当时还不存在的状态。这次的三条修正可以复用：

  1. 路径尽早缓存，退出时再同步兜底；
  2. 按随包路径杀，不按进程名杀；
  3. 把「跳过」也写进日志，否则它和「失败」无法区分。

顺带记住：进程生命周期不只包括进程本身，也包括它监听的地址。绑回环既是安全边界，也是用户体验。
