一个 364MB 的安装包传不上去：从 multipart 上限排到堆内 OOM

上传接口对 2KB、32MB、128MB、192MB 都返回 200，到 256MB 开始稳定 500；364MB 的真实安装包直接失败。第一反应是 multipart 上限，但配置里写的是 1000MB。真正的原因在 JVM 堆里，而且错误被 catch (Exception) 吞掉了。

一、现象：按大小分层失败

先把边界测出来，而不是猜：

文件大小 结果
2 KB / 32 MB / 128 MB / 192 MB 200，返回可访问的存储地址
256 MB（复测两次一致） 500，{"code":"5001","message":"Internal server error"}
364 MB（真实安装包） 500，同样 5001，且先收完整个 body（约 91 秒）才报错

这个分布很有信息量：不是网络中断，不是鉴权失败，也不是大小校验提前拒绝——服务端把整个文件收完了，然后才在处理阶段炸掉。

二、排除 multipart：配置是 1000MB

最像的原因当然是上传大小限制。但把 Nacos 里该环境实际生效的配置拉出来看：

364MB 远小于上限，而且如果真是 multipart 拒绝，不会等到收完 body 才报错。顺带确认了另一个环境里确实有 20MB/100MB 的配置，但线上实例读的不是那一份——排查配置问题，一定要看生效 profile，不是仓库里的默认值。

三、读源码：整个文件被读进一个堆数组

上传实现大致是：

随后 createStorage(contentType, key, request.getBytes(), extName) 又把这份字节数组交给存储客户端，包成 ByteArrayInputStream。也就是说：

  • 文件先以 MultipartFile 形式落盘或缓存在临时区；
  • getBytes() 把它完整物化成一个 byte[]；
  • 后续构造请求时还可能再产生拷贝。

堆需求至少是文件大小本身，加上若干份临时拷贝。对 256MB 的文件，512MB 堆已经没有安全余量。

再看 JVM 参数：测试环境 -Xms256m -Xmx512m -Xmn128m，生产环境 -Xmx2g。192MB 通过、256MB 失败，正好落在 512MB 堆装不下「文件 + 拷贝」的位置。根因到这里就闭合了。

四、为什么错误这么不可读

uploadDesktopFileByPath 里只有：

OutOfMemoryError 继承的是 Error，不是 Exception。它穿过这层 catch，落到框架的通用异常处理，最后只剩一个 5001 Internal server error 和一枚 traceId。一个可恢复的容量问题，被表现成了完全不可诊断的 500。

这也是这次排障最花时间的地方：如果响应里能带上 OutOfMemoryError，排查会从「读源码 + 猜配置」缩短到几分钟。

五、修法：流式上传 + 至少让错误可读

正解不是调堆，而是不要再把整个文件放进内存：

存储客户端本来就提供吃 InputStream 的重载，同文件其它路径已经在用，不需要引入新 API。返回的 key、contentType、URL 结构与旧路径保持同构，调用方无感。

错误处理至少补到 Throwable：

这里要诚实地说边界：

  • 只改了这一个上传接口。同服务里另外 5 个走 getBytes() 的调用点没动，大文件仍会以同样方式 OOM；
  • 调堆只能挪阈值。测试环境提到 2g 能过 256MB，但 364MB 在 2g 上依然没有余量，生产环境本来就是 2g，属于侥幸；
  • 改动的机器上没有 JDK 和本地 Maven 仓库，只做了静态复核（helper 签名、import、catch 顺序、输出同构性），编译与部署由另一侧完成。没有跑过的验证，不能写成已验证。

总结

这次故障的链条是：整包物化 → 堆不足 → Error 穿过 Exception catch → 通用 500。三个环节任何一个被提前处理，都不会演变成「配置看起来完全正确，但就是传不上去」。

留三条可复用的经验：

  1. 按大小分层测试，先拿到失败边界，再决定怀疑方向；
  2. 配置以生效 profile 为准，不要拿仓库默认值下结论；
  3. 上传/下载这类按大小线性的接口，默认按流式设计；getBytes() 只适合小文件，而且要把「多大算小」写进契约。
