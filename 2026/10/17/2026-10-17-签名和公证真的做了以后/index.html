签名和公证真的做了以后：从概念到 Squirrel 装不上的那 88 个文件

之前写过签名、公证与混淆的概念和优先级。这次是真的把 Developer ID 签名接进了构建：签的不只是 .app，还有随包的 JVM、Chromium 和 CLI；签完要刷新校验和；Squirrel 安装还会被 88 个只读文件卡住。概念落到工程里，细节比想象中多。

一、先分清四种状态

「签了」和「能正常安装」不是一回事。实际会遇到四种状态：

状态 codesign --verify spctl 用户体验
完全未签名 失败 失败 某些情况下图形界面反而能放行
adhoc 签名 可能通过 失败 带 quarantine 双击报「已损坏」，且没有「仍要打开」
Developer ID 签名 通过 通过 可以正常打开
Developer ID + 公证 通过 通过（Notarized） 外发分发的要求

一个容易说错的点：adhoc 不是「未签名」。它有自己的签名结构，codesign --verify --deep --strict 可能通过，但 spctl 仍然失败；而完全未签名的包在某些图形界面路径下反而能放行。两者不能混为一谈。

二、签的不只是 .app

这个应用随包带了 Browser4 运行时：JVM、Chromium、CLI，以及 JAR 里嵌的原生库。只让 electron-builder 签外层 .app 不够，里面的 Mach-O 也要签。

  1. JAR 里的 .jnilib 要解压、签名、再放回去，否则运行时会因为签名无效被拒绝；
  2. signIgnore 要排除 Contents/Resources/browser4，否则 osx-sign 会尝试逐个签 .jar，直接卡死。外层流程跳过这块，由我们自己的脚本处理。

另外启用了 hardened runtime，并配了 entitlements（含 disable-library-validation），否则随包的 JVM / 原生库会被运行时拦下。

五、公证：已经接线，但这一轮没跑

公证流程已经接进打包脚本，可以选择 --notarize / --no-notarize，也支持环境变量和交互确认（默认不公证）。

这一轮实测的是 Developer ID 签名 + 不公证：

  • codesign --verify --deep --strict 通过；
  • spctl 显示 Unnotarized Developer ID——这是预期结果；
  • Squirrel 安装与自动升级不受影响；
  • 但 dmg 对外分发需要公证，否则用户首次打开会被 Gatekeeper 拦。

公证之后还要补一项验证：在本机真实开一次采集，确认 JVM 和 Chromium 在 hardened runtime 下能正常启动。签名和公证改变的是信任链，不是运行时行为，但硬编码的 runtime 限制仍可能在这时候才暴露。

六、Windows：这一期不做 Authenticode

Windows 侧的结论是「知道该怎么做，但这一期不做」：

  • 私钥需要放在硬件中；
  • 签名必须带时间戳（/tr）；
  • SmartScreen 不会因为签名立即放行，信誉需要积累；
  • 安装包内再分发了 Browser4 的 CLI、JVM、Chromium，许可与 NOTICE 还没和维护方确认。

所以未签名 setup 经网络分发可能触发 SmartScreen 警告，这是当前预期行为，不是缺陷。

总结

签名与公证落地后，最有价值的不是「证书配好了」，而是这几条顺序与边界：

  1. 由深到浅签名，JAR 内原生库也要签；
  2. 签完刷新 manifest 校验和，否则首启校验失败；
  3. 随包文件的模式位会影响安装，只读文件会让 Squirrel 放弃；
  4. 签名 ≠ 公证；Squirrel 升级不要求公证，但 dmg 外发要求；
  5. 公证后必须做一次真实运行验证，不能只看 spctl。

概念文章可以讲清楚「为什么」，但只有真正出一次包，才会知道卡住安装的是 88 个 0444 的文件。
