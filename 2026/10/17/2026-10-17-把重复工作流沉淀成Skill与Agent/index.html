把重复工作流沉淀成 Skill 与 Agent

项目里陆续沉淀了 9 个 Skill 和 3 个 Agent。它们不是提示词合集，而是把「这类任务该怎么做、做到什么算完成」写成可复用的工作流。真正难的不是写内容，而是划清触发边界。

一、什么样的工作流值得沉淀

不是所有重复动作都值得写成 Skill。值得沉淀的通常同时满足四个条件：

  1. 会反复发生：例如每次出包、每次采集异常排查；
  2. 步骤多且顺序固定：少一步就会漏；
  3. 有明确的完成定义：例如「探针 N/N 通过」「产物 10/10」；
  4. 做错的代价高：删错数据、跨平台出包、把凭据写进仓库。

这个项目里的 9 个 Skill 基本都能对上：

Skill 对应的工作流
import-task-rings 三环 / 计数 / 重试
capture-cleanup 采集清理 + 清本地图引用
package-verify 出包自检 / 跨平台禁令
ui-ux-desktop IA / token / 焦点 / 组件复用
browser4-scrape-debug 采集诊断 / HITL / 熔断 / 批测
merchant-gate-openapi 登录闸门 / OpenAPI 商家上下文
desktop-verify 本机验证方法论（CDP / 探针 / 装机）
ebay-match-draft eBay 预填 / 类目 / Fitment / batchAdd
pull-impact-review 拉最新代码 + mac/win 影响面

它们有一个共同点：不是「知识介绍」，而是「操作手册 + 检查清单」。

二、Skill 与 Agent 的分工

两者解决的不是同一个问题：

  • Skill：描述「这类任务应该怎么做」。它通常是一份流程、约束和验收标准，由当前会话按需加载；
  • Agent：描述「把一段多步任务委派出去」。它有自己的工具、上下文和停止条件。

一个简单的划分：

场景 用什么
我需要按固定流程做一件事 Skill
我需要有人独立完成一段调查 / 改动 Agent
流程里有高风险步骤，需要我确认 Skill + 人工确认
任务可以并行、且结果只需要结论 Agent

项目里的 3 个 Agent 是 scrape-agent、ship-agent、draft-openapi-agent，分别对应采集诊断、发布、草稿接入三条较长的工作流。

三、触发边界比内容更重要

一个 Skill 写得再好，如果在错误的时机被触发，价值就是负的。

这里踩过的几个边界问题：

  • 不要让 Skill 自动执行破坏性操作。清理、卸载、批量替换这类动作，必须有人确认；
  • 触发条件要写「什么时候不要用」。比如「采集只走本仓库 Browser4，禁止外部爬虫」——这条不是建议，是边界；
  • 验证类 Skill 要和具体的验证命令绑定。写「跑一下探针」没用，要写清楚用哪个脚本、预期几项通过；
  • 不要让 Skill 和工程规则漂移。Skill 里复述的规则越多，越容易和 AGENTS.md 不一致。能引用就引用，不能引用就只写操作步骤。

四、把「验证方法」也沉淀

最有价值的一类 Skill 不是「怎么做功能」，而是「怎么证明它是对的」。

desktop-verify 就是这一类：本机验证方法论，包括用 CDP 驱动应用、设计探针、装机与卸载、哪些路径必须真人操作。它解决的问题是：下一个人（或下一个 Agent）不必重新发明一套验证方式，也不会把「界面看到了」当成「功能通过了」。

这和写文档是同一个道理：验证方法本身也是工程产物。

五、维护：Skill 会过期

Skill 最大的风险不是没有，而是过期。过期 Skill 比没有 Skill 更糟，因为它会让人以为流程还被维护着。

目前的维护方式：

  • Skill 只写稳定的流程与边界，具体命令尽量从仓库脚本或文档引用；
  • 工程状态变化时，先更新 ENGINEERING-STATUS.md，再检查相关 Skill 是否需要跟着改；
  • 新增 Skill 前先问「现有 Skill / 文档能不能覆盖」，避免同类流程分裂成多份；
  • 发现 Skill 与实际行为不一致时，优先改 Skill 或删掉，而不是留一条「历史说明」。

六、边界

  • Skill 不是万能的：它依赖模型愿意读、读得懂，也依赖上下文里能拿到正确的文件；
  • Agent 的产出仍然需要人验收，尤其是涉及发布、删数据、改配置的任务；
  • 沉淀过早会过度抽象。我的经验是：同一个流程至少手工走两遍，再写成 Skill；
  • 这套东西不能替代工程约束。硬约束（IPC 白名单、sandbox、禁止跨平台出包）仍然要写在 AGENTS.md 和规则文件里，Skill 只是执行层。

总结

把工作流沉淀成 Skill 与 Agent，本质上是在做三件事：

  1. 把隐性步骤显性化，让流程可重复；
  2. 把完成标准写死，让「做完了」可验证；
  3. 把边界写清楚，让自动化知道什么时候必须停下来。

这三件事和写代码、写文档没有区别。区别只在于，产物是给人和 Agent 共同执行的。
