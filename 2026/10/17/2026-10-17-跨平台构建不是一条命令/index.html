跨平台构建不是一条命令：Windows 与 macOS 出包的边界

「在 macOS 上打 Windows 包」看起来只是换一个 --win 参数，实际上会把 darwin 的运行时打进 Windows 安装包，首启直接报平台不匹配。跨平台构建的边界不止构建命令，还包括 afterPack、产物目录、通道身份和平台矩阵。

一、为什么不能跨平台出包

这个应用随包带了 Browser4 运行时。打包前有一个 stage:browser4 步骤，它会把当前构建机的 platform / arch 写进 manifest，并拷贝对应的 CLI、JVM、Chromium。

  • Windows 包只在 Windows x64 / Windows runner 上构建；
  • macOS 包只在 Apple Silicon 上构建；
  • 不要在 mac 上打 win，也不要在 Windows 上打 mac。

这不是「建议」，是构建产物的正确性问题。

二、afterPack 是单值键，必须自带平台守卫

afterPack 在 electron-builder 配置里只能有一个值，两个平台共用。当前它指向 macOS 的 Browser4 深层签名脚本，但 Windows 打包同样会触发它。

  1. 守卫之前不要加任何代码——读环境变量、写文件、复制文件都不行，否则 Windows 打包会跟着中招；
  2. 将来给 Windows 加签名，不能再加一个 afterPack，必须在同一个脚本里按平台分支。

这类「全局单值钩子」是跨平台构建里最容易埋雷的地方。

三、产物按平台 + 通道分目录

早期的输出目录是 dist/，所有平台和通道混在一起。后来改成：

文件名也带通道，例如 …-test-setup.exe / …-prod-setup.exe，避免测试包和生产包混淆。

这里有一个必须显式处理的坑：自定义 directories.output 后，electron-builder 只自动排除当前输出目录。如果 files 里不显式排除整个 dist{,/**/*}，兄弟目录里的旧 .app、*.nsis.7z 会被打进 asar。实际出现过 asar 约 2.3G、安装包数 GB 的情况。

结论：输出目录是构建输入的一部分，必须把整个 dist 从 files 里排除。

四、test / prod 必须能并存

双通道不只是两个 env 文件，还包括一整套身份隔离：

prod test
显示名 Autovado Merchant Desktop … Test
appId com.autovado.merchant.desktop …desktop.test
Windows exe autovado-merchant-desktop.exe …-test.exe
mac / 开发 userData …/autovado-merchant-desktop …-test
商家 partition persist:merchant-web persist:merchant-web-test
更新缓存目录 默认 带 -test 后缀

少任何一项，两个通道就会互相覆盖。例如更新缓存目录：electron-builder 默认派生的是 sanitize(package.json name) + "-updater"，不带通道后缀，test 与 prod 会共用一个缓存目录。现在由统一的 afterPack 入口按 appId 修正。

五、平台矩阵：只支持两种组合

本期只支持：

  • darwin / arm64
  • win32 / x64

Intel Mac 直接返回 UNSUPPORTED_PLATFORM，不做兼容。这个决定要在客户端和服务端同时生效：

  • 客户端上报 platform / arch；
  • 服务端没有该平台的可用制品时返回 UNSUPPORTED_PLATFORM；
  • 客户端校验响应里的 release.platform/arch 必须与当前进程一致，拿错平台的包直接判无效。

verify:package 也按 process.platform 分发到 macOS / Windows 两套校验，不允许跨平台跑。

六、产物类型也有平台差异

  • Windows：安装和自动更新用同一个 NSIS 包；
  • macOS：自动更新必须用 zip，dmg 只用于手动安装；新用户下载优先 dmg，但 feed 必须能找到 zip。

这不是偏好，是 Squirrel.Mac 的约束。发布时如果只登记 dmg，自动更新会失败。

七、边界

  • Windows 本期没有 Authenticode 签名，SmartScreen 警告是预期行为；
  • macOS 已接 Developer ID 签名，但 dmg 外发所需的公证还没跑；
  • 没有做跨平台的 CI 构建矩阵，出包仍然是「在目标平台上手工执行」；
  • Linux 有构建脚本，但不在本期支持矩阵里。

总结

跨平台构建的核心不是「一条命令能出几个平台的包」，而是承认平台差异并把它写进工程约束：

  1. 在目标平台上构建，运行时不会跨平台；
  2. 单值钩子要带平台守卫，守卫必须是第一行；
  3. 产物目录和通道身份要隔离，否则会互相污染；
  4. 支持矩阵要显式，不支持比「试试看」更安全。

把这些边界写进脚本和规则文件之后，跨平台才从「靠人记住」变成「构建时自动挡住」。
