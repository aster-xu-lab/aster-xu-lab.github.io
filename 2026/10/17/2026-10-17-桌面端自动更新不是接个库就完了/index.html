桌面端自动更新不是接个 electron-updater 就完了

接入 electron-updater 只完成了「下载和安装」这一小段。真正的工作量在另一边：服务端要有一整套版本、制品、校验、策略和灰度模型；客户端要有一个能被验证的状态机，还要在受限时拦住所有会写数据的入口。这篇文章讲这条链路是怎么落地的，以及哪些地方我们选择了接受限制。

一、先把更新当成一个服务端系统

客户端只是一个消费者。服务端至少要回答五个问题：

问题 对应能力
有没有新版本 release + artifact + feed
这个包是不是真的 逐 artifact 校验大小 / SHA-512 / 格式
谁能更新、什么时候必须更新 policy（目标版本、最低版本、生效时间、灰度）
出问题怎么退 revoke
新用户第一次装哪个 latest 接口，独立于策略

几个约束是踩出来的：

  • 版本号共享，制品按平台拆。一个版本号只能有一行 release，但 Windows 和 macOS 的安装包各自登记、各自校验。
  • 校验结果有 24 小时有效期。过期必须重新校验，否则可能把一个已经变化的文件发出去。
  • 发布是一次性的。publish 要求该版本下所有要发布的制品都已校验。某平台晚到，只能给它一个新版本号——两个平台版本号不同是预期行为，不是发错包。
  • 灰度分桶的哈希输入包含 platform + arch，百分比按平台各自生效。

这一套下来，「自动更新」就不再是客户端功能，而是一个小的发布平台。

二、客户端有两个入口，不是一个按钮

普通更新和强制更新在产品上是两条完全不同的路径：

  • 普通更新：侧栏按钮，状态 none / available / downloading / ready / error，后台下载，可以稍后重启；
  • 强制更新：全屏 gate，download → downloading → ready / failed，没有关闭，也没有「稍后」。

强制 gate 的关键不在 UI，而在它必须真的能拦住写入。受限时，三个写入口统一抛 UPDATE_REQUIRED：

  • 开始采集；
  • 重试失败链接；
  • 提交草稿。

验证时做了双向对照：受限时三个入口都拒绝；恢复后，它们分别落到各自的参数校验错误。这样才能排除「一律拒绝」和「探针本身失效」两种假通过。

还有一个容易被忽略的层级问题：商家登录页是挂在主窗口上的 WebContentsView，渲染层级在主页面之上。强制 gate 刚上线时，未登录用户看到的是登录页，不是更新页——CDP 里能读到 gate=true，屏幕上却不是。z-index 无效，因为两者不在同一合成层。最后改成受限时让登录视图让位（setVisible(false)），并处理了离线受限时的初值，避免先闪一下登录页。

三、状态机要能解释「为什么不可重试」

最初的判断用了 checkStatus，但它是「上次检查的结论」，不是本次操作结果。下载失败时它仍然是 UPDATE_AVAILABLE，于是不可重试的错误被显示成「重试下载」。

改完之后，失败分成两类：

  • 撤回、系统不支持、本机配置错误 → 「更新无法继续」+「重新检查」；
  • 传输类失败 → 「重试下载」。

另外补了一个 error 态：普通更新下载失败后，侧栏入口原本会直接消失，用户没有任何重试入口。现在只在有已知目标版本时显示错误状态，避免每次启动都亮红灯。

四、离线也要保持阻断

更新策略在本地有缓存。断网重启后，客户端仍然能恢复「当前版本受限」的结论，继续拦住写入。这里有两个细节：

  • 按服务端时间差与建议间隔调度检查，而不是只信本机时钟；
  • 离线时无法确认策略是否解除，默认保持限制，而不是乐观放开。

离线恢复探针 8/8 通过：stub 切到受限 → 跑一次检查 → 切到离线 → 重启应用 → 限制仍在、写入仍被拒。

五、验证方式：stub + 真实应用

后端用本地 stub 顶替，响应信封、字段、纳秒时间戳逐字段照抄真实接口；应用用隔离的 --user-data-dir 和调试端口启动，用 CDP 驱动。

状态机探针覆盖 8 种决策：UPDATE_DISABLED、UP_TO_DATE、UPDATE_AVAILABLE、待生效强制、已生效强制、RELEASE_REVOKED、业务失败、required 缺 enforceAfter。每个场景同时断言状态字段和 DOM：

  • gate 的 data-stage；
  • 侧栏的 data-state 与 tip；
  • 外壳是否 inert。

每个场景先断言 stub 确实被请求过，否则可能拿上一次的陈旧状态读成通过。这一条是探针设计里最重要的防假通过措施。

六、接受了的限制与还没做的

诚实记录几条边界：

  • 更新永远是整包。electron-updater 会尝试差分下载，但在这个 feed 方案下，它拼出的 blockmap 地址必然 404，每次都回退全量。本期决定接受整包 364 MiB，差分留作后续优化。
  • 删掉了两条死链路：deferUpdate（IPC、落盘、判重都齐，但没有任何 UI 调用）和 rolloutBucket（灰度在后端按 installationId 判定）。没有调用方的功能就是死代码，留着只会让下一个人以为它在工作。
  • prod 环境的接口部署与真实升级尚未验证；mac 的 dmg 外发所需公证也还没跑。
  • macOS 更新必须用 zip，dmg 只用于手动安装；这是 Squirrel.Mac 的约束，不是选择。

总结

自动更新的难点不在「会不会用 electron-updater」，而在三件事：

  1. 服务端要能回答「谁该更新、什么时候必须更新、出问题怎么退」；
  2. 客户端状态机要能区分可重试与不可重试，并且真的拦住写入；
  3. 验证要能证明它没有假通过，而不是只截图看到 gate 出现了。

把这三件事拆开做，更新才是一个可控的生产能力；只接库，得到的只是一个「有时候能升级」的按钮。
