跨平台选型：没有零代价的方案，只有扛得住的代价

跨平台十二年，框架换了一茬又一茬，真正没解决的一直是同一件事：你愿意为「省掉一份代码」付出多少。这篇按桌面、移动、小程序三条战线，把 2026 年的主流方案和它们各自的代价摆到一张桌上。

一、用户先看到的是安装包

我们自己那个桌面端，因为随包带了 Chromium、JVM 和一套 CLI 运行时，安装包一度到了 GB 级。后来做瘦身、拆产物、清 asar 污染，才压回一个能接受的范围。

这件事让我对「选型」的理解变了一层：用户不会先看你的架构图，他先看下载页上那个数字。

一个几十 MB 的工具，下载转化率会明显好于一个几百 MB 的同类产品；一个冷启动要两秒的软件，会被用户在心里标成「重」。这些都不是技术指标，但它们决定了技术方案有没有机会被用起来。

所以跨平台选型的第一问不是「哪个框架先进」，而是「我的用户愿意为这个安装包等多久、占多少内存」。

二、十二年没绕开的三笔账

把时间拉长看，跨平台框架的迭代基本都在处理三笔账，而且这三笔账互相牵制。

第一笔是包体积。 自带浏览器的方案必然重，因为里面捆的是一整套渲染引擎和运行时；借用系统 WebView 的方案会轻很多，但把兼容性责任转移给了各个操作系统。

第二笔是性能。 这里说的不是「卡不卡」这么粗，而是「和原生像不像」。滚动、动画、长列表、复杂表单，这些在原生组件上几乎不用特别优化，到了跨端方案里就要考虑渲染层、通信层和桥接层的损耗。

第三笔是生态和开发体验。 前端人才最多，Web 技术栈上手最快，所以 Web 路线的生态最厚；代价是用 Web 技术做「看起来像原生」的界面，系统菜单、文件选择器、通知这些能力始终要经过一层桥接。

三笔账的残酷之处在于：你很难同时把三笔都付清。 省下体积，往往要拿学习成本或生态缺口来换；买到生态，往往要接受体积和性能的妥协。

三、桌面端：Electron 和 Tauri 的分界不是「新旧」

Electron 经常被说成「上一代技术」，但看 2026 年的桌面软件清单，VSCode、Slack、Discord、Notion 这些产品仍然在 Electron 上。原因不复杂：它的生态、招人成本、调试体验和跨平台一致性，短期内没有对手能全面替代。

它的短板也很明确：安装包大、空闲内存高、冷启动慢。这些是架构决定的，不是优化能抹平的。

Tauri 换了一个思路：UI 用系统自带的 WebView，不再自带浏览器；后端用 Rust。 于是安装包和内存直接降一个量级，权限模型也更收紧——默认不能读文件、不能联网，用多少开多少。

但 Tauri 的代价同样清楚：

  • Rust 的学习曲线，对纯前端团队是实打实的门槛；
  • 生态还在追赶，某些能力得自己写 Rust；
  • 各系统 WebView 的渲染差异要自己兜，兼容性测试省不掉。

所以这两者的分界不是「新与旧」，而是你重的是生态还是体积。

这里有个容易被忽略的判断：换框架不一定能省掉你真正重的那部分。 我们那个桌面端最重的是随包分发的 CLI、JVM 和 Chromium，这部分换成 Tauri 也还在；Tauri 能省掉的只是渲染层自带的那一份 Chromium。如果应用的核心复杂度本来就在运行时和原生依赖上，换框架带来的收益会比预期小很多。

反过来，如果应用是轻量工具、内部工具，或者对启动速度和安装体积特别敏感，Tauri 的收益就很直接。1Password 这类把安全和性能放在体积前面的产品会走这条路，但它的前提是团队愿意为 Rust 买单。

四、移动端：三条路线回答的是三个不同的问题

移动端常被放在一张表里比较，但 Flutter、KMP、React Native 其实在回答三个不同的问题。

Flutter 回答的是「UI 能不能完全一致」。 它自己画 UI，不依赖系统控件，所以像素级统一、动画性能强。代价是它和系统 UI 是两套体系，系统分享、文件选择器这类能力要额外封装，应用看起来也容易「不像这个平台的应用」。

KMP / Compose Multiplatform 回答的是「业务逻辑能不能只写一遍」。 它不追求 UI 复用，UI 各端各写原生，共享的是 Kotlin 写的逻辑层。这条路适合已经有成熟原生团队、又不想维护两套业务代码的组织。代价是 iOS 侧仍然需要原生工程能力，团队得同时懂两套构建体系。

React Native 回答的是「能不能复用现有的人」。 React 生态、前端人才池、npm 依赖，这些是它最大的资产。新架构落地之后，启动、内存和动画的短板补上了不少，但原生模块和版本升级仍然要持续投入。

所以别问「哪个性能最好」，先问：你要复用的到底是 UI、逻辑，还是人？ 这三个答案对应的是三条完全不同的路。

五、小程序派：另一条赛道

如果业务要同时进微信、支付宝、抖音、百度、京东，再加上 App、H5 和鸿蒙元服务，那问题就不是「选哪个跨平台框架」，而是「一套代码怎么覆盖这么多平台」。uni-app 和 Taro 解决的是这个问题。

uni-app 的底子是 Vue，国内占有率高、插件市场丰富、上手快，适合 Vue 团队快速铺多端。新一代的 uni-app x 用 UTS 把代码分别编译成 Kotlin、Swift、ArkTS，思路是不再为了兼容所有平台而只取功能交集。代价是和 HBuilderX 强绑定，路线跟着商业公司的判断走。

Taro 的底子是 React，TypeScript 支持和编译时优化做得更深，适合代码量大、对类型安全有要求、需要混编出 RN 或自研 App 壳的工程。弱点是国内社区活跃度不如 uni-app，调试体验更依赖 VS Code。

鸿蒙是这条赛道 2026 年最大的变量。HarmonyOS NEXT 要求纯血 ArkTS，Taro 走源码级转换，uni-app x 走编译到 ArkTS，两条路都还在快速变化。实操里比较务实的做法是：核心模块用工程能力强的框架写，长尾功能用上手快的框架补，不必强行统一到一个框架里。

六、把选型写成一张代价表

框架没有绝对好坏，只有合不合。把常见场景和要付的代价放在一起，会更容易拍板：

场景 首选 你实际要付的代价
桌面重型工具、插件/扩展生态重 Electron 体积、内存、冷启动
轻量桌面工具、内部工具、性能敏感 Tauri Rust 学习成本、WebView 差异
移动 App、团队是 React 背景 React Native + Expo 原生模块维护、版本升级跟进
移动 App、团队是 Kotlin 背景 KMP / Compose Multiplatform iOS 原生工程能力
追求 UI 像素级一致、复杂动画 Flutter 系统组件桥接、平台观感差异
国内多端小程序、团队是 Vue uni-app HBuilderX 绑定、商业路线依赖
国内多端小程序、团队是 React Taro 社区活跃度、调试体验
已有原生 App，想嵌入小程序 FinClip / mPaaS 它是运行环境，不是替代框架

这张表最想说明的一点是：每一行的第三列都不是空的。 选型不是找「没有缺点」的方案，而是找「缺点你能扛、用户不在意」的方案。

七、几条我自己的判断

第一，先算重写成本，再算包体积。 包体积是用户能感知的，但重写成本是自己付的。为了省 100 MB 去重写一套扩展生态，通常不划算。

第二，团队栈比框架排名重要。 一个纯 React 团队选 Flutter，学习成本会吃掉跨平台省下来的所有人力；一个 Kotlin 团队硬上 RN，也会在原生模块上反复卡住。

第三，不要把「跨端」当目标。 它只是手段。如果产品只有一端，选原生往往更省事；如果只有两端且差异很大，硬套一个框架可能比写两份还贵。

第四，给未来留退路。 把业务逻辑和 UI 分层，把平台能力收进明确的接口后面。这样将来换框架时，换的是壳，不是全部。

八、诚实边界

  • 本文的框架分类和部分事实参考了兮动人的《跨平台12年：从 Electron 到 Tauri，我们到底在选什么》，观点和判断是我自己的。
  • 原文中提到的具体数字（安装包大小、内存占用、启动耗时、采用率、性能提升比例等），我没有逐项核实，而且这些值随版本、平台和打包方式变化很大，不要当作基准数据使用。
  • 我没有在生产环境落地过 Tauri、Flutter、KMP、uni-app 或 Taro。桌面端的经验主要来自一个 Electron 项目，移动端和小程序部分是资料梳理，不是实战复盘。
  • 选型结论有时效性。2026 年的判断，明年可能就不成立了。

总结

跨平台十二年来来去去，核心问题一直是同一个：愿意为「省掉一份代码」付出多少代价。

  • 桌面端付体积和内存，或者付 Rust 和 WebView 兼容性；
  • 移动端在「UI 一致」「逻辑复用」「人才复用」之间三选一；
  • 小程序派付的是生态绑定和平台适配成本。

没有一种方案能把代价收到零。所以选型真正要做的，不是选最酷的那个，而是算清楚：哪个代价你的团队扛得住，哪个代价你的用户不在意。
