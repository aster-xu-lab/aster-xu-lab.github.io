没有测试框架的项目怎么做质量基线

这个桌面项目没有测试框架，也没有 pnpm test。但”没有单元测试”不等于”没有质量门禁”。这篇文章讲我用了哪几道门闩，各自能挡住什么、挡不住什么。

一、先承认：这是个取舍

先说清楚为什么没有测试框架，而不是假装它存在：

  • 这是个 Electron 桌面应用：大量逻辑在进程间通信、原生视图、本地数据库里，纯函数式的单元不多；
  • 核心链路依赖外部页面（抓取），单元测试要么靠 mock 到失真，要么得做端到端；
  • 端到端测试（起真应用、跑真页面）成本和脆弱性都很高。

结论是：首版不引入测试框架，把质量押在”类型 + lint + 运行时验证 + 产物校验”这四道门闩上。不假装有 pnpm test，本身就是一条纪律——因为它会让下一个人以为单元测试是存在的。

三、门闩二：lint（只把 error 当失败）

代码规范检查有一条刻意的策略：只把 error 级别当失败，warning 不拦。

理由很实际：warning 数量一旦失控，开发者会整体忽略 lint 输出，连真正的 error 一起忽略。只拦 error，保证了”门闩的输出永远值得看一眼”。

于是分两个入口：常规 lint（看全部）和 lint:errors（CI / 门闩用，只看 error）。

它的使用时机很关键：在说”做完了”之前、在一次十分钟的构建之前跑。原话是——“不要等十分钟的打包构建，才发现漏了个返回类型”。一个小检查前置，省下一次长构建。

五、门闩三：运行时验证（类型系统查不出的）

有一类错误类型检查永远查不出：比如预加载脚本暴露的接口，在运行时根本不是个对象。

类型上，window.api 声明得清清楚楚；但打包方式一旦出错，它运行时可能是 undefined。TS 完全看不出来——因为它只检查类型，不检查运行结果。

所以有一条纪律：改完预加载，要用调试协议连上去，断言 typeof window.api === 'object'。这是运行时验证，不是类型验证，两者互补。

六、门闩四：产物校验

打包命令成功退出 ≠ 产物正确。所以需要一层专门校验产物本身的门闩：

  • asar 卫生：归档里有没有混进不该有的东西（比如打错的兄弟目录、中间文件）；
  • 可执行位：随包的二进制有没有执行权限；
  • 渠道一致性：产物名、应用 ID、数据目录是否都属于同一个渠道；
  • 随包资源齐全。

还有一道打包前预检，清理散落的中间文件、对意外的顶层路径直接失败——避免”出完包才发现归档脏了”。

核心思想一句话：打包的完整性用产物本身来验证，不要信构建命令的返回值。

七、四道门闩分别挡什么

门闩 挡住 挡不住
类型检查 类型错误、拼写、接口不匹配 运行时错误、逻辑错误
lint 风格、可疑写法 语义错误
运行时验证 契约在运行时是否存在 契约的语义对不对
产物校验 打包配置 / 卫生 / 一致性错误 代码逻辑错误

八、诚实的边界

必须说清楚这四道门闩挡不住什么：

  • 它们挡不住业务逻辑错误——比如状态派生算错了、计数对不上、某个边界没处理。这类问题要靠人工实测 + 记录（工程里有专门的实测记录表，逐条对照验收点）；
  • 它们挡不住”需求和实现不符”——那要靠对照文档；
  • 类型和 lint 只能证明”不违反已知规则“，证明不了”行为正确“。

所以这套门闩的定位是：把”低级错误”挡在门外，把人力留给”逻辑正确性”的人工验证。它不是测试框架的替代品，是在没有测试框架时的最优折中。

总结

  • 无测试框架是刻意的取舍（Electron + 外部依赖场景下单元测试性价比低），不假装有 pnpm test；
  • 四道门闩：类型检查（tsc + vue-tsc 两端）、lint（只拦 error）、运行时验证（CDP 断言 window.api）、产物校验（asar 卫生 / 可执行位 / 渠道一致性）；
  • verify:ready = typecheck + lint:errors，在长构建之前跑；
  • 类型检查查不出运行时契约，”契约存在”必须用运行时验证补；
  • 门闩的思想：用产物本身验证打包，不信构建退出码；
  • 诚实的边界：这些门闩挡不住逻辑错误——那部分只能靠人工实测与记录。
