该不该复用第三方库内置的 LLM 能力：一次 ADR 复盘

我们的采集引擎内置了一整套 LLM 能力——能抽取、能总结、能跑 agent。既然它已经在那儿了，为什么不直接用它做字段映射，非要在主进程里自建一套模型接入？这篇文章是一次 ADR 式的决策复盘。

一、问题：复用”现成的 LLM”到底省什么

场景是：采集到的商品字段要映射到我们商品库的类目属性上。这件事很难用纯规则写全（跨平台字段不同、跨类目属性不同），所以很自然会想：引擎不是自带 LLM 吗？直接用它映射不就行了。

复用的直觉收益是：省掉模型管道的胶水代码——鉴权、HTTP、重试、schema 转换。

二、但它省的，恰好不是难点

把引擎的 LLM 能力拆开看，结论很清楚：

  • 它提供的是通用页面抽取的模型调用，里面没有任何”商品类目 / 属性字典”的概念；
  • 它随包的”知识”目录是空的，随包的技能没有一个是商业类目相关的；
  • 官方文档给的多种抽取方案里，全篇不提”字段映射”或”类目属性”。

也就是说：复用能省的是胶水，省不了映射逻辑本身——而映射逻辑正是这个问题的难点。

这个判断是整次决策的转折点：如果复用省的是难点，那值得容忍它的代价；如果省的是胶水，那代价就得单独算。

三、三条实测的反对事实

真正让决策落定的，是三条实测发现：

# 事实 为什么致命
1 Key 归属错配 Key 必须对后端进程可见（CLI 自己不持有 Key）。应用自持服务端时，只能把 Key 注入服务进程的环境变量，于是引擎全部 AI 能力都能用它，做不到”用户授权某一次调用”的粒度
2 默认把 prompt 与响应全文落盘 引擎的日志记录器会把完整请求与响应写进日志，而且是默认行为、不是开关。商品数据会以明文落在它的日志目录，直接违反”日志不含敏感内容”的验收项
3 依赖开发快照构建 后端整体是 SNAPSHOT 构建，且我们已在同一链路上遭遇过”静默复用外部后端、端口不可配置、杀不掉外部后端”

第 2 条尤其关键：能不能关掉日志落盘，决定的不只是”方不方便”，而是”合不合规”。默认落盘的库，即使功能再强，也不适合碰商品数据。

另外两条工程性理由：可测试性（自建可以 mock、缓存、回放、按次开关；引擎侧不可控）和语义隔离（采集证据是可溯源的，模型候选不该混进去）。

四、更重要的一步：更正了两个”原本以为成立”的理由

一次好的决策复盘，不只是列出支持结论的理由，还要纠错。初审时我列过两条反对复用的理由，实测都不成立：

原判断 实测
“provider 灵活性不足，会被绑死” 错。引擎内置 20+ 个 provider（含十来个国内厂商），都支持覆盖 base url，还有通用的 OpenAI 兼容逃生口
“发送范围不可控，会把整页塞给模型” 夸大。有选择器作用域、输入长度上限、显式截断标记、摘要模式等一连串控制

为什么这个更正很重要？ 因为它改变了决策的论证结构：

结论的依据不是“引擎做不到”，而是”它能做到的部分恰好不是难点，而它的代价落在我们最在意的合规与可测性上“。

前者是”能力之争”（容易被反驳：”明明可以配啊”）；后者是”成本之争”（无法反驳：Key 归属和默认落盘是它的设计事实）。

把”我错了”的那两条写进决策文档，比只写支持结论的三条更有价值——它让后来的人不会重复走这条已经证伪的岔路。

五、自建之后的设计：分层

决定自建，接下来是放在哪一层。最终的分层是：

三条设计约束值得强调：

  1. 不把模型输出写进证据结构。因为证据是要持久化、要可溯源的，模型输出必须是一个独立结构，才能做到可开关、可缓存、可重算、可审计、可拒绝。
  2. 映射层不碰抽取层。抽取层是”确定性 + 不伪造”的边界（缺关键字段一律报错），不能混入非确定性逻辑。
  3. 规则优先，LLM 只补未命中的字段——不是让模型从零做映射。

六、顺序上的一个反直觉结论

方案里明确了一件事：人工确认（L3）必须先于 LLM 建议（L2 的模型部分）。

理由很硬：模型输出必须经人工确认才能用。而复审这套界面一开始连字段都不能编辑——建议做出来了也没地方落地。所以先补”可编辑、可确认”，再谈”建议”。

这是一个容易搞反的顺序：大家总觉得”上 AI”是最高优先级，但没有可确认的界面，AI 的建议就是无根之木。

七、诚实的边界

  • 自建要自己扛：重试、超时、缓存、成本控制都得自己写——这是复用的胶水省下来的那部分，现在得还回去。
  • 复用的例外是允许的：如果目的只是”低成本验证模型能不能提升效果”，可以用引擎做一次性 spike，验证完就换掉，不作为长期架构。
  • 合规是前置条件：即使口头确认可以外发数据，只要没落到文档，就不应该在演示里展示这个能力。
  • 有一条红线要反复划：“把已有属性映射到目标字段” ≠ “凭空补造缺失值”。前者在范围内，后者禁止。

总结

  • 复用内置 LLM 省的是胶水（鉴权 / HTTP / 重试 / schema），省不了映射逻辑——而映射逻辑正是难点；
  • 三条反对事实：Key 归属错配（做不到按次授权）、默认全文落盘（合规致命）、SNAPSHOT 依赖（版本漂移）；
  • 关键的纠错：“provider 不灵活””发送范围不可控”两条实测不成立——所以结论依据是”它能做的不是难点，代价落在合规与可测性“，而不是”它做不到”；
  • 自建分层：抽取 → 字典 → 建议（规则优先，LLM 兜底）→ 人工确认 → 草稿；模型输出不写进证据结构；
  • 顺序反直觉但正确：先做”可编辑可确认”，再做”AI 建议”——没有确认界面，建议无处落地；
  • 红线：“映射已有字段”在范围内，”凭空补造”禁止。
