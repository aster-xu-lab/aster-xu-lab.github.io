Function Calling：让模型输出结构化JSON的工具调用

一、从”聊天”到”干活”的关键一步

对话式 LLM 的输出是自然语言。但让模型真正”干活”——调接口、查数据库、发指令——你需要的是结构化的调用声明：模型明确告诉你”我要调用哪个函数、参数是什么”。

Function Calling（函数调用 / 工具调用）就是干这个的：模型输出结构化 JSON，声明要调用哪个函数、传什么参数，而不是输出自然语言。

二、工作原理：模型”知道能用什么工具”

Function Calling 的本质是：在调用模型时，把”可用工具的清单”（函数名 + 描述 + 参数 Schema）一并传给模型。模型根据用户问题和工具描述，决定”该用哪个工具”，并输出符合 Schema 的参数。

上面这段 tools 结构是 OpenAI 的格式（type: "function" + function.parameters）。Anthropic 的工具定义字段叫 input_schema，模型返回的是 tool_use 内容块，应用回传结果时要用 tool_result 并带上对应的 tool_use_id；OpenAI 侧则用 tool_call_id 关联。字段名和回传结构因厂商而异，不要把一家的格式当成通用协议。

关键点：

  • 工具描述（description）决定选对率：描述写得越清楚，模型选对工具的概率越高。模糊的描述 = 模型瞎猜；
  • 参数 Schema 决定输出格式：模型按 JSON Schema 输出，你的代码直接解析，不用处理自然语言；
  • 模型不真正执行工具：它只输出”调用声明”，真正执行的是你的代码——执行权始终在你手里。

三、一个重要的迁移视角：它和任务编排是同一套思想

我做过 SyncTask 任务编排引擎，看 Function Calling 时发现结构和思想完全相通：

SyncTask 引擎 Function Calling / Agent
Handler 注册表（声明可用能力） tools 清单（声明可用工具）
handlerKey 路由到实现 LLM 推理 → 选 Tool
参数解析/校验（SPI） JSON Schema 校验
executeCore() 执行业务 Tool 被调用 → 返回结果
afterExecute 决定下一跳 LLM 决定下一步

都是”定义能力 → 按需调度 → 可扩展”。区别只有一个：SyncTask 的”决策者”是代码规则（if status == SUCCESS → next），Function Calling 的”决策者”是 LLM。这个迁移视角，是我理解 AI 工具调用最快的入口。

四、应用场景

Function Calling 的典型场景：

  • 让 LLM 调内部 API：查订单、查库存、发通知——把业务能力暴露成工具；
  • Agent 的工具层：Agent 拆解任务后，靠 Function Calling 一步步调工具执行（下一篇讲 Agent）；
  • 表单/查询的自然语言入口：用户说人话，模型转成结构化查询。

五、陷阱与工程化注意

Function Calling 看着简单，落地坑不少：

① 模型可能选错工具。工具多了之后，选错概率上升。对策：工具描述写精确、工具数量控制、关键路径设置人工确认点——涉及金钱/库存的工具调用必须人工确认，不能让模型直接拍板。

② 参数可能编造。模型可能输出一个”看起来合理但不存在”的参数值（比如编一个订单号）。对策：参数校验 + 执行前用真实数据核验，查不到就如实报错，不硬查。

③ 超时兜底。模型接口超时/返回格式异常，要有超时和重试，不能让它卡住整个流程。

④ 结构化 ≠ 可信。模型输出的 JSON 格式对，不代表内容对——结构化解决了”格式”问题，没解决”正确性”问题。正确性要靠执行时的真实数据验证兜底。

六、和结构化输出的关系：别划等号

两者都让模型输出 JSON，但解决的不是同一个问题，不能混为一谈：

Function Calling（工具调用） Structured Output（结构化输出）
输出什么 “要调用哪个工具、参数是什么”的调用声明 业务数据本身，按给定 JSON Schema / 类型填充
谁来执行 应用解析声明后执行工具，再把结果回传模型 应用直接消费这段结构化数据
典型实现 OpenAI tools + tool_calls；Anthropic tools + tool_use 块 OpenAI response_format；Spring AI 的 ChatClient...call().entity(Class) / StructuredOutputConverter
解决什么 让模型能触发外部能力 让模型的自由文本变成程序可消费的数据

它们可以共用 JSON Schema 这套描述能力，但 Function Calling 的产物是”调用意图”，Structured Output 的产物是”数据”。把 Structured Output 说成 Function Calling 的封装，是常见但错误的简化：不用工具的模型也能做结构化输出，用工具的模型也不一定约束了输出 Schema。

共同点只有一句：两者都在把模型的自由文本，变成程序可以直接消费的结构化数据。 没有这一步，LLM 只能当”高级聊天机器人”；有了这一步，LLM 才成为”可编程组件”。

总结

  • Function Calling = 模型输出结构化 JSON 声明调用哪个函数 + 参数，而非自然语言；
  • 本质：定义能力（tools 清单）→ 按需调度（LLM 决策）→ 可扩展；
  • 和执行器（SyncTask Handler）是同一套编排思想，只是决策者从代码变成了 LLM；
  • 陷阱：选错工具、参数编造、超时——要工具描述精确 + 真实数据校验 + 超时兜底；
  • 结构化解决格式问题，不解决正确性问题，正确性靠执行时验证。
