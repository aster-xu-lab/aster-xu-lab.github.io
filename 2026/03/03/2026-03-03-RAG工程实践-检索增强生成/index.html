RAG工程实践：切块、向量化、检索与幻觉控制

写在前面：这篇记录的是一个刚起步的 RAG 场景——把高频 FAQ 切块向量化、pgvector 语义检索、接 LLM 返回，核心在控制幻觉。没有生产级量化指标，重点是工程思路和踩坑。

一、RAG 解决什么问题

大模型有三个天生的缺陷：

  1. 知识过期：训练数据截止在某个时间点，之后的事不知道；
  2. 幻觉：不知道就是不知道，但它会编一个”看起来合理”的答案；
  3. 不能访问私有数据：公司内部资料、个人文档，模型根本没训练过。

RAG（Retrieval-Augmented Generation，检索增强生成）的思路是：模型不知道没关系，把相关文档”喂”给它，让它基于文档回答。

三、切块：RAG 质量的第一个关键

切块策略直接影响检索质量，常见选择：

  • 按固定长度切：简单，但可能把一句话从中间切断；
  • 按语义边界切：按段落/标题切，语义完整，检索命中更准；
  • 带重叠：相邻块留一部分重叠，避免”关键句刚好在缝上”被漏掉。

我的经验：切块粒度要和”回答粒度”匹配。FAQ 场景，一条问答就是一个天然块，不要硬按字数切；如果是长文档，按标题/章节切比按固定字符切好很多。

四、向量库选型：pgvector 是入门首选

向量库的选型看体量和预算：

方案 特点
pgvector PostgreSQL 插件，便宜、不引新组件，百万级以内够用，入门首选
Milvus 专用向量库，分布式、性能强，适合大规模
Chroma 轻量、开发友好，适合原型

FAQ 这种小体量场景，pgvector 是最务实的——它就是个 PG 插件，业务库里加一张向量表就行，不用为几万条 FAQ 专门运维一套向量库。

五、混合检索：向量 + 关键词

纯向量检索有个弱点：语义相近但不精准。比如搜”退货政策”，向量能召回”退换货规则”，但如果用户输入的是精确的订单号、产品型号，向量检索反而不如传统的关键词匹配。

所以更稳的是混合检索（Hybrid Search）：向量检索 + 关键词检索（BM25 之类）同时跑，结果合并去重。向量抓”语义”，关键词抓”精确匹配”，召回率更高。

六、幻觉控制：RAG 的生死线

RAG 做不好，最大的风险是：检索到的内容不对，LLM 还一本正经地基于错误内容编答案。 幻觉控制是我在这套 FAQ 场景里最下功夫的部分：

① 检索不到就明说：TopN 的相似度分数低于阈值时，不硬答，明确告诉用户”这个问题我没有足够的信息，建议转人工或关键词搜索”。这是幻觉控制的第一原则——允许说”不知道”，绝不允许编。

② 加引用来源：要求 LLM 回答时带上”根据文档 X”的来源标注，用户可以核验，模型也更不容易瞎编。

③ 意图识别兜底：在接 LLM 之前，先做一层意图识别——问题类型匹配不上 FAQ 覆盖范围，就直接落到关键词搜索或人工兜底，不硬往 LLM 上引。

一句话：RAG 的幻觉控制不是靠 prompt 技巧，是靠”检索质量 + 拒绝回答”两条腿。 检索不行就明说不知道，比生成一个错误答案安全得多。

七、工程化注意

  • Embedding 模型要固定：建库和检索必须用同一个模型，换模型 = 全部重算向量，否则检索结果全乱；
  • LLM 降级兜底：LLM 接口超时/不稳定时，降级到”直接返回检索到的 TopN 原文”，保证用户至少能看到相关内容，而不是报错；
  • 成本控制：prompt 里拼的检索结果越多 token 越贵，TopN 要控制（3~5 条足够），长文档块要精简。

八、诚实的能力边界

最后说点诚实的：这套 FAQ RAG 是我刚开始做的落地场景，还没有大规模生产数据，也没有量化指标（没有”召回率 88%”这种数字）。它的价值在于把 RAG 的完整链路跑通了——切块、向量化、检索、拼 prompt、幻觉控制、降级兜底，每个环节该踩的坑都踩了一遍。原理清楚、链路跑通、边界诚实，这是我现在能对 AI 工程化说的最准确的话。

总结

  • RAG 解决知识过期 + 幻觉 + 私有数据，靠”检索相关文档喂给模型”；
  • 流程：切块 → 向量化 → 存库（离线）+ 问题向量化 → 语义检索 → 拼 prompt（在线）；
  • 切块粒度匹配回答粒度，向量库小体量选 pgvector；
  • 混合检索（向量 + 关键词）召回更高；
  • 幻觉控制 = 检索质量 + 拒绝回答：检索不到就说不知道，加引用来源，意图识别兜底；
  • 换 Embedding 模型要全量重算，LLM 要降级兜底，TopN 控制成本。
