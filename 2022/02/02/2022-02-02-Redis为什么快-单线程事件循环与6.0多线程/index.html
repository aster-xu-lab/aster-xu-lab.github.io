Redis 为什么快：单线程事件循环，与 6.0 的多线程到底在哪

一、先说结论：三件事，缺一不可

Redis 快，常规答案是三件事：内存存储、单线程免锁、IO 多路复用。但”单线程”三个字很容易让人误解——它到底在解什么、6.0 加了多线程又是怎么回事，值得讲透。

二、IO 多路复用：单线程能服务海量连接的前提

先说”单线程为什么能扛住那么多连接”。答案是我在 IO 模型那篇讲过的 epoll：

  • 一个线程通过 epoll_wait 同时盯着成千上万个 socket，哪个有数据就处理哪个；
  • 没有数据就阻塞在 epoll_wait 上，不占 CPU；
  • 事件驱动，复杂度只跟”就绪事件数”有关，不是连接数。

所以”单线程”和”IO 多路复用”是一体两面：

复用让单线程能同时服务海量连接，单线程让处理免锁。

如果没有多路复用，单线程要么阻塞在 read 上（别的连接全晾着），要么忙轮询（烧 CPU）。有了 epoll，一个线程在海量连接间”谁有数据处理谁”，才有”单线程扛高并发”的可能。

三、单线程：天然无竞态，这才是重点

单线程带来的最大收益不是”省一个线程”，而是天然无竞态：

  • 不需要加锁——单线程串行执行命令，不存在两个线程同时改一个 key；
  • 不需要处理上下文切换——一个线程从头跑到尾；
  • 所有操作内存快，串行执行也足够快。

Redis 的核心瓶颈不在 CPU，在内存和 IO。所以单线程对”内存 + IO 复用”的场景足够，多线程带来的上下文切换和锁竞争反而会拖慢。

四、命令执行是单线程，但不是”全部单线程”

这是最容易误解的一点。Redis 6.0 引入了多线程，但只用于网络读写（IO）：

环节 是否多线程
命令执行（核心） 单线程，串行
网络读写（6.0+ io-threads） 可多线程
AOF/持久化 异步/子进程
懒删除 unlink 异步

6.0 加多线程解的是”网络 IO 搬运”这个瓶颈——把数据从 socket 搬进内存、从内存搬回 socket 这类耗时 IO，分摊给多个线程；但命令的执行仍然单线程串行，所以不会引入竞态。

一句话：核心命令执行保持单线程（免锁），耗时的网络读写用多线程加速（不碰共享状态）。

五、事件循环：单线程 + epoll 怎么协作

Redis 主线程是一个典型的事件循环：

一个线程不断 epoll_wait 拿就绪事件，串行执行每个事件对应的命令。因为单线程，天然无竞态；因为内存操作，串行也快；因为 epoll，空闲时完全不占 CPU。

六、一个常见追问：为什么 Redis 不用多线程

面试常问”既然单线程，为什么不用多线程更快”。诚实的答案：

  1. 瓶颈不在 CPU：Redis 的操作是内存级，快得不得了，真正的瓶颈在网络 IO 和内存，不是计算；
  2. 多线程引入竞态：要加锁、要处理并发，复杂度爆炸，收益是负的；
  3. IO 复用已解决连接问题：单线程 + epoll 已经能服务海量连接，没必要用多线程去”并行处理”。

但 6.0 的网络 IO 多线程是个例外——它解决的是”网络报文搬运占 CPU”的真实瓶颈，而且不碰命令执行的共享状态，是安全的多线程。

七、结合我的项目

我在订单系统用 Redis 缓存扛大促流量，本地 Caffeine 减少 Redis IO。理解 Redis 单线程模型，直接影响两个运维判断：

  • 别用 O(N) 命令（keys、hgetall 大 key）——单线程下一条慢命令卡住的是所有连接；
  • 大 key 删除要用 unlink（异步懒删除），不用 del（阻塞单线程）——这是单线程模型的直接推论。

总结

  • Redis 快 = 内存 + 单线程免锁 + IO 多路复用；
  • 单线程与 IO 复用一体两面：复用让单线程服务海量连接，单线程让处理免锁；
  • 命令执行单线程，网络读写 6.0 起可多线程——多线程不碰共享状态；
  • 瓶颈在内存/IO 不在 CPU，所以多线程对 Redis 是负优化（除网络 IO 外）；
  • 运维推论：别用 O(N) 命令、删大 key 用 unlink——单线程下一条慢命令卡全连接。
