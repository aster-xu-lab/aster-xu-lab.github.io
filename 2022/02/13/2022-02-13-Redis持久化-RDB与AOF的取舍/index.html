Redis 持久化：RDB 与 AOF 的取舍，fork+COW 为什么不停顿

一、两种持久化，两套取舍

Redis 持久化两种方式，解决不同的问题：

RDB 快照 AOF 日志
内容 全量数据的二进制快照（.rdb） 每次写命令的追加日志（.aof）
恢复 快（直接加载快照） 慢（逐条重放命令）
丢数据 多（两次快照之间的写会丢） 少（everysec/always 配置粒度）
文件 小、二进制 大、文本，可重写

RDB：某一时刻的完整快照，恢复快，但快照间隔内的写入会丢；
AOF：每一条写命令，恢复慢，但按策略（每秒/每次写）几乎不丢数据。

组合用法：RDB 做快照备份/副本初始化（恢复快），AOF 保数据（丢得少）。生产通常两个都开。

二、核心问题：快照时主线程为什么不停顿

RDB 快照要写全量数据，如果主线程自己写，会阻塞——但 Redis 用的是 fork 子进程去写快照，主线程继续处理请求。它凭什么能”一边写快照、一边继续写数据”？

答案是写时复制（COW）——我在《fork写时复制COW》那篇讲过机制，这里看它在 Redis 里的应用。

三、fork + COW：快照一致且不阻塞

三个关键点：

  1. fork 不复制数据：只复制页表（O(页表大小)），父子共享物理页，所以 fork 瞬间很快；
  2. COW 按需复制：主线程改哪个页，才复制哪个页——写多少复制多少，不整块拷贝；
  3. 快照天然一致：子进程从头到尾读的是”fork 那一刻”的页，主进程改的是副本，互不干扰。

所以”子进程写 RDB、主线程读写 Redis”两不耽误——不是靠锁，是靠 COW 让主线程写原、子进程读 fork 时刻的副本。

四、代价与风险

COW 不是免费的，两个真实风险：

  1. 内存暴涨：快照期间主线程大量写（改很多页），每个被改页都要复制一份——内存可能飙升，极端情况接近翻倍；
  2. fork 本身卡顿：大内存实例即使只拷页表，页表也可能很大，fork 瞬间会有瞬时卡顿。

所以运维上有两个避坑：

  • 大实例别频繁触发 RDB（快照太频繁，COW 复制累积）；
  • 关注 fork 耗时（INFO 里的 latest_fork_usec），卡顿来自 fork 页表复制。

五、AOF 的重写与风险

AOF 是命令日志，文件会越来越大，所以有AOF 重写：把当前数据集用最少的命令重建一个新 AOF。重写同样走 fork 子进程 + COW，主线程不阻塞，期间新命令写到缓冲区，重写完成后合并。

AOF 的刷盘策略：

  • always：每条命令都 fsync，最安全但最慢；
  • everysec：每秒 fsync，丢最多 1 秒数据，性能好——生产常用；
  • no：交给操作系统，最不安全。

六、一条判断线：要恢复快还是要丢得少

RDB vs AOF 本质是**”恢复快”和”丢得少”**的取舍：

  • 追求恢复快（重启秒开）→ RDB 为主；
  • 追求丢得少（最多丢 1 秒）→ AOF 为主；
  • 生产最佳实践：RDB + AOF 都开，RDB 做备份/副本初始化，AOF 做实时保护。

Redis 4.0 之后默认的混合持久化：用 RDB 做基础快照 + AOF 只记录快照后的增量命令——恢复时先加载 RDB 再重放少量 AOF，又快又丢得少。

七、和我的项目

订单系统的 Redis 缓存数据基本都是可重建数据（从 DB 派生），所以持久化策略偏保守——开 AOF everysec 保安全，RDB 定期做备份。理解 COW 后，我特别在意大促期间不要频繁触发 RDB：峰值写越多，COW 复制越猛，内存和 fork 卡顿风险越高——所以快照安排在低峰，和 MySQL 备份同理。

总结

  • RDB = 全量快照，恢复快、丢得多；AOF = 命令日志，恢复慢、丢得少；
  • 生产组合：RDB 做备份/副本初始化 + AOF 保数据；
  • RDB 不停顿靠 fork + COW：fork 只拷页表，主进程改页才复制，子进程读 fork 时刻的页；
  • 两个风险：写得多内存涨、fork 页表大瞬时卡——大实例少触发 RDB；
  • AOF 刷盘：always / everysec（生产常用）/ no；
  • 混合持久化 = RDB 基础快照 + AOF 增量，又快又丢得少。
