SyncTask Job 与基于日志的消息中间件 - 持久化机制对比

问题的起点

最近在 review 订单中心的 SyncTask 同步任务引擎时，产生了一个疑问：SyncTask 这种把任务写到数据库表里，然后定时轮询拉取执行的模式，跟 Kafka/RocketMQ 那种基于日志的消息中间件，在持久化方面是不是很类似？

答案是有相似的内核，但设计目标完全不同。本文以订单中心 cloud-order 项目中的实际代码为例，深入对比三种持久化机制。

订单中心的三种持久化机制

SyncTask Job — Transactional Outbox 模式

SyncTask 是订单中心自研的统一同步任务调度引擎，负责订单数据到 10+ 个外部系统（聚水潭、无仓、金蝶、FMS 等）的分发同步。它的核心思路非常朴素：

表结构 or_sync_task：

状态机：

生命周期：

  1. 创建：在 @Transactional 方法中，与业务数据一并 INSERT INTO or_sync_task
  2. 拉取：XXL-Job 定时 SELECT ... WHERE status IN (INIT, FAIL, WAIT)
  3. 锁定：@XLock 分布式锁 + 二次查库 + UPDATE status = PROCESSING
  4. 执行：策略路由到对应的 Handler，执行业务逻辑
  5. 完成：UPDATE status = SUCCESS/FAIL/WAIT
  6. 补偿：SyncTaskProcessingBackJob 定时回收卡在 PROCESSING 的僵尸任务

防丢失的核心机制：

  • 分布式锁：拉取层 ORDER_CENTER_REFRESH_TASK + 执行层 ORDER_CENTER#{orderType}#{referenceId}，双层锁防重
  • 二次查库：refreshSyncTask() 加锁后重新从 DB 拿最新数据，再锁定状态
  • 幂等判断：execute() 锁内再次 findById，若已是 SUCCESS/CANCEL 直接返回
  • 僵尸补偿：超过 1 小时的 PROCESSING 任务自动重置为 INIT
  • 原子递增：UPDATE or_sync_task SET retry_times = retry_times + 1，避免 Java 侧读-改-写竞态
  • 线程池拒绝降级：队列满时直接标记 FAIL，下次 cron 重试

RocketMQ — Broker 侧 CommitLog

订单中心消费 33 种消息，涵盖订单流转、物流轨迹、财务开票、售后、即时零售、爬虫任务等全部场景。消费者采用 Spring Cloud Function 的 Consumer<Message<T>> 模式。

RocketMQ 的持久化是 Broker 的责任：

  • Producer 发送消息 → Broker 写入 CommitLog（Append-only 分段文件）
  • Consumer 拉取消息 → 处理 → 提交 offset（记录消费进度到 __consumer_offsets）
  • Consumer 重启后，从上次 commit 的 offset 继续消费

订单中心的幂等去重：
对于广播消费场景，由于同一个消息会被多个消费组消费，RocketMQ 的 offset 机制不够用。项目用 Redis 额外做了一层幂等：RedisKeyUtil.generate("ORDER", msg.keys()) 作为幂等 key，避免重复处理。

日志治理系统 — 三级缓存管道

日志治理是订单中心自研的一套运维诊断系统，它的持久化路径比前两者更复杂：

三阶段设计：

  1. 本地聚合：ErrorLogLocalCache（ConcurrentHashMap + ConcurrentLinkedQueue），按 windowEndKey | md5指纹 聚合次数 + 最新明细
  2. 定时刷 Redis：每 60 秒 drain pending → 合并 → ERROR:WINDOW:COUNT:{windowEndKey} ZSet + ERROR:DETAIL:{md5} String
  3. XXL-Job 落表 + 告警：按时间槽从 Redis 取 TopN → MySQL error_log_statistics + 企微 Markdown/Excel 告警

与消息队列的联动：LogGovernMqAspect 通过 AOP 切入 RocketMQBuilder.process()，将 MQ Tag 写入 MDC，使异常日志可追溯到具体消息来源，实现全链路追踪。

核心对比

维度 SyncTask Job RocketMQ 日志治理
持久化主体 任务执行状态机 消息内容 + 消费进度 异常指纹 + 次数
写入模式 INSERT + UPDATE（行级） Append-only 文件（分段） 本地聚合 → 批量 pipeline
读取模式 SELECT by status Consumer pull by offset 按时间槽 ZSet 读取
数据生命周期 任务完成后长期保留 按 Retention 过期 按时间槽 TTL，落表后清理
防丢失级别 强保证（分布式锁 + 二次查库 + 僵尸补偿） Broker 侧强保证，Consumer 侧 at-least-once 允许少量丢失（@PreDestroy 兜底）
并发控制 锁粒度 = orderType+referenceId 分区粒度 = MessageQueue 无锁，ConcurrentHashMap
重试机制 retryTimes 原子递增，上限 5 次 自动重试 + 死信队列 无（丢了就丢了）
人工干预 UPDATE status=INIT 一键重试 reset offset 或死信队列 不需要

它们都在做同一件事：断点续传

三者本质上都是：把”进行中的流程”的状态/进度持久化到外部存储，以便故障恢复后能从断点继续。

为什么 SyncTask 不用 RocketMQ 替代？

这是一个经常被问到的问题。SyncTask 完全可以用”发一条 MQ 消息 + Consumer 处理 + 失败进死信队列”来替代，但那就丢失了 SyncTask 最核心的能力：

可查、可改、可人工干预：

如果换成 RocketMQ，你做不到 SQL 查询任务状态，也做不到一行 UPDATE 就重置重试。Kafka/RocketMQ 是数据管道（data pipeline），SyncTask 是状态机（state machine）。二者的”读”需求完全不同。

设计决策的本质：

选择 SyncTask 选择 RocketMQ
需要 SQL 查询任务状态 只需要 fire-and-forget
需要人工重试/取消 死信队列 + 管理后台够用
数据规模可控（业务单据） 每秒百万级消息
不想引入额外中间件 已有 MQ 集群
需要事务一致性（@Transactional 同时写） 最终一致性可接受

Transactional Outbox 的精髓

SyncTask 本质上是 Transactional Outbox（本地消息表）模式 的一种工程实现。它的精髓在于：

不需要分布式事务，不需要两阶段提交，不需要额外的消息中间件——一个 MySQL 事务 + 一个定时 Job 就搞定了。这也是为什么很多中小型系统用这种模式替代 MQ：够用、简单、运维友好。

但代价也很明显：

  • 数据库压力（如果任务量大了，轮询会扫表）
  • 时延较高（取决于 cron 间隔）
  • 不具备真正 MQ 的削峰填谷和高吞吐能力

总结

SyncTask 是”状态持久化”（stateful），RocketMQ 是”数据持久化”（data pipeline），日志治理是”统计持久化”（aggregation）。三者都在做持久化——但 SyncTask 持久化的是”任务执行到哪一步”，RocketMQ 持久化的是”消息有没有被消费”，日志治理持久化的是”异常产生了多少次”。前两者需要强一致性不能丢，日志治理允许少量丢失。

这不是学术上的分类，而是工程上三种不同层次的需求，恰好都在”持久化”这个维度上产生了交集。理解清楚它们各自的边界，才能在架构决策中做出正确的选择。
