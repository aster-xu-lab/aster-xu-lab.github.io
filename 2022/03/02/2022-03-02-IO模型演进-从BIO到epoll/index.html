IO模型演进：从BIO到epoll，Redis单线程扛高并发的秘密

从一个真实的瓶颈说起

刚做订单系统的时候，同步任务的调用链上有一个老服务，用的是最朴素的 BIO 写法：一个客户端连接来了就 new 一个线程去处理。QPS 一上来，先是线程数暴涨，然后线程栈把内存吃满，最后干脆拒绝新连接。

这个问题的本质，是阻塞等待——线程花大量时间睡在 read() 上，什么事都不干，却占着一个宝贵的线程资源。

IO 模型演进的全部历史，就是在回答一个问题：怎么让有限的线程，服务尽可能多的连接？

一、BIO：一连接一线程

阻塞 IO 的工作方式：

两个阻塞点：accept() 等新连接、read() 等数据。线程在阻塞期间什么也不干，白白占用内存（默认线程栈 1MB）。

连接数 N → 线程数 N → 上下文切换成本 O(N²)。几千连接就能把一台机器拖垮。

二、NIO：同步非阻塞，还是不行

非阻塞 IO 把 read() 改成”没数据就立刻返回”：

问题在于：非阻塞但不知道”什么时候有数据”。你得一个线程自己轮询所有连接，挨个问”你有数据吗”——这种忙轮询浪费 CPU，而且连接多了线程还是不够分。

所以非阻塞 IO 单独用没啥意义。它需要配合下一个东西：IO 多路复用。

三、IO 多路复用：select / poll / epoll

多路复用的核心思想：一个线程通过一个”监视器”同时盯住 N 个连接，谁有数据就处理谁。

Java NIO 的 Selector 就是对它的一层封装。底层三种实现，进化了三次：

select poll epoll
数据结构 fd 数组 链表 红黑树 + 就绪链表
连接上限 1024（FD_SETSIZE） 无上限 无上限
检查方式 每次遍历全部 fd 每次遍历全部 fd 事件驱动，只遍历就绪的
复杂度 O(n) O(n) O(1)
触发方式 水平 水平 水平 + 边沿

关键差异在最后一行：

  • select/poll 是”主动问”：每次调用都要把全部 fd 传给内核，内核挨个扫一遍看谁就绪。连接一多，哪怕只有 1 个连接有数据，也要扫 N 个 fd。这就是 O(n)。
  • epoll 是”被通知”：注册 fd 时内核维护一棵红黑树，数据到达时由中断/回调机制把就绪的 fd 丢进一个就绪链表。epoll_wait 直接返回就绪链表——有几个事件就返回几个，不用全扫。这就是 O(1) 的来源。

一个常被忽略的点：select 的 1024 上限不只是”改个宏就行”的问题——它每次调用都要把整个 fd 集合从用户态拷贝到内核态，fd 越多拷贝越贵。epoll 靠 mmap 共享内存，绕开了这个拷贝。

四、LT 和 ET：水平触发与边沿触发

epoll 有两种事件通知模式：

LT（水平触发，默认）：只要缓冲区还有数据，每次 epoll_wait 都会再次通知。

  • 简单、不易漏事件——这次没读完，下次还提醒你。
  • 代价：可能重复唤醒。

ET（边沿触发）：只在状态变化时通知一次——从”没数据”变到”有数据”的那一刻。

  • 高效：一次事件驱动，减少重复唤醒。
  • 代价：必须一次把数据读完，没读完它也不会再提醒，丢数据就是你自己的锅。所以 ET 要求 socket 设为非阻塞，配合循环读直到 EAGAIN。

一句话选型：追求高并发低唤醒用 ET，求稳求简单用 LT。Redis 用的是 ET。

五、Redis 单线程的秘密

Redis 快，常被归因于”内存存储”。但同样是内存存储，为什么一个单线程能扛 10 万+ QPS？

真正的答案在 IO 模型：Redis 主线程用 epoll 多路复用一个线程监听大量客户端连接，只处理有数据就绪的连接，没有就绪就阻塞在 epoll_wait 上，不占 CPU。这个模型同时解决了三个问题：

  1. 无阻塞——事件驱动，没有线程睡在 read 上；
  2. 无锁——单线程执行命令，根本不需要加锁，天然无竞争；
  3. 无上下文切换——一个线程从头跑到尾。

一句话：单线程避免竞争，多路复用扛并发。这跟我后面在 Netty 里看到的 EventLoop 是同一套思想。

补一句诚实的细节：Redis 6.0 引入了多线程 IO，但只用于网络读写（把数据从 socket 搬进内存），命令执行仍然是单线程。多线程 IO 解决的瓶颈是”网络报文搬运占 CPU”，不是”命令执行有竞争”。

六、跟我的项目的连接

  • 订单系统里，我控制线程池大小而不是”一连接一线程”，本质就是用有限的线程池复用代替线程爆炸——上下文切换有真实成本，这是我在并发卡里反复强调的。
  • 内部 RPC（Dubbo）的传输层是 Netty，而 Netty 在 Linux 上默认就是 epoll。所以这条 IO 模型的链路，其实每天都在我的系统里跑。

总结

IO 模型演进的脉络：

判断标准就一条：线程在”等待数据”这件事上花了多少成本。 BIO 花一整个线程，select/poll 花一次全量遍历，epoll 把等待成本降到接近零——剩下的就是”来了数据就去处理”。
