零拷贝：4次拷贝变2次，Kafka和Netty的"零"其实是两回事

先看一次最普通的”读文件发网络”

你的服务要从磁盘读一个文件，通过 socket 发给客户端。直觉上这是一次很简单的操作，但操作系统底层要为它搬 4 次数据：

  • ① DMA：磁盘 → 内核页缓存。DMA（Direct Memory Access）由硬件/驱动完成搬运，不占 CPU。
  • ② CPU 拷贝：内核页缓存 → 用户态。这是业务代码能看到数据的地方（FileInputStream.read()）。
  • ③ CPU 拷贝：用户态 → 内核 socket 缓冲区。把数据写进 socket（SocketOutputStream.write()）。
  • ④ DMA：内核 socket 缓冲区 → 网卡。发出去。

所以是 2 次 DMA + 2 次 CPU 拷贝，而且中间还夹着 2 次用户态/内核态切换（进内核读文件、进内核写 socket）。

问题很清楚：数据为了”看一眼”用户态，被 CPU 拷贝了两次——明明只是从磁盘搬到网卡，中间根本不关心内容，却要在用户态兜一大圈。

二、零拷贝 sendfile：让数据别来用户态

零拷贝的思路一句话：数据全程留在内核里，从磁盘直接 DMA 到网卡，不经过用户态。

只剩 2 次 DMA，都是硬件搬运，CPU 一次都不用搬，也没有用户态/内核态切换。Linux 提供的系统调用是 sendfile：

所以”零拷贝”这个叫法很容易误导人——它不是 0 次拷贝，而是 0 次 CPU 拷贝、0 次用户态参与。那 2 次 DMA 搬运仍然存在，只是 DMA 是硬件干活，不消耗 CPU，也跟用户态无关。

关键认知：DMA 让数据在”内核页缓存 ↔ 网卡”之间直达，CPU 只发指令，不搬字节。

三、mmap 是另一个思路

mmap（内存映射）是零拷贝的另一种实现：把文件映射到进程的虚拟地址空间，业务代码读文件时不触发用户态拷贝，因为数据在内核页缓存里，映射后业务代码直接”看到”这块内存。

Java 里 MappedByteBuffer 就是它的封装。不过 mmap 有它的代价：映射需要页对齐、大文件映射会占地址空间、写回时机不可控。sendfile 适合”从文件到 socket”这种不关心内容的搬运，mmap 适合”要真正读/改文件内容”的场景。

四、Kafka 为什么吞吐百万级

Kafka 把”零拷贝”用在了最该用的地方：broker 把日志段文件发给消费者——这正是”读文件发网络、不关心内容”的典型场景。

但零拷贝只是 Kafka 高吞吐的一块拼图。完整链条是：

  1. 日志模型 + 顺序写：消息追加进分区的日志段文件，只在尾部顺序 append、不随机覆盖。机械盘顺序写远比随机写快（随机写要寻道，一次寻道约 10ms；顺序写是连续的，一次 IO 写一片）——这是吞吐的物理地基；
  2. PageCache：读写在操作系统的页缓存上做缓冲，命中页缓存就不碰磁盘，性能”接近内存”；
  3. sendfile 零拷贝：broker 把日志段发给消费者时，数据从磁盘经内核直接 DMA 到网卡，4 次变 2 次。

一句话主线：日志模型 + 顺序 append + PageCache + sendfile，把”落盘”和”网卡发送”都推到最省的道路上。

五、Netty 的”零拷贝”是另一回事

容易被混在一起的是 Netty 的”零拷贝”。Netty 里的零拷贝不是操作系统层面的 sendfile，而是避免内存复制——用 CompositeByteBuf 把多个缓冲逻辑拼成一块、用 slice 把一段缓冲逻辑切出，都不真的 copy 数据：

两种”零拷贝”的区别：

sendfile（OS 层） Netty Composite/slice（应用层）
省的是什么 CPU 拷贝 + 用户态切换 内存复制
数据真的动吗 DMA 搬运（不动 CPU） 完全不动，只动引用
场景 文件 → socket 多个缓冲拼/切

面试/博客里把它俩分开讲，才算真的懂。 我写这篇的时候专门对照了复习卡 09 和 18，很容易把”Netty 零拷贝”和”Kafka sendfile”混成一句话——它们只是名字都叫”零拷贝”，机制完全不同。

总结

  • 普通 IO：4 次拷贝（2 次 DMA + 2 次 CPU），带 2 次用户态/内核态切换；
  • sendfile：2 次 DMA，零 CPU 拷贝、零用户态参与；
  • “零拷贝” = “零 CPU 拷贝”，不是 0 次搬运；
  • Kafka 用它做”日志段 → 消费者”，是顺序写 + PageCache 之后的最后一块拼图；
  • Netty 的”零拷贝”是应用层避免内存复制（Composite/slice），跟 sendfile 机制不同，别混。
