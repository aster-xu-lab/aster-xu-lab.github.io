Netty线程模型：Reactor主从与"一连接一EventLoop"的免锁哲学

写在前面：我的简历没有 Netty 实战经历，这是一篇原理学习笔记。但 Netty 离我并不远——订单系统内部 RPC 用的 Dubbo，传输层就是 Netty。所以理解它的线程模型，对理解自己系统里”高并发 IO 到底怎么扛”是必要的。

一、Netty 解决了什么问题

回顾上一篇 IO 模型的结论：BIO 一连接一线程，连接多就线程爆炸；epoll 让一个线程可以盯 N 个连接。

Netty 就是站在这个基础上的异步事件驱动网络框架——它把 Java NIO 最难写的部分（线程模型、Selector 管理、缓冲区）全部封装好，业务代码只写 Handler：

二、主从 Reactor：Boss 管连接，Worker 管读写

Netty 的线程模型是主从 Reactor，两个线程组：

BossGroup（主）：一组线程（通常 1 个），只做一件事——accept 新连接。新连接进来，把它注册给某个 Worker，自己不处理业务。

WorkerGroup（从）：N 个 EventLoop，负责已建立连接的读写事件。业务 Handler 都跑在这里。

三、EventLoop：Netty 的灵魂

一个 EventLoop = 一个绑定线程 + 一个 Selector，线程长期跑在自己的 EventLoop 里，不断循环：

这里有一个关键的设计：一个 Channel（连接）只会被绑定到一个固定的 EventLoop。

这意味着：单个连接的所有事件都在同一线程里串行处理 → 天然无并发竞态 → 根本不需要加锁。

这就是 Netty 高并发的来源，一句话讲透：

单连接串行免锁，多连接靠多 EventLoop 并行。 不靠多线程抢一个连接，靠多连接分给不同线程。

对比一下：如果用 BIO 处理 1000 个连接，需要 1000 个线程，锁竞争和上下文切换直接爆炸；Netty 用 N 个 EventLoop 处理 1000 个连接，一个连接只属于一个线程，没有锁，也没有跨线程切换（一个连接从头到尾在一个线程）。

四、Channel + Pipeline：责任链处理数据

每个连接对应一个 Channel，每个 Channel 带一条 Pipeline（双向链表），链上挂一串 Handler，分 inbound（入站）和 outbound（出站）两个方向：

两个要点：

1. Handler 可插拔可复用——加一个 Handler 就是加一道处理。编解码器（Codec）本身也是 Handler，比如 LengthFieldBasedFrameDecoder 按长度字段拆帧，直接解决粘包/拆包（TCP 是字节流，没有消息边界）。

2. 这就是责任链模式在 IO 框架里的落地——和我做的仓储系统拦截器链、金蝶补全责任链是同一思想。看到它第一眼我就认出来了。

五、ByteBuf：比 byte[] 聪明在哪

Netty 不用 Java 的 byte[] + offset 手写缓冲，而是自带 ByteBuf：

  • 读写双指针（readerIndex / writerIndex）自动推进，不用手算偏移；
  • 动态扩容；
  • 池化（Pooled）：从对象池取、用完回收，减少频繁创建/销毁缓冲的 GC 压力；
  • 零拷贝：CompositeByteBuf 把多个缓冲逻辑拼成一块、slice 逻辑切一段，都不真的复制数据——注意这是应用层的”避免内存复制”，跟上一篇 sendfile 那种 OS 层零拷贝是两回事。

池化减 GC + 零拷贝省复制，两个点合起来就是高吞吐 IO 场景的关键优化。

六、诚实边界与我的连接

复习卡 18 里我给自己标了诚实边界：简历没写 Netty 实战，被问就说”了解原理、项目里没直接硬造 Netty，但 Dubbo/网关的传输层常见它，原理我清楚”。这篇博客同样是这个定位——它是加分深挖项，不是主打项目。

但有两层真实的连接值得记住：

  1. Dubbo 传输层 = Netty。订单系统内部 RPC 全是 Dubbo，所以我每天调用的 RPC 底层就是这个模型；
  2. Netty 的 EventLoop 串行免锁 ≈ Redis 的单线程事件循环。它们本质都是”单线程避免竞争 + IO 多路复用扛并发”——上一篇讲的 epoll 在这里无缝衔接。

总结

  • Netty = 主从 Reactor：Boss 管 accept，Worker 管读写；
  • EventLoop = 线程 + Selector；一连接绑一 EventLoop → 单连接串行免锁，多连接并行靠多 EventLoop；
  • Pipeline = 双向链表责任链，编解码器也是 Handler，解决粘包拆包；
  • ByteBuf = 双指针 + 池化减 GC + Composite/slice 零拷贝；
  • 底层还是 epoll，和 Redis 单线程事件循环同一套思想。
