fork写时复制COW：从进程克隆到Redis RDB快照

一个经典问题：Redis 做 RDB 快照时，还在源源不断写数据，怎么保证快照的一致性？

答案的关键，是操作系统里的一个机制：fork 写时复制（Copy-On-Write, COW）。

它不只在 Redis 里出现——Java 的 Runtime.exec()、HashMap 的 CopyOnWriteArrayList 变体、Linux 守护进程 fork 子进程……底层都是同一套思路。这篇文章把它的原理讲透。

一、fork：创建子进程

fork() 是 Linux 创建子进程的唯一方式（Java 里 Runtime.exec() 底层就是 fork + exec）。

直觉上，子进程是父进程的复制品，所以 fork 要复制父进程的整个地址空间。但完整复制是灾难：

  • 父进程如果有 2GB 堆，fork 就要复制 2GB 数据——慢，而且大概率白复制；
  • 子进程通常马上 exec 加载一个全新的程序，之前复制的数据立刻作废（fork 完直接 exec 是典型用法）。

朴素 fork 的问题是：为大概率用不到的东西，付了全量的拷贝成本。

二、虚拟内存：fork 便宜的物理基础

要理解 COW，先回顾一下虚拟内存（复习卡 09 第 7 节）：

  • 每个进程有独立的虚拟地址空间，看起来都从 0 到很大、很连续；
  • 物理内存是分页的（4KB/页），两者靠**页表（Page Table）**映射；
  • CPU 每次访存，由 MMU 查页表把虚拟页号换成物理页号，TLB 缓存最近映射避免反复查表。

这里的关键是：页表是”虚拟 → 物理”的映射关系，是独立于数据的元数据。

所以 fork 时，其实不需要复制物理内存数据，只需要复制页表——父子进程的页表指向同一批物理页。

三、写时复制：先共享，要改才复制

COW 的做法，是把”复制”这件事推迟到不得不做的时候：

  1. fork 时：复制页表，但把父子进程的所有页都标记为只读（页表项里清掉写权限位）；
  2. 读：父子和子进程共享同一批物理页，随便读，零成本；
  3. 第一次写：进程要改某个页 → CPU 发现该页只读 → 触发缺页异常（Page Fault） → 内核复制这一页 → 给写者换成新的可写物理页 → 重新执行写指令。

收益：

  • fork 本身几乎零成本——只复制页表，不复制数据；
  • 只读场景（比如父进程 exec 前的配置区、共享代码段）父子共用一份内存；
  • 真正要写多少，才复制多少——写 1 页复制 1 页，绝不整块拷贝。

代价：缺页异常的处理有开销（进内核、分配物理页、复制），频繁写会放大开销。所以 COW 适合”读多写少”的场景——这正好是快照场景的特征。

四、回到 Redis RDB：COW 怎么保证快照一致

Redis 做 RDB 快照的经典做法是 BGSAVE：

  1. 主进程 fork() 出一个子进程；
  2. 子进程把当前内存写进 RDB 文件——它看到的是 fork 瞬间的内存快照；
  3. 主进程继续正常处理写命令，毫不停顿。

这里有个矛盾：子进程写 RDB 文件可能要好几秒，而这期间主进程在疯狂改内存。如果没有 COW，子进程写出来的 RDB 会是一份”写了一半”的脏数据。

COW 解决了它：

  • fork 时，主进程和子进程共享所有物理页（只读）；
  • 子进程读内存 → 看到的是 fork 那一刻的值；
  • 主进程写某个页 → COW 触发，主进程复制该页再写副本，子进程看到的旧页不受影响。

结果：子进程永远在写一份”fork 瞬间的、完整一致的快照”，主进程在副本上继续演进，两边互不干扰。这就是”快照一致性”和”服务不停机”同时成立的底层原因。

代价也讲清楚：主进程写越猛，COW 复制的页越多，内存峰值越高（可能到常驻内存的数倍），这也是为什么 Redis 大实例做 BGSAVE 时要关注内存。

五、COW 思想在 Java 里：CopyOnWriteArrayList

Java 并发包里有个名字直接叫”写时复制”的容器：

跟 OS 的 COW 是同一思路：读不走锁、永远读到一致快照；写时复制一份再改。只是 Java 这个”写时复制”是全量复制数组（因为数组没法按页共享），所以它适合读多写极少的场景，写频繁就是灾难。

六、和业务系统的连接

我在做订单系统的时候，遇到过”大对象复制耗时“的排查：某段代码把一个大 List 深拷贝传给异步线程，高峰期复制占了不少 CPU。本质和朴素 fork 是同一个病——复制了可能没人看的数据。后来改成”只传只读引用 + 需要变更时才复制”，思路就是 COW：把复制推迟到真要改的那一刻。

总结

  • fork 默认只复制页表，物理页父子共享、全部标记只读；
  • 第一次写某页触发缺页异常 → 内核复制该页 → 写者改副本，父子从此分离；
  • COW = 先共享、要改才复制，读多写少场景几乎零成本；
  • Redis RDB 靠 fork + COW 做到”快照一致 + 服务不停机”；
  • CopyOnWriteArrayList 是同思路的 Java 落地，适合读多写极少。
