JVM 线上排查：高 CPU、内存溢出、GC 频繁的完整套路

定位：结合真实线上经验（ThreadLocal 泄漏、慢 SQL、连接池隔离）讲 JVM 排查套路。

一、四个 JVM 工具，别搞混

工具 看什么
jstack 线程状态（死锁/阻塞/高 CPU 定位）
jstat GC、类加载统计
jmap 堆 dump
jinfo JVM 参数

一句话记忆：jstack 看线程、jstat 看 GC、jmap 看堆、jinfo 看参数。

二、场景 1：高 CPU

这是最高频的线上问题，完整套路一条链：

关键点：jstack 里的线程号是十六进制，要把 top -Hp 拿到的十进制线程号转 hex 才能对上。

三、场景 2：内存溢出（OOM）

常见泄漏源（我踩过的）：

  • ThreadLocal value 未清：key 是弱引用、value 强引用，线程池线程常驻 → 泄漏。解法：用完 remove()；
  • 静态集合无限 add；
  • 连接/流未关；
  • 大 List 常驻。

四、场景 3：GC 频繁 / Full GC 卡顿

Full GC 频繁通常意味着老年代快满——要么对象晋升过多（泄漏），要么堆太小。jstat 看 FGC 次数和 FGCT 耗时，趋势比单值重要。

五、一个真实案例：ThreadLocal 泄漏

我在订单系统排查过一次内存问题，根因是 ThreadLocal 的 value 没清：

  • ThreadLocal 的 key 是弱引用，value 是强引用；
  • 线程池线程常驻，value 一直强留在 map 里清不掉；
  • 用久了，value 累积 → 内存缓慢上涨 → 触发 Full GC 频繁。

解法：用完必须 remove()，并且代码审查时重点盯”线程池 + ThreadLocal”的组合。这是 JVM 排查 + 并发知识结合的真实案例。

六、排查方法论

JVM 排查不是背命令，是方法论：

先保现场再动手——线上问题最怕”看一眼就重启”，现场没了就永远定位不到。

七、和我的项目

订单系统可用性 99.9%，这些排查能力是关键支撑。除了 JVM，我做过**连接池隔离（舱壁）**防一个下游拖垮全局、慢 SQL 从千条降到个位数——线上排查是”运维能力”的完整拼图。

总结

  • 四工具：jstack 线程、jstat GC、jmap 堆、jinfo 参数；
  • 高 CPU：top → top -Hp → 线程转 hex → jstack → 定位代码；
  • OOM：先加 dump 参数保现场 → MAT 分析支配树 → 按时间点反查代码；
  • GC 频繁：jstat 看趋势，老年代增长 = 泄漏嫌疑；
  • 常见泄漏：ThreadLocal value 未清（线程池 + ThreadLocal 组合）、静态集合、连接未关；
  • 方法论：保现场 → 看监控 → 分析 → 定位 → 修复验证。
