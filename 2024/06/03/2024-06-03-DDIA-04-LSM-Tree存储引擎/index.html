DDIA-04-从零实现LSM-Tree：日志结构存储引擎的核心思想

为什么需要 LSM-Tree？

假设你现在要设计一个简单的键值存储引擎，能想到的最朴素的方式是什么？

一个带索引的追加写文件。

写入时，在文件末尾追加 key,value，同时维护一个内存哈希表记录 key -> 文件偏移量。读的时候，先用哈希表定位偏移量，再 fseek 读那一行。这其实就是 Bitcask 的核心思路，Riak 的默认存储引擎。

但问题也很明显：内存哈希表必须能装下所有 key 的索引。如果你的 key 很多，或者 key 本身很大，内存就不够用了。

有没有一种结构，能突破内存限制，同时保持写入的高性能？

这就是 LSM-Tree（Log-Structured Merge-Tree）要解决的问题。它背后的核心思想非常朴素，但衍生出的工程实现——LevelDB、RocksDB、Cassandra、HBase——几乎统治了过去十五年的大数据存储领域。

本文将从头推导 LSM-Tree 的设计，并用 Java 代码展示关键数据结构的简化实现。

核心思想：把随机写变成顺序写

磁盘有一个反直觉的特性：顺序写入比随机写入快一个数量级。

在 HDD 时代，这个差距来自磁头寻道延迟。在 SSD 时代，虽然没了机械结构，但顺序写仍然更快——因为 SSD 的写入是以页（Page）为单位的，随机小写入会触发读-修改-写循环，导致写放大。

LSM-Tree 的核心思想只有一句话：

把所有的写入都变成顺序追加，用后台合并（Compaction）来换取读性能。

具体做法：

  1. 写入：不直接修改磁盘上的旧数据，而是把写入操作记录到内存中的排序结构（MemTable），达到阈值后一次性顺序写盘成一个不可变的排序文件（SSTable）。
  2. 读取：先查 MemTable，再按时间从新到旧查各层 SSTable，直到找到 key。
  3. 合并：后台线程定期把多层 SSTable 合并成更少、更大的文件，消除重复 key 和删除标记。

这就是 LSM-Tree 的骨架。写快读慢——但 Compaction 让读也”够快”。

三大核心组件

1. MemTable：内存中的排序缓冲区

MemTable 是写入的第一站。它需要支持：

  • 高效的随机插入
  • 有序遍历（因为刷盘时要按 key 排序写 SSTable）
  • 线程安全

工程实现通常用跳表（Skip List）或红黑树。LevelDB/RocksDB 默认用跳表，因为实现简单且并发友好。

第一，删除是写入墓碑。如果直接在 MemTable 里删掉 key，那查询时直接返回”不存在”就好了。但磁盘上的旧 SSTable 里可能还存着这个 key——不写墓碑的话，查询穿透到下层 SSTable 时就会读到”幽灵数据”。墓碑告诉 Compaction：”遇到这个 key 就真的删掉”。

第二，WAL 先写。MemTable 在内存里，如果进程崩溃，还没来得及刷盘的数据就丢了。WAL（Write-Ahead Log）是一个纯追加写的日志文件，每条写入先记到 WAL，MemTable 刷盘后再清除对应的 WAL 记录。这是数据库 Crash Recovery 的经典范式。

第三，MemTable 切换是原子的。当当前 MemTable 满了需要刷盘时，会先创建一个新的 MemTable 承接写入，旧的慢慢刷盘。这个切换必须是一瞬间的指针替换，不能影响写入服务。

2. SSTable：不可变的磁盘分段

SSTable（Sorted String Table）是 LSM-Tree 的磁盘存储单元。它的特性：

  • 不可变：一旦写入磁盘就不再修改。这是 LSM-Tree 写入性能的根基——没有原地更新，就没有随机 IO。
  • 有序：按 key 排序存储。这使得范围查询和合并都变得高效。
  • 带索引：文件内维护稀疏索引，定位 key 时不需要全表扫描。

Compaction：用后台合并换读性能

没有 Compaction 的 LSM-Tree 会越来越慢——SSTable 文件越来越多，读一个 key 需要逐个查询所有文件。Compaction 的核心目标是：

  1. 合并多个 SSTable 为一个更大的 SSTable
  2. 消除重复 key：保留最新版本，丢弃旧版本
  3. 处理墓碑：遇到墓碑标记，且确认没有更底层的数据，就真正删除
  4. 维护层级结构：让每层的数据量保持在一定范围内

Compaction 的两种策略

工程上有两种主要的 Compaction 策略：

Leveled Compaction（RocksDB 默认）：

  • Level 0 的 SSTable 之间 key 范围可能重叠（因为直接由 MemTable 刷盘产生）
  • Level 1+ 每层内 SSTable 的 key 范围不重叠
  • 每层容量是上一层的 10 倍
  • 当 Level N 满了，选择一个 SSTable，把它和 Level N+1 中 key 范围重叠的 SSTable 一起合并到 Level N+1
  • 优势：空间利用率高（空间放大 1.1 倍左右）
  • 劣势：写放大高（一个 key 可能在每一层都被重写一遍）

Size-Tiered Compaction（Cassandra 默认）：

  • 不按 key 范围分层，而按文件大小分层
  • 当某一层有足够多大小相似的文件时，全部合并成一个更大的文件
  • 优势：写放大低（每个 key 平均只被重写 log(N) 次）
  • 劣势：空间放大高（同一 key 的多个版本分散在不同 Tier，需要更多磁盘空间）

用表格对比：

维度 Leveled Compaction Size-Tiered Compaction
空间放大 ~1.1x（高效） 1.5x-2x（较差）
写放大 10x-30x（较严重） 较低
读放大 低（每层最多查1个文件） 较高（多个Tier都可能有目标key）
适用场景 读多写少 写多读少
代表产品 RocksDB(默认), LevelDB Cassandra, HBase

选择哪种策略，本质上是用写放大换空间放大还是用空间放大换写放大的权衡。

Bloom Filter：说”No”的速度

LSM-Tree 最慢的操作是查一个不存在的 key——因为要一层一层翻遍所有 SSTable 才能确认”真没有”。

Bloom Filter 就是用来加速这个场景的。它是一个概率性数据结构：

  • 查询结果”不存在”：100% 准确
  • 查询结果”可能存在”：有一定误报率（可配置，通常 1%）

实战联想：LSM-Tree 和 SyncTask 驿传引擎的异曲同工

写到这部分，我忍不住想起自己在设计 SyncTask V2 引擎时的经历。

SyncTask 的 V1 版本，每个任务处理一条业务记录，串行执行——就像 B-Tree 的随机写，每次都是一个独立的 I/O 操作。当天订单量上到百万级时，单条处理的开销（锁竞争、数据库往返、序列化）把吞吐量打得死死的。

V2 版本的核心改造只有两条：

  1. CompletableFuture 并行：多个任务一起调度，批量依赖解析
  2. 批次聚合：把零散的订单按渠道+业务类型聚合成批次，一次处理一批

这跟 LSM-Tree 的设计哲学几乎一模一样：

设计理念 LSM-Tree SyncTask V2
聚合零散操作 写入累积在 MemTable，够一批再刷盘 订单聚合成批次，够一批再处理
用稍后的批量代价换当下的性能 用 Compaction 延迟换写入性能 用批次等待延迟换吞吐量
顺序化利用 顺序写磁盘，利用带宽极限 批量DB操作，减少往返次数
不可变快照 SSTable 不可变 批次快照，处理期间数据不变

这让我深刻体会到：分布式系统和存储引擎的很多底层思想是相通的。把零散操作聚合成批量操作，用一点延迟换十倍吞吐，这种 trade-off 几乎出现在每一个需要”工程化”的场景里。

总结

本文从零推导了 LSM-Tree 的核心设计，我们依次梳理了：

  1. 问题：内存哈希表装不下所有 key 的索引
  2. 核心思想：写变成顺序追加，用 Compaction 换读性能
  3. 三大组件：MemTable（内存排序缓冲）、SSTable（不可变磁盘文件）、WAL（预写日志）
  4. Compaction 策略：Leveled（省空间、费写） vs Size-Tiered（省写、费空间）
  5. Bloom Filter：用概率数据结构加速”不存在”查询

LSM-Tree 是理解现代存储引擎的第一步。RocksDB 背后是它，Kafka 的存储设计借鉴了它，甚至 TiKV 的 Raft 层之下也是基于 RocksDB 的 LSM-Tree。理解了 LSM-Tree，你就拿到了打开存储世界大门的钥匙。

当然，本文的实现是高度简化的。真实的 RocksDB 还有这些我们没提到的东西：

  • Block Cache：缓存热点数据块到内存，避免频繁磁盘读取
  • Prefix Seek 优化：利用 key 前缀做范围查询优化
  • Universal Compaction：第三种 Compaction 策略，适合全部数据都在 L0 的场景
  • Column Family：逻辑隔离，各自独立的 Compaction
  • Merge Operator：不只是覆盖写入，支持自定义合并逻辑（如计数器叠加）
