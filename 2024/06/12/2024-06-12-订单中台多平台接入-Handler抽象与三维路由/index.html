订单中台的多平台接入：Handler抽象与三维路由

一、多渠道接入：订单中台最难啃的骨头

订单中台（cloud-order，约 2084 个 Java 文件、5 个子模块、100+ 张表）的核心职责是全渠道订单处理中枢——对接多电商平台、多商家异构下游。

“多平台”意味着什么？真实情况是：每个外部系统都有自己的协议、字段、鉴权方式、消息格式、处理时序。聚水潭、金蝶、FMS、抖音、快手……每个系统的销售单据、采购单据、售后单据、开票单据，接入方式都不同。

如果不做抽象，最直接的写法是：每个平台一套同步逻辑，一个平台一套代码。结果是代码爆炸 + 加一个平台就要复制一遍。

二、Handler 抽象：策略 + 工厂

订单中台的解法是 Handler 抽象：把”同步一个外部系统的一类单据”抽象成一个 Handler，用策略模式 + 工厂模式组织。

核心是开闭原则：新接入一个平台 = 新增一个 Handler 实现，不改动既有 Handler。接入成本从”改一堆代码”变成”加一个类”，从数天降到数小时。

口径说明：订单中台内部有 49 个 Handler（内部数字），对外简历上写”数十种业务同步任务”——这不是藏掖，而是”数十种”本身就是这个量级最准确的表达，避免给面试官一个”49 是不是数出来的”的追问。

三、三维路由：bizType × syncTaskType × syncSystem

Handler 多了，路由就变成关键。我的路由键是三维的：

  • bizType：业务类型——销售、采购、售后、开票；
  • syncTaskType：同步任务类型——下发、回传、对账；
  • syncSystem：目标系统——聚水潭、金蝶、FMS……

三维组合出一个唯一的 handlerKey，每个 Handler 只处理命中自己维度的任务。这跟分库分表的分区键路由是同一思想——用唯一标识把任务精准路由到处理者，避免广播。

新增一种任务，只要三维里有新组合，就注册新 Handler；没有新组合，复用已有 Handler。扩展靠注册，不靠改判断分支。

四、适配器：多平台异构的最后一块

Handler 解决”每个平台一套逻辑”，适配器解决”同一能力不同平台实现不同“——比如”下发订单”这个动作，聚水潭的协议和金蝶完全不一样。

订单中台的适配层是三层 SPI 适配：

引擎只依赖抽象的 SPI（调度、存储、锁、通知……），具体实现由适配器按平台提供。换平台 = 换适配器，引擎不动。

这其实是”依赖倒置 + SPI”的实践：高层不依赖低层实现，依赖抽象。我在 SyncTask 引擎里做了 10 个 SPI 扩展点，都是这个思想的延伸。

五、为什么抽离出 SyncTask 引擎

订单中台有 49 个 Handler，另一个仓储系统有 44 个 Handler，两套业务同步逻辑 80%+ 重复——都是”取参 → 拉数 → 加锁 → 执行业务 → 更新状态”这套固定流程，只是业务不同。

所以我把重复的执行逻辑抽离成独立的 SyncTask Engine（5 个 Maven 模块、10 个 SPI 扩展点）：

  • 引擎核心零框架依赖，只定义”编排骨架 + 扩展点”；
  • 接入方式：引入 Starter → 实现 Handler → 配置参数 → 建表，零 @Configuration 代码；
  • cloud-order 是第一个接入方（孵化地），cloud-wms 是第二个接入方（验证跨项目复用）。

这是”架构减法”的思路：识别 80% 重复 → 抽公共骨架 → 让重复的业务代码消失。订单中台的多平台接入，最后长出来的不是一个”越来越大”的系统，而是一个被抽干的瘦中台 + 一个可复用的引擎。

六、演进：渠道垂直分表 → 分库分表

订单中台的数据存储也经历了演进：早期按渠道垂直分表（拼多多一张表、京东一张表），后来演进到 ShardingSphere 单号主分片（这是另一篇的主题）。

多平台接入和分库分表在这里交汇：接入的平台越多，数据量越大，分片需求越迫切——所以”多渠道”和”分库分表”在订单中台是同一条增长曲线上的两个产物。

七、Design Review 的自我审视

多平台接入做久了容易自我感觉良好，我给自己做过一次系统的 Design Review（8 份系统分析文档），承认了 10 个设计不足，最典型的几个：

  • xxl-job 耦合：早期直接依赖调度框架，后来通过 SchedulerAdapter SPI 解耦；
  • 配置膨胀：Handler 参数配置越加越多，需要规范；
  • V1/V2 继承：老版本用继承扩展，演进后统一用组合/策略；
  • ThreadLocal 泄漏：早期有泄漏问题，后来修复（这也是内存泄漏排查的经典案例）。

承认设计不足不是自我否定，是让系统持续演进的前提。 这 10 个不足后来成了 SyncTask 引擎设计的直接输入。

总结

  • 多平台接入的核心是 Handler 抽象：策略 + 工厂，新平台 = 新 Handler，开闭原则；
  • 三维路由（bizType × syncTaskType × syncSystem）把任务精准路由到处理者，扩展靠注册不靠改分支；
  • 适配器 + SPI 处理异构协议，高层依赖抽象不依赖实现；
  • 80% 重复抽离成 SyncTask 引擎，订单中台从”越做越大”变成”瘦中台 + 可复用引擎”；
  • 多平台接入和分库分表是同一条增长曲线上的两个产物；
  • Design Review 承认 10 个不足，成为引擎设计的输入。
