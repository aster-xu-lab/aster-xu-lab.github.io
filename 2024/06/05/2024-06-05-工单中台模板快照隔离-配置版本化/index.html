工单中台模板快照隔离：配置版本化，一个从0到1项目最该做的决策

一、一个经典的配置版本问题

工单中台的核心实体是”工单模板”：定义了工单的字段、流程节点、处理人规则、SLA 时限等一套配置。业务方会频繁调整模板——加一个字段、改一道审批、换一个处理人。

问题来了：模板改了，已创建的工单怎么办？

两种极端：

  • 工单实例直接引用模板：模板一改，所有历史工单的行为跟着变——昨天创建的工单，今天处理流程变了，字段也变了。历史工单被”新规则”污染，对账、审计全乱；
  • 工单实例完全复制模板：每次创建都全量复制配置，简单粗暴但数据冗余、模板演进成本高。

正确的做法是模板快照隔离：创建工单实例的那一刻，把当时生效的模板配置打一份快照，固化到工单实例上。 之后模板怎么改，都不影响已创建的工单。

  2. 模板可以放心改：业务方调整模板不影响存量工单，改错还能回滚到快照查当时上下文；
  3. 容量可控：快照按”创建即复制”生成，不是实时引用，避免运行时依赖活配置。

这和电商”下单时锁定商品价格/优惠快照“是同一个思想——涉及”实例一旦产生就要长期负责”的场景，配置必须在实例化那一刻被固化。 工单、合同、订单、表单，都是这个模式。

三、双状态机协同：工单的灵魂设计

工单中台的核心不是模板，是双状态机协同——工单表和任务实例两套状态机配合：

  • 工单状态机（工单表驱动）：工单的整体生命周期——待处理、处理中、已完成、已关闭；
  • 任务状态机（任务实例化）：工单拆出的每个任务实例自己的状态——待执行、执行中、成功、失败。

为什么要拆成两套：工单是”聚合视角”，任务实例是”执行视角”。一个工单可能拆成多个任务（比如一次维修工单 → 派单、上门、回访三个任务），任务各有各的状态流转；而工单的整体状态要等所有任务推进到一定程度才收敛。

两套状态机用事件联动：任务状态变化 → 触发工单状态机的推进判断。这比”一个工单一个状态字段”优雅得多——它把”整体进展”和”局部执行”解耦，各自演进、事件驱动。

四、Spec Coding：从0到1项目为什么先写规格

工单中台是从 0 到 1（182 文件 / 约 1.2 万行），我完整实践了一遍 Spec Coding（规格驱动开发），四步：

① 先写 Spec，不直接写代码：产品分析 → 领域建模 → API 契约设计 → ADR 架构决策记录。这一步把”要做什么、为什么这么做”定清楚，作为后续所有工作的依据；

② AI 加速设计评审与框架生成：拿写好的 Spec 让 AI 做设计评审（挑设计漏洞）、生成骨架代码和文档初稿；

③ 人工编码核心逻辑：关键链路——双状态机、Seata 事务边界、模板快照——这些我自己写并逐行审，AI 只搭边角（Controller/Entity/Mapper 样板）；

④ 交付”决策上下文 + 代码”：不是只交代码，把 Spec、ADR 一起交付，让别人能看懂”当时为什么这么设计”。决策上下文和代码同等重要，都可传承。

这套流程的价值，在于决策可追溯：后来的人能顺着 Spec/ADR 继续维护，不是黑盒。这也是工单中台从 0 到 1 之后能被团队接住的关键——代码会变，但”为什么这么做”留在了文档里。

五、API 失败重试：全链路日志 + 双触发

工单要调外部系统（订单中心回写服务人字段、下游状态回传），外部调用失败是常态。我的重试设计是全链路日志 + XXL-Job 定时 + MQ 事件双重触发：

  • 全链路日志：每次调用记录请求/响应/异常，失败原因可查；
  • XXL-Job 定时：兜底扫描失败记录重试，低峰执行；
  • MQ 事件触发：失败立即发事件，MQ 消费重试，比定时快。

定时 + 事件双触发的思路：事件触发保证”失败立即重试”（快路径），定时扫描保证”事件丢了也能兜底”（稳路径）。两条腿走路，互不信任。

六、分布式事务：工单为什么用 Seata AT

工单场景有跨库写：师傅变更回写订单中心——工单库改一条工单、订单中心库改一条服务人字段，两个都是 MySQL 本地写操作。

我选了 Seata AT 而不是 TCC，原因：AT 靠 undo_log 快照自动回滚，纯本地写 + 跨库同步回滚的场景，零侵入、不用写任何补偿逻辑。为这么简单的跨库写套 TCC 的 Try/Confirm/Cancel 三套方法，是过度设计。

对比传统 OMS 项目用 TCC 的原因：那个项目的分布式事务动作不只是本地写，还涉及外部系统/平台库存这种不可回滚的副作用——undo_log 快照回滚不了外部系统状态，必须 TCC 业务侧显式补偿。

选型的判断标准：TCC 和 AT 的差别不在谁更新，而在跨服务的那个动作能不能靠框架自动回滚。能 → AT 零侵入；不能（外部副作用不可逆）→ TCC 自定义补偿。

总结

  • 工单实例化时打模板快照固化配置，模板演进不影响存量工单——“实例一旦产生就要长期负责”的场景都适用；
  • 双状态机协同：工单聚合状态 + 任务执行状态，事件联动，解耦整体与局部；
  • Spec Coding：先写 Spec（含 ADR）→ AI 加速 → 人工写核心 → 交付决策上下文，决策可追溯；
  • 失败重试定时 + 事件双触发，快路径与稳路径互补；
  • 分布式事务AT vs TCC 的判断标准：跨服务动作能否靠框架自动回滚。
