缓存三兄弟与缓存一致性：穿透、击穿、雪崩和延迟双删

一、先分清三个名字很像的问题

“穿透/击穿/雪崩”三个词常被记混，它们其实对应三种完全不同的场景：

问题 定义 关键区分 解决
穿透 查数据库里不存在的数据 缓存和库都没有 布隆过滤器 / 缓存空值
击穿 单个热点 key 过期瞬间 一个 key 扛不住了 互斥锁 / 逻辑过期
雪崩 一批 key 同时过期（或 Redis 挂） 一大批 key 全挂 过期加随机值 / 多级缓存

一句话记忆：穿透 = 数据不存在、击穿 = 一个热点、雪崩 = 一批 key。

二、缓存穿透：查不存在的数据

定义：请求的数据在缓存和数据库里都不存在（比如恶意请求一个不存在的订单号）。缓存永远 miss，每次都打到数据库。

解法：

  • 布隆过滤器：请求先过布隆过滤器，不存在直接返回，不查库（布隆判断”一定不在”是准的）；
  • 缓存空值：查库发现不存在，也往缓存写一个空值 + 短过期，后续请求命中空值。

三、缓存击穿：单个热点 key 过期

定义：单个热点 key 过期瞬间，大量并发请求同时打到数据库（比如一个爆款商品的缓存刚好过期，瞬间涌入的查询全 miss）。

解法：

  • 互斥锁（mutex）：第一个请求拿锁去查库重建缓存，其他请求等锁（拿不到就稍等重试或返回默认值）——保证只有一个请求打库；
  • 逻辑过期：缓存不设物理过期，value 里带逻辑过期时间，发现逻辑过期就异步重建；
  • 不过期：热点数据干脆不设过期，靠主动更新。

四、缓存雪崩：一批 key 同时过期

定义：一批 key 同时过期（比如都设了同一时刻的过期时间），或者 Redis 直接挂了，大量请求同时打到数据库。

解法：

  • 过期加随机值：过期时间 base + random，让一批 key 的过期时间错开；
  • 多级缓存：本地缓存（Caffeine）+ Redis 双层，Redis 挂了本地还能扛；
  • 熔断限流：数据库扛不住时熔断降级，而不是硬扛。

五、缓存一致性：延迟双删

缓存和数据库的双写一致性，是另一个高频问题。核心矛盾：更新数据库和更新缓存的时机。

主流做法是 Cache Aside + 延迟双删：

  1. 先更新数据库；
  2. 删除缓存（而不是更新缓存——因为并发写缓存会引入更多不一致）；
  3. 隔一小段时间再删一次（延迟双删）。

为什么延迟再删一次？因为极端情况下：删完缓存后，另一个线程读到了旧数据库值并写回缓存（读旧库回写），缓存又脏了。延迟一段再删一次，把这个”脏回写”清掉。

更稳的方案还有：消息队列/监听 binlog（Canal）异步删缓存——由数据库变更驱动，不依赖应用层时序。

六、一个务实的选择：删除缓存而不是更新缓存

很多人纠结”更新缓存还是删除缓存”。答案是删除，理由很实际：

  • 更新缓存会引入并发写：两个线程同时写缓存，谁后写谁赢，但可能后写的是旧值；
  • 删除缓存是惰性：下次读 miss 再重建，天然避免了并发写，代价是重建那一下要查库（但有上面击穿的手段兜底）。

所以”先更新 DB 再删缓存”是主流，因为它在”DB 及时性”和”缓存一致性”之间取得了平衡。

七、结合我的项目：Caffeine + Redis 二级缓存

订单中台用了 Caffeine（本地缓存）+ Redis（分布式缓存） 的二级缓存：

  • 第一级 Caffeine：本地内存，命中最快，减少 Redis IO；
  • 第二级 Redis：分布式共享，多实例一致；
  • 缓存一致性：延迟双删 + 版本号控制，更新 DB 后删 Redis，再通过版本号兜底；
  • 缓存降级：大促时降级二级缓存走 Redis，Redis 挂了走本地缓存/降级到 DB 限流。

二级缓存 + 降级，本身也是多级缓存思想对”雪崩”的防御——Redis 挂了对本地缓存是盲区，但至少本地还在扛。

总结

  • 穿透（数据不存在）→ 布隆过滤器 / 缓存空值；
  • 击穿（单热点过期）→ 互斥锁 / 逻辑过期；
  • 雪崩（一批 key 过期）→ 过期加随机值 / 多级缓存 / 熔断限流；
  • 一致性 → Cache Aside + 延迟双删（先更 DB、删缓存、隔一会再删）；
  • 删缓存优于更新缓存：避免并发写，代价是重建那一下；
  • 项目里 Caffeine + Redis 二级缓存 + 延迟双删 + 降级，是大促削峰的完整组合。
