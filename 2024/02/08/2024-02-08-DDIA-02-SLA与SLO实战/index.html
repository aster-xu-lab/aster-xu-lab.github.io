DDIA-02SLA与SLO实战：从99.9%到99.99%的100倍差距

一、一个9的距离，10倍的差距

先看两组数据：

  • 99.9%（三个9）：年度允许宕机时间 = 365 × 24 × 60 × 0.001 = 8.76小时
  • 99.99%（四个9）：年度允许宕机时间 = 365 × 24 × 60 × 0.0001 = 52.56分钟

就多了一个9，宕机预算差了10倍。

这个差距对业务意味着什么？假设你的系统日订单峰值130万、QPS 8000，8.76小时的宕机相当于损失约47万笔订单。而52.56分钟的宕机，损失降到约4.7万笔。两者之间差了42万笔订单，按客单价100块算，那就是4200万的GMV差距。

这不是学术讨论。这是我们订单中心真实走过的路——从99.9%爬到99.99%，花了一年半。

但做到四个9之前，有件事必须先想清楚：你可别上来就跟老板拍胸脯说”我们要做五个9”。每多一个9，成本翻倍起步，而业务的真实容忍度可能根本不需要那么多9。这里的关键，就是SLA、SLO、SLI这三个概念。

二、SLA / SLO / SLI：三个兄弟，各管各的事

DDIA第二章讲非功能性需求时，最核心的一组概念就是SLA、SLO、SLI。我见过太多人把这三个词混着用，面试时被追问一下就露馅。

用一句话讲清楚：

  • SLI（Service Level Indicator）：度量指标。你实际测出来的数字，比如”过去30天，请求成功率是99.95%”。
  • SLO（Service Level Objective）：内部目标。团队给自己定的及格线，比如”请求成功率必须达到99.9%以上”。
  • SLA（Service Level Agreement）：对外承诺。写在合同里的数字，达不到要赔钱的，比如”月度可用性低于99.9%时，赔偿客户当月费用的10%”。

三者的关系是：SLI ≥ SLO ≥ SLA。

你测出来的SLI必须高于SLO，SLO必须比SLA留出缓冲。因为SLA是跟客户签了字的，一旦违约不仅要赔钱，还会丢掉信任。

举个真实的例子。我们订单中心的SLA承诺给业务方是99.9%，但内部SLO定的是99.95%。为什么多留0.05%？因为你要给自己留犯错的空间——突发流量、依赖服务抖动、甚至是一次配置变更不小心踩坑，这些都需要吃掉SLO和SLA之间的缓冲区。如果SLI踩着SLA线走，那下次P0故障你就得写事故报告了。

DDIA里特别强调了一点：SLO必须基于用户感知来定义，而不是服务器指标。同样是我们这边一个反例——监控看服务端口存活率100%，但实际上某条核心SQL被锁了30分钟，用户一直看到的是超时报错。端口活着不代表系统可用。

所以后来我们做了两件事：

  1. SLI定义为”订单创建API的端到端成功率”，从用户侧采集，不是从服务端自报
  2. 监控大盘把”端口存活”拆成”端口存活 + API成功率 + 关键依赖可用”三个维度

三、MTBF和MTTR：故障间隔和修复时间

讲可用性，绕不开两个公式。

MTBF（Mean Time Between Failures）：平均故障间隔时间。系统多久挂一次。
MTTR（Mean Time To Repair）：平均修复时间。挂了之后多久能恢复。

换句话说，修得快比不挂更难，但也更划算。

我们当时分析了一年的故障记录，发现70%的P0/P1故障是在非工作时间发生的——凌晨2点、周六下午、周五晚上。而这70%里，有将近一半是因为值班的人睡着了或者正在外面吃饭，从告警发出到有人响应，MTTR白白多了15-20分钟。

所以后来我们做了一件事：不是因为”主库挂了”导致故障，而是因为”主库挂了但没人切从库”导致故障延长。在主从切换上做自动化，这套机制把MTTR从平均18分钟压到了3分钟以内。

除了自动化主从切换外，我们还引入了两个关键的MTTR缩短手段：

  • 自动化限流降级：当某个依赖（比如支付网关、物流查询）出现超时时，Hystrix线程池自动熔断+降级返回兜底数据，避免线程池耗尽拖垮整个订单链路。人工介入需要5-10分钟，自动化只需要500ms。
  • 慢SQL自动Kill + 通知：日均慢SQL从1124条降到6条的过程中，除了SQL层面的根治，我们还做了兜底——当一条SQL执行超过3秒时，自动kill并通知DBA群，避免慢查询锁住整张表。

这些手段的本质都是同一个逻辑：在MTBF难以大幅提升的情况下，优先压缩MTTR。MTBF的提升需要架构层面的重构（比如数据库分库分表），周期以季度为单位；而MTTR的压缩可以通过自动化手段逐步迭代，周期以周为单位。

四、实战：订单中心99.9% → 99.99%做了什么

回到正题。我们订单中心从三个9爬到四个9，做了一年半，核心就三件事。下面逐一展开。

4.1 主从切换自动化：MTTR从18分钟到3分钟

之前的主从切换流程是这样的：

  1. 告警触发 → 2. 值班打电话给DBA → 3. DBA连VPN确认主库状态 → 4. 手动执行change master → 5. 验证从库数据一致性 → 6. 修改应用配置切换数据源 → 7. 通知业务方恢复

这个流程在理想情况下需要10分钟，但凌晨两点、DBA在睡觉、VPN连不上、从库延迟太大，现实中平均18分钟。

自动化之后：

  1. Sentinel检测主库心跳超时3次 → 2. 自动检查从库延迟 < 1秒 → 3. 自动执行change master → 4. 通过配置中心（Apollo）推送新数据源 → 5. 应用通过Apollo监听自动热切换连接池 → 6. 企微群发通知”主从切换完成，耗时XX秒”

整条链路99%的case在3分钟内完成。唯一保留人工介入的场景是从库延迟超过5秒——这种case需要判断是切还是不切，不能盲目切。

这里有一个教训。自动化切换的第一版我们用过MHA（MySQL High Availability），但MHA的问题是它只管数据库层面的切换，应用层感知不到数据源变化，需要额外一套配置推送机制才能让应用切过来。后来我们干脆把MHA换成了自研的轻量级检测脚本 + Apollo配置推送，逻辑简单透明，出了问题也好排查。

4.2 限流降级体系：QPS 2000 → 8000+不被冲垮

可用性不只是”系统不挂”，还包括”系统在高负载下依然能提供核心服务”。

我们订单中心接入了多个上游——APP端、小程序端、ERP端、第三方渠道。在秒杀或大促时，瞬时QPS能从2000飙到8000+。如果不做限流降级，线程池打满 → 所有接口都不可用 → 即使是非秒杀商品的正常下单也受影响。

我们做了三层：

第一层：网关限流（Sentinel）
在网关层对每个渠道设置独立的QPS上限。比如APP端分配3000，小程序分配2000，ERP分配1000。超过上限的直接返回”系统繁忙请稍后重试”，不让流量进入后端。

第二层：服务降级（Hystrix线程池隔离）
订单创建链路依赖支付网关、库存服务、风控系统、物流查询四个外部服务。每个依赖使用独立的Hystrix线程池，任何一个慢或者挂了，只熔断它自己，不影响其他三个，也不拖垮主线程池。

举个例子：物流查询超时了，Hystrix自动降级，订单创建继续走，只是物流信息先留空。用户看到的是”订单已创建，物流信息稍后更新”，而不是”创建失败请重试”。

第三层：核心接口保护（Semaphore + 漏桶）
对订单创建、支付回调这两个核心接口，使用Semaphore控制最大并发数。当并发达到阈值时，多余请求进入漏桶排队而不是直接拒绝。排队超时（2秒）的才返回失败。

三层做完之后的压测结果：QPS 8000时，非核心接口的错误率上升到了3%（可接受），但订单创建接口的成功率保持在99.95%以上。

4.3 慢SQL治理：日均1124条 → 6条

慢SQL不仅是性能问题，更是可用性隐患。一条慢SQL锁住热点行，连锁反应会导致连接池耗尽，最后整库不可用。

我们的治理分了四个阶段：

第一阶段（第一周）：开启慢查询日志，建立基线
long_query_time = 500ms，跑了一天，结果吓一跳——1124条慢SQL。分类统计后，68%集中在库存扣减（select for update）、订单列表查询（多表join 7张表）、历史数据报表（全表扫描）。

第二阶段（第一个月）：加索引 + 改SQL
这是ROI最高的阶段。库存扣减的where sku_id = ? and warehouse_id = ?没走联合索引，建了(sku_id, warehouse_id, status)联合索引后，执行时间从12秒降到50ms。订单列表的7表join，改成先查订单主表拿到order_id_list，再分两次批量查关联信息，把一次7表join拆成了3次单表查询 + 应用层组装。这个阶段把慢SQL从1124条压到了约200条。

第三阶段（第二~三个月）：读写分离 + 缓存
报表类查询全部切到只读从库，不再阻塞主库。热点商品库存信息加载到Redis，扣减走Redis lua脚本，异步批量落库。这个阶段把慢SQL从200条压到了约30条。

第四阶段（持续优化）：DDL管理 + 自动Kill
建立DDL审批流程——所有生产DDL必须提供explain结果 + 影响行数评估，每月只在周四凌晨2-4点执行。同时布了SQL自动kill机制：执行超过3秒的查询自动kill并通知DBA。这个阶段把慢SQL压到了最终日均6条。

这个1124到6的过程，不仅是SQL优化，更是建立了一套治理体系——从发现问题 → 分类归因 → 分期治理 → 持续兜底，形成闭环。

五、几个9的真实成本

多说一嘴现实问题：每多一个9要花多少钱？

这里有张经验数据（基于我们自己的投入和业界报告）：

可用性 年度宕机时间 架构要求 估算投入
99%（两个9） 3.65天 单实例，人工重启 基准
99.9%（三个9） 8.76小时 主从+监控+值班 +50%
99.99%（四个9） 52.56分钟 自动切换+降级+多活 +200%
99.999%（五个9） 5.26分钟 异地多活+故障演练+全链路压测 +500%~+1000%

从三个9到四个9，人力投入大概是翻倍——你需要有人专门做SRE、做压测、做降级预案、写自动化脚本。从四个9到五个9，需要异地多活，机房成本直接翻倍起步。

所以决策逻辑不应该是”可用性越高越好”，而是：

你的业务在什么阶段？需要几个9？

  • 初创期/内部系统：两个9够了。快速迭代比稳定重要，挂了重启就行。
  • 成长期（有外部客户）：三个9是及格线。客户开始依赖你，但也容忍偶发故障。
  • 成熟期（百万日活/日订单）：四个9是必须的。每一次故障都在消耗信任和GMV。
  • 金融/通信/医疗：五个9是监管要求，不是技术追求。

我们订单中心做到99.99%之后，内部讨论过要不要挑战五个9。结论是不要。不是做不动，是现阶段ROI太低。我们的日订单量130万，但客单价不高、时效要求不是秒级、交易不是金融级一致性。这种情况下，四个9已经足够——52分钟的年度宕机预算，在实际运营中基本够用。

记住一句话：可用性架构的成本是用来买”业务允许出错的额度”，而不是用来追求技术上的完美。

六、总结

回到DDIA第二章的核心观点：非功能性需求不是PM写在PRD里的东西，但它是架构师脑子里必须装着的约束条件。

如果你只记住三件事，我希望是这三件：

  1. SLA是合同，SLO是目标，SLI是标尺。别搞混，面试时把这三个词分清楚，你已经赢了80%的人。
  2. 修得快比不挂更难，但也更划算。MTTR的压缩是ROI最高的可用性投入，自动化切换/限流降级/自动kill，一周就能见效。
  3. 可用性是生意问题，不是技术问题。不要为了多一个9而牺牲迭代速度。业务阶段决定SLO目标，技术只是达成手段。
