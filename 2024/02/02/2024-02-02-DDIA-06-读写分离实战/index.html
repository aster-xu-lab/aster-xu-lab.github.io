DDIA-06-实战：订单中心读写分离——主库扛写从库扛读的正确姿势

一、事故：一条慢SQL引发的血案

那天凌晨两点，我接到了告警电话。

订单中心的接口响应时间从正常的 30ms 飙升到 8s，主库 CPU 负载直接打满 100%。排查后发现，运营同事白天在 BI 后台跑了一个报表查询——一个关联了 6 张表的 LEFT JOIN，扫描 1200 万行数据。这条 SQL 没有被限流，直接跑在主库上，把连接池和 CPU 全部吃光。

问题的本质很清晰：我们只有一个主库，所有的读和写都在同一个 MySQL 实例上。虽然日常写入 QPS 只有 500 左右（日订单 130 万，高峰期也才 ~1000 write QPS），主库本身的写入能力绰绰有余。但那些慢 SQL、报表查询、后台对账任务，都会直接跑在主库上，跟写入抢 CPU、抢 IO、抢连接池。写得再快，被一条慢查询堵住了也是白搭。

DDIA 第 6 章讲复制的时候，开篇就强调了一个核心原则：读写分离是整个复制体系最常见的应用方式之一。我们问题的答案，也正在这里。

二、读写分离的正确认知：不是写扛不住，是读坑了写

很多团队做读写分离，是因为写入 QPS 太高——双十一那种场景，单库写确实扛不住。但对我们这种日订单 130 万的中台场景来说，写 QPS 并不是瓶颈。

真正的瓶颈是 读写的资源竞争。看一组数据就很清楚：

场景 主库 QPS CPU 主库读占比
白天（有报表查询） ~800 75% 65%
白天（无报表查询） ~650 25% 40%
凌晨（对账跑批） ~300 90% 20%

对账跑批的时候只有 300 QPS，但 CPU 却能冲到 90%。为什么？因为那 20% 的读操作里，有大批量扫描 SQL，把 buffer pool 的缓存也污染了——热数据被冲掉，写入变慢，连锁反应。

读写分离解决的不是”写不动”的问题，而是**”读不让写”的问题**。

所以我们的策略是：主库只扛写 + 少量关键读，从库扛所有其他读。主库做得更少，但做得更快、更稳。

中间件选型：Atlas vs ProxySQL vs ShardingSphere-JDBC

确定要做读写分离之后，第一件事是选中间件。市面上主流的方案有三类：

1. Atlas（360 开源，Proxy 模式）

Atlas 是 360 团队基于 MySQL-Proxy 改造的，部署在应用和 MySQL 之间，对应用代码完全透明。

优点：部署成本低，不改代码，配置简单。缺点也很明显：项目已经多年不维护（GitHub 最后一个 release 是 2018 年），对 MySQL 8.0 的新特性支持不全，SQL 解析能力有限。而且 proxy 多了一层网络跳转，在高并发下性能损耗不可忽略（我们压测发现比直连高 10%-15% 的延迟）。

2. ProxySQL（Proxy 模式）

ProxySQL 是更现代的 proxy，支持丰富的路由规则和查询缓存，社区活跃，性能比 Atlas 好。

优点：规则引擎非常强大，支持基于 SQL 类型、schema、用户、正则匹配等多种维度做路由。支持连接池复用，对后端 MySQL 的连接数有很好的控制。缺点：毕竟还是多了一层代理，运维复杂度有增加。需要额外部署和监控 ProxySQL 本身的健康状态。对于 SQL 解析，ProxySQL 有些边界 case（如 SELECT ... FOR UPDATE）需要单独配置规则。

3. ShardingSphere-JDBC（JDBC 层）

Apache ShardingSphere 的 JDBC 模式，以 jar 包形式嵌入应用，在 JDBC 层拦截 SQL 做路由。没有额外的网络跳转，性能损耗极低。

优点：零中间件部署，纯 Java 实现，跟 Spring Boot 集成丝滑。路由规则可以做到很精细——基于 Hint 注解、基于 SQL 类型、基于事务上下文。而且它不仅是读写分离，分库分表、数据加密、影子库压测等都能在一个框架内解决（DDIA 第 7 章我们就用到了分库分表，同一个组件平滑升级）。

缺点：JDBC 层拦截意味着每个应用实例都需要感知主从拓扑。配置变更不像 proxy 那样集中管理，需要走配置中心（但 Apollo/Nacos 一推就行）。另外 SQL 兼容性依赖于 ShardingSphere 的解析引擎，遇到不支持的语法需要做兼容处理。

我们的最终选择：ShardingSphere-JDBC。

理由很简单：我们的技术栈是 Spring Boot + MyBatis，团队对 Java 生态熟悉。性能方面，我们没有中间代理层的损耗——这一点很关键。而且我们把分库分表也规划在了路线图上，ShardingSphere 可以一条龙解决。至于配置变更的问题，我们用 Apollo 管理数据源，节点变更时推送配置即可，应用端无需重启。

三、路由规则设计：不是简单的”写主读从”

很多人以为读写分离就是配一条规则：INSERT/UPDATE/DELETE 走主库，SELECT 走从库。这在 demo 里没问题，但生产环境远不止于此。

层级 2：基于 Hint 的强制主库路由

这是最容易被忽视的问题，也是最容易出 bug 的地方。

写了一个订单之后，立即要查这个订单的详情展示给用户。如果这时候走从库，由于主从延迟（哪怕是 100ms），用户看到的是”订单不存在”——明明刚提交成功，页面却显示 404。这就是经典的写后读一致性问题。

ShardingSphere-JDBC 提供了 HintManager 来解决：

HintManager 基于 ThreadLocal，限定了作用范围（try-with-resources 确保关闭），不用担心线程安全问题。它的粒度是代码级别的，比基于 SQL 正则的 ProxySQL 规则更精确。

我们在以下场景强制走主库：

场景 原因
写后立即读（同一个事务或同一个用户操作流） 主从延迟导致的读不到刚写的数据
用户查看自己的订单详情 用户期望实时一致，不能忍受”订单不见了”
退款/取消操作前的订单状态查询 状态判断必须是实时的，否则可能出现并发操作问题
SELECT ... FOR UPDATE 这是锁定读，必须在主库执行

层级 3：事务内智能路由

在一个事务内，如果一个操作写了数据，后续在这个事务内的所有读都应该走主库。这是 ShardingSphere 默认的行为——事务内第一条写 SQL 之后，所有 SQL 都路由到主库。但要小心一个坑：

四、从库延迟监控：Semisync + 告警 + 自动降级

读写分离最大的敌人不是性能，而是主从延迟。延迟大了，用户读到过期数据，比不分离更糟糕。

我们的延迟防控体系：

第一层：Semisync 半同步复制

MySQL 5.7 原生的 Semisynchronous Replication，主库提交事务时至少等待一个从库确认收到 binlog 后才返回给客户端。代价是写操作的延迟增加约 1-2ms（同机房），换来的是主从延迟从秒级压到 100ms 以内。

注意 rpl_semi_sync_master_timeout = 50。如果 50ms 内没有收到从库的 ACK，就降级为普通异步复制，牺牲一致性保障可用性。这是 CAP 的实践。

第二层：延迟监控告警

我们用 Prometheus + 自研 exporter 监控延迟。规则：

  • Seconds_Behind_Master > 1s：钉钉告警
  • Seconds_Behind_Master > 5s：电话告警 + 自动将该从库摘除
  • Slave_SQL_Running = 'No'：立即摘除 + 尝试跳过错误

第三层：延迟超阈值自动切换读主库

这是最关键的兜底。当所有从库都被摘除，或者延迟超过 10s 时，读流量自动切换到主库——宁可主库压力大一点，也不能让用户读到脏数据。ShardingSphere 本身不提供这个能力，我们通过在数据源上做了一层包装来实现：

五、迁移实战：从单库到读写分离的 4 步走

改架构比写新功能难 10 倍，因为系统一直在线上跑着，用户完全不受影响的前提下完成切换是关键。

Step 1：新建从库 + 全量同步

这里我们用 xtrabackup 而不是 mysqldump，因为订单中心数据量已经 800G 了，mysqldump 导出导入要 6 小时，xtrabackup 只要 1 小时。

Step 2：灰度读流量——挑一个低风险接口先试

全量切换到从库是危险的。我们挑了一个低频接口——“订单物流轨迹查询”——作为第一个试验品。这个接口用户可以接受少量延迟，也不会因为读不到数据而造成严重后果。

跑了两天，接口一切正常，主从延迟在 100ms 以内。

Step 3：逐级放开——从低风险到高风险接口

按风险等级分批切换：

批次 接口类型 数量 观察期
第 1 批 后台管理查询 8 个 3 天
第 2 批 用户历史订单查询 5 个 5 天
第 3 批 订单列表/搜索 3 个 7 天
第 4 批 报表/对账 12 个 7 天

每一批切换时都保持 10% → 50% → 100% 的灰度节奏，监控主库 CPU 和从库延迟。这个过程中我们发现了两个问题：

  1. 后台某些导出接口在从库上也跑了 5 秒以上的查询，把从库 CPU 打到 80%。这说明从库也不是无底洞——我们给这些导出接口单独加了 Redis 缓存，15 分钟过期。
  2. 有一个接口在事务内读了从库——因为事务被标记为 readOnly=true，但 ShardingSphere 仍然走的从库。最后发现是 Spring 事务传播行为的问题，修了注解就正常了。

Step 4：全量切换 + 兜底监控

灰度到 100% 后，主库的 CPU 从 75% 降到了 25%，慢查询数量从 1124 条/天降到了 47 条/天（大部分是定时对账任务，可以接受）。从库的两个节点 CPU 约 40%，远低于告警阈值。

但我们没有放松警惕——在 Grafana 上新增了两块看板：

  • 主从延迟看板：Seconds_Behind_Master 的实时趋势图，配了 >1s 和 >5s 两级告警。
  • 从库读写比例看板：监控从库上是否有非预期的写入——之前就有一个定时任务 HardCode 了主库 IP，差点写到从库去，被我们抓到了。

六、教训与反思

教训 1：读写分离要趁早

我们 1124 条慢 SQL 其实不是一天冒出来的。回溯日志发现，系统的慢查询数量是从产品上线第 3 个月开始线性增长的——每加一个报表功能，就多几条慢 SQL。如果一开始就搭好读写分离的架子，不会拖到主库被打爆才动手。

教训 2：从库账号一定要只读

我们的 order_readonly 账号只有 SELECT 权限。这个看似多的配置步骤，帮我们挡掉了一个严重事故——某个服务的老版本代码里有一个 updateById，因为代码分支混乱被发到了线上，如果不是从库账号只读，它会悄悄写从库，造成主从数据不一致。账号只读让它直接报错，暴露了问题。

教训 3：写后读一致性是先有概念再有解法

很多同学觉得读写分离就是”配上就行”，但生产上真正坑人的是写后读。用户提交订单 → 跳转到订单详情 → 报 404 的体验，比不做读写分离还糟糕。我们在设计阶段就把需要强制走主库的场景梳理了出来，用 HintManager + 代码规范双重保障。

教训 4：读写分离不是终点

迁移完成半年后，数据显示从库的 QPS 增长到单节点 3000+，CPU 接近 60%。按这个趋势，再过 6 个月从库也会成为瓶颈。到那时，就不是”主库扛写从库扛读”能解决的了——需要把数据按分片键切开，引入分库分表。

这也正好衔接到 DDIA 第 7 章的主题——分区（Partitioning）。读写分离解决的是读写的资源隔离问题，而分库分表解决的是单库数据量和读写量的天花板问题。两者不是替代关系，而是递进关系。

写在最后

回到标题的”正确姿势”——读写分离不是一个技术选型问题，而是一个工程体系问题：

  1. 选对中间件：ShardingSphere-JDBC 对 Java 生态最友好
  2. 路由要聪明：不是简单的读从写主，要处理好写后读一致性
  3. 延迟要可控：Semisync + 监控 + 自动降级，三层保障
  4. 迁移要稳妥：分批灰度，从低风险到高风险

主库的慢 SQL 从 1124 条/天降到 47 条/天，CPU 从 75% 降到 25%。这不是因为硬件升级了，而是因为读和写不再打架了。
