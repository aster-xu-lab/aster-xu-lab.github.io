DDIA-10-Raft共识算法图解：选主+日志复制+安全性

引言：主从复制的终极矛盾——谁说了算

在分布式系统的演进中，主从复制（Leader-Follower Replication）解决了读写分离和备份容灾的问题。但它留下了一个根本性矛盾：Leader挂了谁顶上？

传统方案是让运维手动切主，或者写一个外部管理器（MHA、Orchestrator等）去监控切换。但这本质上是把”分布式一致性”外包给了一个非分布式的外部组件。外部管理器成了新的单点——它自己也可能挂，它做决策时也可能出现网络分区导致脑裂。

共识算法（Consensus Algorithm）就是为此而生的。它不是”更好的切主脚本”，而是让一群节点在没有人工干预和外部组件的条件下，就某个值达成一致的能力。在分布式系统中，”某个值”通常是：谁当主。

这篇文章我们聚焦Raft——它被设计出来就是为了解决Paxos”太难懂”的问题。我见过不少面试者背Raft的三个阶段，但一问”为什么Leader只能提交当前Term的日志”就答不上来。读完本文，你不仅能答上来这个问题，还能把它和订单中心的真实架构联系起来。

一、Raft的铺垫：为什么需要共识算法

1.1 单主架构的困局

标准的主从复制架构：一组节点，Leader接收写入并复制到Follower。读写分离，容灾备份。看起来很完美，直到Leader挂了。

此时你需要选一个新Leader。谁来选？如何保证所有节点一致？这里有一个核心命题：

分布式一致性的核心是”单个Leader”，而选举Leader本身就是一个分布式一致性问题。

你会发现这是一个鸡生蛋蛋生鸡的循环。Single-decree Paxos、Zab、Raft都是为了在一个故障模型（非拜占庭）下解决它。

1.2 共识算法的三个等价定义

一个有效的共识算法需要满足三点（等价表述）：

  1. Termination：最终一定会选出有效的领导者
  2. Agreement：所有正常节点上的共识值一致
  3. Validity：达成共识的值必须是某个节点提出来的（不能凭空捏造）

在Raft中，这三个属性分别由随机超时（解决Termination）、日志匹配/最终一致性（解决Agreement）、以及Leader选举的多数派投票（解决Validity）来保证。

1.3 关键：共识解决的是”一致”而非”实时”

很多人混淆了”共识”和”实时同步”。共识不保证任意时刻所有节点状态一致——它只保证最终它们会收敛到一个一致的状态，且一旦一个值被”决定”就绝不会被推翻。

这意味着：在任何一个瞬间，两个节点可能持有不同的值。但经过有限步骤后，它们必然会一致。理解这一点才能真正理解脑裂为什么可以优雅解决。

二、Raft的三个角色与状态转换（图解）

Raft将整个共识过程分解为三个独立的子问题，这也是它相比Paxos可理解性大幅提升的核心原因。

2.1 角色模型

每个Raft节点在任意时刻处于三种角色之一：

  1. Follower：被动节点，不发起任何请求，只响应Leader和Candidate
  2. Candidate：参选者，发起选举请求以当选Leader
  3. Leader：唯一的领导者，处理所有客户端请求，向Follower复制日志

角色转换规则用ASCII图表示：

Follower → Candidate：Follower在选举超时时间内未收到Leader心跳，递增Term，转换为Candidate，为自己投票，向所有节点发送RequestVote。

Candidate → Leader：若同一个Term内获得多数票，升级为Leader，立即发送心跳（空AppendEntries）宣告自己的权威。

Candidate/Leader → Follower：若收到来自更高Term的RequestVote或AppendEntries（RPC中的Term字段），立即退回为Follower。

Candidate → Candidate（重新选举）：选举超时或出现平票（分裂投票），递增Term重新选举。

2.2 Term（任期）——Raft的全局时钟

Raft把时间划分为Term，每个Term以选举开始。如果选不出Leader（平票），该Term结束直接进入下一Term。Term是单调递增的整数，它是Raft的”逻辑时钟”——所有RPC都携带Term字段，收到更高Term的一方立即退位。

Term解决了两个经典问题：

  • 过期Leader检测：旧Leader在网络分区中醒来，收到更高Term的节点直接拒绝，旧Leader发现不再有法定人数，退位。
  • 陈旧请求识别：Follower收到小Term的请求直接丢弃。

三、Leader选举：随机超时为何如此精妙

3.1 心跳和超时

Leader周期性地向Follower发送AppendEntries心跳（间隔约50-100ms）。如果Follower在选举超时（Election Timeout，150-300ms）内没有收到心跳，就认为Leader失联，开始选举。

3.2 随机超时的精妙设计

选举超时不是固定值，而是在150ms到300ms间随机选取。这可能是Raft最巧妙的设计之一：

为什么要随机？

如果所有节点的超时时间相同，Leader挂掉后，所有Follower会在同一时刻同时变成Candidate。N个节点竞逐N票，必然平票，进入下一轮，再次同时苏醒同时平票……系统陷入死锁。

随机超时打破了这种同步。每个节点的超时不同，超时最早的先变成Candidate，在自己Term内拿到多数票的概率极高。这就是”随机化解决分布式死锁”的经典案例。

3.3 选举流程详解

这里日志比较是关键：Raft确保只有包含所有已提交日志的节点才能当选Leader。这是安全性保证的核心。

当Follower和Leader不一致（如Follower落后或多了未提交的旧Leader日志），AppendEntries中的一致性检查会失败。Leader的对策是：

每次失败后，prevLogIndex 减1重试。最终找到一个完全匹配的日志位置，然后Leader用本地日志覆盖Follower该位置之后的所有日志。

这意味着：Follower上任何与Leader不一致的日志都会被覆盖。只要某条日志被复制到多数节点，它就安全了——因为后续的Leader必然包含它。未被复制到多数的日志，可能在重新选举后被覆盖。

五、安全性：Leader只提交当前Term的日志

这是Raft最容易被忽视却最关键的规则，也是面试常见的深度问题。

5.1 为什么需要这个规则？

看这个时序：

如果没有”Leader只能提交当前Term”的规则，S1可能在没收到AppendEntries之前就通过心跳把Index 3提交了，然后S1的日志被下一任Leader覆盖，导致”已提交日志被篡改”——破坏了安全性。

5.2 规则内容

Leader不能通过”数副本数”来提交之前Term的日志条目。只能提交当前Term的日志，当当前Term的日志被提交时，之前Term在该Index之前的日志因为”日志属性的递归性”也被隐式提交。

这个规则的底层原理：

  • Raft的日志匹配性质（Log Matching Property）：如果两个日志在同一Index上的Term相同，则它们从1到该Index的所有日志完全相同。
  • 因此只要提交了当前Term的一条日志，它之前的日志天然就是安全的——因为它们必定存在于多数节点的日志中，下一任选举出来的Leader（必须拥有多数派的最新日志）必然也包含它们。

这条规则确保了已经提交的日志永远不会被覆写。

六、网络分区场景深度解析

6.1 场景设定

5节点集群：A、B、C、D、E。Term 1，A为Leader。

现在发生网络分区：{D, E} 被隔离，剩下 {A, B, C}。

D的日志也不会被提交：D只复制到E（2/5<3/5），不够多数。当网络恢复后，D和E会收到A（或新Leader）更高Term的心跳，它们的未提交日志会被覆盖。

6.3 为什么旧Leader不能提交？

把问题反过来想：

如果A挂了，D在隔离区自封Leader（5节点2票不可能当选），但当A真的挂了，集群剩下B、C、D、E→4节点，D和E的2票仍然<3票，无法当选。

但如果网络分区把5节点分成3+2，大于半数的一方能继续工作，少数方无法选举——这就是Raft用”多数派”保证的：

任何时刻最多只有一个分区能形成多数派，因此最多只有一个合法的Leader。

脑裂在此模型中不再是Bug，而是”被设计成不可能的Feature”。

6.4 双分区都达到多数的极端情况？

如果是偶数节点（如4节点），分区成2+2，两边都无法达到多数（各自只有半数），整个集群不可用——Stop The World。

这也是Raft推荐奇数节点（3、5、7）的原因之一：确保单一多数派的存在，提升可用性。

七、Raft vs Paxos：可理解性的革命

7.1 Paxos为什么难懂

Paxos（Lamport 1998）是第一个完备的共识算法，证明了分布式一致性问题在非拜占庭模型下可解。但它的描述是”单次决议”（Single-decree），要把多个日志条目串起来需要Multi-Paxos——而Multi-Paxos没有统一的工业标准，每个实现有自己的补丁。

Paxos的难点：

  • 描述方式是反直觉的（”一个值被选中当且仅当…”的命题逻辑）
  • Roles和Phase混在一起，学习者需要同时追踪多个维度
  • 从Paxos到工程实现中间有巨大的鸿沟

7.2 Raft的设计哲学

Raft作者Diego Ongaro在论文中明确说：他们的设计目标是understandability。为此采取的策略：

设计策略 具体做法
问题分解 Leader选举、日志复制、安全性拆成独立子问题
状态空间压缩 强Leader模型，日志只从Leader流向Follower
角色明确 三态Follower/Candidate/Leader，转换规则清晰
机制简单化 随机超时替代Paxos中的复杂冲突解决

Raft没有在正确性或性能上超越Paxos（它们的FLP不可能上界是一致的），但它大幅降低了实现和理解的难度。这就是为什么etcd、consul、TiKV、nacos都选择了Raft而非Multi-Paxos。

第一阶段：MHA（Master High Availability）

问题很明显：

  • MHA本身是单点：需要额外监控MHA进程
  • 切换不透明：判定”Master挂了”的逻辑在外部，无法参与集群共识
  • 脑裂可能：网络分区时MHA可能误判，切出新Master后原Master还在线
  • 依赖SSH：网络抖动可能影响切换的可靠性

8.2 MySQL Group Replication（MGR）——内置Paxos

第二阶段：MGR（MySQL Group Replication）

MGR内置了一个类Paxos的共识引擎（MySQL Group Communication Engine，基于XCom），主要改进：

对比优势：

维度 MHA + 半同步复制 MGR (Paxos)
选主 外部Manager触发，秒级 组内自动选举，毫秒级
数据一致性 半同步可能丢最后一秒数据 共识提交，已提交的不丢
脑裂 可能发生（网络分区+多Master） 多数派机制拒绝少数派写入
运维复杂度 需维护Manager + 切换脚本 内置，无需外部组件
性能 单主写入，性能高 共识协议有额外延迟，性能略低

坦诚地说：MGR更可靠但更复杂。日订单130万的场景下，MGR的写入延迟增加了2-5ms（共识轮次开销），而MHA在主从复制上几乎没有额外延迟。但MGR换来了：

  • 不会出现MHA误判或未触发的脑裂场景
  • 切换速度快（MHA秒级 → MGR毫秒级）
  • 不需要维护额外的Manager进程

最终我们选择的是：核心交易表走MGR单主模式，查询类的非关键表走异步复制。

九、成熟的Raft开源实现——什么时候直接用它

9.1 三大主力

实现 语言 使用场景 特点
etcd (Raft库) Go Kubernetes/分布式配置中心 Raft论文独立作者的实现，最权威参考
consul (Raft库) Go 服务发现/健康检查 带完整的Membership/TTL健康检查
nacos (CP模式，Raft) Java 阿里微服务生态 SOFAJRaft，阿里自研，TP999优化好

9.2 什么时候直接用，什么时候自己造

直接用（99%的情况）：

你需要的不是”一个Raft实现”，而是”一个高可用的KV存储/配置中心/服务发现”。etcd和nacos已经是完整的分布式基础设施产品，直接部署远比手写靠谱。

如：配置中心需要在多地部署且需要强一致性 → 部署etcd集群，gRPC/HTTP API即开即用。

自己实现Raft（1%的情况，但需要极其谨慎）：

当你的系统有特殊约束时：

  • 需要嵌入Java进程内部（如订单状态机需要本地强一致日志）→ 可基于SOFAJRaft（nacos使用的Java Raft库）嵌入
  • 需要自定义存储后端（etcd默认是BoltDB/MVCC存储）→ 用CockroachDB的上层封装，或者基于Dragonboat（Go高性能Raft库）
  • 学习目的：实现一个微型Raft库（几百行核心逻辑）是极好的分布式系统练习

我的建议：除非你的需求明确超出了etcd/consul/nacos的能力边界（且团队有分布式系统专家），否则永远不要自己实现Raft。 这句话适用度90%。

总结

Raft将共识分解为三个子问题：

  1. Leader选举：Term + 随机超时 → 打破对称死锁
  2. 日志复制：AppendEntries + 多数派提交
  3. 安全性：只能提交当前Term的日志 → 间接保证旧日志安全

这三个子问题结合起来，解决了一个本质上”鸡生蛋”的问题：用多数派投票选Leader，Leader来同步日志，日志确定了选主的资格。这是一个优雅的自我参照。

关键设计直觉拿走：

  • 多数派保证：任何时刻最多一个分区有法定人数 → 最多一个Leader
  • 随机化打破对称：不需要协调者也能解决选主冲突
  • 日志只单向流动（Leader→Follower）：简化一致性追溯

关于实现：能用etcd就别自己写Raft。但如果面试官问”Raft的日志提交规则为什么需要只有当前Term”，你现在知道答案了。
