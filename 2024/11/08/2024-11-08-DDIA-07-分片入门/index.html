DDIA-07-分片入门：当一张表大到MySQL装不下

引子：一张表，装不下了

你负责的订单表，从一开始的几千行，到几十万，再到几千万。头一年，加索引、SQL优化都还顶得住。第二年，某个促销日之后，库房主管给你打电话：”系统卡了，捡货单刷不出来。”

你登上运维平台一看，MySQL的CPU一直在80%以上，磁盘已经用了460GB。再看那张t_order表，1.2亿行。

不是你的SQL写得不好，是这张表真的装不下了。

这就是分片（Sharding）要解决的问题。本文是DDIA学习笔记第7篇，聊聊分库分表的入门认知：什么时候该分、分片和垂直拆分有什么区别、分片的核心难点在哪里，以及一个来自真实业务场景的推演。

一、什么时候需要分片

不是表大了就得拆。加索引、优化SQL、读写分离、加缓存，这些手段都试过之后，才轮到分片。判断标准可以从三个维度看：

1.1 单表数据量

MySQL InnoDB的一张表，B+树的高度取决于数据量和索引大小。假设一行数据1KB，2千万行大约就是20GB。这时候B+树高度大概3到4层——还在可控范围。

超过2千万行之后，B+树的层数开始升高，每次查询涉及的磁盘IO次数增加，而MySQL的Buffer Pool就那么几百GB，热数据开始溢出到磁盘。实际上2千万行没有普遍意义—— 这和行宽强相关。如果你的表一行只有200字节，一亿行也比不上一条宽表的2千万行。关键还是看磁盘和性能。

一个更普适的经验值：单表超过20GB时，就开始警惕。

1.2 磁盘空间

单机磁盘容量是硬限制。云服务器附带的SSD云盘，典型容量在500GB到2TB之间。当你的一张表连同索引占用了300GB，剩下的空间还要留给binlog、备份、其他表——基本上已经到了该拆的时候。

这里有一个很容易忽略的点：MySQL的数据文件和索引文件都在同一台机器上。 你把热数据和冷数据分区？MySQL不管你这些，索引还是得在这台机器上。

1.3 写入吞吐

即使磁盘没满、行数没超，单库的写入吞吐也是有限制的。一个MySQL实例，能扛的TPS取决于硬件和配置——高端物理机可能几万TPS，云数据库通常几千到一万。如果你的业务写入量持续增长，早晚要面对这个瓶颈。

这三个维度不需要同时满足，任何一个先到极限，就是动手的信号。

二、分片 vs 垂直拆分：两种不同的拆分思路

很多团队聊”分库分表”，实际上包含了两种性质完全不同的操作。理解它们的区别，是做拆分的起点。

2.1 垂直拆分（按业务）

垂直拆分就是把不同业务的数据放到不同的库。比如：

垂直拆分的本质是把耦合低的业务域分开。带来的好处：

  • 独立的数据库资源（连接池、缓存、CPU），业务之间不互相拖累
  • 可以针对不同库做独立的优化和扩容
  • 符合微服务拆分的方向，每个服务有自己的数据库

技术上垂直拆分相对简单，因为不同业务的数据原本就没有强关联——订单表和用户表的join，本来就不应该在生产环境运行。

2.2 水平分片（按数据行）

水平分片是把同一张表的数据行分布到多个数据库实例或表中。

水平分片才是DDIA第7章讨论的”分区（Partitioning）”。这才是真正的技术难题——本来一张表里的数据现在散落在多台机器上，所有跨分片的操作都变得复杂起来。

2.3 真实世界的组合

实际项目里，两种方式是一起用的：先垂直拆库，再水平分片。

垂直拆分把业务边界划清，水平分片解决单库容量问题。一个典型的电商中台：

  • 订单库 → 按user_id分4个库 → 每个库16张表 → 总共64张表
  • 用户库 → 先不拆，量小
  • 商品库 → 先不拆，读多写少，加缓存

三、分片的核心问题

一旦数据分散到多个节点，四个问题随之而来。

3.1 分片键的选择

这是分片最重要的决策，做错了代价极大——所有数据已经在各个库里了，要迁移等于重新上线一套系统。分片键的选择第一原则：让大多数查询命中一个分片。

如果你的查询是：

而分片键是user_id，这就麻烦了——这个查询必须广播到所有分片，然后在中间件层合并结果。这就是”分片键不匹配查询条件”的痛苦。

所以选择分片键，就是选择你的业务查询最大的那个入口条件。在订单系统里，用户查自己的订单占了绝大多数场景，分片键当然是user_id。在商户后台查询系统里，商户按店铺查订单，那分片键可能得是merchant_id。

3.2 跨分片查询

有时候跨分片查询无法避免。最常见的是管理员后台的模糊查询、全量数据导出、跨用户的数据分析。

处理策略有三种：

  1. 能改成逐个分片查询就逐个查，在应用层汇总
  2. 建冗余表或搜索引擎（如把订单同步到Elasticsearch），复杂的多维查询走搜索引擎
  3. 容忍慢，后台查询本身就不是高频场景

这里有一个认知纠正：并不是所有查询都必须快。 管理员半夜跑一个报表，等10秒完全可以接受。关键是不要把后台查询的复杂性带到核心交易链路里。

3.3 分布式事务

分片之后，单机事务变成了跨节点的事务问题。

比如创建订单的经典场景：

  • 插入订单到分片A（用户的订单表）
  • 扣减库存（库存表可能在不同库）
  • 扣减优惠券（优惠券表又有自己的分片）

这三个操作跨了不同数据库实例，ACID事务不可用。

工业界的处理方式：

  • 尽量避免。好的数据建模可以最小化跨分片写入。如果把库存扣减改成异步，把优惠券扣减也异步化，那么核心的”创建订单”只是一个单分片的写操作。
  • 最终一致性。用本地消息表 + 重试机制，确保各方最终达到一致。这是绝大多数互联网公司的选择。
  • 分布式事务框架。Seata AT模式、TCC模式，本质都是两阶段提交的变种，代价是性能和可用性。

两阶段提交不是一个新技术。DDIA第9章对2PC有详尽的分析——它的核心问题在于协调者成为单点，而且持锁时间太长。在生产环境中大规模使用，要非常谨慎。

3.4 数据均衡

即使你选了很好的分片键，数据分布也可能不均匀。比如电商平台，”张三”只有3个订单，”李四”有3000个订单——按user_id哈希，hot user会导致某些分片数据量远大于其他分片。

更隐蔽的问题是：新建的分片一开始数据很少，旧的快满了。这是时间维度的不均衡。

常见的应对：

  • 一致性哈希：减少节点增减时的数据迁移量
  • 虚拟分片：先分1000个逻辑片，10个物理节点各分100个。扩容时移动一些逻辑片到新节点
  • 定期rebalance：容忍一定程度的不均衡，在维护窗口做数据迁移

四、实战推演：1.17亿行的决策链

这里用我经历过的电商场景做一个推演：130万日订单。

第一阶段：什么都不做

起始状态：一张t_order单表。索引整齐，SQL规范，Buffer Pool配到了128GB。数据开始累积。

第二阶段：时间维度拆分（按天分区）

MySQL 5.5+支持Range分区。可以按create_time做日分区：

好处：按时间范围的查询（查询某天的订单）直接被分区裁剪。坏处：和分片键原则并不匹配——用户按自己ID查询时，仍然要扫全表。

< 这个方案适用于日志类数据、流水类数据。对于订单，治标不治本。

第三阶段：分表（按月）

130万/天 × 90天 = 1.17亿行。什么时候开始分？一个好的测算：

  • 单表1000万行开始准备方案
  • 单表2000万行开始执行
  • 单表5000万行之前必须完成

按这个节奏，日订单130万时，最迟第16天就要动手。当然实际上不会第16天就全量分——你还有MySQL分区扛一阵。但架构方案必须在数据到1000万之前敲定。

按月分表：t_order_202601、t_order_202602……应用层根据查询时间自动路由。

好处：实现简单，每张表数据量可控（130万×30=3900万行）。
坏处：跨越时间查订单仍然要扫多张表，而且没有解决单库磁盘问题——所有月表都在同一个数据库实例里。

第四阶段：分库（按user_id）

当数据量积累到一定程度（比如12个月的表都在这一个库里），单库磁盘和写入吞吐开始告警。这时候才走到最终形态：按user_id分库，每个库里再按月分表。

路由逻辑：user_id % 4 → 定位到db_order_N → 根据月份定位到具体表。

这个架构的查询逻辑：

  • 用户查自己的订单：user_id % 4 → 单个数据库 → 按月表范围 → 1-3张表
  • 运营查某天的全部订单：4个库各查1张月表 → 中间件合并
  • 运营跨90天统计数据：这是数据仓库的事，不要来搞OLTP数据库

关键决策回顾：为什么不是按order_id分片？

因为用户查询的入口90%是user_id。按order_id分片，用户查”我的订单”就要广播到所有分片——每个用户每次请求都打满所有库，并发一大直接雪崩。

分片键的第一原则再次强调：让大多数查询命中一个分片。

这个推演中的刻意留白

上面这个推演隐含了一个假设：你用了一个中间件来自动路由（ShardingSphere-Proxy或Sharding-JDBC），然后你的代码里至少应用层知道user_id和月份这两个路由信息。如果没有这样的中间件，手写路由逻辑也能用——只是开发团队要多写一坨代码，维护成本涨一截。

五、和DDIA第7章的呼应

DDIA第7章从更本质的角度讨论了分区，很多概念和分库分表直接对应。

5.1 分区路由：哈希 vs 范围

  • 哈希分区：user_id % N → 数据均匀分布，但不支持范围查询
  • 范围分区：按时间范围切分 → 范围查询（查某段时间）走单分片，但数据可能不均匀

我们第四阶段的分库分表方案，是对DDIA这个理论的最好应用——先按哈希（user_id）横向分布，再按范围（月份）纵向分布。两者组合使用，取各自的优势。

5.2 二级索引：本地索引 vs 全局索引

分片之后，非分片键的索引怎么办？比如订单表里有status状态字段，现在数据散在四个库里。

DDIA区分了两种方案：

本地索引：每个分片独立维护自己的索引，status索引在每个数据库里都有。查WHERE status='PAID'时必须广播到所有分片，然后在中间件合并。优点是简单，缺点就是广播查询的性能损耗。

全局索引：建一张全局的索引表，里面的内容是(status, order_id, user_id)，这张索引表本身也要分片，但查询时先查索引表找到目标分片，再精准查询。优点是无需广播，缺点是引入了额外的数据和维护成本。

工业界的折中：本地索引 + 分片键。 当你的绝大多数查询都能带上分片键的时候，本地索引完全够用。对于少数的跨分片查询，用搜索引擎（ES）或者异步构建宽表来解决。

六、总结：分片不是银弹

分片解决问题，也制造问题。

你得到什么

  • 容量无限扩展（理论上，加机器就行）
  • 每个分片的性能可控（数据量降下来了）
  • 故障隔离（一个分片挂了不至于全体不可用）

你失去什么

  • Join没了。跨分片join直接不能用了，所有的关联必须在应用层做
  • 事务没了。跨分片写操作不再原子化，需要最终一致性方案
  • 运维复杂度暴增。建表要建N个库、数据迁移工具、监控要分片级别的
  • 开发心智负担。每一个SQL都要想：这是走一个分片，还是广播？

什么时候不应该分

  1. 数据量还没到。 1000万行以下的表考虑分片属于过度设计，给自己找麻烦
  2. 可以归档。 很多”大表”有90%是冷数据，归档到对象存储比拆分更简单
  3. 读写分离 + 缓存能解决。 绝大多数读多写少的业务不需要分片

应该分的信号

当你的DBA开始用”这周还行，下周不好说”来形容数据库——别等了，开始做方案。
