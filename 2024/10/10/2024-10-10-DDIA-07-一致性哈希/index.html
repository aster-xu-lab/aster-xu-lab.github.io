DDIA-07-一致性哈希：当分片不再是2的幂次

引言：一次扩容引发的血案

凌晨两点，告警群炸了。

Redis 缓存命中率从 98% 直线掉到 12%，MySQL 连接池瞬间打满，订单查询超时，用户端白屏。值班同学紧急回滚扩容操作，15 分钟后恢复。事后复盘，根因只有一句话：缓存 key 用 hash(key) % N 计算分片，加了一台 Redis 后 N 从 10 变成 11，90% 的缓存 key 指向了错误节点，缓存集体失效，DB 被穿透。

这不是虚构故事。六年前，我刚接触分片系统时，这就是我亲手踩过的坑。当时直觉是”多加几台机器分散压力”，完全没意识到取模分片的数学本质：N 变化 = 全量重新映射。

DDIA 第 7 章把这个问题抽象到了极致：一致性哈希 vs 固定分区，本质是在”动态性”和”确定性”之间做取舍。本文从一个真实的扩容翻车案例开始，把一致性哈希的原理、虚拟节点机制、与 Redis Cluster 的关系，以及它为什么不适用于关系数据库分片，逐一说清楚。

一、哈希取模：直觉方案，致命缺陷

1.1 取模的数学本质

这个公式简单到任何工程师都能秒懂。当 N=4 时，四个节点均匀分担流量，一切完美。

1.2 扩容时发生了什么

假设 N 从 4 变成 5，我们需要回答一个问题：有多少 key 会被迁移到新节点？

具体来说：原本落在节点 0 的 key，在新映射下是否还落在节点 0？不一定了。

设 key-A 的哈希值对 4 取模余 0，当 N=5 时，同一个哈希值对 5 取模可能余 3。原本存在节点 0 上的数据，现在要去找节点 3 读——缓存必然 miss。

二、一致性哈希：环形空间上的分片艺术

2.1 把哈希空间卷成一个环

一致性哈希的核心思想是：把哈希值空间首尾相连，形成一个环。

  • 哈希函数输出范围：0 ~ 2^32 - 1（以 MD5/SHA1 为例）
  • 节点不再对应到下标 0,1,2,3…，而是对应到环上的一个位置
  • 数据的存储规则：沿环顺时针走到第一个（或下一个）节点

这就是它和取模的本质区别：取模是”点到点的静态映射”；一致性哈希是”点到节点的动态寻址”。

场景 取模哈希迁移量 一致性哈希迁移量
10 节点加 1 个 90% ~9%
100 节点加 1 个 99% ~1%

这不是渐进优化，这是两个数量级的差距。取模哈希让你不敢弹性扩缩；一致性哈希让你随时弹。

2.3 删节点：同样的局部影响

节点宕机或下线时，只影响该节点上的数据，这些数据被顺时针重分配到下一个节点。其他节点的数据完全不动。

这也是为什么一致性哈希天然适合做状态服务器的路由：用户会话绑定、客户端连接路由、分布式锁归属——这些场景中，节点增减时你希望尽可能不动已有映射。

三、虚拟节点：当物理节点太少时

3.1 真实世界的环是不均匀的

一致性哈希在理想环下完美工作，但真实世界的物理节点不是均匀分布在环上的。

三台机器在环上的哈希位置完全随机，这意味着：

  • 节点 A 和 B 之间可能填充了 50% 的环空间
  • 节点 B 和 C 之间可能只有 15%
  • 结果：A 承担了 50% 的请求，C 只有 15%

这叫作数据倾斜（Data Skew）。

3.2 虚拟节点 = 打散重分布

解决方案很优雅：每个物理节点映射到环上的多个位置。

200 个虚拟节点分布在环上的不同位置。当 600 个虚拟节点（3 物理 × 200 虚拟）近乎均匀地覆盖整个环，每个物理节点负担的数据量就会非常接近 1/3。

一个关键性质：虚拟节点本质是用节点数量换取负载均衡。 虚拟节点数越多，负载越均匀；但维护成本也越高。经验值是 100-200 个，实际足够覆盖绝大多数场景。

3.3 为什么是 100-200 个

这个数字并非臆造。Apache Cassandra 的默认配置 num_tokens=256，elastiCache 和 Twemproxy 也采用了类似的量级。

背后有一个统计原理：N 个随机点落在 [0,1) 上，相邻点间距期望值是 1/N，标准差约也是 1/N。虚拟节点把间距的标准差压到这个数量级，从而把负载差异控制在几个百分点。

Redis 团队的选择很务实：slot 数量固定为 16384，意味着映射表大小可控（16k 个 bitmap），cluster nodes 通信协议包的 payload 也足够紧凑。 这本质上是一种”固定哈希槽 + 动态 slot 分配”的做法，DDIA 第 7 章中称之为固定分区（Fixed-Partition）——分区的数量不随节点变化，但分区到节点的映射可以动态调整。

五、实战选择：一致性哈希 vs 取模 vs 固定分区

5.1 什么时候用一致性哈希

一致性哈希的最佳战场有三个条件：

  1. 节点需要频繁动态扩缩
  2. 数据迁移成本极高（缓存冷启动、大规模状态同步）
  3. 不需要范围查询（一致性哈希天然打乱数据顺序）

典型场景：

  • 分布式缓存分片：Memcached 集群（Twemproxy）、Redis Cluster、ElastiCache
  • 网关/负载均衡的状态路由：客户端 IP/会话 ID → 固定后端（sticky session）
  • 分布式调度器：Celery/Quartz 的集群状态归属

5.2 什么时候不要用

关系数据库分片不要用一致性哈希。

为什么？因为把订单 ID 做一致性哈希，订单数据在物理节点上是随机分布的：

同一个用户的三笔订单落在了三个不同的节点上。做”查某用户的所有订单”，需要 scatter-gather 到所有节点，然后排序合并。节点一多，查询效率断崖下跌。

六、DDIA 第七章的呼应

DDIA 第 7 章的核心洞察之一是：分区策略的本质是在”使分区变小变多”（fine-grained partitioning）和”使分区变少变大”之间做权衡。

一致性哈希代表了”极细粒度分区”的思路——每个 key 都是独立的一小片，重构映射时成本极低——一个节点下线只需要重映射它上面的那部分 key，剩下的不动。这种策略天然适合无状态、不需要跨分区查询的缓存和路由场景。

而固定分区代表了”粗粒度区块分配”的思路——分区数不变，节点增减时把分区在节点间重新分配。这种策略适合需要跨分区聚合、范围和批量查询的存储场景。

有趣的是，Redis Cluster 用 16384 个 slot 走在了极细粒度和固定分区之间的中间地带。 slot 足够多使得负载偏差小到一个可管理的范围，但又不会多到让重分配复杂到不可实现——迁移的最小粒度是一个 slot，而不必到 key 级别。

至于哈希取模，DDIA 几乎没有为其辩护。它的适用场景只有一种：你确定 N 永远不变。 而在云计算的世界里，”永远不变”是少数，”随时会变”才是常态。

总结

一致性哈希不是银弹，但它解决了一个真实而痛苦的问题：如何让分布式系统的数据映射，在节点变化时只发生局部调整，而不是全量重分布。

核心思路：环形空间 → 顺时针寻址 → 加减节点只影响相邻节点。 虚拟节点补上最后一环——少量物理节点也能做到近似均匀分布。

Redis Cluster 以它的 16384 个哈希槽，用一种务实的方式证明了”一致性哈希的思想”在生产环境中的巨大威力。而订单分片等存储场景，则提醒我们：凡是要范围查询、要批量检索的时候，一致性哈希不是答案。 用固定分片 + 映射表，把 Hash 层和物理层解耦，才是存储分片的正确姿势。

六年前扩容翻车的凌晨，我学到的是：hash(key) % N 用起来很快，还起来很贵。六年后的今天，每当设计一个新的分片系统，我都会首先问自己两个问题：

  1. 节点数量会不会变？ 会 → 取模出局
  2. 需不需要范围查询？ 需要 → 一致性哈希出局

解决这两个问题，剩下的工程细节都在可控范围之内。
