DDIA-08-事务不是万能的：长事务、死锁与乐观锁实战经验

你以为事务是万能的

很多Java后端写业务代码的时候，有一个迷之自信：「出问题就回滚嘛，事务包住就行了」。

于是就出现了这样的代码：

这个事务涵盖了数据库操作、HTTP调用、MQ发送，执行一次至少3-5秒。看起来一切正常地对吗？「原子性」保证了任何一个环节失败就回滚，逻辑上没毛病。

但你猜生产环境会怎么样？

在日订单峰值120万+、QPS 8000的场景下，这个「完美事务」会在三小时内把数据库连接池打满，然后整个订单服务开始拒绝服务 —— 不是哪个组件坏了，就是「事务写得太长」这一个问题。

这就是我这篇文章要说的：事务不是万能膏药。用得不对，事务本身会成为系统雪崩的起点。

本文会从长事务的危害开始，讲到死锁的形成与排查，再到乐观锁和悲观锁的实战选型，最后总结事务边界设计的原则。读完你会明白：写对事务，不是知道ACID四个字母就够了。

一、长事务：温柔的杀手

1.1 长事务是怎么定义出来的？

先说一个反直觉的事实：很多长事务的锅不在DB，在应用代码。

@Transactional 注解往 Service 层方法上一贴，所有的事情都在一个事务里做——这是我见过的绝大多数长事务的根因。在「本地事务 vs 分布式事务」的讨论之前，先来问自己一个更基础的问题：这个方法里的所有操作，真的都需要在同一笔事务中吗？

从数据库的角度看，一个事务持有的锁从第一条写SQL开始，到 COMMIT 才释放。如果这个间隔是5秒，那锁就持有了5秒。在线程池只有50个连接的情况下，5个并发这样的操作就能把所有连接占满。

连接数被占满 → 新来的请求排队等连接 → 等了30秒超时 → 用户看到报错 → 重试 → 重试带着新请求再排队 → 更慢 → 雪崩。

二、死锁：两个事务互相等待的僵局

2.1 死锁的四个必要条件

大学操作系统课里讲过死锁四个条件，但到了数据库层，它们变成了更具体的形态：

条件 在数据库中的表现
互斥 行级锁（X锁）同一时刻只能被一个事务持有
持有并等待 事务A持有行1的锁，同时在等待行2的锁
不可抢占 MySQL InnoDB不会强行夺走已持有的锁
循环等待 事务A等事务B释放锁，事务B也在等事务A释放锁

四个条件缺一不可。但实际操作中，只需打破其中任意一个就能消灭死锁。应用层最常打破的是「持有并等待」——缩短事务时间，或者一次性获取所有需要的锁。

2.2 MySQL的死锁检测和排查

InnoDB 对死锁有两层机制：

第一层：innodb_lock_wait_timeout（默认50秒）。一个事务等待行锁超过这个时间就自动回滚。50秒对于 Web 请求来说太长了——用户的请求早就超时了，但数据库连接还在被这个等待中的事务所占用。这是一个被动防御，不是解决方案。

第二层：死锁检测（默认开启，innodb_deadlock_detect=ON）。InnoDB 内部维护了一个等待图（Wait-for Graph）——节点是事务，有向边表示「事务A在等待事务B释放锁」。检测器周期性扫描这个图，发现环就判定为死锁，选择回滚代价较小的事务（undo log 较小的那个）。

这个机制的代价是：当事务数量很大时，等待图检测本身也消耗CPU。如果你有1000个并发事务都在争同一组行，检测器每次要遍历这1000个节点的等待关系——MySQL 官方文档称之为「死锁检测的 O(N²) 问题」。但这通常出现在单热点行的并发争用场景，不是事务数量问题，而是同一把锁上的堆积问题。

三、乐观锁 vs 悲观锁：不是孰优孰劣，是场景匹配

3.1 两种锁的哲学差异

悲观锁：假设冲突一定会发生。SELECT FOR UPDATE 一把梭，先占坑再干活。适合「冲突概率高」的场景。

乐观锁：假设冲突很少发生。读数据时不加锁，更新时检查数据有没有被别人改过。适合「冲突概率低」的场景。

乐观锁的关键是 version = #{version} 这个条件：如果在你读之后、写之前有别人修改了，version 已经变了，这条 UPDATE 的 affected rows = 0。框架层检测到行数为0就知道并发冲突了，要么重试（CAS循环），要么抛错让用户重新操作。

两者本质的区别是：悲观锁用「等待」解决并发冲突，乐观锁用「重试」解决并发冲突。

3.2 扣库存用乐观锁——冲突少时的性能利器

扣库存是乐观锁的教科书级应用场景。

为什么？因为库存扣减冲突只发生在「同一SKU的高并发秒杀」场景中。正常情况下的电商流量是分散的——10万个SKU，QPS 8000，平均每个SKU每秒只有0.08个扣减请求。绝大多数扣减都是一次成功，没必要用悲观锁让其他请求排队等。

但如果你用了 SELECT FOR UPDATE 扣库存，所有对同一SKU的请求都会串行化——即使库存还有10万件，每次也只能一个请求在修改。吞吐量直接砍掉一个数量级。

用乐观锁 + version 号的方案：

原理：你去读库存的时候，不拿任何锁。更新的时候，用一个 WHERE 条件检查「你读到的数据有没有被别人动过」。没有→更新成功。有→重试。

在冲突少的场景下，CAS 重试几乎不会发生，吞吐量接近无锁的水平。而悲观锁即使不发生冲突，也要付出获取锁、释放锁的额外开销。

3.3 审核订单用悲观锁——防止同一个人做两次审核

审核订单是另一个极端——冲突概率极高。

运营后台的订单审核场景：审核员A打开订单，审核员B也打开同一订单。如果不用锁，两个人可能同时点「通过」，导致订单被处理两次。

这种情况如果用乐观锁，用户体验会很差——审核员填了审核意见、点了通过，结果系统告诉你「该订单已被其他人修改，请刷新重试」。在客服场景下这个体验是不可接受的。

所以审核订单用悲观锁：

为什么这里合适？

  • 审核频率低，锁持有时间极短（几十毫秒）
  • 冲突概率高——多人审核同一个队列
  • 用户体验要求高——不能让审核员填完表单后发现被别人审核了

四、事务边界设计原则

前面讲了那么多踩坑经验，可以归纳为四条事务设计原则。这些原则看起来简单，但每一条背后都有线上事故的教训。

原则一：事务尽可能短

衡量标准：事务时间 = 第一条写SQL到COMMIT的时间，目标是 < 100ms。

怎么做到？把不需要事务保护的操作移出去。日志记录、Redis缓存更新、ES索引同步——这些操作失败了不需要回滚数据库，那就不要放在事务里。

如果你的框架代码里有 AOP 切面在事务里写了操作日志，把它改成异步事件，在事务提交后再处理。

原则二：不在事务里调RPC/HTTP

这是最容易犯的错，也是后果最严重的。一个HTTP超时5秒，数据库锁就持有了5秒。几十个这样的请求就能把连接池打满。

正确做法：事务完成 → 提交 → 再发RPC。如果RPC失败，用补偿逻辑处理，不要试图用事务回滚来撤销已提交的数据（那会变成分布式事务的话题了）。

原则三：不在事务里发MQ

和RPC同样的道理。MQ发送也有网络开销，如果Broker慢了，连接就被卡住了。

更隐蔽的问题是：如果你在事务里发MQ，恰好MQ发送成功但事务回滚了，消费者会处理一个已经不存在的业务数据。或者事务提交了但MQ发送失败，下游没收到通知。

正确的做法是事务提交后再发MQ：

或者更可靠的方式：用本地消息表（创建订单的同时在同一个事务里插入一条消息记录），然后独立的任务去扫描消息表并发送MQ。这是最终一致性的标准做法。

原则四：控制事务内的数据量

如果你在一个事务里更新了超过1000行，请停下来问自己：这1000行真的需要在同一个事务里吗？

批量操作尤其要注意。处理1万条数据，拆成10个1000条的小事务，每个事务30ms，总共300ms。比一个10万行的大事务锁5分钟好一万倍。

V2修复：事务拆解 + afterExecute 编排

V2做了两个关键改动：

第一，事务瘦身。 execute() 方法不再用 @Transactional。数据库操作（读订单、写日志）放在独立的短事务方法里，HTTP调用放在事务外。

第二，引入 afterExecute 编排。 不用 DAG，不引入新的调度框架。每个 Handler 的 execute() 完成后，从 afterExecute() 返回触发条件，由 SyncTask 引擎判断是否触发下游 Handler。

这个案例的教训是：事务是数据库一致性工具，不是业务流程编排工具。你用事务去兜业务逻辑的完整性，代价是锁资源和连接资源——而这些资源是数据库最珍贵的、最不能被长时间占用的。

六、和DDIA第8章「串行化执行」的呼应

DDIA第8章讨论的是隔离级别的另一极——从可序列化快照隔离（SSI）到真正的串行化执行。Martin Kleppmann 在书里提出了一个有意思的观点：如果事务足够快，串行化执行反而是最简单的并发控制方案。

VoltDB、H-Store 这些内存数据库正是这么做的——在单个CPU核上顺序执行事务，因为没有等待锁的时间，吞吐量反而不低。

但现实中 MySQL 的事务做不到那么快，所以我们用 MVCC + 锁的混合方案。DDIA第八章讨论的各种隔离级别和并发控制机制，在工程实践中的落地，本质上就是在回答一个问题：你的应用能接受多大的并发冲突？

如果你能接受「偶尔的版本冲突→重试」，那乐观锁是答案。
如果你需要「强一致、零冲突」但能接受排队，那悲观锁是答案。
如果你不想排队也不想冲突，那就需要「没有事务」——把系统设计成幂等的、可补偿的，用最终一致性代替强一致性。

这和SyncTask引擎的 afterExecute 编排决策是一脉相承的：不要用一个中心节点去控制所有流程，让每个节点独立决策、独立执行，用异步事件串起整个链路。这是一种从「强一致命令式」到「最终一致响应式」的思维转变。

写在最后

回到开头那个「所有东西包在一个事务里」的代码。

它不是写得不对——它在学校作业和Demo项目里完全正确。但当数据量变成130万日订单、QPS变成8000、表里有几千万行数据，这个「正确」就变成了「灾难」。

写了7年业务代码，我越来越觉得：事务的正确使用，不是看你用了什么注解、开了什么隔离级别，而是看你的事务边界画在哪里。

边界画得对——事务短小精悍、锁持有时间以毫秒计、RPC和MQ在外面——你的系统就像流水线上的工人，每个人只拿自己需要的零件，做完立刻放回去。

边界画得不对——事务包山包海、锁持有5分钟、加了各种超时重试——你的系统就像一个把所有工具都抱在怀里不让别人碰的工人，所有人都在等他放下来。

事务不是万能的。使用事务的第一条准则，就是知道什么时候不该用事务。
