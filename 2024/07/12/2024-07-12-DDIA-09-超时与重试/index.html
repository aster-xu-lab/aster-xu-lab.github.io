DDIA-09-超时与重试：如何设计一个不会雪崩的重试策略

引言

2024年双十一大促，凌晨刚过零点，我们团队接到告警：订单创建接口RT从80ms飙升至12秒，大量超时。令人意外的是，下游核心服务CPU其实只有40%，数据库连接池也远未打满——真正的原因是某个不设防的重试逻辑快速放大了流量，把系统推下了悬崖。

这个问题把我拉回了DDIA第9章的开篇句，Martin Kleppmann用一句话点破了真相：

“分布式系统的很多问题，根本原因都是不可靠的网络”

网络不可靠，所以我们需要超时和重试。但重试本身又可能成为新的风险源头。怎么破？这就是本文要探讨的核心问题。

01 超时的两难：快刀斩不了乱麻

超时是分布式系统里最基础的防御手段。无非一句话：等太久了就别等了。但设多少合适？

阈值设得太短——误杀。 比如某接口P99延迟是200ms，你把超时设在100ms，那么所有超过100ms的正常请求全被当做失败，然后触发重试逻辑，请求量翻倍。

阈值设得太长——资源浪费。 超时3000ms，下游已经挂了的服务，你还要等上3秒才释放连接。在高并发下，这几秒钟的连接堆积足以打满连接池，让其他正常请求无连接可用。

更隐蔽的问题是：超时不只是客户端的事。请求发出去之后，其实经过了DNS解析、建立TCP连接、TLS握手、发送请求字节、等待响应、接收响应——这其中任何阶段都可能卡住。如果你用的是JDK原生的URLConnection，只设一个read timeout是不够的，connect timeout同样重要。

一个典型的反例：某支付回调接口只设了read timeout=5s，但没设connect timeout。当对方服务器防火墙把SYN包直接丢弃（不回复RST），TCP连接会一直卡在SYN_SENT状态，直到操作系统层面的tcp_syn_retries耗尽，那可能是几分钟后的事。

实战建议：

  • 参考P99/P999延迟，设超时为P99的1.5~2倍
  • 同时配置connect timeout和read timeout
  • 对不同的下游服务设不同的超时，不要一刀切

02 重试的三重风险：你以为的安全网其实是加速器

重试是最直观的容错手段——调用失败了，再试一次。但直觉往往是错的。

2.1 放大效应

最简单的模型：一个请求进到网关，网关调用服务A，服务A调用服务B，服务B调用服务C。每层都设了重试3次。

  • 如果服务C偶尔挂掉一次，服务B重试3次 = 流量3x
  • 服务A收到到这3次请求，可能也会触发重试 = 流量9x
  • 网关看到这9次失败的请求，重试 = 流量27x

一个请求在最坏情况下被放大27倍。如果原本系统有10%的余量，瞬间就打到了270%。

如果系统中还有多层嵌套调用和多个下游服务相互重试，流量放大的比例还会更高。这被称为重试放大风暴（Retry Storm）。

2.2 雪崩加速

打个比方：一个商场只有一个收银台，平时客人很少，一切正常。突然来了100个客人排队，收银员已经很吃力了。这时候队伍里有人等得不耐烦，跑回去重新排队（重试）。结果队伍更长，更多人等不住也跑去重试。最后整个队列崩溃。

分布式系统同理。当下游已经开始出现延迟飙高时，重试等于向已经饱和的系统注入更多请求，加速崩溃。

核心洞见：重试不能解决容量问题，只能解决偶发性网络抖动。 如果下游是被压垮的，重试只会让它死得更透。

2.3 非幂等操作的重试

假设一个扣库存操作：

第一次调用：服务端扣了库存，但响应在网络层丢失
客户端收到超时 → 重试 → 又扣了一次库存

这就是非幂等操作重试的经典问题。用户只想买1件，被扣了2件。

03 指数退避 + 抖动（Jitter）

这是解决”雷鸣群”（Thundering Herd）问题的经典组合。

3.1 为什么需要退避

假设服务端短时间不可用（比如正在重启），客户端立即重试大概率还是会失败。退避（Backoff）的核心思想是：等一等，给下游一点恢复的时间。

最简单的退避是固定间隔：每次重试等待固定时长。但这样当多个客户端同时重试时，它们的重试节奏完全一致——你等1秒重试，我也等1秒重试，大家一起在1秒的时候把请求砸过来。

指数退避（Exponential Backoff） 每次等待时间翻倍：

  • 第1次重试：等100ms
  • 第2次重试：等200ms
  • 第3次重试：等400ms
  • 第n次重试：等100ms × 2^(n-1)

3.2 Jitter：为什么必须加随机

指数退避解决了等待时间的问题，但没有解决”多个客户端重试节奏同步”的问题。

假如100个客户端同时遇到故障，都从第1次重试开始，那它们的第1、2、3次重试时间完全重合，依然会产生瞬间的流量尖峰。这就是雷鸣群效应——所有客户端在同一时刻发起重试，像雷电同时劈下。

加Jitter（抖动/随机延迟） 之后：

每个客户端的重试时间被打散，流量被”抹平”成一个均匀的流，而不是周期性的尖峰。

AWS的架构博客里有一张著名的图，展示了有无Jitter对重试流量形态的影响：没有Jitter，重试流量是一个个等高的尖峰；加了Jitter，流量变成一条平滑的曲线。

3.3 实现参考

关键点：

  • 指数部分要封顶，不然第10次重试的等待时间可能是几十秒
  • Jitter的范围建议设置在退避时间的50%左右
  • 设置最大重试次数（比如3次），超过后直接失败

04 断路器（Circuit Breaker）

退避+重试解决的是瞬时故障。但如果下游服务挂了，重启需要5分钟，你还继续重试，那重试到最后也只是等超时，白白浪费资源。

这时候需要断路器（Circuit Breaker）。

4.1 三种状态

断路器有三种状态：

关闭（Closed）：正常状态。请求直通下游，同时统计成功/失败次数。当失败率超过阈值，跳转到打开状态。

打开（Open）：熔断状态。请求不发给下游，直接快速失败（fail-fast）。同时启动一个定时器。

半开（Half-Open）：定时器到期后，允许少量请求通过，探测下游是否恢复。如果这些请求成功，切回关闭；如果失败，重新打开。

4.2 阈值设计

这不是一个拍脑袋的数字。常用的组合：

  • 滑动窗口：统计最近N个请求的成功率（而非绝对次数），比如最近100个请求中失败超过50%
  • 最小请求数：窗口内至少要有一定量的请求才计算失败率，避免启动之初几个失败就触发熔断
  • 熔断时长：打开状态持续多久？建议30~60秒
  • 半开请求数：半开时放多少请求去探测

一个典型的配置组合：滑动窗口10s，最小请求数20，失败率阈值50%，熔断时长30s，半开请求数3。

4.3 断路器 ≠ 解决一切

  • 断路器解决的是”下游短时间不可用”的问题。如果下游是容量不足导致的持续高延迟，断路器打开会直接拒绝大量请求，这不是断路器的错，是容量规划的问题
  • 断路器打开会导致部分请求快速失败，这可能比”等超时”体验更差——需要上层业务做对应处理（降级、兜底）
  • 断路器状态切换要打日志，最好带上触发原因的上下文

05 幂等的重要性

没有幂等，就没有安全的重试。

即便你在应用层不去主动重试，网络层的TCP重传、客户端的双击、消息队列的at-least-once投递，都可能导致”同一个操作被执行多次”。

5.1 幂等的几种实现方式

唯一约束（数据库层面）

最简单也是最可靠的方式。比如订单号作为唯一键，插入第二次时直接报唯一键冲突，业务层捕获后查询已有结果返回。

幂等Token

客户端在发起请求前先获取一个Token，请求时带上Token。服务端检查Token是否已被使用。

服务端将Token+处理结果存入Redis/数据库，设置合理过期时间。重试请求带上同样的Token，直接返回缓存的第一次处理结果。

版本号（乐观锁）

第二次执行时版本号不匹配，affected rows = 0，业务层判断为”已被处理”。

数据库幂等表

整个处理逻辑放在事务中：先插入幂等记录（唯一键），再执行业务逻辑。如果insert报唯一冲突，说明已经处理过。

5.2 幂等Key的设计原则

  • Key必须有业务含义：不能是random UUID。订单用订单号，支付用支付流水号
  • Key的作用域要清晰：全局唯一还是用户维度？
  • 幂等记录的TTL：不能无限保留，建议7~30天
  • 幂等≠缓存：幂等返回的是”第一次处理的结果”，不一定等于当前的业务状态

06 实战：SyncTask引擎的超时控制演进

6.1 SyncTask引擎简介

SyncTask（驿传引擎）是我们团队自研的异步任务调度框架，用于支撑电商中台里大量需要跨系统数据同步的场景——订单同步到WMS、库存同步到OMS、会员数据同步到CRM——日均执行数百万次任务调度。

引擎基于线程池实现，每个任务提交到线程池后异步执行。

6.2 V1版本的痛点：无超时控制

V1版本最简单的设计：

没有超时。没有超时意味着什么？

真实故障案例：某次上游接口变更，一个数据同步任务里的HTTP调用对方新接口时，对方服务端不响应也不关闭连接，调用方永远卡在read()上。线程池核心线程全部卡死，后续所有任务排队积压。监控显示线程池繁忙，但CPU使用率接近0——所有线程都在等IO。

只能重启。

V1的核心缺陷：

  1. 无任务级超时：单个任务卡死会永久占用线程
  2. 无法感知任务状态：不知道哪些任务在正常运行，哪些卡住了
  3. 重启是唯一的恢复手段

V2的核心改造是引入CompletableFuture：

orTimeout是Java 9引入的，超时后自动以TimeoutException完成Future。无需再手动管理Timer或ScheduledExecutorService。

维度 V1 V2
任务超时 无 CompletableFuture.orTimeout
卡死线程恢复 需要重启 超时后自动释放线程
线程池满处理 无限排队 拒绝策略 + 队列容量限制
可观测性 黑盒 afterExecute记录执行时间/超时/异常
优雅关闭 无法 shutdown + awaitTermination + 超时强制关闭

6.5 排队超时

一个容易被忽略的细节。任务提交到线程池时，如果核心线程都在忙，任务会进入等待队列。如果队列满了，触发拒绝策略。

07 回看DDIA：超时是不可靠网络的对策

DDIA第9章的标题是”一致性与共识”，但开篇大量篇幅在讲分布式系统里的网络问题。

Martin Kleppmann的核心论点可以归纳为：

  1. 网络是不可靠的——你以为的”请求发出去了”可能是”请求消失了”
  2. 超时是应对不可靠网络的第一道防线——你不能无限等
  3. 但超时本身引入了新的不确定性——你不知道超时的时候下游到底执没执行
  4. 所以需要幂等——让”不确定执没执行”变成”执行多次也没关系”
  5. 进一步需要分布式共识——当多个系统都要达成一致时，仅仅幂等是不够的

我们的实践和DDIA的理论形成了闭环：

  • 超时控制（CompletableFuture.orTimeout）→ DDIA的”超时是必要之恶”
  • 重试+退避+Jitter → DDIA的”雷鸣群”问题的工程解法
  • 断路器 → DDIA没有专门讲但工程上同样关键——防止对不可用的下游持续重试
  • 幂等设计 → DDIA提到的”精确一次语义”的工程实现基础

DDIA教给我们的是原理——“为什么要这么做”。而SyncTask V1到V2的演进，则说明了”不这么做会发生什么”。

08 总结：一个百战不殆的重试策略

从头梳理一个安全的重试策略应该包含哪些要素：

1. 超时配置

  • 读超时+连接超时
  • 基于P99/P999动态调整
  • 不同下游不同超时

2. 重试条件

  • 只重试可重试的错误（网络超时、连接拒绝、5xx部分状态码）
  • 不重试4xx（除非429）
  • 非幂等操作默认不重试

3. 退避策略

  • 指数退避+Jitter
  • 最大退避时间封顶
  • 最大重试次数限制

4. 断路器

  • 滑动窗口统计失败率
  • 最小请求数避免误触发
  • 半开探测

5. 幂等

  • 唯一约束 / 幂等Token / 版本号
  • 幂等Key有业务含义
  • 设置合理TTL

6. 监控告警

  • 重试率
  • 断路器状态变化
  • 任务排队时长

如果要从这六条里挑一个最容易被忽视但后果最严重的，一定是幂等。

再完善的退避算法，再精妙的断路器设计，如果没有幂等做底，重试策略就是一座建在沙地上的城堡。
