DDIA-06-多主复制与无主复制：CAP定理的博弈现场

前言

上一篇文章我们聊了单主复制的实现细节——一个 Leader 负责所有写入，若干 Follower 异步追赶日志。这是绝大多数关系型数据库的默认模式，简单、可靠、符合直觉。

但现实世界的需求远比”一主多从”复杂。如果你的用户分布在全球，纽约和东京的同事需要同时编辑同一份文档怎么办？如果你不想承受主从切换的中断时间怎么办？如果你的数据库挂了一台节点，另几台还在跑，但数据不完整，该不该让它继续对外服务？

这些问题，单主复制回答不了。它们属于多主复制和无主复制的领地——也是 CAP 定理真正拳拳到肉的博弈现场。

这一篇，我会从多主复制的冲突地狱讲起，穿过无主复制的 Quorum 修复机制，最后回到电商场景，看看为什么订单选了单主，购物车可以多主，而 SyncTask 的任务状态存储明明无主复制就够用，却还是用了 MySQL。

一、多主复制：多个 Leader 的美丽与危险

1.1 为什么要多个 Leader

单主复制最大的痛点，不是性能，是可用性。一旦 Leader 宕机，写入就被阻塞，直到选出一个新 Leader。这个切换过程即使优化到极致（比如 Raft 的 Leader 选举在亚秒级完成），也有一个不可避免的停顿窗口。

多主复制（Multi-Leader Replication）的设计意图很直接：每个节点都可以接受写入，写入后异步同步到其他节点。客户端写到最近的数据中心，延迟低；一个数据中心挂了，其他照常写入，可用性高。

典型场景：

  • 多数据中心部署：每个数据中心有自己的 Leader，区域内写入延迟低，跨数据中心异步同步。
  • 离线客户端：比如协作编辑工具（Google Docs 的早期架构思路），用户在本地先改，网络恢复后再同步。
  • 审计/日志类系统：写入天然隔离、极少冲突的场景。

听起来很美，但代价是什么呢？

1.2 冲突：多主复制的阿喀琉斯之踵

两个 Leader 同时接受写入，同一个 key 被改成不同的值——这个矛盾不解决，多主复制就是一场灾难。DDIA 给出了几种策略，我用一个实际例子串起来。

场景：用户 Alice 在全球有两个数据中心（北京和法兰克福），她在两地各改了一次昵称。北京数据中心把昵称改成了”AliceBJ”，法兰克福改成了”AliceEU”。两个 Leader 都接受了写入，然后各自向对方同步。到了对方眼里：同一个 key(user:alice:nickname)，两个不同的新值，谁对？

最后写入胜出（LWW）

最简单粗暴的方案：谁的写入时间戳更大，谁赢。

问题在于，分布式系统中没有全局一致的时钟。NTP 同步有误差，几十毫秒的偏差就可能导致”先写入的反而被认为是后写入的”。更糟的是，LWW 会静默丢弃数据——被覆盖的那个值永久消失，且没有任何异常提示。对于一个计数器类字段（比如库存），LWW 是灾难性的：扣了两次库存，数据库里可能只体现一次。

LWW 适合的场景极其有限：写入天然幂等、数据是覆盖式语义，比如缓存、用户头像图片URL。DDIA 的原话是：”LWW is the only conflict resolution method supported by many replicated databases, because it is simple to implement. Unfortunately, it is also quite prone to data loss.”

版本向量（Version Vectors）

更精细的方案是用版本向量追踪每个 key 的因果依赖关系。

继续刚才的例子：初始版本是 [A:1]（节点A写入一次）。北京写入后变成 [A:2]，法兰克福写入后变成 [B:1]（假设B是法兰克福的副本）。两个版本向量没有因果关系——既不是 [A:2] 比 [B:1] 新，也不是反过来。系统检测到并发冲突。

这时候怎么办？把冲突抛给上层处理。

  • 应用层合并：DynamoDB、Riak 的做法，冲突写入时保留多个值（兄弟值/siblings），读的时候一起返回，由客户端决定怎么合并。购物车场景特别适合——两个客户端加了不同商品，合并就是取并集。
  • CRDT（Conflict-free Replicated Data Types）：把数据结构的数学性质利用起来，让它们一定可以无冲突合并。比如一个计数器，不用 set 语义（count=5），而用 increment 语义（+1, -1），合并时把所有操作的 effect 加起来——加法交换律保证了无论什么顺序合并，最终结果一致。

冲突避免

最聪明的策略可能是不产生冲突。如果能把同一个用户的所有写入都路由到同一个数据中心，那么针对该用户的写入就不存在跨数据中心冲突。这个策略叫”sticky session”或”读写一致性保证”，很多全球部署的系统（如钉钉/飞书的会话服务）就靠它避免了复杂的多主冲突检测。

但它的前提是用户粒度足够细、数据中心间流量可以按用户稳定路由。一旦一个数据中心挂掉需要流量切换，冲突还是会发生。

二、无主复制：Dynamo 的遗产

2.1 没有 Leader，人人平等

2007年，Amazon 发了那篇著名的 Dynamo 论文，提出了无主复制（Leaderless Replication）模型。核心思想极简：客户端把写入发给所有副本（或一个协调者代发），不用区分 Leader 和 Follower。任何副本都可以被读、被写。

这个设计哲学来自 Amazon 的电商需求：购物车服务在黑五高峰期必须可写——哪怕部分节点挂了，大部分节点扛着让用户下单，一致性差一点可以容忍，但不能不可用。

2.2 Quorum 读写：W + R > N

无主复制的核心机制是 Quorum。假设你有 3 个副本（N=3）：

  • 写入时至少等待 W=2 个副本确认，认为写入成功。
  • 读取时至少读 R=2 个副本，从最新值中取结果。

只要 W + R > N，读操作就一定能碰到最新的写入——因为写入的 W 个节点和读取的 R 个节点必有交集。

这给了运维一个调节旋钮：

配置 (N=3) W R 特性
读写强一致 2 2 W+R=4>3，单节点故障不影响，一致性与延迟平衡
写快读慢 2 1 写入需等2个节点，读任意1个即可，可能读到旧值
读快写慢 1 3 写入只等1个节点就返回，读要读3个取最新
纯写优化 1 1 极致低延迟，但可能读写都错开，一致性无保障

灵活的代价是：客户端需要自己处理版本冲突。

2.3 读写修复：让系统自愈

无主系统里，节点挂了又回来、写入漏了某几台——这些都是常态。两种修复机制并行运转：

读修复（Read Repair）：客户端读取时，发现有的副本返回旧版本，就把新版本写回到旧版本的节点上。读得多，修得快。

反熵过程（Anti-Entropy）：后台进程持续对各节点做 Merkle 树比较，发现不一致就把数据推齐。不管你读不读，数据最终会一致。

一个是请求驱动的”随手修”，一个是后台的”系统性修”，两者互补。

2.4 Sloppy Quorum：当 N 变了

正常情况，写入发到固定的 N 个节点。但某些节点宕机了怎么办？

Dynamo 的设计很极端：临时找 N 个健康节点接收写入，标记为”hinted handoff”——代理节点暂存数据，等原节点恢复后再传回去。这叫 Sloppy Quorum（宽松法定人数）。

它不是真正的 Quorum——写入的节点和读的时候可能完全没有交集。Sloppy Quorum 保证的是持久性（写入不被丢），不是一致性。但它换来的是极高的写入可用性：只要还有 N 个节点活着，写入就能成功。

三、CAP 定理：P 到底是什么意思

3.1 不选 P 的代价

CAP 定理被传得太多，也误解最多。很多人都说”分布式系统 P 是必然的，只能选 C 或 A”。这话对，但没说出关键。

P（Partition Tolerance）是指网络分区时系统仍能继续运行。它不是”要不要 P”，而是”当网络分区发生了，你选择牺牲什么”。如果分区不发生，你可以同时拥有 C 和 A。分区是触发器。

问题的本质是：当节点之间无法通信时，你是拒绝写入（保持一致性），还是接受写入（保持可用性）？

不选 P 的意思其实是：当发生分区时，你选择停止服务。MySQL 单主复制在 Leader 宕机时的行为就是这样——写入被阻塞，直到选举完成。这对于订单系统是对的：宁可短暂不可用，也不能丢掉一笔扣款或重复创建订单。

选 A 的意思就是：即使分区，每个分区内的节点继续独立接受写入。购物车就是这样——你宁可用户加了两件商品最后合并多出一件（删掉就行），也不能让用户在黑五高峰期点不动”添加到购物车”按钮。

3.2 不是二分法，是连续谱

实际上，哪有什么”完全选C”或”完全选A”。现实是一个连续的权衡光谱：

金融行业选强一致，因为一块钱都不能错。订单支付选”读自己写入”的一致性保证（read-your-writes），用户付完钱必须看到最新状态。社交媒体时间线选因果一致——你评论了必然在帖子上显示，但可能比回复晚几秒。浏览历史选最终一致，你昨天看过的商品今天看少那么一条，没人在意。

无主复制和多主复制适合光谱右侧的场景。单主复制处于左侧。

四、实战：为什么电商订单不能学 Dynamo

4.1 订单：单主复制的必然选择

假设我们把电商订单放到 Dynamo 风格的无主集群里，用 W+R>N 保证”最终一致”：

  • 用户 A 下单买了一个库存只剩 1 件的商品。
  • 写入发到了节点 X 和 Y（W=2），确认成功。
  • 用户 B 几乎同时下单同一商品，写入发到了节点 Y 和 Z（也是 W=2）。
  • 两个写入都认为库存还有，都确认成功。

这是经典的”超卖”问题。在分布式环境下，这本质上是并发写入冲突，而不是单纯的 SQL 查询问题。锁、事务、串行化——这些需要强一致的单点决策，在无主复制里做起来不是完全不可能，但极其复杂且性能差。

更重要的是业务逻辑的验证成本。订单不仅仅是一个 CRUD，它涉及：库存检查、价格校验、优惠券核销、风控拦截。每一步都可能因为一个”最终一致性延迟”而判断失误。在无主模式下，你需要处理”写入时看到的库存是最新的吗？”这个元问题，它把业务复杂度抬高了一个数量级。

所以 MySQL 的单主复制 + 行锁 + 事务，成了订单系统的标准答案。代价是可用性——Leader 挂了写入就停，但我们选择了”宁可停写也不写错”。可用性靠别的机制补（MHA/Orchestrator 自动切换 + 同城双活）。

4.2 购物车：多主/无主的天然优配

购物车的语义完全不同：

  • 多个客户端并发加商品 → 取并集就行，合并成本极低。
  • 数据丢失可接受——用户发现少了一个商品，”再加一次”比”多扣一笔钱”风险小得多。
  • 写入可用性优先——黑五高峰期，加购不能因为一个机房故障卡顿。

这就是 Dynamo 的原始场景。Redis Cluster（多主分片）和 Cassandra（无主）都是购物车的合理选择。Redis 用 hash slot 把购物车按用户分片，每个 slot 单主写入天然避免冲突；Cassandra 用 LWW + TTL 做最终一致，丢弃旧版本也不痛不痒。

4.3 浏览历史：最终一致的完美案例

用户浏览了什么商品，幂等写入就行。丢了几条不会投诉，多了几条更好（反正用户不在乎）。场景完美适配 Dynamo 风格——无主复制 + 读修复，用一个 Cassandra/Riak 集群就解决了。甚至可以用 Redis 的 SortedSet 做最近浏览，E9x 可用性就够了，不用 99.99%。

五、SyncTask：为什么明知无主复制够用，还是选了 MySQL

讲一个我自己的案例。

SyncTask 是电商中台的任务调度引擎，有一个表叫 sync_task_execution，存储每次任务执行的当前状态。这个表的使用模式非常特殊：

  • 只写一次：任务执行过程中状态从 PENDING → RUNNING → SUCCESS/FAILED，但每一次状态变更都记录在独立的事件行里，而不是原地更新。
  • Append-Only：本质是事件日志，新状态追加新行，不修改旧行。
  • 写入频率不高：峰值时每分钟几千条，不是高并发写场景。

按 CAP 的光谱分析，这个表的一致性要求极低：不存在并发写冲突（每次任务执行只有一个调度器线程在更新），读的时候取”最新一条”就行，稍有延迟也能接受。从纯技术角度，无主复制 + Quorum 读写完全够用，甚至更配——更好写入可用性，自治修复，不需要关心 Leader 选举。

但我们还是用了 MySQL 单主。原因不在技术，在生态：

5.1 运维统一性

整个中台的技术栈是 Spring Boot + MyBatis + MySQL。线上巡检、慢SQL监控、数据备份恢复、迁移工具链——全是围绕 MySQL 构建的。引入 Cassandra 意味着要养一套新的监控、告警、备份体系，运维成本远超单主复制的”痛点”。

5.2 团队学习成本

团队成员对 MySQL 的调优、索引设计、慢查询分析非常熟练。引入无主复制，要培训所有人理解 Quorum 读写、反熵修复、Hinted Handoff 的副作用。招聘时也需要加一个技术栈要求，过滤掉很多优秀候选人。这笔隐形成本比技术上的”不够优雅”更致命。

5.3 数据关联查询

sync_task_execution 的状态经常要和任务定义表、调度记录表做 JOIN 查询。MySQL 的 SQL 能力让这些关联查询在几十毫秒内完成。如果状态存在 Cassandra，要么反范式化把数据冗余进去，要么在应用层做两次查询再拼接——不管是哪种，都是对开发体验的降级。

5.4 够用原则

最终促使我拍板的，是一个简单的计算：

  • MySQL 单主复制的写入瓶颈大约在 2000-5000 TPS（取决于事务大小）。
  • SyncTask 的峰值写入约 10 TPS。
  • 即使业务增长 100 倍，MySQL 也绰绰有余。

在瓶颈到来之前，不引入不必要的复杂度——这是我 7 年中学到的最重要的一条架构原则。DDIA 的价值不是让你用遍每一种技术，而是让你清楚地知道每一种选择的边界在哪里，然后在边界内找到最务实的方案。

六、总结：怎么选，才不后悔

三种复制模式的决策框架，可以归纳为一张两轴图：

冲突概率低 冲突概率高
可用性优先 无主复制（Dynamo/Cassandra） 多主复制 + 应用层冲突解决（CRDT）
一致性优先 单主复制（MySQL/PostgreSQL） 单主 + 串行化事务（Spanner/CockroachDB）

几点我自己的实战心得：

  1. 先问”写错了会怎样”。订单扣款错了要退款、要客服、要客诉，成本巨大——选强一致。购物车多一件商品删掉就是——选最终一致。这不是技术问题，是业务风险评估。

  2. 可用性的缺陷比一致性的缺陷更难发现。一致性问题你会立刻看到（用户投诉数据不对），可用性问题可能发生在半夜 3 点你不在的时候。但可用性缺陷的代价可能是整站宕机——所以金融系统宁可选 C，社交系统宁可选 A。

  3. LWW 是最后的选择，不是第一选择。除非你明确知道你的数据是覆盖式语义（缓存、配置、最新状态），否则不要指望”时间戳大者胜”能正确。

  4. MySQL 生态的力量远超技术特性。很多架构选型不是选”最好的技术”，而是选”对我们团队最好的技术”。MySQL 的单主复制不完美，但它的运维成熟度、团队熟练度、工具链完整性，构成了巨大的惯性——这个惯性本身也是一种架构资产。
