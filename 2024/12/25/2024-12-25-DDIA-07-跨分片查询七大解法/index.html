DDIA-07-跨分片查询的七大解法：从分页到聚合

引言

当单表数据量突破千万级，分库分表几乎是所有中台系统的必经之路。在一个日订单130万的电商中台里，订单表按 user_id 做了 64 分片，单库单表可以扛住日常写入。但有一天，运营提了一个需求：”商家后台里，按商家ID查订单列表，还要支持按金额排序和分页。”——你盯着代码，发现 merchant_id 并不是分片键。

这就是跨分片查询的起点。DDIA第6章花了大量篇幅讨论分区（partitioning）与二级索引的关系，我结合自己的实战经验，把跨分片查询的七大解法、分页陷阱、COUNT误区完整梳理出来。

一、跨分片查询的本质困境

在分库分表架构中，数据路由的关键是分片键。一条 SQL 带上分片键，中间件能精确定位到目标分片；不带上分片键，就需要”广播”到所有分片，再把结果聚合。广播查询的代价随分片数线性增长——64个分片就需要查64次。

但业务查询的维度往往是多维的：买家端按 user_id 查订单是天然的分片键命中；商家端按 merchant_id 查、运营后台按 order_status 查、财务按 payment_time 对账——这些查询全都会变成广播。

本质上，这是一个”用写入冗余换查询效率”还是”用查询开销忍耐多维度访问”的权衡。下面七种解法，就是从不同角度对这个权衡的回答。

二、跨分片查询的七大解法

解法1：分片键查询

最基础也最优先考虑的方式。设计分片键时，把最高频的查询维度作为分片键，让核心链路不需要跨片。

以订单系统为例：买家端的”我的订单”是C端最高频场景，所以 user_id 作为分片键是合理的。所有买家查询订单的链路——列表、详情、物流查询——都不需要跨片，性能最优。

局限：它只能覆盖一个维度的查询。当出现第二个高频查询维度（如商家端按 merchant_id 查），就必须引入其他方案。

解法2：异构索引表

这是我在项目中用得最多的方案。核心思路是：维护一张独立的映射表，以非分片键维度为分片键，值只存目标分片键。查映射表先定位到目标分片键集合，再去业务表精确查询。

  2. 数据一致性：写入时，订单表 + 索引表的写入要在同一个事务内，或者至少用最终一致性（MQ异步补偿 + 对账任务）。我偏好”先写订单表，再异步写索引表，人工/自动对账兜底”。

  3. 索引表膨胀控制：索引表本身也是分片的，数据量和主表等量级，所以存储成本翻倍。如果业务上允许多个索引维度，每条订单需要维护 N 张索引表，这时候就要权衡——到底是索引表比搜索引擎方案更省心。

适用场景：非分片键维度的精确查询或简单排序+分页。不适合复杂的全文搜索。

解法3：冗余存储

更激进的做法：同一份数据，按不同分片键各存一份完整的副本。

写入时双写两份，查询时各取所需。DDIA 中称为”基于文档分区的二级索引”的反向操作——每个分区维护自己的本地索引，而这里是每个维度维护自己的全量数据。

优点：查询逻辑简洁，不需要两步走，直接单表查。缺点：存储翻倍、写入RT增加、一致性更难保证。一般只在”两种查询维度同等高频且对一致性容忍度较高”的场景使用。我在项目中使用较少，更多用异构索引表。

解法4：搜索引擎

把数据的搜索职责从关系型数据库剥离出去，交给ES/Solr。写入时同步到搜索引擎，所有多维度查询走搜索引擎，ES返回主键ID再回数据库取全量。

优势：搜索引擎天然支持多维度过滤、全文搜索、聚合分析，比MySQL更专业。代价：增加了一个重量级组件，数据同步的延迟和一致性是独立的挑战。需要MQ同步链路（Canal + Kafka → ES）、对账脚本、数据修复工具。

在130万日订单的规模下，我选择异构索引表覆盖核心业务查询，ES覆盖运营后台和报表类查询。异构索引表保障核心链路的实时一致，ES承载灵活的多条件筛选。

解法5：分布式查询引擎

Presto/Trino 这类引擎的核心能力是跨数据源联邦查询。它们在数据分析场景很有价值——BI报表可能需要关联MySQL订单表和Hive日志表，这时交给Trino做跨源JOIN。

但在在线业务中使用需要慎重：Trino的设计目标是交互式分析（秒级），不是OLTP（毫秒级）。用户打开App等3秒查一次订单列表是不可接受的。我见过有人拿Trino做分页——Query下发到所有Worker，结果集汇总到Coordinator，数据量一大很容易OOM。把它用在离线报表、数据探索、对账批量跑批，是正确姿势。

解法7：全局二级索引（NewSQL）

TiDB、OceanBase、CockroachDB 这类 NewSQL 数据库，在分片的基础上原生支持全局二级索引。不需要像解法2~4那样在应用层手动维护。

索引数据本身也会被分片存储，但查询时数据库自动完成跨分片的索引查找和数据回表。这是最理想的方案，前提是你用的就是NewSQL。对于已经跑在MySQL分库分表上的存量系统，迁移成本太高，不现实。

三、分页问题：跨分片查询的经典陷阱

全局offset分页为什么错

假设订单表128个分片，按时间排序，每页20条，要第100页（offset=2000）。如果每个分片单查 LIMIT 2000, 20，应用层只能拿到 128×20=2560 条数据中排序取前20条——第100页的数据大概率散落在某些分片的深处，其他分片的第100页结果根本不在全局第100页中。

正确的全局分页，需要每个分片取 OFFSET 0 LIMIT (offset + pageSize)，即每个分片都取前2020条，应用层汇总128×2020=258560条数据，排序后取第2000~2020条。数据量一上来就崩。

三种分页方案

方案一：游标分页（推荐）

改为基于游标的”下一页”模式，彻底放弃 offset。每次传上一页最后一条的排序字段值，数据库只需从那个位置往后取，不需要 offset 跳过。前端UI改为”加载更多”或无限滚动。

局限：不支持跳页（直接跳到第N页），只能一页一页往下翻。对于绝大多数用户，跳页是伪需求——谁买东西翻到第100页去？但对于运营后台，跳页可能是真的需要，这时要结合ES或限制最大页数。

方案二：ES的from+size（限制深度）

ES默认限制 from + size <= 10000，这是ES在分布式场景下对深分页的保护。可以适当放宽但必须有上限。ES的search_after（游标）也支持。

方案三：直接禁止深分页

简单粗暴但有效。给运营提供更精确的筛选条件（时间范围、状态过滤），而不是让他们翻到第50页。

跨分片 COUNT 有一个容易踩的坑。直观写法：

如果数据在各分片是互斥的（以 user_id 分片，按 user_id 过滤），这种写法没有问题——每个 user_id 只在一个分片中，count+sum 等价于全局COUNT。

但如果某个 user_id 的订单可能横跨多个分片（这本身就是设计错误），或者做 COUNT DISTINCT（如按商家统计去重买家数），sum(distinct_count_per_shard) 就是错的——同一个买家可能在两个分片各出现一次。

实践建议：

  1. 普通的COUNT(*)，如果数据互斥（分片键命中），直接 sum 各分片结果是正确的。
  2. COUNT DISTINCT，除非能保证去重键就是分片键或者与分片键一一对应（如 user_id 分片的表 COUNT DISTINCT user_id），否则必须拉回数据到应用层去重，或者交给ES/HyperLogLog（近似去重）。
  3. 大表的全局 COUNT 本身就是昂贵的操作，优先考虑异步计算（定时任务更新统计表，或者用ES的基数聚合）。

五、实战推演：订单列表查询

最后用一个完整的场景串联上面的方案。

场景设定

  • 订单表 64 个分片，分片键 user_id
  • 买家端（C端）：按 user_id 查自己的订单列表，需要排序+分页
  • 商家端（B端）：按 merchant_id 查自家所有订单，需要排序+分页+按状态筛选
  • 日订单量：130万

买家端方案：分片键查询（解法1）

买家端的所有查询都带 user_id，命中分片键。直接走单分片查询，无需跨片。

B端C端共享一份订单数据，买家场景天然最优。这就是分片键选型的意义——让最高频场景零额外成本。

商家端方案：异构索引表（解法2）

商家端的查询维度是 merchant_id，与分片键不同。

方案评估：

  • 解法6（Scatter-Gather）：64分片广播，每个商家请求都广播64次，RT超过500ms，不可接受。
  • 解法4（ES）：可以做，但需要额外维护MQ同步链路，核心竞争力链路不希望依赖外部组件的一致性问题。
  • 解法3（冗余存储）：存储翻倍，写入链路复杂。
  • 解法2（异构索引表）：索引表按 merchant_id 分片；写入异步同步但核心链路闭环；索引表只存关键字段。

六、选择决策矩阵

场景 推荐方案 理由
C端高频查询，能命中分片键 解法1：分片键查询 零额外成本，天然最优
B端高频查询，非分片键但维度固定 解法2：异构索引表 索引表同类分片，闭环可控
运营后台，多条件组合筛选 解法4：搜索引擎 ES专业做搜索和聚合
分析报表，跨源关联 解法5：分布式查询引擎 Trino/Presto联邦查询
低频后台查询，容忍较高延迟 解法6：Scatter-Gather 最简单兜底方案
有能力迁移到NewSQL 解法7：全局二级索引 最理想的终极方案
双维度同等高频且一致可容忍 解法3：冗余存储 双份存储，各自独立查

没有银弹。一个成熟的系统通常同时使用多种方案：分片键查询兜底高频链路，异构索引表覆盖B端，ES承载灵活搜索，Trino做离线分析。

总结

跨分片查询的本质矛盾是：分区带来了水平扩展能力，却牺牲了多维查询的便利性。我们做的所有事情——异构索引表、搜索引擎同步、Scatter-Gather聚合——都是在”写入冗余”和”查询广播”之间的不同位置找到自己的平衡点。

在130万日订单的系统里，我学到的最重要一课是：不要追求一个完美的统一方案，而是为每个查询场景选择成本最低的策略。C端用分片键命中、B端用异构索引表、运营用ES——这三条链路独立演进，各自治愈，远比一个试图统一所有的”大一统”方案更健壮。

最后留一个思考题：如果你的订单表需要同时支持”按 user_id”、”按 merchant_id”、”按履约仓库”三个维度的查询，你会怎么设计？欢迎在评论区交流。
