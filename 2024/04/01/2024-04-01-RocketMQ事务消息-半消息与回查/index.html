RocketMQ事务消息：半消息与回查，怎么做到"业务成功消息必达"

先抛一个问题：业务成功了，消息却没发出去

订单中台里，一个典型场景是”订单下发下游系统”：先在自己的库里提交订单状态，再发一条 MQ 消息通知下游。

最朴素的做法是”先发消息，再提交业务”，或者反过来”先提交业务，再发消息”。但两种都有漏洞：

  • 先发消息再提交业务：消息发出去，下游立刻来消费，可本地事务还没提交，读到的是”还没落定”的数据，甚至本地事务最后回滚了——消息是幽灵消息；
  • 先提交业务再发消息：业务提交成功了，但发消息那一刻网络抖一下、Broker 没收到，消息就丢了——下游永远不知道这单发生了，漏消息。

这两个方向都在赌：本地事务和发消息这两件事，无法保证原子性。要么都发生，要么都不发生。

RocketMQ 的事务消息就是来解决这个问题的。

二、事务消息：半消息 + 回查

核心思路是”先把消息寄存起来，等本地事务的结果出来再决定放行还是销毁“。完整流程：

几个关键点：

  • 半消息对消费者不可见——避免”消息到了，业务还没提交”的幽灵消息问题；
  • 回查是兜底——靠它解决”Producer 发完半消息挂了，本地事务结果石沉大海”的场景。Broker 主动找 Producer 要答案，所以 Producer 端必须实现一个查本地事务状态的接口（LocalTransactionChecker）；
  • 业务实现方要保证：本地事务成功 ⟺ 发 Commit。如果本地事务提交了但 Commit 消息丢了，靠回查也能补上（回查时查本地事务已提交 → 返回提交）。

这样，业务提交和消息放行被绑定成了原子操作：要么本地事务成功且消息可见，要么都不发生。

一个容易混的点：事务消息是最终一致性——半消息转正的瞬间才可见，中间是”暂存”状态，不是强一致。它跟 Seata 的 TCC（强一致，Try 预留 + Confirm/Cancel）不是一回事。

三、存储架构：事务消息为什么能”先寄存”

事务消息能”先寄存、后转正”，依赖 RocketMQ 的存储设计——消息先落盘，消费可见性另算：

  • 写：所有消息顺序追加进同一个 CommitLog 文件——顺序写盘，这是 RocketMQ 高吞吐的物理地基（和 Kafka 分区顺序写是同一思想，只是 RocketMQ 所有队列共用一个文件）；
  • 读：消费端先查 ConsumeQueue 拿到消息在 CommitLog 里的偏移，再去读真正的内容；
  • 半消息的”不可见”就是不建 ConsumeQueue 索引——消息在 CommitLog 里躺着，但消费端查不到它；Commit 后补建索引，消费者就能看到了。

四、顺序消息：同 key 进同一队列

这跟 Kafka 的分区有序是同一个模型：RocketMQ 的 Queue ≈ Kafka 的 Partition，同 key 哈希进同一队列/分区 + 队列内有序 + 单线程消费。

注意区分全局顺序和分区顺序：全局顺序要整个 topic 只用一个 Queue、一个消费者，代价是完全没有并发；绝大多数业务场景要的是分区顺序（局部有序）——同一个订单内的消息有序，不同订单之间随便并发。

五、订单中台里的落点

这是我简历上 RocketMQ 的真实场景：订单中台管核心交易链路，用事务消息保证”订单下发/回传不丢”。SyncTask 引擎驱动的各种同步任务里，涉及”本地改状态 + 通知下游”的关键路径，就靠这套事务消息 + 可靠投递撑着。

业务提交成功但消息没发出去 = 漏消息，这是交易链路绝不能容忍的——事务消息就是把这条边界堵死。

总结

  • 朴素方案的两个方向都漏：先发消息再提交有幽灵消息，先提交再发消息会漏消息；
  • 事务消息 = 半消息（暂存不可见）→ 执行本地事务 → Commit/Rollback → 宕机则 Broker 回查；
  • 本质是最终一致，跟 TCC 的强一致不同；
  • 存储靠 CommitLog 顺序写 + ConsumeQueue 索引，半消息”不建索引”实现暂存不可见；
  • 顺序消息：同 key 哈希进同一 Queue + 队列内 FIFO + 单线程消费 = 分区有序。
