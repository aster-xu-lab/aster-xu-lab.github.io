消息不丢的三端保障与消费幂等：分布式系统的最后一公里

一条消息从发出到消费，要过三个关口

生产端 → Broker → 消费端。任何一个环节都可能丢消息、重消息。所以”消息可靠性”从来不是一个单点问题，而是三端各自的职责：

环节 主要风险 保障手段
生产端 发出去，Broker 没收（网络抖动/超时） 同步发送 + Confirm 确认 + 重试；本地消息表 / 事务消息
Broker 端 存了但宕机丢（内存没落盘/单副本） 同步刷盘 + 集群多副本（主从）
消费端 消费了没处理完就挂 手动 ack + 失败重试（处理成功才 ack）

三端合起来，才构成”不丢”。只靠任何一端都是空谈。

一、生产端：消息发出去，怎么确认真到了

最简单的确认机制是 Confirm 确认：Producer 发消息后，Broker 落盘成功会回一个确认（ack）；没收到确认就重试。

但 Confirm + 重试还有一个经典缺口：业务提交了，消息却没发出去。这不是网络问题，是”本地事务和发消息”的原子性问题——我在 RocketMQ 事务消息那篇里详细讲过：先发消息再提交有幽灵消息，先提交再发消息会漏消息。

所以生产端真正的强保证是两个方案：

  • 本地消息表：把”要发的消息”和业务操作放在同一个本地事务里落库，再靠一个定时任务扫描消息表去发、发成功标记已发送。业务提交成功 ⟹ 消息一定在表里，最终一定发得出去；
  • 事务消息（RocketMQ）：半消息 + 回查，把”本地事务成功”和”消息可见”绑定成原子操作。

两个方案的本质都一样：把”发消息”这件事纳入一个可回滚、可重试的持久化上下文，而不是依赖一次网络调用成功。

二、Broker 端：存下来，还要扛得住宕机

消息到了 Broker，要保证”存下来且不丢”，两道防线：

  1. 同步刷盘：消息写入后同步落盘，而不是攒一批再刷（异步刷盘丢窗口小但存在）。写入确认必须建立在”真的落盘了”之上；
  2. 多副本：单机存了盘，机器坏了磁盘也带走了。要有主从副本，主挂了从能顶上（RocketMQ 主从、Kafka 分区副本 + ISR）。

这两个分别防”进程/系统崩溃丢内存”和”机器故障丢磁盘”。

三、消费端：处理成功才 ack，是最后的防线

消费端最容易”看似消费了，其实没处理完”：

  • 自动 ack：消费端收到消息就自动确认，万一处理逻辑抛异常，消息已经确认了——丢了；
  • 手动 ack：处理成功才确认，失败就不确认，Broker 会重新投递。

但手动 ack + 重试，带来了下一个问题：消息会重复。

四、重复消费：可靠投递的必然代价

为什么消息会重复？三个源头：

  1. 生产端重试：发消息超时重试，其实第一条 Broker 已经收到了，重复；
  2. 消费端 ack 失败重投：处理成功了，但 ack 在网络里丢了，Broker 以为没成功，重新投递；
  3. 消费端崩溃：处理到一半挂了，没 ack，恢复后重新投。

所以重复消费是分布式投递的常态，不是异常。指望”消息不重复”是错的方向，正确的方向是：让消费端对重复无害——幂等。

五、幂等：消费端的必备能力

幂等的定义：同一个操作执行一次和执行多次，结果一样。实现手段按强度递增：

① 唯一业务 key + 数据库唯一约束

消息带唯一业务 key（订单号/单据号），消费端先查再插，配合 DB 唯一索引兜底：

② Redis setnx：key 不存在才执行，SET key value NX 原子占位。

③ 状态机防重：业务本身有状态流转，重复消息来的时候检查”当前状态是否已经处理过这一步”，是则跳过。这比上面两种更贴合业务——状态本身就是幂等键。

我的 SyncTask 引擎里用的是”分布式锁 + 二次查库“的双重防重：先拿分布式锁保证同一任务不被并发执行，执行前再查一次库确认状态没变。这套设计本质上就是状态机防重 + 锁兜底的组合，和消息消费幂等是同一个思想。

六、死信队列：毒消息的隔离区

重试也救不回来的消息（业务逻辑永远失败、消息格式损坏），不能无限重投卡死队列。达到重试上限后，消息进死信队列（DLQ）：

  • 隔离毒消息：坏消息挪走，不阻塞正常消息消费；
  • 做延迟/补偿：我做过”到期任务进死信队列触发处理”——把到期还没完成的任务通过死信机制捞出来做补偿，其实就是拿死信当延迟队列用。

RabbitMQ 用 x-dead-letter-exchange 配置死信路由，RocketMQ 有重试队列 + 死信 Topic。

七、从 At-Least-Once 到 Exactly-Once

聊到可靠性，绕不开三个投递语义：

  • At-Most-Once（至多一次）：可能丢，不可能重复——最省事，但业务不可接受；
  • At-Least-Once（至少一次）：可能重复，不可能丢——这是 MQ 的默认保证，靠生产端确认 + 消费端手动 ack 实现；
  • Exactly-Once（精确一次）：不丢不重——分布式下没有银弹，实际是 At-Least-Once + 消费端幂等 拼出来的。

结论：不要幻想 MQ 帮你做到精确一次，接受 At-Least-Once，然后消费端自己把幂等做扎实。 幂等是分布式系统的最后一公里。

总结

  • 三端不丢：生产端 Confirm + 重试 / 本地消息表 / 事务消息、Broker 刷盘 + 多副本、消费端手动 ack + 重试；
  • 重复消费是可靠投递的必然产物，正确方向是消费端幂等；
  • 幂等：唯一 key + DB 唯一约束 / Redis setnx / 状态机防重（我 SyncTask 用的双重防重就是这个思想）；
  • 死信队列隔离毒消息，还能当延迟队列做补偿；
  • 分布式下没有 Exactly-Once，实际是 At-Least-Once + 幂等。
