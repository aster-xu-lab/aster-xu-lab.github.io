DDIA-04-列式存储：为什么SELECT *在数仓里是性能杀手

一、一个反直觉的事实：同样的数据，两种存法性能差100倍

假设你有一张订单明细表，50个字段，1亿行数据。两个查询：

查询A是典型的OLTP场景——根据主键精确命中一行，把这一行的所有字段读出来。MySQL的B+Tree聚簇索引干这件事非常高效：一次索引查找，拿到整行数据，结束。在合理的硬件上，耗时通常是毫秒级。

查询B是典型的OLAP场景——扫描大量数据，但只涉及 category_id、amount、create_time 三个字段。如果这张表有50个字段，用MySQL执行查询B时会发生什么？数据库引擎会把50个字段全部从磁盘读到内存，哪怕你只需要3个。 在1亿行的体量下，这个查询跑上几分钟甚至更久是常态。

为什么？因为MySQL的数据是按行组织的。一行的所有字段存储在连续的磁盘页上。当你读一行时，整行都被加载到Buffer Pool。不是你不想只读3个字段——是行式存储的物理布局决定了你做不到。

这就是列式存储存在的根本原因。

二、行存和列存：存储方向的根本分歧

2.1 行式存储（Row-Oriented Storage）

行式存储将同一行的所有列连续存放。下图所示，一行的 order_id、user_id、amount、status、create_time 等字段紧挨着存放在磁盘上：

这种布局对OLTP场景极度友好：

  • 按主键查一行：一次I/O拿到全部需要的数据
  • INSERT/UPDATE/DELETE：只需修改一个数据页上的连续区域
  • 事务：行级锁的最小粒度天然对应物理存储单元

MySQL InnoDB的聚簇索引、PostgreSQL的Heap存储都是行式布局。这就是为什么OLTP数据库对单行操作的性能能做到微秒级——存储布局和访问模式默契匹配。

2.2 列式存储（Column-Oriented Storage）

列式存储将同一列的所有行的值连续存放。同样的订单表，列存的物理布局是这样的：

现在回头看查询B（SELECT category_id, SUM(amount) ...），列存只需要读 category_id 和 amount 两列的数据文件。其他48列全部躺在磁盘上纹丝不动。I/O直接降为原来的 2/50 = 4%。

这才是列存的核心优势：查询只读需要的列，I/O量和查询涉及的列数成正比，和总列数无关。

这也是为什么在数仓里 SELECT * 是大忌：你强迫数据库把所有列都解压读取，完全抵消了列存的设计优势。

三、列式压缩：为什么同一列的数据更容易压

列存的另一个杀手级优势是压缩率。同一列的数据具有相同的类型和相似的值域，压缩算法可以在这个前提下做到极致的压缩比。

3.1 位图编码（Bitmap Encoding）

当列的基数（不同值的数量）非常低时，位图编码是最佳选择。

假设 order_status 只有五个值：待支付、已支付、已发货、已完成、已取消。传统的行存会为每一行存储一个字符串或整数。而位图编码为每个可能的值创建一个位数组（bit array），第i位表示第i行是否等于该值：

查询”所有已完成订单”变成了 已完成 AND (其他过滤条件) 的位运算——这是CPU最喜欢的操作，而且位图在内存中可以做到极高的空间效率。一亿行的 order_status，用位图编码只需要 5 x 1亿 bits = 约60MB。而同样的数据按行存储，即使只用一个 TINYINT（1字节），也要约100MB，压缩后可能更小，但查询时需要遍历每一行做比较，无法利用位运算的SIMD加速。

3.2 游程编码（Run-Length Encoding, RLE）

当一列的值存在大量连续重复时，RLE可以用 (值, 重复次数) 对来表示：

一个典型场景是排序后的 category_id 列。如果你按品类对订单表做了排序（这在列存中很常见——Parquet把排序优化称为row group排序），同一品类的数据会连续排列。RLE可以将存储体积压缩到原来的一个零头。

更极端的情况：一个布尔类型的 is_deleted 列，绝大多数行都是 false。存成RLE只需要 (0, 一亿) ——几个字节搞定。

3.3 字典编码（Dictionary Encoding）

字典编码的思想很朴素：把列中实际出现的所有不同值放在一个字典数组里，然后用指向字典的整数下标替代原始值：

字符串列是字典编码的绝佳场景。product_name 可能有几万个不同商品名，但很多商品名会在多行中重复出现。用字典编码后，原本几十字节的商品名变成了2或4字节的整数下标，再配合RLE或位压缩，压缩比可以达到10:1甚至更高。

3.4 组合使用：Parquet的压缩策略

生产环境中，成熟的列式存储格式会分层组合使用这些算法。Apache Parquet（Spark/Hive/Trino生态的事实标准）的处理流程是：

  1. 行组（Row Group）：将数据按行切分成多个行组（通常几百MB一个）
  2. 列块（Column Chunk）：每个行组内按列切分
  3. 页（Page）：每个列块再按一定行数（通常1万行）切成多个页
  4. 编码：在每个页内，根据数据特征自动选择最佳编码——字典编码用于字符串、RLE用于排序后的列、delta编码用于时间戳、bitshuffle用于浮点数
  5. 通用压缩：编码后的数据再用Snappy/Gzip/Zstd等通用算法做二次压缩

这种分层设计让Parquet在真实业务数据上能拿到3到10倍的压缩比。1TB的MySQL数据，导出成Parquet通常只有100-300GB。

四、为什么SELECT *在列存中是性能杀手

现在我们可以从原理上理解为什么 SELECT * 在列存中会带来灾难性的性能退化。

4.1 列数越多，性能退化越严重

列存的性能优势建立在”按需读列”的基础上。一个50列的表，查询只需要3列，I/O约等于3/50 = 6%。但如果 SELECT *，你要求引擎把所有50列都读出来——I/O回到行存级别，但失去了行存对单行操作的优势。

更要命的是：在Parquet这类格式中，读取每一列意味着打开不同的列块文件、解压不同的数据页、做不同的反序列化。50列就是50个独立的I/O和解压任务。而在行存中，一行数据在一个页上，一次I/O全部搞定。所以 SELECT * 在列存中不仅没有优势，反而比行存更慢。

4.2 内存放大效应

列存在内存中通常以”列向量”的形式组织数据。当你 SELECT * 时，引擎需要为每一列在内存中构建一个完整的向量。如果表的行数很大，50列的向量加起来可能远超物理内存，引发频繁的内存溢出或swap。

而如果你只查3列，内存占用只有50列的6%。这就是为什么同样的查询引擎（比如ClickHouse），合理选择列时跑得飞快，一旦有人写 SELECT * 就开始疯狂报OOM——不是引擎不行，是你的用法违背了它的设计假设。

4.3 网络传输放大

在分布式查询场景中，SELECT * 还会放大网络传输量。每个节点需要把读取的列数据传输到聚合节点。同样50列vs3列的区别，在单机上已经很明显，在包含几十个节点的分布式集群中更是灾难性的——网络带宽是分布式系统的稀缺资源，你不太想让每一帧都是最大化利用。

4.4 一个具体对比

假设1亿行、50列的报表查询：

查询类型 列存(3列) 列存(SELECT *) 行存(SELECT *)
磁盘读取 ~6GB ~100GB ~100GB
解压计算量 3列解压 50列解压 按页读取（天然整行）
内存峰值 ~2GB ~30GB ~4GB（Buffer Pool可复用）
典型耗时 2-5秒 数分钟甚至OOM 5-15分钟

这是一个简化的估算，真实场景取决于硬件、文件格式、压缩算法等因素。但比例关系是对的：列存的 SELECT * 比行存的 SELECT * 还慢，因为它多出了50次列文件打开+解压+反序列化的开销，而行存是一次性任务。

五、实战：供应链计划日报表从分钟级到秒级

理论讲完了，下面是我在真实项目中的体会。

5.1 背景

我负责的 cloud-supplychain-planning 系统（5.3万行代码）需要生成供应链日报表。日报表涉及的数据维度很多：商品信息、库存水位、安全库存阈值、销量预测值、补货建议、超时告警记录等。最早的设计方案是在MySQL中直接关联这些表做聚合查询，SQL类似这样：

这个查询跨了5张表，每张表10到30个字段不等。MySQL要做大量的JOIN、临时表、文件排序。在几十万行数据量的初期，查询还能在30秒左右完成。但随着数据量增长到百万级，查询经常跑到3-5分钟，高峰期甚至超过10分钟——日报表每天早上8点生成，经常到8:15还没跑完，业务方已经开始催了。

5.2 问题本质

这不是MySQL的错。MySQL是行式存储，为OLTP优化。你让一辆轿车去拉货，它当然能拉，但拉得慢、拉得少、油耗还高。关键不是轿车不好，是让它干卡车该干的活。

上面的查询只需要10个左右的字段，但MySQL关联5张表时，每张表的全部字段都要被读进内存参与JOIN。表越多、字段越多，无效I/O的比例越大。

5.3 方案：HBase列存特性+预聚合

我们的改造策略是：利用HBase的列族特性实现列式存储的等效效果，同时做预聚合避免实时JOIN。

HBase的存储模型和传统行存不同。它虽然按行键组织数据，但在列族内部，数据是按列组织的（HFile使用列式存储格式）。更重要的是，HBase的列族允许你按需读取指定的列——你可以只读 stock 列族下的 current_stock 和 warehouse_id 两列，而不碰 product_info 列族下的其他20列。这在效果上非常接近真正的列式存储。

具体改造步骤：

第一步：设计HBase表结构。 按照报表查询的维度，把相关字段组织到两个列族：

  • cf:stock — 库存相关字段（current_stock、safety_stock、warehouse_id、stock_gap）
  • cf:forecast — 预测相关字段（forecast_7d、forecast_30d、forecast_accuracy）
  • cf:warning — 告警相关字段（warning_count、last_warning_time、warning_type）

RowKey设计为 warehouse_id:product_id 的组合，使得按仓库查询时能利用HBase的RowKey range scan。

第二步：批处理预聚合。 每天凌晨通过离线任务，从MySQL的5张表中JOIN出日报表需要的约15个字段，写入HBase。凌晨执行没有并发压力，MySQL可以慢慢跑JOIN。

第三步：日报表查询改为直接从HBase读取。 按仓库维度扫描HBase的RowKey，只读 cf:stock 和 cf:forecast 两个列族，忽略不相关的列。

5.4 效果

指标 改造前（MySQL JOIN） 改造后（HBase列存+预聚合）
日报表查询耗时 3-10分钟 3-8秒
涉及字段数 ~80+（5张表总字段） ~15（预聚合后）
实际读取字段 全部 按列族按需读取
存储空间 原始MySQL数据 约1/3（HBase列式+压缩）
对线上业务影响 高峰期查询加重MySQL负载 完全隔离

这个改造的核心思想就两点：

  1. 把OLAP查询从行存引擎搬到类列存引擎——MySQL做JOIN是不可选的I/O灾难，HBase按列族读取是按需I/O
  2. 用空间换时间、用预计算换实时计算——凌晨跑JOIN没人催你，白天查报表时直接读预计算好的结果

这当然不是最优方案——如果资源允许，直接用ClickHouse或Doris做OLAP引擎会更理想。但在4人团队、没有专职DBA和基础设施支持的约束下，用已有的技术栈（HBase集群是现成的）做出80分的方案，比等待一个100分的方案更实际。

六、列存的真实劣势：为什么它不是”更好的MySQL”

读完以上内容，很容易产生一个误解：”列存这么好，为什么不把所有数据库都换成列存？”

答案是：列存有不可忽视的劣势。这些劣势决定了它只能做OLAP，不能做OLTP。

6.1 写入慢

当你INSERT一行数据时，行存只需要在一个数据页上追加一行。列存呢？它必须把一行拆成N列，分别写入N个列文件中各自合适的位置。如果列文件使用了排序优化和压缩，写入时还需要重建压缩页。这就是为什么ClickHouse建议批量写入（一次写几万行，而不是逐行INSERT）——逐行写入列存相当于每插入一行就做一次全列拆解+压缩+写入，性能差到不能看。

6.2 不适合点查

这个查询在行存中一次索引查找即得。在列存中呢？引擎需要找到 order_id=12345678 在哪一行（比如第8765432行），然后去每一列中读取第8765432行位置的值。如果表有50列，就是50次”定位到第8765432行+读取一个值”的I/O操作。这对于百万行级别的小表勉强可用，但延迟仍然远比行存高。

列存的设计哲学是”读少量列的大量行”，而不是”读全部列的少量行”。点查完美违背了这个设计哲学。

6.3 UPDATE代价高

UPDATE一行在行存中是一次原地修改（不考虑MVCC的复杂性）。在列存中，UPDATE意味着找到该行在每一列中的位置，修改后触发该列的压缩页重建。如果列文件是只追加（immutable）的设计（如Parquet），UPDATE直接不支持——你需要整个文件重写。

这也就是为什么ClickHouse被设计为append-mostly引擎，Parquet文件一旦写入就不应该修改。

七、存储选型的本质：轿车和卡车，没有谁更好

回到标题的问题：为什么 SELECT * 在数仓里是性能杀手？

因为数仓用的是列式存储。列存的设计假设是”每次查询只读少数列”。你写 SELECT * 等于要求引擎违反设计假设去工作——它当然能做，但做得极差，差到不如行存。

这里有一个很多人会忽略的深度：

架构选择的本质是约束选择。 你选择列存，就是选择”牺牲单行写入和点查的速度，换取大批量列裁剪查询的极速”。你在享受3列查询从10分钟缩到3秒的同时，默默接受了INSERT不能逐行做、UPDATE几乎不支持的事实。

反过来，你选择行存（MySQL/PostgreSQL），就是选择”牺牲大批量聚合查询的速度，换取单行操作和事务的极致性能”。你在享受订单创建接口3ms响应的同时，默默接受了日报表要跑10分钟的事实。

这不是技术优劣的问题，是分工不同的问题。 就像你不会用卡车去跑F1赛道，也不会用轿车去拉集装箱。OLTP和OLAP的存储选型同理——MySQL干MySQL的活，ClickHouse干ClickHouse的活，各司其职。

在架构设计中承认”没有万能方案，只有合适方案”，是一个工程师从初级走向成熟的标志。

八、延伸思考

8.1 列存和LSM-Tree的关系

列存和LSM-Tree（Log-Structured Merge-Tree）经常一起出现。ClickHouse的MergeTree引擎就是基于LSM思想+列式存储的组合。LSM负责解决高吞吐写入的问题（随机写→顺序写），列存负责解决高效查询的问题（只读需要的列）。两者在架构上是正交的、互补的。

8.2 宽表设计和列存

数仓建模中的”宽表”（几百个字段的扁平表）天然适合列式存储。因为列存只读需要的列，宽表的”宽”在列存中并不会带来I/O惩罚——你不查的列根本不会被读取。但在行存中，宽表意味着每一行都很大，即使你只查3个字段，IO也会被迫读取整行。这就是为什么数据仓库的建模风格（宽表、星型模型、雪花模型）和列存如此契合。

8.3 现实世界的混合架构

大多数稍具规模的互联网公司，不会只用一种存储引擎。通常是这样的组合：

存储 用途 存储方向
MySQL / PostgreSQL 在线事务（订单、支付、用户） 行存
Redis 缓存、计数、分布式锁 内存（行式）
Elasticsearch 全文搜索、日志检索 倒排索引（列式变体）
ClickHouse / Doris 实时分析、BI报表 列存
HBase / Cassandra 海量K-V存储 宽列存储（类列存）
Hive / Spark + Parquet 离线数仓、ETL 列存（Parquet格式）

我之前所在系统的现实约束则是——MySQL做事务，HBase做大数据量宽表查询，Redis做缓存，RabbitMQ做异步。没有ClickHouse也没有Doris，团队规模不允许我们维护太多基础设施。但核心原理是一样的：让不同的引擎去做它擅长的事。
