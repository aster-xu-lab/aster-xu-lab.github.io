关灯

轻量级业务任务编排引擎。从「主动不做 DAG」的设计取舍，到调度、可靠性、Starter 接入，最后落到和 Agent 编排的对照。

共 15 篇，按推荐顺序连读。标 必读 的是这一系列的核心，时间有限先读这三篇。

一、设计取舍

  1. 轻量级业务任务编排引擎 SyncTask Engine 设计手记
    为什么自研而不用现成方案，引擎的核心设计是什么，SPI 扩展点怎么玩。
  2. 放弃 DAG：为什么我用 afterExecute 埋点替代了编排引擎
    同步链只有 11 个 Handler、链结构半年才变一次——为这种规模引入 DAG 值不值。
  3. SyncTask 引擎设计复盘：为什么主动选择「不做 DAG」 必读
    49 + 44 个 Handler、80% 逻辑重复的业务现场，以及”主动不做三件事”背后的决策逻辑。

二、调度与可靠性

  1. SyncTaskJob 引擎 V2：从 CountDownLatch 到 CompletableFuture
    93 个 Handler 的并行控制。V1 用 CountDownLatch 踩到的坑，以及 V2 换来的超时控制。
  2. 双层权重调度：分层时间轮在业务调度中的应用
    新任务要快、失败要退避、扫描要省——三层要求怎么用调度组合同时满足。
  3. SyncTask 调度引擎深挖：双层权重调度与分层时间轮 必读
    一套没有引入任何延迟队列或退避算法的调度方案，以及它为什么不会被故障拖垮。
  4. 分布式任务引擎的可靠性设计：防重、断点续传与四级告警
    任务引擎挂了意味着数据没同步、订单漏处理——防重、断点续传、指数退避、四级告警四个机制。

三、和消息表、中间件的关系

  1. SyncTaskJob 就是一张本地消息表
    从 sync_task 这张表的角度，重新理解整个引擎的设计。
  2. SyncTask Job 与基于日志的消息中间件：持久化机制对比
    “状态持久化”和”数据持久化”是两种东西——为什么它不能和 RocketMQ 直接类比。
  3. SyncTaskJob vs nFlow：两套编排引擎的架构对照
    和北欧开源引擎 nFlow（2014 年起用于生产）逐项对比后的取舍。

四、工程接入

  1. SyncTask Engine 全家桶
    引擎的仓库入口与模块索引。
  2. Spring Boot 自动装配与 SyncTask Starter
    从 @SpringBootApplication 拆开自动装配的原理，再看 Starter 怎么做到零配置。
  3. SyncTask Starter 的工程细节：零配置接入是怎么做到的
    接入一个业务任务从数天降到数小时，靠的不是引擎本身，而是 Starter。

五、迁向 Agent

  1. Agent Team 用 DAG，SyncTask 却放弃 DAG
    同一个 DAG 决策，两个项目给出相反答案——差异到底在哪。
  2. 从 SyncTask 到 Agent：编排引擎思想的工程迁移 必读
    做 Agent 时最大的优势不是 Python 也不是 Prompt，而是这套编排经验——讲具体的工程迁移做法。
