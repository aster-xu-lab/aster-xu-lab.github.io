关灯

从分片键选型、无停机迁移，到中台接入与上线一周年稳态运营。偏生产复盘，少理论堆砌。

共 16 篇。前五篇讲怎么选，中间四篇讲怎么迁，最后三篇是上线之后的账。

一、选型与接入

  1. 渠道垂直分表的困局与 ShardingSphere 破局
    订单中心对接 20+ 电商平台，最初按渠道垂直分表——这条路为什么走不通。
  2. ShardingSphere-JDBC 快速入门与核心概念
    6000 万行的表撑不住了。手写路由、改所有 DAO 有多痛，以及核心概念怎么理解。
  3. ShardingSphere 分片策略实战：5 种算法怎么选
    分片策略本质是回答”这条数据该存到哪张物理表”——5 种内置算法逐一验证后的选型建议。
  4. 分片键怎么选：从时间主分片修正为单号主分片
    一次真实的选型修正：最初按时间选，业务确认所有事件都按单号处理后改掉。
  5. 分片键选型的算账：为什么单号主分片
    最容易被问倒的第一题是”为什么分”——三个判断信号，缺一不可。

二、迁移与扩容

  1. 6000 万订单表迁移到分片：双写 + 灰度 + 回补 + 回滚
    四个环节缺一不可。附带一条硬教训：批量回补用 DataX，别逐条 INSERT。
  2. 分库分表迁移复盘：从分片键决策到无停机上线 必读
    销售信息表逼近 6000 万行后，从”要不要分”一路做到无停机上线的完整复盘。
  3. 分片扩容的无停机流程：存量回填、binlog 增量与对账
    这里的”双写”是零侵入的：业务只写老表，增量靠 binlog/Canal 异步补。
  4. 非分片键查询：id-mapping、Doris 与 ES 的边界
    按 user_id 查订单怎么办？”上 ES”是方案先行——正确顺序是先问业务要不要这个查询。

三、配套与踩坑

  1. SpringBoot + MyBatis-Plus + ShardingSphere 生产接入
    前面都是纯 JDBC 讲原理，这篇换到真实生产栈，验证 BaseMapper / ServiceImpl 还灵不灵。
  2. ShardingSphere 与 ORM 兼容性踩坑合集
    分页插件、跨分片 total/pages 这些最容易翻车的点，逐条实测。
  3. 分片之后的排序与分页，到底怎么做
    单表一条 LIMIT 就完事，分片后要先改写再归并，深分页更是性能灾难。
  4. Kafka 在 Canal→Doris 链路中的削峰角色
    按单号分片后，跨分片的复杂统计做不了——这条路怎么补。

四、中台与周年复盘

  1. 从传统 OMS 到订单中台
    不是换个名字，是架构范式的升级：单体→多平台接入，垂直分表→水平分片，手工同步→编排引擎。
  2. 从 CAP 到订单中台：最终一致架构的取舍与实践 必读
    落地时”三选二”是错的——应该按操作类型分流，每条链路单独选。
  3. 分库分表上线一周年复盘：稳态运营、对账与扩容规划 必读
    不复盘”怎么迁移”（前文讲过），只复盘上线之后：稳态运营、对账机制、8→16 扩容推演。
